课程总览 课程资料

90 天拆分规则说明

基于 Day01/Day02 实际形态，提炼出的每日任务拆分逻辑

核心拆分原则

1. 按功能模块 + 技术栈深度递进，不是按知识点平均分配

不是：Day01 学 Vue 响应式、Day02 学 TypeScript 类型、Day03 学组件通信... 而是：Day01 交付一个能跑的 Agent 面板（从 v1 单组件 → v3 分层架构），顺带学会 Vue 响应式 / 判别联合 / reducer / 状态机。

原则：

  • 每天交付一个完整的功能模块（能跑、能测、能看到效果）
  • 功能模块自然引出3-6 个核心知识点（不是为了教知识点而造功能）
  • 知识点按技术栈深度递进：v1 最简单 → v2 加一层 → v3 生产可用

2. 三个阶段的拆分逻辑

阶段一（Day 1-30）：前端 → AI 前端

项目载体：p1-monitor 智能运维监控（Vue 3 + TypeScript + WebSocket + Agent UI）

拆分规则：

  • Week 1（Day 1-7）：实时指标合同、Vue 状态与 WebSocket 可靠性

    • Day 1：Agent 运行时展示面板（基础架构 — 事件流 / 状态机 / reducer / 分层）
    • Day 2：领域合同（数据边界 — zod schema / DTO/Domain 分层 / 版本合同）
    • Day 3：异步与竞态（并发控制 — 取消旧请求 / loading 状态 / 竞态问题）
    • Day 4：Vue/ECharts 原理（图表渲染 — ECharts 集成 / 60 点滑窗 / 生命周期清理）
    • Day 5：WebSocket 全栈（实时推送 — NestJS Gateway / metric.created 事件 / Pinia Store）
    • Day 6：实时可靠性（连接保护 — 心跳 / 重连 / 去重 / REST 补偿）
    • Day 7：事件与算法（异常检测 — Z-Score 算法 / 测试驱动 / 时间顺序）

  • Week 2-4：Agent 交互 / SSE 升级 / 历史恢复 / 审批流程 / 多 Agent 协同（待规划）

递进逻辑：

  1. Day 1 定义事件类型 → Day 2 加 schema 校验 → Day 5 挂 WebSocket 真推送 → Day 6 加重连保护
  2. Day 3 并发读取 → Day 4 图表渲染 → Day 7 异常检测算法
  3. 每一天都复用前几天的代码（Day 2 复用 Day 1 的 AgentEvent，Day 5 复用 Day 2 的 schema）

阶段二（Day 31-60）：AI 前端 → AI 全栈

项目载体：p1-monitor 后端 + p1-monitor 全栈（NestJS + Python/FastAPI + RAG）

拆分规则：

  • Week 5-6：NestJS 后端架构（Module / Controller / Service / Prisma ORM）
  • Week 7：LangChain.js RAG 核心逻辑（文档分割 / Embedding / 向量检索）
  • Week 8：Vercel AI SDK Tool Calling（Tool 定义 / Schema / 执行逻辑）

递进逻辑：

  • 前端已建好 UI，后端从 0 搭起，前后端通过 Day 2 定义的 schema 合同对接
  • RAG / Tool Calling 是 Agent 核心能力，在真实项目里实现（不是玩具 demo）

阶段三（Day 61-90）：AI 全栈 → AI Agent 工程师

项目载体：p2-agent-workbench 多 Agent 协同工作台

拆分规则：

  • Week 9-10：LangGraph.js 状态机编排（StateGraph / Node / Edge / Human-in-the-loop）
  • Week 11-12：多 Agent 协同（Agent 间通信 / 任务分发 / 结果聚合）
  • Week 13：生产部署（Docker / CI/CD / 监控告警）

递进逻辑：

  • p1-monitor 是单 Agent 场景，p2-agent-workbench 是多 Agent 协同
  • 从"调用一个 Agent"升级到"编排多个 Agent 协同完成复杂任务"

3. 每一天的内部拆分逻辑：v1 → v2 → v3 三版演进

为什么用三版演进，而不是直接给 v3？

教学法选择：

  • ❌ 直接给最佳实践（v3）：学生看不懂为什么要这么复杂，会觉得"过度设计"
  • ✅ 三版演进：v1 极简 → v2 加一层 → v3 生产可用，每一版都在解决前一版的具体痛点

Day01 示例：

  • v1（最小闭环）：单组件 + 几个 ref，只展示文本流
    • 痛点：事件类型没建模，加工具调用时要大改
  • v2（加一层）：TypeScript 判别联合 + composable，加工具调用 + 审批
    • 痛点：事件数组在组件里 reduce，状态逻辑和 UI 耦合，难测试
  • v3（生产可用）：domain/features 分层 + 纯 reducer + 状态机
    • 终态：状态逻辑能独立测试，换事件源（WebSocket → SSE）只改一行

Day02 示例：

  • v1（最小闭环）：只定义 TypeScript interface，as 强断言
    • 痛点：编译通过不等于运行正确，后端返回 { id: 123 } 会崩溃
  • v2（加一层）：zod schema 运行时校验，DTO/Domain 分层
    • 痛点：后端升级 v1 → v2，前端 schema 未同步，页面白屏
  • v3（生产可用）：加 schemaVersion 字段 + v1-to-v2 兼容适配器
    • 终态：前端能同时处理 v1 和 v2 事件，不会白屏

三版演进的拆分规则

版本 代码量 功能完整度 知识点数量 学生感受
v1 50-100 行 核心流程能跑 1-2 个 "原来这么简单，我能写"
v2 200-300 行 加一个关键设计维度 3-4 个 "原来 v1 有这个问题，v2 这么解决"
v3 500-800 行 生产可用 6-10 个 "原来生产代码要考虑这么多，但每一步都有理由"

关键：v1 和 v2 不是"练习题"，而是真实的演进路径。很多项目就是从 v1 开始，踩坑后重构到 v2，再踩坑后重构到 v3。

4. 知识点的选择规则：项目驱动，不是知识点驱动

错误示例（知识点驱动）

Day 1: Vue 响应式原理（ref / reactive / computed / watch）
Day 2: TypeScript 类型系统（interface / type / 泛型 / 条件类型）
Day 3: 组件通信（props / emit / provide/inject / EventBus）
...

问题：

  • 学生学完 Day 1 会觉得"学了一堆 API，不知道怎么用"
  • 知识点之间没有连贯性，Day 2 和 Day 1 没关系
  • 没有真实项目承载，全是玩具 demo

正确示例（项目驱动）

Day 1: 交付 Agent 运行时展示面板（v1 → v2 → v3）
  顺带学会：
  - Vue 响应式（v1 用 ref 存状态）
  - 判别联合（v2 建模 9 种事件类型）
  - reducer（v3 纯函数归约事件）
  - 状态机（v3 终态保护）
  - 分层架构（v3 domain / features / app）

Day 2: 升级 Day 1 的事件类型为运行时合同
  顺带学会：
  - zod schema（v2 运行时校验）
  - DTO/Domain 分层（v2 网络层 ≠ 业务层）
  - branded type（v2 ServerId 不能和 MetricId 混用）
  - 版本合同（v3 schemaVersion 字段）
  - 兼容适配器（v3 v1-to-v2 弃用窗口）

优势：

  • 学生先交付功能（有成就感），再理解为什么需要这些知识点
  • 知识点有真实项目承载，学完能直接用
  • Day 2 直接复用 Day 1 的代码，知识点有连贯性

5. 时间分配规则：90 分钟阅读 + 90 分钟动手

为什么是 3 小时？

参考依据：

  • Pomodoro 番茄工作法：25 分钟专注 + 5 分钟休息 × 6 轮 = 180 分钟
  • 认知负荷理论：3 小时是成年人持续学习的上限，再长注意力下降
  • 真实项目验证：Day01 从 0 搭到 v3 完整测试通过，熟练者需 2.5-3 小时

内部时间盒

阶段 时长 内容 类型
A 30 分钟 阅读第 3 节（v1 教程） 阅读
B 30 分钟 阅读第 4 节（v2 教程） 阅读
C 30 分钟 阅读第 5 节（v3 教程） 阅读
D 60 分钟 在自己项目里实现 v3 完整功能 动手
E 20 分钟 写核心逻辑测试 + 两个反证实验 动手
F 10 分钟 运行 lint/typecheck/test/build，提交 commit 动手

设计原则：

  • 前 90 分钟只读、不写（避免边读边写导致思路混乱）
  • 后 90 分钟只写、不读（读完 v3 你会发现前面卡住的地方多半是"没看到全景"造成的）
  • E 阶段的"反证实验"强制学生验证 v1/v2 的痛点（不是纸上谈兵）

6. 项目选择规则：真实场景，有明确的业务目标

为什么选 p1-monitor（智能运维监控）？

业务目标明确：

  • 用户：运维工程师
  • 痛点：服务器 CPU/内存异常时，手动排查太慢
  • 价值：Agent 自动诊断 + 推荐修复方案 + 一键执行

技术栈覆盖全：

  • 前端：Vue 3 + TypeScript + WebSocket + ECharts
  • 后端：NestJS + Prisma ORM + PostgreSQL
  • AI：LangChain.js RAG + Vercel AI SDK Tool Calling + LangGraph.js 状态机

真实度高：

  • 不是 Todo List / 博客系统这种玩具项目
  • 有真实的并发问题（Day 3 竞态）、可靠性问题（Day 6 重连）、算法问题（Day 7 异常检测）
  • 面试时能说"我做过 Agent 监控系统"，不是"我跟着教程做了 Todo List"

为什么 Day 31-60 换 p1-monitor 后端，Day 61-90 换 p2-agent-workbench？

递进逻辑：

  • Day 1-30：前端视角，把 Agent UI 做扎实（事件流 / 状态管理 / 实时推送）
  • Day 31-60：全栈视角，理解 Agent 后端怎么实现（RAG / Tool Calling / NestJS 架构）
  • Day 61-90：工程视角，理解多 Agent 协同（LangGraph 编排 / 任务分发 / 生产部署）

为什么不一直做同一个项目：

  • 避免"一个项目做 90 天"导致的疲劳感
  • p1-monitor 是单 Agent 场景，Day 61 后要做多 Agent，自然要换项目
  • 但 p2 会复用 p1 的很多代码（事件合同 / 状态管理 / WebSocket 封装）

7. 验收标准：功能 + 测试 + 反证实验

为什么有"反证实验"？

Day02 示例：

  • 反证实验 1：v1 的痛点（强断言挡不住脏数据）
    const fakeServer: unknown = { id: 123, name: 'srv-001' }
const server = fakeServer as Server
console.log(server.id.split('-'))  // 💥 运行时崩溃
  • 反证实验 2：v2 的痛点（没有版本字段无法兼容旧格式）
    const v1Event = { runId: 'run-001', type: 'tool.succeeded', payload: { ... } }
const result = AgentEventSchemaV2.safeParse(v1Event)
expect(result.success).toBe(false)  // v2 schema 拒绝 v1

目的：

  • 强制学生亲眼看到 v1/v2 的问题（不是"老师说有问题就有问题"）
  • 加深对"为什么要这么设计"的理解
  • 面试时能说"我遇到过这个坑，然后这么解决的"

8. 课后巩固：课末三问 + 真实情境题 + 教师五连问

课末三问（§10）

Day02 示例：

  1. 为什么必须分 DTO 和 Domain 两层？
  2. schemaVersion 放在事件的哪一层？payload 内还是外？为什么？
  3. 兼容适配器什么时候删？

设计原则：

  • 问题直指当天的核心设计决策（不是"什么是 zod"这种查文档就能答的）
  • 学生要自己写答案（不是选择题），写完后教师五连问会追问细节

真实项目情境题（§11）

Day02 示例：

  1. 后端突然说"我们给 tool.succeeded 加了 tokens 字段，你前端要不要改？" 你怎么回答？
  2. 你的同事说"zod schema 太啰嗦了，我直接用 TypeScript interface 不行吗？" 你会怎么解释？

设计原则：

  • 模拟真实工作场景（后端改接口 / 同事质疑方案）
  • 考察学生能否把今天学的知识迁移到新场景

教师五连问（§13）

Day02 示例：

  1. 演示验收：请演示你的 contracts.spec.ts 测试全部通过的截图。
  2. 核心挑战：Day02 最难的部分是什么？你卡在哪里最久？
  3. 对比思考：v1/v2/v3 三版你觉得哪一版最关键？为什么？
  4. 项目对手戏：假设 Day 5 挂 WebSocket 时后端推来一个 v3 事件（schemaVersion: 'v3'），你的代码会怎么处理？
  5. 知识盲区：zod 的 .passthrough() 和 .strip() 和 .strict() 有什么区别？

设计原则：

  • 第 1 题验收功能（必须有截图证明跑通了）
  • 第 2-3 题考察反思能力（卡在哪里 / 哪一版最关键）
  • 第 4 题考察迁移能力（今天学的能否应对后续 Day 的场景）
  • 第 5 题考察知识边界（故意问一个今天没讲但相关的点）

9. 对你的具体问题的回答

Q: 为什么要按照现在的方式拆分每天的学习？

A: 按功能模块 + 技术栈深度递进，不是按知识点平均分配。

  • Day 1: 交付 Agent 面板（v1 → v3），顺带学 Vue / 状态机 / reducer
  • Day 2: 升级 Day 1 的事件类型为运行时合同，顺带学 zod / DTO/Domain 分层 / 版本合同

Q: 有什么规则吗？

A: 9 条核心规则（见上文 §1-§8）：

  1. 功能模块 + 技术栈深度递进
  2. 三个阶段（前端 → 全栈 → Agent 工程师）
  3. 每天内部 v1 → v2 → v3 三版演进
  4. 项目驱动，不是知识点驱动
  5. 90 分钟阅读 + 90 分钟动手
  6. 真实场景，有明确业务目标
  7. 功能 + 测试 + 反证实验
  8. 课末三问 + 真实情境题 + 教师五连问
  9. 每一天都复用前几天的代码（Day 2 复用 Day 1，Day 5 复用 Day 2）

Q: 是按照项目还是前端 AI？

A: 按项目，但项目是为"前端 AI"服务的。

  • 载体项目：p1-monitor（智能运维监控）、p2-agent-workbench（多 Agent 协同）
  • 核心目标：60 天后能独立开发一个 Agent 全栈应用（前端 UI + 后端 RAG/Tool Calling + 多 Agent 编排）
  • 不是"学前端"也不是"学 AI"，而是"学怎么把前端和 AI 结合起来解决真实问题"

Q: 每天的学习知识点都是按照什么来的？

A: 按功能模块自然引出的知识点，不是硬凑。

  • Day 1 要做 Agent 面板 → 自然需要事件流 / 状态机 / reducer
  • Day 2 要挡非法输入 → 自然需要zod schema / DTO/Domain 分层 / 版本合同
  • Day 3 要并发读取 → 自然需要取消旧请求 / 竞态控制 / loading 状态

不是：先列出"前端必学 50 个知识点"，然后每天教 2 个。

总结：拆分的本质是"螺旋上升"

Day 1: 定义事件类型（纯 TS interface）
  ↓
Day 2: 加运行时校验（zod schema）
  ↓
Day 5: 挂 WebSocket 真推送
  ↓
Day 6: 加重连保护
  ↓
Day 15: 加历史恢复
  ↓
Day 31-60: 后端从 0 实现 Agent（复用前 30 天定义的合同）
  ↓
Day 61-90: 多 Agent 协同（复用前 60 天的状态管理 / 事件流封装）

核心：不是"Day 1 学完 Vue，Day 2 学完 TS"，而是"Day 1 用 Vue 做一个能跑的东西，Day 2 把它升级得更健壮，Day 5 挂上真数据，Day 31 理解它的后端怎么实现，Day 61 把它扩展到多 Agent"。

每一天都在同一个项目里累积，60 天后你手上有两个真实的 Agent 项目（p1-monitor + p2-agent-workbench），不是 90 个互不相关的玩具 demo。

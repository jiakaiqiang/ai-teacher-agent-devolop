深挖 1：TypeScript 判别联合 —— 从今天项目里的 AgentEvent 讲起

为什么先挖这个：12 号报告里把「技能区没有 TypeScript」列为高级前端最明显的缺口（第 1 页/第 4 节 B 级第 1 条）。而今天 v3 项目里，AgentEvent 就是判别联合最典型的教科书应用。挖懂它，你在简历上就有了写「TypeScript」的第一个证据。

1.1 场景锚点（10 秒定位）

今天 v3 里，后端会一条一条推 9 种不同事件给前端。前端 reducer 要根据 type 字段做 9 种不同处理。这里存在一个天然矛盾：9 种事件的字段完全不一样（text.delta 有 text，tool.started 有 callId 和 toolName，run.failed 有 code 和 message），但它们又必须能被同一个函数 reduceAgentEvent(state, event) 接收。

如果你有 6 年经验、只写过 Vue 中后台，遇到这种场景 90% 的反应会是：

// 反应 1:偷懒
type AgentEvent = { type: string; data: any }

// 反应 2:自以为严谨
interface AgentEvent {
  type: string
  callId?: string
  text?: string
  code?: string
  message?: string
  toolName?: string
  // ... 20 个可选字段
}

两种都是错的。正确的写法是判别联合（Discriminated Union）。

1.2 项目代码原样

src/domain/agent/agent-event.ts：

export type RunId = string & { readonly __brand: 'RunId' }

type EventMeta = {
  runId: RunId
  sequence: number
  occurredAt: string
}

export type AgentEvent =
  | (EventMeta & { type: 'run.started';         payload: Record<string, never> })
  | (EventMeta & { type: 'text.delta';          payload: { text: string } })
  | (EventMeta & { type: 'tool.started';        payload: { callId: string; toolName: string; argumentSummary: string } })
  | (EventMeta & { type: 'tool.succeeded';      payload: { callId: string; resultSummary: string; durationMs: number } })
  | (EventMeta & { type: 'tool.failed';         payload: { callId: string; code: string; message: string } })
  | (EventMeta & { type: 'approval.required';   payload: { approvalId: string; action: string; risk: 'low' | 'medium' | 'high' } })
  | (EventMeta & { type: 'run.cancelled';       payload: { reason: string } })
  | (EventMeta & { type: 'run.failed';          payload: { code: string; message: string } })
  | (EventMeta & { type: 'run.finished';        payload: { summary: string } })

export function assertNever(value: never): never {
  throw new Error(`Unhandled AgentEvent: ${JSON.stringify(value)}`)
}

1.3 拆解：这段代码里的 5 个设计点

设计点 A：为什么用 type 不用 interface

interface 不能定义联合类型（union）。你不能写：

interface AgentEvent =                              // ✗ 语法错误
  | { type: 'text.delta'; text: string }
  | { type: 'run.started' }

interface 只能描述「一个对象的形状」，不能描述「多个对象之一」。type 才能用 | 组合。

记忆法：interface 定义结构，type 定义结构或组合。凡是涉及「或者/联合/交叉/元组」的场景，一律用 type。

设计点 B：RunId 为什么要 branded type

export type RunId = string & { readonly __brand: 'RunId' }

__brand 字段在运行时不存在（它只活在 TypeScript 的类型系统里）。运行时 RunId 就是普通字符串。它的作用只在编译期：

function reduce(state: AgentRunState, event: AgentEvent) {
  const otherRun = 'run-999' as string
  event.runId = otherRun            // ✗ 编译报错:string 不能赋给 RunId
  event.runId = otherRun as RunId   // ✓ 通过,但必须显式声明"我知道我在做什么"
}

这叫「名义类型模拟」（TypeScript 是结构类型系统，原生不区分同结构的两种类型）。用途：防止手滑把普通 string 传给期望 RunId 的地方。类似的场景还有 UserId、OrderId、Timestamp。

设计点 C：payload: Record<string, never> 和 payload: {} 的区别

  • {} 表示「任意非 null/undefined 的对象」，连 { foo: 1 } 都能过。
  • Record<string, never> 表示「键是 string，值必须是 never」—— 因为 never 类型不接受任何值，所以这个对象必须是空的。
const a: {} = { anything: 1 }                   // ✓
const b: Record<string, never> = { anything: 1 } // ✗ 编译报错
const c: Record<string, never> = {}              // ✓

run.started 事件不需要任何 payload，但又不能省略 payload 字段（否则 9 种事件形状不一致，判别联合的一致性会崩）。用 Record<string, never> 精确表达「这里有个 payload 字段，但里面必须是空的」。

设计点 D：为什么每一行都写 EventMeta & { ... }

EventMeta 是所有事件都有的公共字段（runId、sequence、occurredAt）。用 &（交叉类型）把它拼上，等于给每种事件都加上这三个字段：

(EventMeta & { type: 'text.delta'; payload: { text: string } })
// 等价于
{
  runId: RunId
  sequence: number
  occurredAt: string
  type: 'text.delta'
  payload: { text: string }
}

为什么不提取到外层？比如这样：

// 反例:看起来更简洁,但改动更麻烦
type AgentEvent = EventMeta & (
  | { type: 'text.delta'; payload: { text: string } }
  | { type: 'run.started'; payload: Record<string, never> }
)

这样其实也能工作。真实项目里两种写法都有，视个人偏好。但把 EventMeta & 写在每一行有一个心理效果：清楚地强调「每一种事件都是完整的 event，不要漏掉公共字段」。当你未来给某种事件单独扩字段（比如 text.delta 加个 chunkIndex）时，写在每行的形式更容易改。

设计点 E：9 种事件的字面量类型 'text.delta' | 'run.started' | ...

关键在 type: 'text.delta' 这里的 'text.delta' 不是 string 类型，而是字符串字面量类型（String Literal Type）。它是只有「text.delta」这一个值的类型。

正是因为每种事件的 type 都是字面量类型，TS 才能做类型收窄（narrowing）：

function handle(event: AgentEvent) {
  if (event.type === 'text.delta') {
    // 到这里,TS 知道 event 一定是 (EventMeta & { type: 'text.delta'; payload: { text: string } })
    console.log(event.payload.text)        // ✓
    console.log(event.payload.callId)      // ✗ 编译报错:text.delta 没有 callId
  }
}

如果 type 是普通 string 类型，TS 无法收窄，你在 if 里访问 event.payload.text 就要冒着运行时 undefined 的风险。

1.4 原理：TS 编译期到底做了什么

跑一遍下面这段「心算」，你就理解了判别联合的运行机制：

function reduce(state: AgentRunState, event: AgentEvent): AgentRunState {
  //                                        ↑ event 类型是 9 种事件的并集
  switch (event.type) {
    //     ↑ event.type 类型是 'run.started' | 'text.delta' | ... 9 个字面量的并集
    case 'text.delta':
      //   ↑ 匹配到 'text.delta' 字面量
      //   TS 把 event 的类型从"9 种之一"收窄成"1 种(text.delta)"
      return { ...state, timeline: [...state.timeline, { detail: event.payload.text }] }
      //                                                              ↑ event.payload 已是 { text: string },直接访问 .text 无警告
    case 'run.started':
      //   TS 把 event 类型收窄成 run.started
      return { ...state, status: 'running' }
    // ... 其余 7 种
    default:
      // 到这里,前面 9 种都处理过了,TS 认为 event 是"9-9=0 种"—— 即 never 类型
      return assertNever(event)
      //                 ↑ 只有 never 类型能被赋给参数类型 never,编译通过
  }
}
关键洞察：判别联合的核心不是「我写了 9 个类型」，而是「TS 能从一个字段的值，反推出整个对象的形状」。这个反推的能力，就是它比 { type: string; data: any } 强 100 倍的地方。

1.5 反例 A：如果用 { type: string; data: any } 会怎样

假设你回退到反应 1 的写法：

type BadEvent = { type: string; data: any }

function reduce(state: AgentRunState, event: BadEvent) {
  if (event.type === 'tool.stared') {  // ← 拼错了:stared 少了一个 t
    // TS 认为 event.type: string, 'tool.stared' 也是 string,可以比较
    // 编译通过,运行时永远进不来这个分支
    return { ...state, timeline: [...state.timeline, { title: event.data.tolName }] }
    //                                                            ↑ tolName 拼错,data 是 any,TS 什么都不管
    //                                                            运行时 event.data.tolName 是 undefined
    //                                                            timeline 里出现 "调用工具:undefined"
  }
}
能编译。能运行。用户能看到 bug。这就是 12 号报告第 3 页说「"智能助手"和"大模型分析报表"不能证明 AI 前端能力」的技术根源之一 —— 用 any 让类型系统失效，等于回到 JavaScript。

判别联合的价值，反过来说就是：同样的拼写错误，在判别联合里编译期就红了。

function reduce(state: AgentRunState, event: AgentEvent) {
  if (event.type === 'tool.stared') {  // ✗ 编译报错:'tool.stared' 不在 9 种字面量的并集里
    // ...
  }
}

1.6 反例 B：用 interface + 手动 union（半吊子写法）

我见过 3 年经验的前端写成这样：

interface EventBase {
  type: string
  runId: string
}
interface TextDelta extends EventBase {
  type: 'text.delta'
  text: string
}
interface ToolStarted extends EventBase {
  type: 'tool.started'
  callId: string
  toolName: string
}
type AgentEvent = TextDelta | ToolStarted

问题在哪？

  1. EventBase.type: string 是宽类型，子接口的 type: 'text.delta' 是窄类型。虽然 TS 允许 extends 时收窄字段，但当你在 reducer 里对 event: EventBase 做 if (event.type === 'text.delta') 时，TS 无法收窄成 TextDelta。判别联合失效。
  2. 每个事件都用一个独立的 interface，9 种事件就是 9 个 interface，加 1 个 union。9 个文件级导出，污染 IDE 的自动补全。
  3. 想加新事件时，要写 3 处：新 interface、把它加到 union、reducer 里加 case。用 type 只需要写 2 处。

这种写法看起来「更 OOP」，但在 TypeScript 的类型系统里，type + union 是原生一等公民，interface + union 是二等公民。碰到并列关系的类型，一律用 type。

1.7 分层提问 —— 先答，再看下一层的解答

问题 1（白板级）

如果我把 AgentEvent 里所有 9 种事件的 type 字段都改成 type: string，reduceAgentEvent 里的 switch case 还能编译通过吗？会出什么问题？

展开答案

能编译通过。因为 event.type === 'text.delta' 是 string === string 的比较，TS 允许。

但是收窄会失效：switch 每一个 case 里，event 的类型仍然是完整的 AgentEvent union，访问 event.payload.text 会报错（因为不是所有 9 种事件都有 payload.text）。你只能加类型断言或者用 if + in 操作符手动缩窄，代码立刻膨胀。

更严重的是，default 分支里 event 类型不再是 never，assertNever(event) 编译报错。exhaustive check 直接失效。

问题 2（项目级）

今天 fixture 里的第 4 个事件是 { type: 'tool.succeeded', payload: { callId: 'c1', resultSummary: 'CPU 平均 87%', durationMs: 1800 } }。如果我在 fixture 里少写一个字段，写成 { type: 'tool.succeeded', payload: { callId: 'c1' } }，谁会先报错？TypeScript 编译期，还是 vitest 运行时？为什么？

展开答案

TypeScript 编译期先报错。因为 sample-run.ts 里 sampleEvents: AgentEvent[] 有明确类型标注，TS 会检查每一个元素是否符合 AgentEvent 中的某一种。当 payload 缺字段时，TS 找不到能匹配的分支，报错："Type '{ callId: string }' is missing the following properties: resultSummary, durationMs"。

这就是判别联合的第二个价值：它不仅在 reducer 里保护「消费方」，也在 fixture / 网络反序列化的地方保护「生产方」。少写一个字段，数据源头就红。

延伸思考：Day 2 要给 AgentEvent 加 Zod Schema，做的其实是同一件事的运行时版本 —— 编译期靠 TS，运行时靠 Schema。两者一里一外，构成完整的合同边界。

问题 3（工程级)

Day 5 会把事件源从 fixture 换成 WebSocket，后端可能会发过来 { type: 'budget.exceeded', payload: { limitTokens: 10000 } } 这种今天 AgentEvent 里没有的新事件。在不改 AgentEvent 类型定义的前提下，前端会发生什么？改了 AgentEvent 类型但没在 reducer 里加 case，又会发生什么？

展开答案

场景 A：不改 AgentEvent 类型定义

WebSocket 收到 JSON，反序列化后如果不经过 Schema 校验，就以 unknown / any 进入前端。你在 reducer 里做 switch(event.type)，匹配不到任何 case，走到 default: assertNever(event) —— 运行时抛异常。UI 崩掉，但至少你会看到错误。

如果开发者偷懒把 default 改成 return state 静默忽略，budget.exceeded 事件会被默默丢弃，用户等到花儿都谢了也不知道 Agent 被预算限制阻断了。这就是 12 号报告说「AI 助手不能证明 AI 前端能力」的另一层原因：新事件类型的接入策略，是 AI 前端的核心工程能力。

场景 B：改了 AgentEvent 类型，但没在 reducer 里加 case

TS 编译报错。default: assertNever(event) 这一行报："Argument of type 'BudgetExceededEvent' is not assignable to parameter of type 'never'"。

你根本没法把这段代码 build 出去，更别说部署。这就是 exhaustive check 的价值 —— 它把「忘了处理新事件」从线上事故变成编译错误。

问题 4（进阶）

在 reducer 里，case 'tool.succeeded' 分支需要通过 callId 找到之前 tool.started 时创建的 timeline item。假设某个恶意 payload 传了 callId: '__proto__'，项目会不会有原型链污染风险？为什么？

展开答案

项目里目前用的是 state.timeline.map((item) => item.key === 'tool-' + event.payload.callId ? {...} : item)，不会污染原型链。因为 map 是数组遍历，访问 item.key 是字符串比较，不涉及对象属性设置。

但换一种写法就危险了。假设 reducer 里为了性能改用 hash map：

const toolsByCallId: Record<string, TimelineItem> = {}
toolsByCallId[event.payload.callId] = { ... }
// 如果 callId 是 '__proto__',这一行会污染 Object.prototype

这就是为什么面试官问「你怎么处理 AI 场景下的安全边界」时，只答「XSS/CSRF」不够。判别联合只解决「事件形状对不对」，不解决「payload 内容对不对」。后者要靠 Schema（Day 2）、沙箱、参数白名单。12 号报告 B 级第 4 条「安全与权限」的深度就是从这里开始。

问题 5（架构级）

今天 AgentEvent 是前后端共享合同。如果这个类型定义只放在前端 src/domain/agent/agent-event.ts，而后端（未来 Day 22 后的 NestJS）自己另写一份 TypeScript 类型或者用 class，会出什么问题？怎么设计才能避免？

展开答案

问题：两份类型定义手动同步，一份改了另一份忘改，合同漂移。前端加了 budget.exceeded，后端还在发 v1 事件；后端加了 retry.attempted，前端 exhaustive check 直接崩。这是 12 号报告第 2 页说「AgentEvent v1 到 v2 客户端漂移」背后的技术原因。

避免方式（选一个）：

  1. Monorepo + 共享包：在 packages/contracts/ 里放 agent-event.ts，前后端都从这里 import。改一次同步两处。今天的 p1-monitor 目录如果未来变成 monorepo，应该用这个方案。
  2. Schema-first：用 Zod / TypeBox / Protobuf 定义 Schema，通过工具生成 TS 类型。合同的权威版本是 Schema 文件，前后端各自消费。Day 2 会走这条路。
  3. OpenAPI + 代码生成：如果通信是 HTTP，直接从 OpenAPI 生成两边的 client/server。事件流场景不太适用，更适合传统 REST。

延伸思考：面试官问「你怎么维护前后端类型一致性」，一句「我们用 Zod 生成类型」是及格，能讲清「为什么不选 monorepo 共享 TS 类型 —— 因为运行时也需要校验、Zod 一次搞定两件事」就是高级。

1.8 项目对手戏 —— 判别联合怎么和 reduceAgentEvent 配合

单独一个 AgentEvent 类型没什么用，它必须和消费方（reducer）配合才产生工程价值。今天 agent-run-state.ts 里的这段是最好的对手戏：

export function reduceAgentEvent(
  state: AgentRunState,
  event: AgentEvent,
): AgentRunState {
  if (event.sequence <= state.lastSequence) return state
  if (isTerminal(state.status)) return state

  switch (event.type) {
    case 'run.started':
      return { ...state, runId: event.runId, status: 'running', lastSequence: event.sequence }
    case 'text.delta':
      return { ...state, lastSequence: event.sequence,
        timeline: [...state.timeline, { key: `text-${event.sequence}`, kind: 'text', title: '模型输出', detail: event.payload.text }] }
    // ... 其余 7 个 case
    default:
      return assertNever(event)
  }
}

这段代码里判别联合起了三层作用：

  1. 入参保护：调用 reducer 时，event 必须是 9 种之一；传别的形状，TS 编译期红。
  2. 分支收窄：每个 case 里，event 的类型被自动缩窄到那一种，访问 payload 有精确提示。
  3. 遗漏检测：default: assertNever(event) 强制你必须处理完 9 种。加第 10 种时编译报错。

Day 5 换成 WebSocket 后的心智负担分布：

环节谁在保护
WebSocket 反序列化（JSON → 对象）Zod Schema（Day 2 加）
对象是否属于 9 种事件之一判别联合（今天已加）
reducer 内部访问 payload 字段类型收窄（今天已加）

前端安全度 = 上面 4 层的乘积。缺一层，漏洞就会出现在那一层。这就是「完整的合同边界」的含义，也是简历上写「设计前端合同边界」的证据。

1.9 面试真题拆解 —— 从今天的 AgentEvent 出发怎么答

真题 1：「你在项目里怎么用 TypeScript？」

烂答法：「我用 TypeScript 定义了接口，让代码更规范。」
及格答法：「我在监控项目里用 TypeScript 定义了 AgentEvent 判别联合，一共 9 种事件，每种事件有自己的 payload 形状。reducer 里的 switch 能做类型收窄，访问字段有精确提示。」
优秀答法（30 秒）：「我把前后端的实时事件合同用 TypeScript 判别联合固化 —— 9 种事件、每种字面量类型、共享 EventMeta。reducer 里用 exhaustive check（default 分支 assertNever），加新事件类型时编译期强制我处理，避免了"新事件被 UI 静默吞掉"这类 bug。这个类型定义未来会通过 Zod Schema 生成，同时管住编译期和运行时。整个合同变化的爆炸半径，从"线上事故"降到"编译错误"。」

2.1 场景锚点（10 秒定位）

今天 v3 里，fixtures/sample-run.ts 用 setTimeout(..., 100/200/300ms) 把 9 个事件串起来，模拟后端推送。前端 useAgentRun composable 监听 events: Ref<AgentEvent[]>，每次 push 新事件就触发 watchEffect 重新 reduce，Vue 自动刷新 UI。

核心疑问：为什么 setTimeout 能让 UI "一段一段出现"？如果把所有 setTimeout 都改成 0ms，UI 会怎样？如果改成 Promise.resolve().then(...)（微任务），又会怎样？

2.2 项目代码原样

src/features/agent-run/fixtures/sample-run.ts：

export function startSampleRun(events: Ref<AgentEvent[]>) {
  events.value = []
  setTimeout(() => events.value.push(sampleEvents[0]), 100)
  setTimeout(() => events.value.push(sampleEvents[1]), 200)
  setTimeout(() => events.value.push(sampleEvents[2]), 300)
  // ... 共 9 个 setTimeout
}

src/composables/useAgentRun.ts（今天未写，Week 2 会补，这里先展示逻辑）：

import { ref, watchEffect } from 'vue'

export function useAgentRun(events: Ref<AgentEvent[]>) {
  const state = ref<AgentRunState>(initialState)

  watchEffect(() => {
    state.value = events.value.reduce(reduceAgentEvent, initialState)
  })

  return { state }
}

2.3 拆解：这段代码里的 3 个设计点

设计点 A：为什么用 setTimeout 而不是同步 push

如果改成同步：

export function startSampleRun(events: Ref<AgentEvent[]>) {
  events.value = []
  events.value.push(sampleEvents[0])
  events.value.push(sampleEvents[1])
  events.value.push(sampleEvents[2])
  // 9 个 push 在同一个宏任务里完成
}

结果：UI 直接跳到最终状态（awaiting-approval），中间 8 次状态变化用户看不到。因为 Vue 的响应式更新是异步批量的：同一个宏任务里多次改 events.value，Vue 只在这个宏任务结束后、下一次渲染帧才刷新 DOM，合并成一次更新。

设计点 B：setTimeout(..., 100/200/300) 的延迟是相对起点还是相对前一个

答案：相对起点（调用 startSampleRun 的那一刻）。9 个 setTimeout 都在同一个同步代码块里注册，100ms/200ms/300ms 都是从 t=0 开始算。不是"第 1 个执行后等 100ms 再执行第 2 个"。

验证：如果改成 setTimeout(..., 0) 全部 0ms，9 个回调会在同一轮宏任务队列里依次执行（顺序由注册顺序决定），UI 仍然是一次性跳到最终状态。要让 UI 分段出现，延迟必须 > 0，强制每个回调在不同的宏任务里执行。

设计点 C：为什么不用 requestAnimationFrame？

流式文本的"一段一段"不是动画帧的"逐帧渲染"。requestAnimationFrame 的回调在浏览器准备重绘前执行，每秒最多 60 次（16.6ms 一帧）；setTimeout 的回调在宏任务队列里执行，可以任意间隔。

今天的事件间隔是 100ms/200ms/300ms（模拟网络延迟），远慢于 16.6ms。如果用 requestAnimationFrame：

  • 你只能控制"在下一帧执行"，不能控制"在 200ms 后执行"；
  • 浏览器标签页切到后台时，requestAnimationFrame 会暂停，setTimeout 不会（只是降到 1000ms 最小间隔）；
  • requestAnimationFrame 适合连续动画（滚动/位移/透明度渐变），不适合离散事件流。

2.4 原理：Event Loop 三层队列的执行顺序

跑一遍下面这段"心算"，你就理解了为什么 setTimeout 能让 UI 分段更新：

// t=0: 同步代码执行
startSampleRun(events)
  → events.value = []
  → 注册 9 个 setTimeout 回调到宏任务队列（100ms/200ms/.../900ms 后触发）
  → 同步代码结束

// t=0~100ms: 当前宏任务结束 → 清空微任务队列 → 渲染帧（如果需要）
  → Vue 的 watchEffect 调度器把响应式更新放进微任务队列
  → 微任务队列清空后，浏览器检查是否需要渲染
  → 初始状态 UI 渲染完成（空的时间线 + idle 徽章）

// t=100ms: 第 1 个 setTimeout 回调执行（新的宏任务）
events.value.push(sampleEvents[0])  // run.started
  → watchEffect 检测到 events.value 变化
  → 把 re-reduce 任务放进微任务队列
  → 当前宏任务结束
  → 清空微任务队列: state.value = events.value.reduce(...) 执行
  → 浏览器渲染: 徽章变 running，时间线出现第 1 条

// t=200ms: 第 2 个 setTimeout 回调执行
events.value.push(sampleEvents[1])  // text.delta
  → 微任务队列: re-reduce
  → 渲染: 时间线出现第 2 条（文本）

// ... 以此类推，9 个事件分别在 9 个宏任务里执行
// 每次宏任务 → 微任务 → 渲染，用户看到 9 次 UI 更新
关键洞察：分段出现的本质是把数据变更拆到多个宏任务。同一个宏任务里改 100 次 events.value，Vue 只渲染 1 次；拆到 100 个宏任务里，Vue 渲染 100 次。setTimeout 的作用不是"让代码慢下来"，而是"把回调推迟到下一个宏任务"。

2.5 反例：如果用 Promise.resolve().then(...)（微任务）会怎样

export function startSampleRun(events: Ref<AgentEvent[]>) {
  events.value = []
  Promise.resolve().then(() => events.value.push(sampleEvents[0]))
  Promise.resolve().then(() => events.value.push(sampleEvents[1]))
  Promise.resolve().then(() => events.value.push(sampleEvents[2]))
  // ... 9 个 Promise
}

结果：UI 仍然一次性跳到最终状态。原因：

  1. 9 个 Promise.resolve().then(...) 的回调都进入微任务队列；
  2. 当前宏任务（startSampleRun）结束后，Event Loop 清空微任务队列 —— 9 个回调在同一轮微任务清空里依次执行；
  3. 9 次 events.value.push 都在渲染前完成，Vue 批量合并成 1 次更新。
微任务 vs 宏任务的分水岭：微任务在当前宏任务结束后、渲染前清空；宏任务在下一轮 Event Loop 执行。要让 UI 分段出现，必须用宏任务（setTimeout / setInterval / MessageChannel）把变更推到不同轮。

2.6 分层提问 —— 先答，再看下一层的解答

问题 1（白板级）：
如果把 9 个 setTimeout 的延迟都改成 0ms，UI 会怎样？会分 9 次渲染，还是 1 次？

展开答案

会分 9 次渲染（假设浏览器来得及渲染）。setTimeout(..., 0) 不是"立即执行"，而是"放进宏任务队列，最快下一轮 Event Loop 执行"。9 个回调虽然延迟都是 0ms，但它们仍然是 9 个独立的宏任务，按注册顺序依次执行。每个宏任务结束后，Event Loop 都有机会渲染。

但有个坑：浏览器的渲染帧率是 60fps（16.6ms 一帧），如果 9 个宏任务在 16.6ms 内全部执行完，浏览器可能合并成 1 次渲染。要保证 9 次渲染，延迟至少要 > 16.6ms。

问题 2（项目级）：
今天 v3 的 reduceAgentEvent 是纯函数（同步、无副作用）。如果在 reducer 里加一行 console.log(event.type)，你会在浏览器控制台看到 9 行日志。这 9 行日志是在 9 个宏任务里打印的，还是在 9 个微任务里？

展开答案

在 9 个微任务里打印。因为 watchEffect 的回调是在微任务里执行的（Vue 的响应式调度器用 Promise.resolve().then(...) 包裹）。

时间线：

  1. t=100ms：宏任务执行 events.value.push(sampleEvents[0])
  2. 微任务：watchEffect 回调执行 → reduceAgentEvent 执行 → console.log 打印第 1 行
  3. 渲染：UI 更新
  4. t=200ms：宏任务执行 events.value.push(sampleEvents[1])
  5. 微任务：console.log 打印第 2 行
  6. 渲染：UI 更新

关键：reducer 本身是纯同步函数，但它被 watchEffect 包裹后，执行时机由 Vue 的调度器控制 —— 进入微任务队列。

问题 3（工程级）：
Day 5 要把 fixture 换成真 SSE，后端每 100ms 推一个事件。如果网络突然卡顿，3 个事件在同一个瞬间到达前端（EventSource 的 onmessage 连续触发 3 次），UI 会怎样？

展开答案

UI 仍然会分 3 次更新，因为 onmessage 的每次触发都是独立的宏任务。即使 3 个事件在网络层几乎同时到达，浏览器的 EventSource 实现会把它们拆成 3 个独立的 onmessage 回调，每个回调在独立的宏任务里执行。

但如果你手写 SSE 解析逻辑（Day 5 会讲），在一个 ReadableStream 的 chunk 里收到 3 个完整事件，你必须手动拆成 3 次 events.value.push：

for (const event of parsedEvents) {
  setTimeout(() => events.value.push(event), 0)
}

否则 3 次 push 在同一个宏任务里，UI 只更新 1 次。

问题 4（架构级）：
为什么 reducer 必须是纯函数？如果在 reducer 里写 localStorage.setItem(...) 或者 fetch(...)，会出什么问题？

展开答案

问题 1：副作用的执行时机不可控。watchEffect 的回调在微任务里执行，但你不知道它会被触发多少次。Vue 的响应式系统在依赖收集阶段可能多次运行 watchEffect，如果 reducer 里有 fetch(...)，可能同一个请求发 3 次。

问题 2：破坏时间旅行调试。纯函数保证 reduce(state, event) 可以在任意时刻重放 —— 给定相同的 state 和 event，输出永远一样。有副作用后，重放会重复执行副作用（比如重复写 localStorage、重复发请求）。

问题 3：测试成本暴涨。今天的 agent-run-state.spec.ts 只需要 expect(reduce(state, event)).toEqual(...)，不需要 mock localStorage、不需要 mock fetch。有副作用后，每个测试都要 setup/teardown，测试变成集成测试。

正确做法：副作用放在 reducer 外面 —— 用 watch 监听 state 变化，在 watch 回调里执行副作用。Day 17 埋点会讲。

真题 1："setTimeout 和 setInterval 有什么区别？"

烂答法："setTimeout 只执行 1 次，setInterval 重复执行。"

及格答法："setTimeout 在延迟后执行 1 次回调；setInterval 每隔一段时间重复执行，但间隔不精确 —— 如果回调执行耗时超过间隔，下一次会立即触发。"

优秀答法（30 秒）："我在监控项目的 fixture 里用 setTimeout 模拟事件流 —— 9 个事件分别在 100ms/200ms/.../900ms 后触发。我不用 setInterval 是因为事件间隔不均匀，用 setTimeout 更灵活。两者的核心区别：setTimeout 把回调推到指定延迟后的某一轮宏任务；setInterval 尝试每隔 N ms 推一次，但如果回调执行时间 > N，队列里会堆积回调 —— 浏览器的实现通常会跳过堆积的回调。真正要做定时轮询，我会用 setTimeout 递归（回调结束后再 setTimeout 下一次），这样能保证上一次执行完才开始计时下一次。"

真题 2："微任务和宏任务有什么区别？举例说明。"

烂答法："微任务比宏任务先执行。Promise 是微任务，setTimeout 是宏任务。"

及格答法："每个宏任务结束后，Event Loop 会清空微任务队列，然后才执行下一个宏任务。微任务包括 Promise.then、MutationObserver、queueMicrotask；宏任务包括 setTimeout、setInterval、I/O、UI 渲染。"

优秀答法（挂钩今天的项目）："区别的本质是执行时机和渲染边界。我在监控项目里踩过这个坑：最开始想用 Promise.resolve().then(...) 模拟事件流，结果 UI 一次性跳到最终状态 —— 因为 9 个 Promise 回调都在同一个宏任务结束后的微任务清空阶段执行完，浏览器还没来得及渲染，数据已经全部 push 进去了。改成 setTimeout 后，9 个回调分散到 9 个宏任务，每个宏任务结束后都有渲染机会，UI 才能分段出现。微任务的边界是当前宏任务，宏任务的边界是下一轮 Event Loop。要让 UI 响应中间状态，必须用宏任务拆分数据变更。Vue 的响应式更新用的是微任务（queueMicrotask 或 Promise.then），所以同一个宏任务里改 100 次数据，Vue 只渲染 1 次。"

真题 3："Vue 3 的响应式更新是同步还是异步的？为什么要异步？"

烂答法："异步的，因为性能好。"

及格答法："异步的。Vue 用 scheduler 把响应式更新推到微任务队列，批量执行。好处是同一个宏任务里多次改同一个响应式变量，只触发 1 次更新。"

优秀答法（30 秒）："Vue 3 的响应式更新是异步批量的 —— 用 queueMicrotask（或降级 Promise.then）把更新推到微任务队列。今天项目里我在一个 setTimeout 回调里 push 1 个事件，watchEffect 检测到 events.value 变化后，不是立即执行 reduce，而是把 reduce 任务放进微任务队列。当前宏任务结束后，微任务队列清空，reduce 执行 1 次，然后浏览器渲染。如果同步更新，每次 push 都立即 reduce + 渲染，9 个事件就是 9 次同步 reduce + 9 次同步渲染 —— 主线程阻塞，用户会看到卡顿。异步批量的价值是把多次数据变更合并成 1 次计算 + 1 次渲染，前提是这些变更在同一个宏任务里。要让 UI 响应中间状态，必须把变更拆到多个宏任务。"

3.3 拆解：纯函数的 3 个保证

保证 A：相同输入 → 相同输出（引用透明）

const state1 = reduceAgentEvent(initialState, event1)
const state2 = reduceAgentEvent(initialState, event1)  // 完全一样的入参
expect(state1).toEqual(state2)  // ✓ 深度相等

如果 reducer 里读了 Date.now() / Math.random() / localStorage.getItem(...)，这个保证就破了 —— 同样的入参，两次调用可能返回不同结果。测试变成概率通过。

保证 B：不可变（不改入参）

const oldState = { status: 'idle', runId: null, timeline: [], lastSequence: 0 }
const newState = reduceAgentEvent(oldState, event)
expect(oldState.status).toBe('idle')  // ✓ 旧状态未被改
expect(newState.status).toBe('running')  // ✓ 新状态是新对象

如果 reducer 里写 state.status = 'running'; return state（改入参再返回），测试里 oldState 和 newState 会指向同一个对象，断言 oldState.status 会失败。更严重的是：时间旅行调试（重放事件序列）会失效，因为你没法回退到"修改前的状态"。

保证 C：无副作用

副作用包括：

  • 写外部状态（localStorage.setItem / 改全局变量 / 改入参）；
  • 发起网络请求（fetch）；
  • 操作 DOM（document.querySelector）；
  • 记日志（console.log）—— 严格来说也是副作用，但测试时可以容忍。

无副作用 = 测试不需要 setup/teardown。你可以连续跑 100 个测试用例，每个都是独立的 reduceAgentEvent(state, event) 调用，互不干扰。

3.4 原理：为什么纯函数让测试成本指数级下降

对比两种写法的测试成本：

特性 纯函数 reducer 有副作用的 reducer

测试稳定性 100%（无外部依赖） 95%（localStorage mock 可能失效、并发测试可能污染）

并发测试 ✓ 互不干扰 ✗ 共享 localStorage，需要加锁
关键洞察：测试成本 = 隔离成本。纯函数的隔离成本为 0（不需要隔离，因为没有共享状态）；有副作用的函数，隔离成本随副作用种类指数增长（1 种副作用 = 1 个 mock，3 种 = 3 个 mock + 它们之间的交互）。

问题 1（白板级）：

问题 2（项目级）：
今天的 reducer 测试用 expect(next).toBe(state) 判断"未变"（引用相等）。如果把 toBe 改成 toEqual（深度相等），测试还能通过吗？两者有什么区别？

展开答案

能通过，但意义不同：

  • toBe 比较引用（===）—— 两个变量是否指向同一块内存；
  • toEqual 比较内容（递归比较每个字段）—— 两个对象的字段值是否一样。

今天的测试用 toBe 是为了验证 reducer 的短路优化：

if (event.sequence <= state.lastSequence) return state  // ← 直接返回旧引用

如果改成 toEqual，测试仍然能通过，但你就验证不了"reducer 没有创建新对象"这个性能优化了。toBe 能检测到这个细节：

const s1 = reduceAgentEvent(initialState, event1)

问题 3（架构级）：

  () => state.value.status,

    if (newStatus !== oldStatus) {
      fetch('/api/analytics', {
        method: 'POST',
        body: JSON.stringify({ event: 'status_change', from: oldStatus, to: newStatus }),

    }
  }
)

  1. Reducer 保持纯净 —— 只负责计算新状态；
  2. Watch 是"观察者" —— 状态变了它自动触发，不需要在 reducer 里手动调；
  3. watch 默认只在值真正变化时触发（Vue 内部用 === 比较）—— 和 reducer 返回旧引用的优化天然契合。

4.2 项目代码原样（Day 5 预告版）

Day 5 会用 fetch + ReadableStream 替换 fixture：

const response = await fetch('/api/agent/run', {
  method: 'POST',
  headers: { 'Accept': 'text/event-stream' },
  body: JSON.stringify({ prompt: '...' }),

const reader = response.body!.getReader()
const decoder = new TextDecoder('utf-8')  // ← 关键：带状态的解码器
let buffer = ''

while (true) {
  const { done, value } = await reader.read()
  if (done) break

  buffer += decoder.decode(value, { stream: true })  // ← stream: true 是关键

  const lines = buffer.split('\n\n')
  buffer = lines.pop()!  // 最后一块可能不完整，留到下一轮

4.3 拆解：这段代码里的 3 个设计点

设计点 A：为什么要 new TextDecoder('utf-8')，不能用 String.fromCharCode？

TextDecoder 是有状态的解码器。当你调用 decoder.decode(chunk, { stream: true }) 时：

  1. 如果 chunk 末尾有不完整的 UTF-8 序列（比如汉字"正"的 3 字节 E6 AD A3 只收到前 2 字节 E6 AD），解码器会暂存这 2 字节；
  2. 下一个 chunk 到达时，解码器把暂存的 2 字节和新 chunk 的第 1 字节（A3）拼起来，解码出"正"；
  3. 如果用 String.fromCharCode(...chunk)，你会看到乱码 ��（两个 U+FFFD 替换字符）。

{ stream: true } 的作用：告诉解码器"这不是最后一个 chunk，如果有不完整序列，别抛错，暂存起来"。最后一个 chunk 传 { stream: false }（或不传），解码器会把暂存的字节强制解码（如果还不完整就输出 �）。

设计点 B：为什么要 buffer.split('\n\n') 再 lines.pop()？

SSE 的格式是 data: ...\n\n（两个换行符分隔事件）。一个 chunk 可能包含：

  • 1.5 个事件（一个完整 + 半个）；
  • 0.5 个事件（上一个 chunk 的后半 + 这个 chunk 的前半）。

buffer 是行缓冲区：

// 第 1 个 chunk: "data: {\"type\":\"run.started\"}\n\ndata: {\"type\":"
buffer = "data: {\"type\":\"run.started\"}\n\ndata: {\"type\":"
lines = ["data: {\"type\":\"run.started\"}", "data: {\"type\":"]
buffer = lines.pop()  // "data: {\"type\":" 留到下一轮

// 第 2 个 chunk: "\"text.delta\"}\n\n"
buffer = "data: {\"type\":\"text.delta\"}\n\n"
lines = ["data: {\"type\":\"text.delta\"}", ""]
buffer = ""  // 空串，下一轮继续

为什么 pop()：最后一块可能是不完整的行（没有 \n\n 结尾），留到下一轮和新 chunk 拼起来。

设计点 C：取消请求时怎么清理

用户点"停止"按钮时，要调用 reader.cancel() 并中止 fetch：

const abortController = new AbortController()

const response = await fetch('/api/agent/run', {
  signal: abortController.signal,
  // ...
})

// 用户点停止
function onStop() {
  abortController.abort()
  reader.cancel()  // 释放流的锁
}

不调 reader.cancel() 的话，while (true) 循环会一直等 reader.read()，浪费内存。

4.4 原理：UTF-8 跨 chunk 解码的字节级心算

UTF-8 编码规则：

  • ASCII（0-127）：1 字节，高位为 0（0xxxxxxx）
  • 2 字节字符（如拉丁扩展）：110xxxxx 10xxxxxx
  • 3 字节字符（如中文）：1110xxxx 10xxxxxx 10xxxxxx
  • 4 字节字符（如 Emoji）：11110xxx 10xxxxxx 10xxxxxx 10xxxxxx

心算例子：汉字"正" = U+6B63 = UTF-8 E6 AD A3（3 字节）

// Chunk 1: 前 10 字节包含 "正在" 的 "正" 的前 2 字节
[... E6 AD]

decoder.decode(chunk1, { stream: true })
  → 解码前面的完整字符
  → 看到 E6（1110 0110），判断这是 3 字节字符的开头
  → 看到 AD（1010 1101），这是第 2 字节
  → 第 3 字节缺失 → 暂存 [E6 AD]，返回前面解码的字符串

// Chunk 2: 第 1 字节是 "正" 的最后 1 字节
[A3 ...]

decoder.decode(chunk2, { stream: true })
  → 取出暂存的 [E6 AD]
  → 拼上 chunk2 的第 1 字节 A3 → [E6 AD A3]
  → 解码成 U+6B63 = "正"
  → 继续解码 chunk2 剩余部分
关键洞察：TextDecoder 的状态是暂存的不完整字节。没有 { stream: true }，解码器会把不完整字节当错误，输出 �；有了它，解码器会等下一个 chunk。

4.5 反例：如果用 String.fromCharCode 会怎样

const text = String.fromCharCode(...chunk)  // ✗ 错误

String.fromCharCode 把每个字节当作一个 Unicode 码点（U+0000 到 U+00FF）：

// Chunk 1: [E6 AD]
String.fromCharCode(0xE6, 0xAD) = "æ­" = "æ­"  // ✗ 乱码

// Chunk 2: [A3 ...]
String.fromCharCode(0xA3, ...) = "£..." = "£..."  // ✗ 乱码

"正"永远拼不出来，因为它的 3 字节被拆成了 3 个独立的单字节字符。

4.6 分层提问 —— 先答，再看下一层的解答

问题 1（白板级）：
Emoji "😀" 的 UTF-8 编码是 4 字节 F0 9F 98 80。如果第 1 个 chunk 包含前 3 字节，第 2 个 chunk 包含最后 1 字节，decoder.decode(chunk1, { stream: true }) 会返回什么？

展开答案

返回空字符串 ""（假设 chunk1 里只有这 3 字节）。解码器看到 F0（11110 000），判断这是 4 字节字符的开头，但只收到 3 字节，暂存 [F0 9F 98]，等下一个 chunk。第 2 个 chunk 到达时，拼成 [F0 9F 98 80]，解码出 "😀"。

如果去掉 { stream: true }：decoder.decode(chunk1) 会抛错或返回 ���（3 个替换字符），因为解码器认为这是最后一个 chunk，3 字节无法构成完整字符。

问题 2（项目级）：
Day 5 的代码里，buffer.split('\n\n') 后为什么要 lines.pop()？如果不 pop，直接 for (const line of lines)，会出什么问题？

展开答案

会把不完整的行当完整行解析，导致 JSON.parse 报错。例如：

// Chunk 1: "data: {\"type\":\"run.started\"}\n\ndata: {\"type\":"
lines = ["data: {\"type\":\"run.started\"}", "data: {\"type\":"]

// 如果不 pop，第 2 行进入 for 循环
JSON.parse("{\"type\":")  // ✗ SyntaxError: Unexpected end of JSON input

pop() 的作用是把最后一块（可能不完整）留到下一轮，和新 chunk 拼起来后再解析。

边界情况：如果 chunk 刚好在 \n\n 处断开，split('\n\n') 最后一个元素是空串 ""，pop 掉也无害。

问题 3（工程级）：
如果后端在一个 SSE 消息里推 3 个事件（用 \n\n 分隔），前端会一次性收到 3 个事件吗？还是分 3 次 reader.read()？UI 会怎样？

展开答案

取决于 TCP 分包。如果 3 个事件的总字节数 < TCP MSS（通常 1460 字节），浏览器可能在一个 reader.read() 里收到 3 个；如果超过，会分多个 chunk。

关键是：buffer.split('\n\n') 会把一个 chunk 里的多个事件拆开：

// 一个 chunk 包含 3 个完整事件
buffer = "data: {...}\n\ndata: {...}\n\ndata: {...}\n\n"
lines = ["data: {...}", "data: {...}", "data: {...}", ""]

for (const line of lines) {
  events.value.push(JSON.parse(line.slice(6)))  // 3 次 push
}

UI 会怎样：和深挖 2 讲的一样 —— 3 次 push 在同一个宏任务里，Vue 批量更新，UI 一次跳 3 格。要让 UI 分段出现，必须把每个 push 包在 setTimeout(..., 0) 里（或者后端每次只推 1 个事件，间隔 > 16ms）。

4.7 面试真题拆解 —— 从流式处理出发怎么答

真题 1："你怎么处理 AI 流式响应的中文乱码？"

烂答法："用 UTF-8 解码。"

及格答法："用 TextDecoder 的 { stream: true } 参数，让解码器暂存不完整的 UTF-8 字节，等下一个 chunk 拼起来再解码。"

优秀答法（30 秒）："核心问题是多字节字符可能被 TCP 拆包。中文是 3 字节 UTF-8，如果一个汉字的前 2 字节在 chunk 1、最后 1 字节在 chunk 2，直接 String.fromCharCode 会输出乱码。我用 TextDecoder 的 { stream: true } 参数 —— 解码器看到不完整序列时会暂存，等下一个 chunk 到达后拼起来解码。监控项目 Day 5 换成真 SSE 时踩过这个坑：最开始没加 { stream: true }，每次 chunk 边界刚好在中文字符中间时，UI 就出现 ��。加上后，解码器自动处理跨 chunk 的字符。Emoji（4 字节）同理。这个参数的本质是把无状态解码变成有状态解码。"

真题 2："SSE 和 WebSocket 有什么区别？什么场景用 SSE？"

烂答法："SSE 是单向的，WebSocket 是双向的。"

及格答法："SSE 是服务端推（Server-Sent Events），基于 HTTP，只能服务端→客户端；WebSocket 是全双工，基于 TCP，双向通信。SSE 更简单，适合服务端主动推送的场景（通知、日志流）。"

优秀答法（挂钩今天的项目）："两者的核心区别是连接模型和复杂度。SSE 是 HTTP 长连接 + text/event-stream，浏览器原生支持（EventSource），自动重连、自动解析 data: 格式；WebSocket 是独立协议（ws://），需要握手升级，没有自动重连。监控项目用 SSE 是因为：Agent 执行是单向推送（后端推事件，前端只在最开始发一次 prompt），不需要中途双向交互。SSE 的价值是简单 —— 我只需要 fetch + ReadableStream，不需要额外的 ws 库、不需要处理心跳。唯一的坑是手动解析 SSE 格式（data: ...\n\n）和跨 chunk UTF-8 解码，但这比 WebSocket 的帧解析 + ping/pong 简单。如果是聊天室（双向高频），我会用 WebSocket；如果是日志流、进度推送、AI 流式输出，SSE 够用且更轻。"

真题 3："用户点停止按钮时，怎么取消 SSE 请求？"

烂答法："关闭连接。"

及格答法："用 AbortController，fetch 时传 signal，点停止时调 abort()。"

优秀答法（30 秒）："要做两件事：中止 fetch 和 释放流的锁。我用 AbortController 的 signal 传给 fetch，用户点停止时调 abortController.abort() —— 这会让 fetch 抛 AbortError，中断网络请求。同时调 reader.cancel() 释放 ReadableStream 的锁 —— 如果不调，while (true) 循环会一直等 reader.read()，内存泄漏。监控项目 Day 5 会加这个逻辑：在 useAgentRun composable 里，onUnmounted 自动调 abort() + cancel()，保证组件卸载时清理资源。这个模式和 Vue 的生命周期天然契合 —— 组件挂载时开始 SSE，卸载时自动清理。"

5.4 原理：为什么 domain 层不能依赖 Vue

如果 reduceAgentEvent 里 import ref：

import { ref } from 'vue'  // ✗ 破坏 domain 纯净性

  // ...

破坏了三个价值：

  1. 可移植性：reducer 不能在 Node.js 环境跑（Vue 依赖 DOM）—— Day 15 要在 Node.js 里跑回放测试，有 Vue 依赖就跑不了；
  2. 测试成本：单元测试要 import Vue 的测试工具（@vue/test-utils），从 <1ms 的纯函数测试变成 10ms+ 的组件测试；
  3. 心智负担：看到 domain 层文件，你不知道它是不是纯函数 —— 可能藏了 ref / watch / onMounted，可测试性未知。
关键洞察：domain 层的纯净度 = 项目的可测试性下限。domain 层越纯，单元测试越快、越稳；domain 层有副作用，整个项目的测试成本指数增长。

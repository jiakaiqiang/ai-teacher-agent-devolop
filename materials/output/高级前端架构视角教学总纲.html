课程总览 课程资料

高级前端架构视角教学总纲

适用范围：90 天 AI 前端 -> AI 全栈 -> Agent 工程师转型路线
技术主线：Vue 3 + TypeScript，不以 React 作为前 60 天前提
定位：使用高级前端工程师的思考方式教学，但不提前授予高级职级。

1. 教学目标

整套课程不把前端理解为“写页面、调接口”。高级前端视角要求学生能对用户侧系统的完整质量负责：

  • 从业务目标建立领域模型，而不是直接按页面拆组件。
  • 主动定义 API、事件、状态和错误合同，而不是被动接受后端返回值。
  • 理解浏览器、网络、BFF、数据库、模型和 Agent Tool 的完整数据流。
  • 在正常、加载、空数据、失败、超时、取消、重连、降级和恢复状态下保持一致体验。
  • 用性能预算、安全边界、Trace、测试和发布策略证明系统可交付。
  • 能与产品、后端、AI、测试、安全和 SRE 讨论边界与取舍。
  • 知道何时抽象、何时保持简单，避免为了“架构感”制造多余层次。

架构能力的核心不是使用多少设计模式，而是管理变化、复杂度和风险。

2. 十个贯穿维度

架构维度 高级前端必须回答的问题 项目证据
业务与领域 用户真正完成什么任务，核心实体和状态是什么 用户旅程、领域模型、术语表
系统边界 浏览器、BFF、AI 服务、数据库、工具各负责什么 C4 图、模块边界图、责任矩阵
合同治理 API/事件如何版本化、校验、兼容和失败 OpenAPI/Schema、事件合同、错误模型
状态与数据流 谁拥有状态，如何处理并发、过期和恢复 状态机、数据流图、reducer 测试
模块与演进 如何减少耦合并支持后续功能变化 目录边界、依赖规则、ADR
性能与容量 延迟、渲染、内存、包体、并发预算是多少 性能预算、Profile、容量估算
安全与隐私 哪些输入不可信，权限在哪里执行，日志能记录什么 Threat Model、安全测试、脱敏规则
可靠性与降级 下游失败时用户还能完成什么，如何恢复 故障矩阵、超时/重试/幂等、Runbook
可观测性 如何从用户现象定位到前端、BFF、模型和工具 Trace、指标、结构化日志、告警
交付与治理 如何测试、灰度、回滚、控制变更风险 CI/CD、发布清单、回滚演练、复盘

3. 每日架构学习闭环

每一天都按同一架构闭环执行：

  1. 问题建模：明确用户、场景、约束、成功指标和非目标。
  2. 现状阅读：阅读当前代码和数据流，禁止脱离项目凭空设计。
  3. 方案比较：至少比较两个方案，写出复杂度、风险和演进成本。
  4. 边界先行：编码前定义合同、状态、模块责任或失败语义。
  5. 纵向实现：完成可以进入真实项目主链路的最小增量。
  6. 失败验证：注入异常，证明超时、取消、重复、越权或降级行为。
  7. 数据验证：用测试、Trace、Profile 或指标验证结论。
  8. 架构复盘：记录今天的决定、技术债、触发重构的条件和后续演进。

每天至少提交一个架构证据：状态图、时序图、C4 局部图、ADR、Schema、Threat Model、性能预算、故障矩阵或发布清单。只画图但无法对应代码，不计入有效证据。

4. 各阶段的高级前端视角

Day 1-20：前端系统架构

  • 从运维领域模型推导页面、状态和事件合同。
  • 区分 REST 快照、WebSocket 广播和 SSE 单次诊断流的职责。
  • 管理异步竞态、重复事件、重连、取消和页面恢复。
  • 把 Agent Tool、证据、批准和错误设计成可审计用户体验。
  • 建立 XSS、敏感参数、长会话性能和前端 Trace 边界。

阶段架构产物：Frontend C4、实时数据时序图、事件 Schema、状态机、性能预算、Threat Model、故障矩阵。

Day 21-40：从前端负责人进入 Node/BFF 架构

  • BFF 与领域服务的边界，DTO 与领域模型的转换。
  • API 兼容、错误语义、鉴权、资源权限和审计。
  • PostgreSQL 事务/索引、Redis、BullMQ 如何影响前端一致性与体验。
  • Tool Registry、Human-in-the-loop、恢复和全链路 Trace。
  • 前后端团队如何通过合同测试和版本策略独立发布。

阶段架构产物：BFF 边界图、API 错误模型、数据模型、权限矩阵、队列状态机、端到端 Trace 图。

Day 41-60：从前端负责人进入 AI 全栈架构

  • NestJS BFF 与 FastAPI AI Service 的服务边界和失败隔离。
  • Provider 抽象、结构化输出、Prompt 版本、模型降级和成本记录。
  • RAG 摄取、检索、rerank、引用和 Eval 如何形成可验证闭环。
  • 前端如何表达证据不足、低置信度、评测差异和模型降级。
  • 多租户、Docker、CI/CD、OpenTelemetry、事故演练和回滚。

阶段架构产物：AI 服务 C4、RAG 数据流、Eval 门禁、模型路由 ADR、SLO、部署拓扑和回滚 Runbook。

Day 61-70：Local CLI Runtime 与轻量多 Agent 协同架构

  • 本机 Codex/Claude CLI 如何通过统一 Runtime Adapter、ProcessSupervisor 和事件合同接入。
  • coordinator、executor、validator 的 TaskContract、Handoff、Artifact、证据门禁和责任边界。
  • 事件如何支持 UI 展示、取消、恢复、审计和跨角色投影。
  • 角色权限、命令 allowlist、worktree 隔离、受限 DAG、Budget 和终止语义。

阶段架构产物：Local CLI Runtime 组件图、协同状态机、Task/Handoff/Artifact 合同、worktree 时序、预算策略和安全边界图。

Day 71-80：MCP、Human Runtime 与生产 RAG 架构

  • MCP Host/Client/Server 的发现、调用、取消、能力协商和信任边界。
  • Human Runtime 的批准、拒绝、超时、幂等、Pause/Resume 和重启恢复。
  • RAG 的黄金集、Hybrid/Rerank、引用、降级和权限隔离。
  • 前端如何让工具风险、人工介入、检索证据和恢复状态可理解。

阶段架构产物：MCP 对接 ADR、Human 状态机、RAG Eval、恢复时序图和沙箱 Threat Model。

Day 81-90：动态委派与生产治理架构

  • 将既有固定 coordinator/executor/validator 升级为动态委派时的合同、责任和停止边界。
  • 任务依赖、并发、Artifact 交接、冲突和最终验收。
  • Eval、A/B、Trace/Replay 如何衡量多 Agent是否真的优于单 Agent。
  • SLO、容量、成本、权限、沙箱、回滚和 ROI 如何进入生产评审。
  • 前端/平台控制面如何支持运营者观察、干预和追责。

阶段架构产物：多 Agent C4、任务/Artifact 合同、冲突策略、Eval Pipeline、SLO/容量模型和生产就绪评审。

5. 架构决策记录模板

重要选择必须写 ADR：

# ADR-NNN：决策标题

## Context
业务问题、当前系统、约束和非目标。

## Options
至少两个可行方案及其复杂度、性能、安全和演进成本。

## Decision
选择什么，为什么适合当前阶段。

## Consequences
获得什么、牺牲什么、引入哪些技术债。

## Validation
用什么测试、指标、Trace 或故障实验证明决策有效。

## Revisit Trigger
出现什么数据或业务变化时必须重新评估。

不允许用“业界都这样”“框架推荐”作为唯一决策理由。

6. 高级前端代码审查视角

每天审查 Codex/Claude Code diff 时，必须回答：

  • 这段代码属于哪个领域和模块，依赖方向是否正确？
  • 网络、模型和工具输入是否在边界处校验？
  • 状态是否只有一个权威来源，是否存在竞态和重复执行？
  • 加载、空、失败、取消、超时、降级和恢复是否完整？
  • 是否引入 XSS、越权、敏感日志或供应链风险？
  • 性能成本是否可测，资源是否在卸载/中断时释放？
  • 如何测试，如何观测，如何回滚？
  • 这个抽象解决真实重复和变化了吗，还是提前设计？

无法回答这些问题的 AI 代码不能合并。

7. 架构门禁

六个阶段考试都必须包含架构单项，架构得分低于 70% 时阶段总分最高 69：

阶段 架构答辩主题
Day 20 浏览器实时数据、Agent 诊断 UI、状态和故障恢复
Day 40 Vue、BFF、数据库、缓存、队列和 Tool Loop 边界
Day 60 Vue、NestJS、FastAPI、RAG/Eval、部署与观测
Day 70 Agent Loop、Runtime、Tool、MCP 和预算控制
Day 80 Context、Memory、Workflow、队列、恢复和沙箱
Day 90 多 Agent、Artifact、Eval、Trace、SLO、成本和生产治理

架构答辩不能只展示最终图。教师会随机改变一个约束，例如流量增长十倍、模型不可用、跨租户、事件重复或成本减半，学生必须说明系统如何演进。

8. 反模式

  • 先建 utils/components/services 大目录，再寻找业务边界。
  • 为了展示高级而引入微前端、微服务、事件总线或复杂设计模式。
  • 组件层直接理解模型 Provider、数据库或工具内部细节。
  • 用 Pinia 保存所有状态，不区分服务端状态、路由状态和临时 UI 状态。
  • 只处理成功路径，用 toast 代替错误模型和恢复策略。
  • 只看平均延迟，不看 P95/P99、错误率、取消率和用户感知。
  • 有架构图但代码依赖相反，或 ADR 没有验证和重审条件。
  • 把使用 Codex/Claude Code 的速度当作架构能力。

9. 最终能力定位

完成课程后，应能以高级前端的思考方式承担 AI 产品前端和跨栈协作：定义合同、识别风险、设计降级、建立证据并推动端到端交付。

但“使用高级视角完成训练”不自动等于“高级前端工程师职级”。职级还需要更长周期的生产规模、跨团队影响、线上事故和持续演进经验。求职时应以真实项目证据表述，不虚构年限和生产规模。

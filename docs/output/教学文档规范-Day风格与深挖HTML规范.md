## 0. 立项前提：这是"学习文档"不是"交付文档"

- 用户目标是 **60/90 天深度学习**，不是快速产出功能。文档服务学习曲线，不是服务产品排期。
- 硬红线：**AI 辅助 30% + 手写核心 70%**。以下内容 AI 只出结构、脚手架、样板、类型骨架，**禁止** AI 直接生成完整实现：
  - NestJS Module / Controller / Service / Provider / Middleware / Guard / Interceptor 完整代码；
  - Vercel AI SDK Tool Calling 的 `tool()` 完整实现、Schema `z.object` 完整字段、执行体；
  - LangChain.js 的 RAG 关键链路（分割策略、embedding、reranker、hybrid search 组合）；
  - LangGraph.js 的 StateGraph、Node 逻辑、Edge 条件路由、human-in-the-loop 实现；
  - 具体业务算法（异常检测、聚合、缓存、重试策略等）；
  - System Prompt / Few-shot / 多轮上下文管理的 prompt 主体；
  - Try-Catch / 日志 / 重试 / 断点调试的错误处理主体；
  - Schema 字段主体（zod 的 `z.object` 具体字段、Prisma 具体列除表结构骨架外的业务字段）；
  - Adapter / 映射函数 / reducer / 状态机的主体逻辑；
  - 单元测试用例的断言体与 payload 内容（外壳可生成，见 §0.1）。
- 允许 AI 直接生成（30%）：`package.json` / `tsconfig` / `docker-compose` / `.gitignore` / `Dockerfile` / `README` 骨架、DTO 类型骨架（`type XxxDto = z.infer<typeof XxxSchema>` 这种 2 行文件）、Prisma Schema 表结构骨架、Swagger 装饰器、测试框架样板（`describe / it / expect` 外壳）、环境变量类型、基础 CRUD 的 `findMany/create/update/delete`、基础 RESTful 路由声明、TypeScript 类型 / 接口 / Enum 声明、`throw new Error('TODO: 手写实现')` 空壳、`New-Item -ItemType Directory` 等目录创建脚本。
- 生成 30% 内容时必须在文档里标注 `> ✅ 这是样板代码，可以直接使用。建议：快速浏览确认格式即可。`
- 遇到 70% 内容的请求，**必须拒绝生成**，改为提供学习指导（阅读链接 + 核心概念 + 手写步骤 + 验收清单）。拒绝话术使用 `C:\Users\kaiqj\.claude\CLAUDE.md` 里的「拒绝模板」。

## 0.1 三种标注符号（强制统一）

`Day*.md` / 深挖 HTML 里必须使用以下三种标注，**不得混用其他 emoji 或颜色标签**：

| 符号 | 语义 | 使用场景 | 示例 |
|---|---|---|---|
| `> ✅` | AI 生成的样板代码，用户浏览即可 | 30% 内容处必须打此标 | `> ✅ 这是样板代码，可以直接使用。建议：快速浏览确认格式即可。` |
| `> ❌` | AI 拒绝生成的核心逻辑，用户必须手写 | 70% 内容处必须打此标 + 学习指导 | `> ❌ AI 不生成 Schema 完整字段——这是核心业务逻辑（属规范 §0 硬红线）。你必须手写 Schema 字段。` |
| `> ⚠️` | 骨架版占位 / 待用户确认的选题 / 强红线警告 | 文档尚未展开、深挖 HTML 未确认选题、`git push` 警告等 | `> ⚠️ 本文件目前是「结构骨架 + TODO 占位」，正文尚未展开。` |

**红线**：`> ✅` 后不得跟"你自己写"这类矛盾表述；`> ❌` 后必须紧跟"学习指导"（阅读链接 / 核心概念 / 手写步骤 / 验收清单）；`> ⚠️` 是提醒不是禁止，允许配合 TODO 占位使用。

## 2. §1.4 "目录结构" 章节内部结构（强制）

必须包含 5 个子块，缺一 BLOCK：

1. **一句话说明为什么放在最前面**：读者读代码前先立骨架，才不会看某个文件时不知道它在哪一层。
2. **完整目录树**：ASCII 树 + 每个文件后跟中文一句话说明职责。至少覆盖 domain / features / composables(或 shared) / 编排层 4 层。
   - **新增文件必须用 `★` 前缀标注**（例如 `★ AgentEvent 9 变体 + schemaVersion`），与已存在文件区分。
   - 前置 Day 已建的文件在树里保留但不加 `★`，可加注释"Day 01 已建"。
3. **三版演进对应的文件差异表**：v1 / v2 / v3 三列，行=文件，格子=建 / 不建 / 改。
4. **依赖方向图**：单向箭头。明确标注"红线：xxx 层出现 import 上层就是塌方"。红线要具体到"什么样的 import 语句就算塌方"，不写"不要循环依赖"这种空话。
5. **动手前先问自己 3 个问题**：答不上就带着问题读下去。每题给出后面章节的锚点（例如"见 v3 的第 5.4 节「层与依赖方向」"）。骨架版可写 `TODO：展开正文时把三个问题的完整答案补上`。

## 3. §3-§5 "三版演进" 规则（强制）

**v1 → v2 → v3 是本课的核心教学法**，用来演示"为什么最终代码要长成 v3 那样"。每一步重构必须解决前一步暴露的具体痛点。

### 3.1 三版通用规则

- v1 = 最小闭环。**只解决当天核心概念的 1 个维度**。允许把所有东西塞在一个文件里。
- v2 = 加一个关键设计维度。这个维度必须是 v1 无法优雅表达的。**在 v2 章节末尾必须写"暴露的痛点"，直接引出 v3**。
- v3 = 终态。补齐错误 / 边界 / 分层 / 可测试性。v3 就是用户最终交付的形态。
- 每一版都要有：**要实现什么**（用户视角） → **完整代码**（不省略、不 `...`） → **用到的知识点**（每个点讲清"解决的问题 / 运行机制 / 项目落点 / 生产误区 / 验证方法"） → **暴露的痛点**（v3 章节改为"用到的知识点"，不再有痛点）。

### 3.2 当天主题不适合三版演进时

个别 Day 的主题天然不适合"功能递增"的三版演进（例如 Day02 "领域合同"、Day23 "评测 Eval"、Day89 "复盘"）。此时：

- §1.3 明确说明"本日不用功能递增三版演进"，并给出替代结构。已有先例：
  - **保护递进型（Day02 领域合同）**：v1=只定义 Domain 类型不做校验 / v2=加 zod Schema + DTO/Domain 分层 / v3=加版本合同 + 兼容适配器。三版依次给出的是"保护强度"而非"功能范围"。
  - **实验对照型**：实验 A / 实验 B / 实验 C，每个实验独立可跑，用来对比同一问题的三种解法。
- §3-§5 章节标题相应改写，但**必须保留 3 个递进阶段 + 每阶段"要实现什么/完整代码/知识点/痛点"结构**。禁止合并为一节。
- 骨架版 Day 允许各版正文写 `TODO（阶段 2 展开）：...` 占位，但必须在占位里说清"AI 只出什么、用户手写什么"（例如 `AI 只出 interface 骨架，业务字段由用户手写`）。

### 3.3 v3 "完整代码" 逐文件展示的写法

- 每个文件用二级块 `**src/domain/xxx.ts**` 标题。
- 代码块用 ` ```typescript ` / ` ```vue ` / ` ```json ` 精确标注语言。
- 关键行用行内注释解释"为什么这么写"，**不写"这里做什么"**（做什么由代码本身说清楚，为什么才是学习价值）。

## 4. §7 验收清单（强制）

**只放验收，不放脚手架。** 7.1-7.5 已前置到 §1.5。

- 7.6 E：写核心逻辑测试（20 分钟）
  - 至少 6 个测试用例覆盖：happy path / 边界 / 错误 / 幂等 / 状态转移 / 反例。
  - 测试针对 v3 里最纯的那一层（reducer / service / schema validator），**不 mount 组件、不启服务器**。
- 7.7 F-1：反证实验 1（5 分钟）
  - 临时删除 v3 里一个关键保护（去重 / exhaustive check / schema 校验 / 权限守卫），跑测试观察失败输出。
  - **截图或复制失败输出，保存到 `docs/evidence/day-{N}/{实验名}.md`。**
  - 完成后**恢复代码**。文档里明确写"实验完成后恢复代码"。
- 7.8 F-2：反证实验 2（5 分钟）
  - 同上，换另一个保护。
- 7.9 F-3：验证 + 提交（10 分钟）
  - `pnpm typecheck && pnpm lint && pnpm test && pnpm build` 四件套。
  - Conventional Commits 提交信息模板，标注 Day 号、v1/v2/v3 阶段。
  - **禁止**在文档里写 `git push`。commit 后由用户自己决定何时 push。

## 6. 深挖 HTML 规范（`Day{N}深挖-{弱项主题}.html`）

深挖 HTML 是 **补弱专用文档**，只在当天主题触碰到用户能力缺口时才生成。**必须由用户先确认要挖哪几个弱点、锚点在项目里的哪段代码**，AI 不自作主张选题。

### 6.1 文件命名

`Day{N}深挖-{主题}.html`。主题短语用中文名词，例如 `前端底子补弱`、`NestJS 依赖注入`、`RAG 检索精度`、`LangGraph 状态机`。

### 6.2 结构（强制）

```
<header>
  标题 + 一句话摘要（挖哪些弱点、依据哪份能力报告）
  返回 Day{N}.md 的链接
  TOC：编号 + 每个深挖的标题
</header>

<!-- 6 篇深挖，每篇结构一致：-->
<section id="dig-{n}">
  <h2>深挖 {n}：{主题} —— 从今天项目里的 {锚点} 讲起</h2>
  <h3>{n}.1 场景锚点（10 秒定位）</h3>          ← 项目里的哪段代码
  <h3>{n}.2 项目代码（原样）</h3>               ← 直接粘贴 v3 里的对应代码
  <h3>{n}.3 设计点拆解</h3>                     ← 3-5 个设计点
  <h3>{n}.4 原理</h3>                           ← 为什么这样设计
  <h3>{n}.5 反例</h3>                           ← 常见错误写法与失败输出
  <h3>{n}.6 分层提问（点开答案）</h3>           ← <details><summary> 折叠答案，用户先自答
  <h3>{n}.7 项目对手戏</h3>                    ← 假设面试官挑战"为什么不用 XXX"的对话
  <h3>{n}.8 面试真题三档答法</h3>               ← 烂 / 及格 / 优秀 三档模板
</section>

<footer>
  返回 Day{N}.md 链接 + 配套文档链接
</footer>
```

**禁止在深挖 HTML 里放动手脚手架**（`§7.1-7.5` 的内容不进 HTML）。深挖 HTML 只讲"为什么这么写"和"怎么在面试里讲"，不讲"怎么建目录"。

### 6.3 视觉与交互

- 单文件 HTML，内联 CSS，无外部依赖。
- 代码块内联语法高亮（`<span class="k">` 关键字、`<span class="s">` 字符串、`<span class="c">` 注释、`<span class="t">` 类型、`<span class="f">` 函数）。
- `<details>` 折叠答案，`<summary>` 是问题，用户先自答再展开。
- 顶部 TOC 用 `<ol>` 锚点跳转。
- 使用 `<div class="callout">`、`<div class="callout ok">`、`<div class="callout warn">` 三种提示块。

### 6.4 内容硬要求

- 每篇深挖必须锚定当天项目里的**一段真实代码**（v3 里的），不能凭空造例子。
- 分层提问至少 3 个层次：新手看不懂的、面试常问的、资深才会追问的。

### 6.5 选题依据

## 模型中转站的接入约定

- 后端连接模型使用三个环境变量：`LLM_BASE_URL`、`LLM_API_KEY`、`LLM_MODEL`。换中转站或默认模型只改 `.env`，不改代码。D57另支持可选非秘密 `LLM_MODEL_ROUTES`，只配置同一连接下的 `alias/model` 白名单，不含地址和凭据。embedding 模型同样用 `EMBEDDING_MODEL` 单独配置。
- 2026-11-18 用户选定本机开源中文 embedding。上述 EMBEDDING_MODEL 属于中转站方案。W11 的本机实现使用固定 Ollama 标签和 Qwen3-Embedding-0.6B Q8_0，按 1024 维建索引。安装与复现见 [D72](教程/D72-集合建模与向量索引.md)。
- `.env` 不提交到 Git，仓库里只放 `.env.example`。**密钥只写在本机 `.env` 里，不要贴进教程、代码或聊天记录。**
- 中转站常见的问题：偶发 429、5xx、524 超时，以及流式输出中途断开。W7 先处理流式中断，W9 的模型网关会专门处理超时、有限次重试和错误映射。这也是面试里“AI 接口不稳定怎么办”的实战素材。
- 中转站能看到你发出的全部内容。练习只用模拟数据，**不要把公司的真实工单、日志、客户信息发给模型**。
- W7 之前请准备好：中转站地址、密钥，以及它支持的聊天模型名和 embedding 模型名。embedding 在 W11 才用到，如果中转站不提供，W11 前再定替代方案。

## 贯穿项目：智能运维工单系统

运维公司向客户公司发放管理员账号。客户管理员审批本公司注册、查看本公司工单。获批的客户或第三方人员选问题分类，填写描述、附上日志并主动提单。数据库在同一事务保存工单、材料及初始事件。

Agent 根据意图、日志与 RAG 给出有出处的建议。证据不足时展示人工入口，由提单人点击。已经给出建议时，提单人点“未解决”也进入人工环节。系统按提交时的问题分类找到运维部门负责人，负责人指派本部门内部处理人。

处理人提交后状态为已处理，负责人复核后为已复核。提单人确认有效后为已完成，反馈未解决则回原处理人。系统把成功方案提取为候选，承办部门负责人整理、审核，通过后按批准版本发布到共享知识库。原单和日志继续按所属权限读取。[逐周业务对照](06-运维服务工单教程改版方案.md) · [逐日讲义入口](07-教程改版逐日执行计划.md)。

```text
ops-ticket/
├── apps/web/          Vue 3 工单工作台
├── apps/server/       NestJS 业务后端：报障、人工处理、用户与权限、AI 网关
├── python/bridge/        Python 阶段加入：embedding 与 Milvus 读写服务
├── packages/shared/   前后端共享的类型与校验 schema
└── infra/             docker-compose：PostgreSQL、Redis、Milvus
```

**数据职责**：PostgreSQL 是工单和知识文档的唯一权威来源。Milvus 只存向量和检索需要的字段，内容都可以从 PostgreSQL 重建。文档删除、权限变化时，两边怎样保持一致，是 W11 的重点。

**运行资源**：Milvus 单机版要同时起 Milvus、etcd、MinIO 三个容器，比 PostgreSQL 吃内存。W11 开始前先确认本机 Docker 的内存配额；不需要时可以只起 PostgreSQL 和 Redis。

## S1 全栈（W1-W6）

目标：从“会写接口、会增删改查”走到“能独立交付一个可靠的后端”。判断标准是你能看出 AI 生成的后端代码在事务、并发、权限上哪里有问题，而不只是能把接口写出来。每天的功能都要带测试，从 W1 起就用 Docker 里的真实 PostgreSQL 跑集成测试，不等到最后一周才补。

### W1 数据建模与查询（细到每天）

| 天 | 时长 | 知识点 | 当天做出 |
|---|---:|---|---|
| D1 周一 | 2h | 前 20 分钟按清单初始化项目：monorepo、Nest、Vue、全局校验管道、统一响应和异常格式（你已经会，只给需求和参考源码）。之后：工单领域建模，实体、关系、状态，以及哪些字段必须由数据库保证 | 项目能启动；一份工单系统的 ER 图和字段约束表 |
| D2 周二 | 2h | Docker 运行 PostgreSQL；Prisma schema、迁移的生成与回滚、种子数据；为什么迁移文件要提交、不能手改数据库 | 工单、设备、告警、处理记录、用户五张表落库，有可重复执行的种子数据 |

### W2-W6

|---|---|---|---|
| W2 | 事务与并发一致性 | 事务的 ACID；隔离级别与它能防住的异常（脏读、不可重复读、幻读）；工单状态机（待派单 → 人工处理中 → 已处理 → 已复核 → 已完成）的流转校验；状态变更和处理记录写在同一个事务里；乐观锁（版本号）防止两人同时接单；唯一约束实现幂等；死锁的成因与排查 | 两次并发派单只有一次成功，另一人收到 409；同一请求键重试只建一单；并发场景有测试 |

个人建议：每周日的复盘加一项“审 AI 代码”。拿一段 AI 生成的接口代码，找出事务、权限、幂等上的问题。你是 Codex 和 Claude Code 的重度用户，这是你最需要练的能力，也是 2026 年面试新出现的考点。

## 企业级的验收标准

“企业级”在这里指下面这些可以验证的要求，不是功能多。每周的周六集成都按对应条目验收，不满足就算没做完。

| 方面 | 必须满足 | 对标参考 |
|---|---|---|
| 工具调用 | 参数一律在服务端校验，不信任模型；写操作重复执行不会产生重复副作用；任何下游故障都不会让 Agent 卡死，只会以明确错误结束；每次调用都能在审计里查到谁、何时、什么参数、结果如何 | OWASP LLM Top 10 的“过度代理”（Excessive Agency）、“无界消耗”（Unbounded Consumption） |
| 权限管理 | 通过 Agent 能做的事，严格不多于这个用户直接调 API 能做的事；高危操作必须审批，审批内容和执行内容逐项一致；不可信内容里的指令触发不了任何工具 | OWASP LLM Top 10 的“提示词注入”“过度代理”；MCP 规范的授权部分 |
| 上下文管理 | 每一步发给模型的内容都能查到并回放；压缩后关键事实保留有测试证明；token 成本有记录、有预算上限 | 模型厂商的上下文与 Prompt 缓存文档 |
| Agent 评测 | 评测可复现（固定数据、录制工具结果）；有安全违规这类一票否决的指标；LLM 评审有人工校准；改动必须过 CI 门禁 | OpenTelemetry 生成式 AI 语义约定（用于 Trace） |

具体阈值（例如成功率要达到多少）要在 W16 测出基线后再定，现在不预设数字。各项对标资料到对应那一周会按当时的最新版本核对，因为这些规范更新很快。

题库情况：题库里 Agent 相关的题大多从前端角度出发。例如“如何处理 Context 窗口限制的 UI 提示”（2026 微信读书 Agent 方向 p8），“如何防御 Prompt Injection”（2026 腾讯音乐、2026 千问）。企业级的权限、评测深度题几乎没有，这几周的面试题以网上找的最新题为主，标明来源链接和日期。

## 一、题库原题

### 题 1：怎么让数据库查询更快？

来源：《滴滴前端面试真题》第 3 页。这是一份前端面经，面试官在问完 Node 之后追问了后端问题。

<details>
<summary>原文（第 3 页，候选人的回答）</summary>

> 怎么让数据库查询更快
>
> 1. 索引
> 2. 如果数据量太多了可以拆表，分多个数据库
>
> 数据库是用的什么？mysql

</details>

<details>
<summary>补充讲解：这个回答只够一面，换成你会怎么答</summary>

候选人的两点方向没错，但没有一个能经得起追问：“索引怎么建？”“建了为什么还慢？”“拆表之后跨表查询怎么办？”回答这类开放题，按“先定位、再优化、最后验证”的顺序讲，每一步都给出具体手段。

**1. 先定位慢在哪里，不要上来就加索引**

- 找出慢查询：PostgreSQL 用 `pg_stat_statements` 扩展统计每类 SQL 的调用次数和总耗时，或者设置 `log_min_duration_statement` 把超过阈值的 SQL 写进日志。应用层看链路追踪，一个请求下挂了几十条 SQL 就是 N+1。
- 看执行计划：`EXPLAIN ANALYZE`。关键信号是 `Seq Scan` 加上 `Rows Removed by Filter` 远大于需要的行数，或者有一步 `Sort` 处理了大量数据。

**2. 再对症优化，成本从低到高**

| 手段 | 适用 | 本项目的例子 |
|---|---|---|
| 消除 N+1 | 循环里逐条查询 | 实测 21 条 SQL 降到 2 条 |
| 只取需要的列 | `SELECT *` 或 ORM 的 include 取了大字段 | D3 的 select 白名单 |
| 建合适的索引 | 筛选和排序走了全表扫描 | 实测 `(status, created_at DESC)` 让 Q1 从 9.1 ms 降到 0.06 ms |
| 改写查询 | 对索引列做了函数运算、深分页 | D5 用游标分页替代 offset |
| 加缓存 | 读多写少、能接受短暂不一致 | W4 用 Redis |
| 读写分离 | 读远多于写，单机扛不住 | 要处理主从延迟，刚写的数据从从库读不到 |
| 分区、分库分表 | 单表数据量极大，前面都做了还不够 | 代价最大：跨库的查询、事务、唯一约束都会变难 |

**3. 最后验证**：优化前后各跑一次 `EXPLAIN ANALYZE`，并且在接近真实的数据量上测。讲义里只有 5 条种子数据时，有没有索引都是零点几毫秒，看不出区别，所以才要先灌 10 万张工单。

**关于“拆表、分多个数据库”**：这是最后的手段，不是第二个手段。面试官听到你把它排在第二位，会认为你没做过真正的优化。

</details>

## 二、网络最新题

### 题 2：什么是最左前缀原则、覆盖索引和回表？哪些写法会让索引失效？

来源：掘金《MySQL 索引面试全解：从 B+ 树到索引设计》，2026-07-03（https://juejin.cn/post/7658114338290237491）。原文以 MySQL InnoDB 为背景。

<details>
<summary>完整答案</summary>

**最左前缀**：复合索引按列的顺序排序，查询条件必须从第一列开始连续使用，才能用上它。实测 `(priority, status, created_at)` 这个索引，查询只带 `status` 时整个索引都用不上，退回顺序扫描（6.7 ms）；同时带 `priority` 和 `status` 时直接索引扫描（0.08 ms）。

原文还提到一个高频细节：在 MySQL 里，范围条件（`>`、`<`）之后的索引列无法再用于精确定位。原理是同一个范围内，后面那一列不再整体有序。

**回表**：MySQL 和 PostgreSQL 在这里差别很大，要分开讲。

- **MySQL InnoDB**：表数据就存在主键索引（聚簇索引）的叶子节点上；二级索引的叶子只存“索引列 + 主键”。用二级索引查到主键后，再到主键索引里取整行，这就是回表。
- **PostgreSQL**：表数据单独存在“堆”（heap）里，所有索引（包括主键）的叶子存的都是“索引列 + 这一行在堆里的位置”。所以 PostgreSQL 的每次索引扫描默认都要回到堆里取数据，查询计划里叫 `Index Scan`。

**覆盖索引**：查询需要的列全部在索引里，就不用回表。

- MySQL 的 `EXPLAIN` 在 Extra 列显示 `Using index`。
- PostgreSQL 显示为 `Index Only Scan`。实测：`SELECT status, created_at ... WHERE status = 'pending'` 两列都在 `(status, created_at)` 索引里，计划是 `Index Only Scan`，`Heap Fetches: 0`；多取一列 `ticket_no`，就变回普通的 `Index Scan`。
- PostgreSQL 的覆盖索引还有一个条件：它要通过“可见性映射”确认这些行对所有事务都可见，确认不了就还是要回堆检查，`Heap Fetches` 会大于 0。`VACUUM` 会更新可见性映射。所以频繁更新的表上，Index Only Scan 的效果会打折扣。
- PostgreSQL 11 起可以用 `INCLUDE` 把不参与排序的列附加在索引叶子上：`CREATE INDEX ... ON tickets (status, created_at DESC) INCLUDE (ticket_no)`，专门为了覆盖。

**索引失效的常见写法**（PostgreSQL 实测）：

| 写法 | 结果 |
|---|---|
| 不带复合索引的第一列 | 用不上，见上面的最左前缀 |
| 对索引列做函数运算：`WHERE lower(status) = 'pending'` | 顺序扫描。要么改写条件，要么建表达式索引 `ON tickets (lower(status))` |
| 前导通配符：`LIKE '%00500%'` | B-tree 无法定位，实测是把整个唯一索引从头扫到尾再过滤（扔掉 99894 行） |
| 前缀匹配：`LIKE 'B000500%'` | **PostgreSQL 特有的坑**：数据库的排序规则是 `en_US.utf8` 时，普通索引不能按前缀定位，实测同样是整个索引扫一遍。需要建 `varchar_pattern_ops` 的索引，实测后变成真正的范围查找 `Index Cond: (ticket_no ~>=~ 'B000500' AND ticket_no ~<~ 'B000501')` |
| 条件匹配的行太多 | 规划器认为顺序扫描更便宜，不用索引。例如查“已关闭”的工单（占 75%），走索引反而要多次随机读 |

最后一行是面试官爱问的“加了索引反而更慢 / 没用上”：索引适合筛选出少量行；条件命中表的大部分时，顺序扫描更快，规划器的选择是对的。

</details>

### 题 3：线上一条 SQL 很慢，你怎么排查和优化？

来源：掘金《如何医治一条慢 SQL？》，2025-05-13（https://juejin.cn/post/7503453467487748159）。原文以 MySQL 的订单列表为例。

<details>
<summary>完整答案</summary>

按“发现 → 定位 → 优化 → 验证 → 防复发”回答，每一步给出工具：

**1. 发现**

- 数据库侧：PostgreSQL 打开 `pg_stat_statements`，按总耗时排序，找出最耗资源的 SQL 模板；或者设置 `log_min_duration_statement = 200`，把超过 200 毫秒的 SQL 记进日志。
- 应用侧：接口的 P95、P99 延迟监控；链路追踪里看一个请求下面挂了哪些 SQL、各花多久。W6 会接入。

**2. 定位**：拿到具体的 SQL 和参数，执行 `EXPLAIN (ANALYZE, BUFFERS)`。重点看：

- 有没有大表的 `Seq Scan`，`Rows Removed by Filter` 是否远大于返回的行数；
- 有没有一步 `Sort` 或 `Hash` 处理了大量数据，或者用到了磁盘（`Sort Method: external merge`）；
- 估算行数（不加 `COSTS OFF` 时显示的 `rows=`）和实际行数差得很远，说明统计信息过时，先 `ANALYZE`；
- `Buffers` 的 `read` 很多，说明数据不在内存里，要从磁盘读。

注意 `EXPLAIN ANALYZE` 会真的执行语句，排查 `UPDATE`、`DELETE` 时要放进事务里执行完回滚。

**3. 优化**：对症下药，原文总结为“索引不是银弹，覆盖才是王道”。

- 缺索引：按等值条件在前、排序列在后的顺序建复合索引（讲义 1.3）。
- 索引失效：改掉对列做函数运算、前导通配符等写法（见题 2）。
- 取了多余的列：去掉不需要的列，必要时做成覆盖索引。
- 深分页：`OFFSET 100000` 要先扫过前 10 万行，改成游标分页（D5）。
- 应用层的 N+1：合并成批量查询（题 4）。

**4. 验证**：优化后在同样的数据量上再跑一次 `EXPLAIN ANALYZE`，对比执行方式和耗时；上线后看监控里的延迟是否下降。

**5. 防复发**：新索引通过迁移提交，而不是在生产库上手工执行（D2、讲义 3.2）；代码评审时检查查询是否带了筛选和 limit；慢查询日志设告警。

**一个容易被忽略的点**：生产环境大表上建索引，用 `CREATE INDEX CONCURRENTLY`，否则建索引期间会阻塞写入（见 D2 面试题 5）。

</details>

### 题 4：什么是 N+1 查询？怎么发现、怎么解决？

来源：掘金《数据库之必备经验视角：什么是 N+1 查询问题？》，2025-09-11（https://juejin.cn/post/7548714961372069914）。

<details>
<summary>完整答案</summary>

**是什么**：先用 1 条查询取出 N 条主记录，再对每一条各发 1 条查询取关联数据，一共 N+1 条。常见于 ORM 的懒加载，或者自己在循环里调用查询。

**为什么危害大**：每条查询都要经过一次网络往返和数据库解析，总耗时随 N 线性增长。实测在本机（数据库就在同一台电脑上，网络往返很短）：

```text
写法一 循环里逐个查询：21 条 SQL，30.4 ms
写法二 select 声明关联：2 条 SQL，8.9 ms
```

数据库在另一台机器上时，单次往返通常是零点几到几毫秒，差距会更明显；每页条数从 20 变成 100，写法一就是 101 条 SQL。

**怎么发现**：

1. 开发时打开 ORM 的查询日志，看一个接口发了多少条 SQL。Prisma 7 用 `log: [{ emit: 'event', level: 'query' }]` 加 `$on('query')`。
2. 线上看链路追踪：一个请求下面重复出现几十个结构相同、只是参数不同的数据库调用。
3. 写测试时断言查询次数，防止以后被人改回去。

**怎么解决**：

1. **用 ORM 的关联查询**：Prisma 在 select 或 include 里声明关联。实测 Prisma 7 的做法是 2 条 SQL：先查工单，再用 `WHERE id IN (...)` 把所有处理人一次取回，在内存里拼接。
2. **用 JOIN**：一条 SQL 连表取回。按关联字段筛选时，Prisma 生成的就是 JOIN（讲义推导题 1.4 实测过）。
3. **批量加载**：GraphQL 里用 DataLoader，把同一轮里的多个单条查询合并成一次 `IN` 查询。
4. **只要数量时用聚合**：Prisma 的 `_count`，而不是逐条 `count()`（D3）。

**追问：IN 查询和 JOIN 哪个好？** 各有适用场景。JOIN 一次往返，但一对多时主表的数据会随着子表行数重复，传输量变大；IN 查询两次往返，每张表的数据只传一次。关联的行数少、主表行很宽时，IN 更好；需要按关联表的字段筛选或排序时，必须 JOIN。

</details>

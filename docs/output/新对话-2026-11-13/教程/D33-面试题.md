## 一、题库原题

### 题 1：SSE 和 WebSocket 有什么区别？如何选择？

来源：题库文件 `2026京东前端面试-AI Coding方向.pdf`，题目第 1 页，原文答案第 2 页。题库文件名不代表企业官方发布。检索使用本地 58 份题库缓存及 show_answer.py，保留原题和答案，只调整换行与列表符号。

**原题原文**：SSE 和 WebSocket 有什么区别？如何选择？

<details>
<summary>原文答案</summary>

- SSE (Server-Sent Events)：基于 HTTP，单向通信（服务端 -> 客户端）。天然支持断线重连，协议轻量，由于是文本协议，更适合处理 AI 的流式文本输出。
- WebSocket：全双工通信（双向）。协议相对复杂，适用于需要高频双向交互（如实时协作、语音通话）的场景。
- 选择依据：若只需展示 AI 生成过程，SSE 是首选（兼容性好、开发成本低）；若涉及实时双向对弈、复杂的游戏化交互，选 WebSocket。

</details>

<details>
<summary>补充讲解与项目答案</summary>

工单的派单、接单和评论已有普通 HTTP 接口，通知链路只需要服务器向页面发送新通知，因此选 SSE。将来增加高频双向协作，可以重新评估 WebSocket；协议名称不能替代场景与运维成本分析。

SSE 响应 Content-Type 是 text/event-stream，以 UTF-8 文本行组成事件、空行结束事件。JSON 只是 data 的内容；多行 data 按规则拼接。带 event 的消息要监听相应事件名，缺省才触发 message。浏览器的原生解析和重连规则见 [WHATWG SSE 规范](https://html.spec.whatwg.org/multipage/server-sent-events.html)。

**原文要补上的边界**：原生 EventSource 可以重连，但服务端如果没有历史和游标查询，丢失内容不会自动回来。本项目一次性票据在首个连接已消费，原 URL 自动重试会失败，因此 D34 要关闭旧连接、重新签票。消息持久化、补发和客户端去重仍由应用实现。SSE 文本可以携带编码后的二进制，编码增加体积，不应说它可以原样发送任意二进制。

本轮没有做 SSE/WebSocket/轮询性能对比，也没有实际安装 WebSocket 服务。本项目实测 SSE 和普通 API 出口，原样输出：

```json
{"case":"sse-protocol","status":200,"contentType":"text/event-stream","buffering":"no","rawFrame":"event: ready\nid: n-2\nretry: 1500\ndata: {\"cursor\":\"n-2\"}","heartbeatPreservedCursor":true,"ordinaryResponseWrapped":true}
```

ready 中的游标由当前通知位置产生，不是固定值。心跳显式沿用这个位置，因为 [Nest SSE 文档](https://docs.nestjs.com/http/server-sent-events) 与安装源码都说明：事件未提供 id 时 Nest 会自动编号。

</details>

## 二、网络最新题

### 题 2：EventSource 不能传 Authorization，换成 Fetch 读取 SSE 是否就能自动拥有补发与重连？

来源：[掘金《fetch-event-source源码解读》](https://juejin.cn/post/7604039449468665906)，2026-02-09。已获取并阅读正文；题目从自定义请求头、读取流和重试代码提炼。以下答案按标准和本项目补充，不把原文示例作为本项目已安装的库。

<details>
<summary>完整答案</summary>

Fetch 可以设置请求方法和 Authorization 头，也能读取 response.body，但裸 Fetch 不会替应用实现 SSE 解析、游标保存、重试和 UI 清理。需要逐块解码、按完整事件组帧、处理多行 data，管理 AbortController 和重试定时器，并在重连时带上已成功处理的位置。

原生 EventSource 没有自定义 Authorization 参数，但内置事件解析与重连。D33 为沿用它而增加短期票据：JWT POST 签票，再 GET 建流；GETDEL 保证一次兑换。D34 将新连接的 lastEventId 放进签票 body，因为新建的 EventSource 无法任意设置 Last-Event-ID 头。

**原文需要纠正的地方**：文中把 Content-Type: text/event-stream 写成固定请求头要求。它是 SSE **响应媒体类型**；请求 Accept: text/event-stream 表达希望接收什么，Authorization 表达身份。还不能用 parseInt 能得到整数就认定 retry 合法，规范要求该字段全部是 ASCII 数字。协议依据是 [WHATWG 的解释规则](https://html.spec.whatwg.org/multipage/server-sent-events.html#interpretation)，本轮未运行 fetch-event-source 库或自制完整协议解析器。

本项目并发票据的实际输出：

```json
{"case":"ticket-race","instances":2,"succeeded":1,"rejected":1}
```

只把 GETDEL 改为 GET 的反证实际失败：

```text
 FAIL  test/notification-stream.e2e-spec.ts > SSE 实时通知（D33 e2e） > 同一票据并发兑换：只能成功一次
AssertionError: expected 2 to be 1 // Object.is equality

- Expected
+ Received

- 1
+ 2
```

文件按原始字节恢复，SHA-256 一致，复测通过：

```text
 Test Files  1 passed (1)
      Tests  1 passed | 14 skipped (15)
```

票据只用于建立连接，不代替 JWT，不存浏览器持久存储。URL 中的票据仍应避免进入访问日志；本机没有配置生产代理日志脱敏。现有流到期前也不会自动重新校验 JWT，租约负责限制这段时间。

</details>

### 题 3：服务端一行行发数据，客户端能把每次网络 chunk 当作完整通知吗？

来源：[掘金《SSE》](https://juejin.cn/post/7642528539570372662)，2026-05-23。已阅读正文，文章用 Swift 增量读取场景说明流式体验。这里转换为本项目的通知事件组装题，未运行 Swift 或模型接口。

<details>
<summary>完整答案</summary>

不能。一次网络读取可能只有半个字段，也可能包含多条事件；文本字符也可能在字节边界拆开。完整 SSE 事件按文本行和空行边界解析，data 可以有多行。原生 EventSource 会处理这些协议细节；本项目的 Node HTTP 测试辅助积累完整空行块后再断言，不能把它当作覆盖所有换行形式的通用解析器。

**原文需要补充的地方**：按单行 data 读取是它展示的特定输出格式，不是完整 SSE 协议。增量读取也不等于可靠送达；前端在成功处理事件后保存游标，后端必须查询持久历史，才能补回断线期间的通知。协议规则见 [WHATWG SSE](https://html.spec.whatwg.org/multipage/server-sent-events.html#parsing-an-event-stream)。

D33 首次只取最近 50 条，携带游标后每批 100 条升序补发；实测在锚点后新增 105 条，原样输出：

```json
{"case":"sse-batches","storedAfterCursor":105,"initialRecent":50,"resumed":105}
```

请求头 Last-Event-ID 可以覆盖票据中的旧位置，之后只补发更大的序号。本项目在服务端支持标准头，但浏览器新建连接使用签票 body。首连最近 50 条不是全部历史，收到的条数也不是未读总数。

</details>

## 三、本项目追问

### 题 4：为什么 Pub/Sub 只传用户 ID？序列递增为什么还要用户锁？

来源：D33 通知 Worker、补读测试与独立进程验证。

<details>
<summary>完整答案</summary>

Pub/Sub 是即时信号，订阅者离线期间不保存历史；[Redis 官方文档](https://redis.io/docs/latest/develop/pubsub/) 将其投递语义定义为至多一次。本项目的事实是 PostgreSQL 通知行，Pub/Sub 只告诉连接“这个用户可能有新行”，各实例再按 userId 和游标查询。

通知 Worker 事务内写入，提交后才发布。发布失败不把已提交通知改成失败，连接每 5 秒补读。本轮用模拟 publish 拒绝和真实查询验证恢复：

```json
{"case":"sse-publish-fallback","publishRejected":true,"databaseRows":1,"pollMs":100,"received":1}
```

Redis Pub/Sub 不按数据库号隔离，所以频道主动包含库号。连接要先订阅再读取，读取期间的唤醒通过 dirty 标记保留；不能只订阅一次等待信号，也不能丢掉用户查询条件。

**序列不等于提交顺序**：A 分到 10 未提交，B 分到 11 先提交，客户端推进到 11 后可能永久跳过 10。生产写入入口先锁用户行，再分配序号并提交；多个用户按固定 ID 顺序取锁，减少死锁。不同用户的序号可以交错，只要每个用户自己的提交顺序受保护。序列空洞仍然允许。

```json
{"case":"sse-commit-order","laterBlockedByUserLock":true,"sequenceFollowsCommit":true}
```

同进程两个应用与独立 Node 子进程都用真实 Redis 唤醒。本页明确区分独立进程验证，原样结果：

```json
{"case":"sse-two-processes","applicationProcesses":2,"receivedWithinMs":30,"subscriberPollMs":5000,"received":1}
```

本轮没有验证主从切换、进程强杀或长期积压，有限延迟样本不能当作实时送达 SLA。

</details>

### 题 5：票据和游标都属于本人，为什么补发查询仍要 userId？断连后释放了什么？

来源：D33 行范围反证与连接生命周期测试。

<details>
<summary>完整答案</summary>

票据证明连接者身份，游标证明某个起点有效；它们都不能限制后续查询的结果。查询只写 streamSeq > after 会混入全局序列中其他用户的行。每一批都必须带 userId。

只删补发查询 userId 的反证实际泄漏另一人的通知并失败：

```text
 FAIL  test/notification-stream.e2e-spec.ts > SSE 实时通知（D33 e2e） > 游标补发只查询当前用户，不能混入其他人的通知
AssertionError: expected [ …(2) ] to deeply equal [ Array(1) ]

- Expected
+ Received

  [
+   "01a1e48b-b9b9-76be-a34d-880076b4532f",
    "01a1e48b-b9bc-742b-8713-55cf3d739aee",
  ]
```

恢复后的同一测试通过：

```text
 Test Files  1 passed (1)
      Tests  1 passed | 14 skipped (15)
```

断连、完成或错误会让 Nest 退订 Observable；返回的清理函数释放本连接的 Pub/Sub 订阅、心跳、轮询和租约定时器。它不会取消已经发出的 Prisma 查询，所以查询返回后还要检查 disposed，不再继续发送。

ready、heartbeat、reauth 保留当前通知 ID，不能靠 Nest 自动编号，否则心跳会把 Last-Event-ID 变成无效通知游标。到期发 reauth 后关闭，前端需要新票据；查询失败发通用错误，不把内部 SQL 细节送到浏览器。原样生命周期输出：

```json
{"case":"sse-cleanup","shortenedLeaseMs":1800,"reauthReceived":true,"activeAfterClose":0,"queriesAfterDisconnect":0}
```

租约用例缩短为 1800ms；生产默认为 120 秒。慢客户端的待发上限设置为 64K 字符，不是总内存限制；真实背压压测留到 W6。

</details>

## 一、网络最新题

### 题 1：用户的 Token 应该存在 localStorage 还是 HttpOnly Cookie？

来源：掘金《高频面试题：Token 存 localStorage 还是 HttpOnly Cookie？》，2026-01-04（https://juejin.cn/post/7590735421262233641）。原文对比了 localStorage、普通 Cookie、HttpOnly Cookie 三种方式，推荐生产环境用 HttpOnly Cookie，并给了 `SameSite` 和 CSRF 令牌的防御方案。

<details>
<summary>完整答案</summary>

**从两种攻击来比较**（原文的核心框架）：

| 存法 | XSS 能读到吗 | CSRF 会自动带上吗 |
|---|---|---|
| localStorage / sessionStorage | 能 | 不会，要手动放进 `Authorization` |
| 普通 Cookie | 能 | 会，两头的风险都有，不推荐 |
| HttpOnly Cookie | 不能 | 会，要单独防 CSRF |

**原文推荐 HttpOnly Cookie 的理由**：XSS 的入口很多（未转义的输入、被污染的第三方脚本、富文本渲染），很难保证一个都没有；CSRF 的防御手段成熟、成本低：

- `SameSite=Lax`：跨站发起的 POST、PUT、DELETE 不带 Cookie，一行配置挡住大部分 CSRF。
- CSRF 令牌：服务端发一个随机值放在普通 Cookie 里，前端读出来放进请求头，服务端比较两者。攻击者的页面能让浏览器自动带上 Cookie，但读不到 Cookie 里的值，构造不出请求头。

**要补充的两点**：

1. **HttpOnly 只是让令牌偷不走，XSS 仍然能用它**。注入的脚本可以直接在你的页面里发请求，浏览器照样带上 Cookie。所以 HttpOnly 把“攻击者拿走令牌、在任何地方任意使用”降级成“只能在用户打开页面的这段时间里冒充他”，并没有消除 XSS 的危害。防 XSS 本身（转义、CSP、不用 `v-html` 渲染用户输入）始终是第一位的。
2. **`SameSite=Lax` 防的是跨“站”，不是跨“源”**。`a.example.com` 和 `b.example.com` 是同一个站，如果某个子域名被攻破，`SameSite` 挡不住它发出的请求，这时候 CSRF 令牌才是真正的防线。

**本项目的选择**：sessionStorage 加 `Authorization: Bearer`。理由是接口测试、以后的 Agent 和 MCP 客户端都用同样的方式调用，不用处理 CSRF；代价是 XSS 能读到令牌。配套的措施是令牌 2 小时过期、令牌里只放用户 id 和用户名、前端不用 `v-html` 渲染用户内容。面试时这样回答：先讲两种攻击的对比，再讲你在什么场景下选了什么、接受了什么代价、用什么措施兜底，最后说明如果是面向公众的系统，你会怎样迁移到 HttpOnly Cookie。

</details>

## 二、题库原题

### 题 2：谈谈前端安全，如何防范 XSS 和 CSRF？

出处：《2026美团前端全栈开发》第 8-9 页（二面第 5 题）。

**原题**：5. 谈谈前端安全，如何防范 XSS 和 CSRF？（难度：★★，考点：Web 安全）

<details>
<summary>原文答案</summary>

> 答案要点：
> XSS 是脚本注入，CSRF 是跨站请求伪造，两者攻击维度不同。
>
> - XSS 防范：对用户输入进行转义（如 < 转为 <）、使用 CSP 安全策略、对 Cookie 设置 HttpOnly。
> - CSRF 防范：使用 SameSite Cookie 属性、请求头增加自定义 Token 校验、验证 Referer/Origin。
>
> 常见坑：
>
> - 认为只要用了框架（如 React）就绝对不会有 XSS，忽略了 dangerouslySetInnerHTML。
>
> 追问：
>
> - 如果 Token 存储在 LocalStorage 中，能防范 CSRF 吗？

（原文“< 转为 <”应为把 `<` 转成 `&lt;`，PDF 抽取时实体被还原了。）

</details>

<details>
<summary>本教程补充：讲清两者的区别，回答追问</summary>

**一句话区分**：XSS 是攻击者的脚本跑在了**你的页面里**；CSRF 是攻击者的页面借用了**你的登录状态**向你的网站发请求，它自己看不到响应。

**Vue 里的 XSS**：模板里的 `{{ }}` 默认转义，对应原文“常见坑”里 React 的 `dangerouslySetInnerHTML`，Vue 的风险点是 `v-html`。本项目的工单标题、处理说明都是用户输入，一律用 `{{ }}` 渲染。W8 渲染 AI 回复的 Markdown 时会遇到真正的挑战：Markdown 转出的 HTML 要经过白名单过滤才能用 `v-html`。

**追问：Token 存在 LocalStorage 里，能防 CSRF 吗？** 能。CSRF 依赖浏览器**自动**带上凭证，而 `Authorization` 请求头只能由页面上的脚本手动加，攻击者的页面在另一个源上，读不到你的 localStorage，也就构造不出这个请求头。本项目就是这样：没有 Cookie，CSRF 无从下手。代价是 XSS 能直接读走令牌（题 1）。所以“存在哪”本质上是在 XSS 和 CSRF 之间选择你更有把握防住哪一个。

**验证 Referer/Origin**：服务端检查请求的 `Origin` 头是不是自己的域名，是一种简单的补充手段；但有些情况下浏览器不发这个头，不能作为唯一的防线。

</details>

### 题 3：JWT 有哪些信息？JWT 的加密泄露了怎么办？

出处：《360前端面试》第 2-3 页（第 4、5 题）。

**原题**：4. JWT的加密泄露怎么办？ 5. JWT有哪些信息

<details>
<summary>原文答案</summary>

> 4. JWT的加密泄露怎么办？
> 如果出现加密泄露的话基本上已经是很严重的问题了，因为我项目有说到jwt进行加密，因此问到了这个问题。
>
> 1. 重新生成密钥：立即生成一个新的加密密钥，并将其用于签署新的JWT。这将使以前的JWT失效，并防止攻击者使用已泄露的密钥生成有效的JWT。
> 2. 吊销已发出的JWT：如果可能的话，您可能需要在服务器端实施一种机制，使得已经发出的JWT失效。这可以通过在JWT中添加一个唯一的标识符（例如，UUID），并在服务器端跟踪这些标识符的列表来实现。
> 3. 增加监控和审计：加强对JWT的监控和审计，以便及时发现任何异常活动。
>
> 5. JWT有哪些信息
> ……JWT（JSON Web Token）由三部分组成，它们用点号（.）分隔开来。这三部分分别是：
>
> 1. Header（头部）：包含了JWT的元数据信息，例如类型（typ）和所使用的算法（alg）。通常是一个JSON对象。
> 2. Payload（载荷）：包含了JWT的主要内容，例如用户的身份信息或其他数据。通常也是一个JSON对象。
> 3. Signature（签名）：由前两部分使用指定的算法进行签名生成的，用来验证JWT的真实性和完整性。签名是Base64编码后的字符串。

（原文第 5 题前面还有一段关于“为什么需要 JWT”的介绍，这里省略。）

</details>

<details>
<summary>本教程补充：纠正“加密”这个说法，讲清楚三种泄露</summary>

**最重要的纠正：常见的 JWT 是签名，不是加密**。原文多处说“对用户信息进行加密”，这是面试中很常见的误解，面试官很可能就是冲着这一点追问的。HS256 这类 JWT 的头部和载荷只是 base64url 编码，任何人拿到令牌都能解出来看；签名保证的是**没被改过**，不是**看不到**。所以载荷里绝不能放密码、手机号这类敏感信息。本项目的载荷只有 `sub`（用户 id）和 `username`。真正加密的令牌叫 JWE，很少用。

**“泄露”要分三种情况**：

| 泄露了什么 | 后果 | 怎么办 |
|---|---|---|
| 某个用户的令牌 | 攻击者在过期前可以冒充这个用户 | 等它过期；要立即失效就得在服务端记录状态（黑名单、令牌版本号，见讲义推导题 1.3） |
| 签名密钥 | 攻击者可以给**任何用户**签发令牌，最严重 | 立即换密钥（所有已发出的令牌全部失效，所有人重新登录）；排查泄露途径；查审计日志里这段时间的异常操作（D18） |
| 载荷里的信息 | 如果放了敏感信息就泄露了 | 从一开始就不放 |

原文第 1 条“重新生成密钥使以前的 JWT 失效”是对的，这正是密钥泄露时的标准处理。补充一点：为了平滑地轮换密钥，可以在头部带一个 `kid`（密钥编号），服务端同时认新旧两把密钥一段时间，等旧令牌都过期再下线旧密钥。但如果是因为泄露而轮换，旧密钥要立刻作废，不能有过渡期。

**本项目的密钥管理**：`JWT_SECRET` 只在 `.env`，启动时检查长度不少于 32 个字符，缺失就拒绝启动，代码里不写默认值。

**追问“签名算法”**（原题第 6 题）：HS256 是对称的，签发和校验用同一把密钥，适合只有一个服务签发和校验的场景（本项目）；RS256、ES256 是非对称的，私钥签发、公钥校验，适合多个服务要校验令牌、但只有认证服务能签发的场景。校验时要固定算法，否则可能遇到“`alg: none`”或者把公钥当成 HS256 密钥的攻击。`@nestjs/jwt` 默认用 HS256。

</details>

## 三、补充题

### 题 4：（补充题）用户密码怎么存？为什么不用 MD5 或 SHA-256？

本题没有对应的网络原文，来自讲义 1.1 的实测。

<details>
<summary>完整答案</summary>

**要防的情况**：数据库泄露后，攻击者拿着哈希去还原密码。

**MD5、SHA-256 不行**：它们被设计得很快，显卡每秒能算几十亿次，常见密码很快就被试出来；不加盐的话，同样的密码哈希相同，还能直接查预先算好的表。

**正确的做法**：

1. **用专门的慢哈希**：Argon2id（首选）、scrypt、bcrypt。它们故意很慢、占内存，暴力破解的成本高几个数量级。本项目用 Node 自带的 scrypt（N=2^15、r=8、p=1），实测哈希一次 62-79ms。
2. **每个密码一个随机盐**，和哈希存在一起。本项目实测同一个密码两次哈希结果不同。
3. **参数和算法一起存**，例如 `scrypt$32768$8$1$盐$哈希`，以后能升级强度。
4. **校验用恒定时间比较**（`timingSafeEqual`）。
5. **限制密码长度上限**，防止超长输入拖慢服务器。

**容易被追问的**：

- “前端先 MD5 一下再传，是不是更安全？”不是。前端哈希后的值就成了真正的密码，截获它一样能登录。传输安全靠 HTTPS，存储安全靠服务端的慢哈希。
- “用户忘记密码怎么办？”只能重置，不能找回。能把原密码发给用户的系统，说明它存的是明文或者可逆加密。

</details>

### 题 5：（补充题）登录时“用户不存在”和“密码错误”为什么要返回一样的结果？

本题没有对应的网络原文，来自讲义 1.2 和反证实验 A 的实测。

<details>
<summary>完整答案</summary>

**防止用户名枚举**。两种情况提示不同，攻击者就能先试出哪些用户名存在，再集中破解；在一些场景里，“某人在这个系统里有账号”本身就是敏感信息。

**光是错误信息一样还不够，响应时间也要一样**。用户不存在时，代码自然会跳过耗时的密码校验。本项目实测（各 10 次取中位数）：

| 写法 | 用户不存在 | 密码错误 |
|---|---:|---:|
| 用户不存在时也用一个假哈希校验一次 | 94ms | 93ms |
| 用户不存在时直接返回 | 7ms | 106ms |

后一种写法错误信息完全相同，接口测试全部通过，但时间差一目了然。

**同样的思路用在别的地方**：

- “忘记密码”接口：不管邮箱存不存在，都提示“如果该邮箱已注册，你会收到邮件”。
- 注册接口没法完全避免（总要告诉用户“用户名已被占用”），所以要配合限流（W4）。

**这类问题为什么测试发现不了**：普通的接口测试只比较响应体。时间侧信道要专门测，而且计时测试受机器负载影响，一般放在安全检查里，不放在每次都跑的测试里。

</details>

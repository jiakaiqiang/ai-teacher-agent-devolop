### 第 1 题：Node.js 已经异步，为什么还要把告警交给队列？

答案来源：[D29 面试题](D29-面试题.md) 题 2、3。场景文章为[《Node.js 天生就是异步的，为什么还要消息队列？》](https://juejin.cn/post/7685816258889547814)，2026-09-16；本周复用 D29 已核对题目。

追问：

1. 返回 202、Worker completed、通知出现分别能说明什么？
2. 为什么队列 Redis 不能直接复用 allkeys-lru 的缓存 Redis？
3. 503 后客户端重试，怎样判断或限制重复？

<details>
<summary>完整参考答案与追问</summary>

async/await 解决当前进程的异步等待，不提供持久的待处理任务、重试、消费并发和失败查看。进程退出以后，普通后台 Promise 没有可靠的恢复入口。告警接口把工作交给 BullMQ，Worker 复用业务事务建单，接口返回 jobId，客户端再查处理结果。

202 表示受理；Worker completed 且返回有效结果表示这次业务处理成功；通知行、SSE 到达和已读又是后面的事实。D34 的浏览器链路记录可以用来解释这些节点，原样阶段证据：

```json
{"case":"browser-w5-chain","accepted":202,"jobState":"completed","ticketNo":"T20261116-0002","assignStatus":200,"recipient":"bob","notifications":1,"unread":1,"onlyTicketUrls":true}
```

这是 2026-11-16 的 D34 浏览器阶段：监控上报与 carol 派单使用真实 HTTP，bob 在浏览器接原生 EventSource，Outbox 手动投递；不能说成“carol 页面操作”或“本次浏览器演示证明自动调度”。

队列 Redis 使用 noeviction 与 AOF，缓存 Redis 使用 allkeys-lru；淘汰任务键会破坏队列状态，所以分开。AOF everysec 不承诺故障时绝无丢失，也不消除重复消费。本机重启演示不能推出主从切换或掉电保证。

本项目入队最多等 2 秒。请求返回 503 时，Redis 命令可能只是还未完成，不能认为它已撤销。用稳定业务键计算 jobId，并由数据库 `(source, dedup_key)` 唯一约束兜底；请求重试也不能随便换去重键。缓存查询可降级查库，告警队列受理失败可返回 503，已持久通知的唤醒失败则保留数据库事实并轮询补读，各阶段按自己的事实选择策略。

</details>

### 第 2 题：消息为什么会重复？jobId 去重与业务幂等有什么区别？

答案来源：[D30 面试题](D30-面试题.md) 题 1、2、3。场景文章为[《加了幂等表，为什么消息重试反而不执行了？聊聊 MQ 消费幂等的边界》](https://juejin.cn/post/7650369633807990826)，2026-06-12；此处按 D30 与当前项目整理。

追问：

1. 业务已提交，但 Worker 未完成任务确认就停止了，会怎样？
2. 先写“消费成功”标记，再执行事务，失败重试有什么问题？
3. 为什么去掉数据库幂等以后，走队列的测试仍可能全绿？

<details>
<summary>完整参考答案与追问</summary>

生产者超时重发、Worker 在副作用与任务确认之间停止、锁续期失败导致停滞恢复，都可能让同一个业务动作重做。至少一次处理需要应用的幂等结果；它还受持久化、重试上限和失败处理边界影响，不能概括成所有故障下“不会丢”。

jobId 去重减少同一队列里已有任务的重复入队，依赖该任务还保留在队列中。任务移除、重放或直接业务调用都要看数据库结果。本项目告警唯一键是 `(source, dedup_key)`，通知唯一键是 `(event_id, user_id)`；每个业务动作都有自己的键。

幂等标记若在业务之前独立提交，业务失败后重试会被“已经成功”的标记挡住。数据库标记与业务同事务提交/回滚，或让唯一业务行本身成为完成事实；外部短信等副作用要单独设计幂等和重试，不能塞进本地数据库事务的保证里。

测试也要分层：队列去重可能先挡掉所有重复请求，使数据库约束的缺失没暴露。D30 曾绕过队列直接并发调用业务入口检查最终行数；今天的范围与分页反证同样先让目标测试基线通过再改坏，避免其他故障掩盖目标。D30 停滞演示用强制关闭和缩短锁时间模拟，不是本轮生产进程强杀或主从故障。

</details>

### 第 3 题：Outbox 修复了哪些窗口？为什么投递器仍需要锁和消费幂等？

答案来源：[D31 面试题](D31-面试题.md) 题 1、2。场景文章为[《数据库写成功，MQ 消息却丢了？4 个故障窗口拆透 Transactional Outbox》](https://juejin.cn/post/7694664695189798947)，2026-10-10；原文纠正与项目取舍见 D31。

追问：

1. 把 Outbox 放另一个数据库能不能仍叫同一本地事务？
2. Redis 入队成功，publishedAt 更新的事务却回滚，会怎样？
3. 为什么持行锁调用 Redis 是当前仍保留的风险？

<details>
<summary>完整参考答案与追问</summary>

业务与“要通知的事件”使用同一个 tx，提交时一起保留，回滚时一起撤销。修复的是业务提交却没有事件、事件先被消费但业务回滚的双写窗口。把 Outbox 搬到另一数据库，普通本地事务不能一起提交；隔离连接池可以讨论，表不能为了隔离压力而分出事务边界。

投递器在事务中用 FOR UPDATE SKIP LOCKED 领取未投递行，入队成功后标 publishedAt。D31 的多个投递器实验与锁反证见原讲义；当前也有维护队列全局并发限制，但手动入口、重试和故障窗口仍要求数据库与业务层防线。

Redis 与 PostgreSQL 没有共同的本地提交：入队成功而投递事务回滚，下轮会重投。固定 outbox-事件ID 任务键减少重复，通知唯一键最终防新增重复行。任务 completed 也不代表用户阅读；已读必须另外保存。

当前投递器持 Outbox 行锁调用 Redis，网络慢时会拖长事务、占连接并延迟其他维护工作。限制批量和等待时间只是当前取舍；规模增大可以研究短事务租约、失效接管和重试告警，但本周没有实现。Outbox 清理、失败告警和保留期也仍未完成，不在复盘口述中说成已经落地。

</details>

### 第 4 题：共享定时任务怎样避免每个实例各注册一份？SLA 升级怎样防竞态？

答案来源：[D32 面试题](D32-面试题.md) 题 1-5。场景文章为[《第十四课：异步处理 — 缓存、队列与定时任务》](https://juejin.cn/post/7637803221285699594)，2026-05-09。waitForCompletion 与旧 repeat 示例的纠正沿用 D32 已读官方文档、安装类型与实测。

追问：

1. Worker concurrency:1、全局并发 1 与 upsert ID 分别限制谁？
2. 超时 31 分钟才恢复扫描，首次标记与升级怎么办？
3. 已指派未接单、本组无人有 ticket:assign、重开以后标记如何处理？

<details>
<summary>完整参考答案与追问</summary>

相同 Redis、prefix、队列内，各实例用固定 sla-scan-v1、outbox-relay-v1 调用 upsertJobScheduler；同 ID 更新配置，不能每次随机生成新 ID。调度 ID 与某次任务 ID 是不同对象；周期任务仍可能重试，upsert 不提供业务一次且仅一次。

本地 concurrency:1 限制一个 Worker；setGlobalConcurrency(1) 限制整个 maintenance 队列的 Worker；两类任务共用这个名额。D32 独立进程演示验证重复注册与关闭连接后重建 Worker，无需重新 upsert 仍继续处理。配置 0 只跳过注册，不删除已经存在的共享调度。

升级从 slaDueAt 起算，超时满 30 分钟、已首次超时、仍 pending、slaEscalatedAt 为空。维护同轮先首次扫描再升级，所以恢复时可以立即进入已满足条件的升级；UPDATE 要重新检查状态、到期和标记条件，标记与 Outbox 同事务。接单交错时，只先 SELECT 不够；UPDATE 判断时状态已变成 processing 就不升级。

已指派但未接单仍是 pending，升级收件人是消费时同班组有 ticket:assign 权限的人，不是再通知处理人或跨组兜底。无人符合时记录事件而返回 notified:0，当前没有补投告警。标记按这张工单只写一次，目前重开不自动清零；若要“每次重开重新计时”，要先改业务约定。

旧 queue.add repeat 示例不能直接套到安装的 BullMQ 6.7.6；D32 使用 upsertJobScheduler。Cron 的 waitForCompletion 在运行中跳过触发，不是把每次触发排队补跑。maintenance 的全局并发也会带来慢 SLA 扫描延迟 Outbox 的代价，长期积压仍未验证。

</details>

### 第 5 题：为什么通知选 SSE？不能带 Authorization 时如何建流和重连？

答案来源：[D33 面试题](D33-面试题.md) 题 1、2。题库关联为《2026京东前端面试-AI Coding方向.pdf》，题目第 1 页、原文答案第 2 页；以下是本项目的复盘答案。网络场景为[《fetch-event-source源码解读》](https://juejin.cn/post/7604039449468665906)，2026-02-09，原文补充见 D33。

追问：

1. SSE 的 data 是否等于网络 chunk？命名事件与心跳 ID 怎么处理？
2. 为什么票据使用 GETDEL，GET 的反证出现什么结果？
3. 浏览器新建 EventSource 怎么带回游标？

<details>
<summary>完整参考答案与追问</summary>

业务操作已有普通 HTTP，通知是服务端向页面的单向增量，因此用 SSE。WebSocket 更适合需要频繁双向通信的情形，但本周没有性能比较。SSE 响应为 text/event-stream，UTF-8 文本行、空行结束事件；网络 chunk 可以拆开字符和事件，不能直接把每块 JSON.parse 成通知。原生 EventSource 负责协议组帧，本项目命名 notification/ready 等事件分别监听。

原生 EventSource 无法设置任意 Authorization 头。JWT POST 换 30 秒一次性票据，专门守卫在 SSE 响应头写出之前兑换；Public 只跳过普通 JWT 守卫。GETDEL 原子取出消费，防一张票据同时建两条流。D33 原样记录：

```json
{"case":"ticket-race","instances":2,"succeeded":1,"rejected":1}
```

把 GETDEL 改 GET 的反证使两次兑换都成功，见 D33 的原样失败与恢复记录。一次性票据仍可能进访问日志，生产代理脱敏没有在本轮配置；不把长期 JWT 放 URL。

首连票据已消费，原生自动重试旧 URL 会失败。D34 error 先 close，取消旧签票，退避重新签票；reauth 立即再签。新 EventSource 不能自由设置 Last-Event-ID 头，因此把已成功处理的 n- 游标放进签票 body。后端支持标准头优先的客户端，但本浏览器实现用 body。

所有控制事件保留当前通知位置，不另外造业务 ID；heartbeat 不代表又处理了一条通知。notification 契约与事件游标一致且回调成功以后才推进位置。D34 模拟 EventSource 与假时钟记录：

```json
{"case":"frontend-renewal","sourcesCreated":3,"oldSourceClosed":true,"cursorPreserved":"n-9"}
```

真实浏览器另验证过 3500ms 缩短租约的续签，未等待默认 120 秒；这两个验证不能混成同一实测。

</details>

### 第 6 题：Pub/Sub 信号丢了为什么还能补通知？序号递增为何仍需要用户锁？

答案来源：[D33 面试题](D33-面试题.md) 题 4、5；事实依据是 D33 写入、查询与跨进程验证。Pub/Sub 语义见该题引用的 Redis 官方正文。

追问：

1. 用户离线时，消息保存在什么地方？
2. A 先分到较小序号却后提交，B 先提交较大序号，会漏哪里？
3. 游标属于本人，为什么补读查询仍带 userId？断连清理什么？

<details>
<summary>完整参考答案与追问</summary>

通知表是持久事实，Pub/Sub 只告诉各实例某个 userId 可能有新行。发布发生在事务提交后，失败只记告警，不否定已提交行；连接每 5 秒补读，按本人范围和 n- 游标继续。D33 缩短轮询并模拟 publish 拒绝的原样记录：

```json
{"case":"sse-publish-fallback","publishRejected":true,"databaseRows":1,"pollMs":100,"received":1}
```

这证明本次落库后可由轮询恢复；不是 Redis 主从切换或全部网络故障实验。Redis Pub/Sub 本身不按库号隔离，频道包含库号，避免测试和开发唤醒互串。

序列分配先于提交，不能自动充当任意写入口的提交顺序。A 分到 10 尚未提交，B 的 11 先提交，客户端推进到 11 后只找更大值，A 的 10 会漏。生产通知 Worker 按固定用户 ID 顺序先锁用户行，锁内分配序号、写行并提交；同一用户的提交顺序受保护，其他用户可以交错，序列有空洞仍正常。D33 原样记录：

```json
{"case":"sse-commit-order","laterBlockedByUserLock":true,"sequenceFollowsCommit":true}
```

锚点归属验证与实际查询范围是两层。本人锚点后面、前面都有别人通知，仍必须带 userId；D33 去掉补读 userId 的反证混入别人的行。连接退订清本次监听、轮询、心跳和租约 timer；客户端 close 不自动取消已经发出的数据库查询。慢客户端、长期内存和代理验证都未完成。

</details>

### 第 7 题：通知列表、SSE 与已读请求怎样合并？切用户为什么会产生竞态？

答案来源：[D34 面试题](D34-面试题.md) 题 1、3、4、5。题库关联为《2026深度求索web前端高级工程师-AIGC.pdf》第 2 页 Fetch 取消题；网络场景为[《竞态条件（race condition）》](https://juejin.cn/post/7618786159652945920)，2026-03-19，原文与边界见 D34。

追问：

1. 数据库只有一条通知，为什么前端还要按 ID 去重？
2. 两个已读请求都成功，未读数该减几次？
3. 只挡旧成功响应，旧 catch/finally 与 401 会怎样？

<details>
<summary>完整参考答案与追问</summary>

数据库唯一约束防重复行，HTTP 最近列表与 SSE 重放仍可能多次传来同一行。前端按通知 ID 合并，最近列表只有 50 条，全部未读由服务器统计，不对每条增量简单加一。读取期间的新行暂存合并，dirty 让刷新串行补一轮；knownRead 与 revision 防旧快照覆盖本地已读结果与计数。D34 单元的原样记录：

```json
{"case":"frontend-snapshot-race","staleResponseArrived":true,"keptLiveRows":1,"finalUnread":1}
```

已读接口条件为 id+userId+readAt:null，之后同一 id+userId 读回；重复已读返回首次 readAt，别人或不存在的行 404。两个 HTTP 成功只发生一次状态变化，未读由服务端重新 count：

```json
{"case":"read-idempotent","requests":2,"succeeded":2,"uniqueReadAt":1,"unreadDelta":-1}
```

JS 回调串行不等于网络返回按请求顺序。bob 的响应、source 回调、catch/finally 可能晚于 alice 登录。以 username+token 为身份键，同步 watch 清旧作用域；所有异步写状态检查当前身份与 source。旧 401 只有 requestToken 仍是当前 token 才注销，否则会把新用户踢出。D34 受控 Promise 记录：

```json
{"case":"frontend-user-switch","lateOldTicketIgnored":true,"lateOldListIgnored":true,"newUserRows":0}
```

abort 只停止响应 signal 的工作；EventSource 用 close，timer 用 clearTimeout。刷新权限但身份键没变时无需重建连接。其他标签页的已读目前没有即时广播，之后 ready、新通知或刷新才同步总数；本周没有完成完整辅助技术审计和长期重连压测。

</details>

### 第 8 题：历史分页与 SSE 复用序号，怎样保证不重复、不串人、不丢精度？

来源：本项目 D35 变式、3 个游标单元、6 个真实接口用例与两个反证；关联 [D35 讲义](D35-第五周复盘.md) 1.1-3.3。此题为项目追问，不标成企业原题。

追问：

1. limit+1 的额外行能用作下一页锚点吗？为什么不是 <=？
2. h-0 页面为空，unreadCount 为什么仍可能为 5？
3. BigInt 怎样进入查询又不进入公开 JSON？每页事务能冻结整个浏览过程吗？

<details>
<summary>完整参考答案与追问</summary>

history 按 streamSeq 降序，h- 游标向旧记录取 `<before`；SSE 按升序向新通知取 `>after`，n-/h- 互不混用。历史缺省最新，h-0 是最旧边界；正锚点必须存在且属于本人。锚点只给位置，每页 SELECT 和总未读 count 仍带登录 userId；不接收客户端 userId 改范围。

取 limit+1 只判断有没有更多，展示前 limit 条，游标来自最后展示项。若取探测行作锚点，严格比较会跳过探测行；若用 <=，边界重复。本轮真实结果：

```json
{"case":"history-pagination","stored":9,"pageSizes":[4,4,1],"received":9,"distinct":9}
```

BigInt 编解码用十进制字符串，输入检查格式、长度与 signed bigint 上限，不能先 Number 再转 BigInt；单元用大于安全整数的值验证往返。内部 streamSeq 用于位置，序列化前解构移除，公开通知行沿用 D34 ISO 字段。初次专项曾因展开整行而 500，已经修正；原始 response.body 的字段断言防 schema 解析剥掉额外字段后掩盖泄露。

总未读只 count 本人的 readAt:null，不带页面边界。页外行标已读后仍保留在历史；h-0 页面空，全部未读仍为 5 的原样记录：

```json
{"case":"history-read-boundary","stored":6,"totalUnread":5,"emptyPageItems":0,"readRowStillInHistory":true}
```

每次请求使用 RepeatableRead，使本次锚点、页面与总数共享快照；不跨 HTTP 请求冻结。两页之间新增通知，总数会变化，旧页仍向小序号翻，刷新首页看新行。当前不支持事件时间排序、未读筛选或锚点物理清理；这些会改变游标产品语义，需要重新约定。

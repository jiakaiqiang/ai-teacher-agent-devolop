## 一、网络最新题

### 题 1：什么是死锁？数据库怎么处理？应用层应该怎么重试？

来源：掘金《数据库死锁-应用层重试》，2026-07-20（https://juejin.cn/post/7663860024171347968）。原文以 MySQL 为例，强调重试的是整个事务而不是单条 SQL，并给了手动重试和 Spring `@Retryable` 两种写法。

<details>
<summary>完整答案</summary>

**是什么**：两个或多个事务各自持有对方需要的锁，又都在等对方释放，等待关系形成一个环，没有外力就永远等下去。只是 A 等 B、B 在正常执行，那是排队，不是死锁。

**数据库怎么处理**（PostgreSQL，本项目实测）：一个事务等锁超过 `deadlock_timeout`（默认 1 秒）后检查等待图，发现环就让其中一个事务报 `40P01 deadlock detected`，并回滚它，另一个事务继续。实测两个事务交叉锁两张工单，1001ms 后一个报错，错误详情写明“进程 X 在等事务 Y，被进程 Z 挡住”，另一个随即成功。

**应用层怎么重试**（原文的核心观点，正确）：

- 重试**整个事务**，不是失败的那条 SQL。被选中的事务已经整体回滚，之前的修改全部作废，只重试一条 SQL 等于丢掉了前面的步骤。
- 次数有限，加退避。本项目的 `withTransactionRetry` 最多重试 3 次，每次随机等几十毫秒，次数越多等得越久。
- 事务里不能有副作用，因为会被执行多次。

**但重试只是兜底**。本项目实测：批量指派按请求顺序逐张加锁，两个请求顺序相反，加上重试后两个都能成功，但每轮从 23ms 变成约 1120ms，因为每次都要先死锁、白等 1 秒才会被发现。根治的办法是固定加锁顺序（题 2），改完后每轮约 23ms、不再死锁。面试时先说根治，再说兜底。

**原文有两处要纠正**：

1. **MySQL 的错误码写错了**。原文用 `e.getErrorCode() == 40001` 判断死锁。`getErrorCode()` 返回的是 MySQL 自己的错误号，死锁是 **1213**；`40001` 是它的 SQLSTATE，要用 `getSQLState()` 取。按原文的写法，死锁永远判断不出来。
2. **锁等待超时和死锁的回滚范围不一样**。MySQL 的锁等待超时（1205）默认只回滚超时的那条语句，事务还开着（由 `innodb_rollback_on_timeout` 控制，默认关闭）；死锁则回滚整个事务。原文把两者放在同一个重试分支里，重试之前要先确保整个事务已经回滚。PostgreSQL 没有这个区别：死锁（40P01）和等锁超时（55P03）都会让整个事务中止。

（MySQL 的两点来自 MySQL 官方文档的行为说明，本教程没有在 MySQL 上实测。）

</details>

### 题 2：怎么避免死锁？

来源：掘金《PostgreSQL 锁与死锁：结合 DevMind 讲清楚》，2026-09-30（https://juejin.cn/post/7691153237450407979）。作者在 PostgreSQL 17 上用两个连接实测了各种锁的等待情况，还复现了一次由外键检查引起的隐蔽死锁。

<details>
<summary>完整答案</summary>

**1. 固定加锁顺序**。所有事务按同一个顺序锁资源，就不会形成环。批量操作时，一条语句排序后一次锁住：

```sql
SELECT id, ticket_no, status FROM tickets
WHERE ticket_no = ANY($1)
ORDER BY ticket_no
FOR UPDATE;
```

本项目实测：两个批量指派各 10 张工单、顺序相反，按请求顺序逐张加锁时连续 5 轮每轮都死锁；改成上面的写法后 5 轮都没有死锁。顺序必须是全系统统一的约定，一个接口按编号、另一个按 id，照样可能死锁。

**2. 先锁再检查**。在锁住之后检查状态，检查和修改之间别人就改不了。先用普通 `SELECT` 读、判断，再去改，是最常见的并发错误。

**3. 用刚好够用的锁**。原文的经验：不改主键时用 `FOR NO KEY UPDATE` 代替 `FOR UPDATE`。往子表插入或修改数据时，外键检查会给父表的那一行加一把 `FOR KEY SHARE`，它和 `FOR UPDATE` 冲突，和 `FOR NO KEY UPDATE` 不冲突。原文的死锁就是这样出现的：代码里根本没有锁父表，是外键检查悄悄加的锁和另一个事务的 `FOR UPDATE` 形成了环。

**4. 一开始就加最终需要的锁**。两个事务都先 `FOR SHARE`，然后都想改同一行，各自在等对方放掉共享锁，这是锁升级导致的死锁。

**5. 事务要短**。事务里不要调外部接口、调模型、等用户操作。持锁越久，和别人交叉的机会越多。

**6. 兜底：重试 40P01**。做不到固定顺序时（例如两条完全不同的业务路径），捕获死锁、重试整个事务。

**7. 写并发测试**。死锁只在真正并发时出现。本项目的测试同时发出两个顺序相反的请求，连续 5 轮。

**容易被忽略的一点**：`UPDATE ... WHERE id IN (...)` 这种批量更新，数据库按什么顺序锁行是不保证的，取决于查询计划。本项目实测，去掉 `ORDER BY` 后仍然没有死锁，因为查询恰好走了工单编号的唯一索引、行已经按编号排好了；但这是计划的副作用，不能依赖。

</details>

### 题 3：线上出现锁等待或请求卡住，怎么排查？

来源：掘金《PostgreSQL 事务与并发系列 · 第三期》，2026-04-24（https://juejin.cn/post/7632034549904228390）。原文讲了表锁、行锁、建议锁、死锁检测，并给了几个监控查询。

<details>
<summary>完整答案</summary>

**第一步：谁在等谁**。

```sql
SELECT pid, application_name, state, wait_event_type,
       pg_blocking_pids(pid) AS blocked_by,
       now() - xact_start AS xact_age, left(query, 80) AS query
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0 OR state = 'idle in transaction';
```

本项目实测：A 锁住工单不提交，B 去改同一张，查出来 B 的 `blocked_by` 是 A 的 pid、`wait_event_type` 是 `Lock`；A 的状态是 `idle in transaction`。

**第二步：判断挡路的事务在干什么**。

- `idle in transaction`：开了事务却什么也没做、也没提交。多半是代码在事务里调了慢的外部接口，或者出错后没有回滚。看 `xact_age`，挂了几分钟就是问题。
- `active`：还在执行，可能是一条慢查询，用 D4 的 `EXPLAIN ANALYZE` 继续查。

**第三步：看锁的细节**（需要时）。`pg_locks` 里 `granted = false` 的就是在等的锁。本项目实测：B 在等 A 的 `transactionid` 上的 `ShareLock`，也就是等 A 的事务结束；B 还持有这一行的 `tuple` 锁，表示它排在等这一行的队伍最前面。

**第四步：处理**。`pg_cancel_backend(pid)` 取消它当前的语句；`pg_terminate_backend(pid)` 断开连接，事务回滚。先确认它是谁、在做什么。连接时设置 `application_name`，排查时能直接认出是哪个服务的连接。

**预防**：

- `lock_timeout`：等锁超过时间就报 55P03，请求返回明确的错误而不是挂住。本项目批量指派设 2 秒，实测约 2 秒后返回 409 `RESOURCE_LOCKED`；去掉以后，请求一直挂着，直到测试超时。
- `idle_in_transaction_session_timeout`：自动断开长时间 `idle in transaction` 的连接。
- `log_lock_waits = on`：等锁超过 `deadlock_timeout` 时写日志，死锁时日志里有双方的完整语句。

**原文有一处不准确**：原文说“PostgreSQL 有一个后台进程 deadlock_timeout，每隔这么长时间检查一次”。`deadlock_timeout` 是一个配置项，不是进程；也不是定时扫描，而是某个事务等锁等满这个时间后，由这个事务自己去检查有没有环。所以没有锁等待时，死锁检测完全不会运行，把这个值设大一点能减少检测的开销，代价是真的死锁时要等更久才被发现。

</details>

## 二、补充题

### 题 4：（补充题）`deadlock_timeout`、`lock_timeout`、`statement_timeout` 有什么区别？

本题没有对应的网络原文，来自讲义 1.1 和 1.4 的实测。

<details>
<summary>完整答案</summary>

| 配置 | 管什么 | 到时间后 | 默认值 |
|---|---|---|---|
| `deadlock_timeout` | 等锁多久之后开始检查死锁 | 有环：回滚一个事务，报 40P01；没有环：继续等 | 1 秒 |
| `lock_timeout` | 一条语句最多等锁多久 | 报 55P03，事务中止 | 0，不限制 |
| `statement_timeout` | 一条语句最多执行多久（包括等锁和真正执行） | 报 57014，事务中止 | 0，不限制 |

本项目实测：死锁时两边都等了约 1001ms，正好是 `deadlock_timeout`；`lock_timeout` 设 500ms 时等了 501ms 报错（D10 演示脚本），设 2 秒时接口约 2 秒返回 409。

**怎么设**：

- `deadlock_timeout` 一般不动。
- `lock_timeout` 按接口设，在事务里用 `set_config('lock_timeout', '2s', true)` 只对当前事务生效。线上执行 `ALTER TABLE` 这类迁移前也要设，否则它在等锁时会挡住后面所有的查询。
- `statement_timeout` 可以给整个应用的数据库用户设一个兜底值，防止一条失控的查询拖垮数据库；跑报表、迁移的连接单独放宽。

`lock_timeout` 必须小于 `statement_timeout` 才有意义，否则总是 `statement_timeout` 先到。

</details>

### 题 5：（补充题）批量接口为什么要限制一次处理的数量？

本题没有对应的网络原文，来自讲义第六节的建议。

<details>
<summary>完整答案</summary>

一个事务处理的行越多：

1. **持锁越久、锁的行越多**。别的请求碰到其中任何一行都要等，等待时间就是整个批量事务的执行时间。
2. **和别人交叉的机会越多**，固定顺序能消除死锁，但消除不了等待。
3. **失败的代价越大**。全部成功或全部失败，一行出问题整批重来。
4. **请求体和响应时间不可控**。一次传一万个编号，校验、查询、写入的时间都难以预估，可能撞上网关超时。

本项目批量指派一次最多 50 张（DTO 的 `@ArrayMaxSize(50)`），超过返回 400。更多的工单由前端分批提交，或者改成异步任务（W5）：接口只登记任务，后台分批处理，前端轮询或接收通知。

这和前端的分页、虚拟列表是同一个思路：不要一次处理太多。

</details>

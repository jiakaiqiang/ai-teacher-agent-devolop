<details><summary>补充、纠正与项目回答</summary>

## 2. 网络提炼：Counter、Gauge和Histogram怎样选？

<details><summary>完整答案</summary>

Counter适合累计事件，例如完成的请求数；进程重启可以归零。Gauge适合当前状态，例如SSE连接、队列失败任务数量、未投递Outbox。Histogram记录一组观测值分布，本章单位秒、经典桶累计小于等于边界，还输出sum/count。

请求数不是QPS；同窗口Counter增量除窗口秒数才是平均速率。sum/count只是平均耗时，不能得到准确P95。经典桶只能估计分位值，分辨率由桶边界决定，超过最大有限桶的长尾也需考虑。多个实例应先合并同边界的桶计数，再求分位，而不是平均各自P95。

本章没有运行PromQL或采集服务器。文章中的error_rate Gauge缺少窗口口径；本项目保留请求总计与5xx分类，在后续窗口计算中明确分母与低样本策略。

**追问**：指标每次抓取都重新建Registry，会丢累计请求吗？不会，本章累计HTTP Registry是应用长驻；只有队列、Outbox、SSE这类本次快照使用临时Registry，最后merge。

</details>

## 3. 网络提炼：错误率5%应怎样计算，文章里的规则哪里不够？

<details><summary>完整答案</summary>

必须确定时间窗口、计数范围、失败定义和最小样本。比如同一实例/路由的一分钟已完成普通HTTP，5xx增量除总完成增量。4xx可以另设业务口径，aborted单独观测，不在不说明的情况下塞进5xx。

第二篇来源的告警示例只有5xx Counter的rate大于0.01，表示每秒错误次数超过0.01，不是1%的错误率，因为缺少总请求速率作分母。规则评估也属于Prometheus，Alertmanager主要处理通知分组/路由/抑制；不能把所有规则都说成Alertmanager直接计算。

没有请求时分母为0，不能宣布“零错误率且健康”；一次请求一次失败是100%，也不等于有充分样本证明持续故障。D42用最小样本与连续窗口做一个纯函数变式；这不是已经部署的生产SLO。

**追问**：为什么不把400当服务崩溃？参数错误、越权、限流可能是正常保护，仍值得观测，但和服务器内部错误的处置不同。

</details>

## 4. 项目题：为什么不用原始URL和用户ID做标签？

<details><summary>完整答案</summary>

每个不同组合都是新的时间序列。工单号、查询串、一次性票据随请求增长，带来内存和存储成本，也可能泄露敏感值。用匹配后的路由模板合并；未知路径固定unmatched、未知方法OTHER。requestId放日志，用来下钻单次请求。

反证把模板换成originalUrl，失败输出实际出现模拟工单ID和query，还把应为2的同路由计数拆成1：

```text
 FAIL  test/operations.e2e-spec.ts > 运行指标与本机集成（D41） > 路由模板合并工单编号且不带敏感 query
AssertionError: expected 'ops_http_requests_total{method="GET",…' to be 'ops_http_requests_total{method="GET",…' // Object.is equality

Expected: "ops_http_requests_total{method="GET",route="/api/tickets/:ticketNo",status_class="4xx"} 2"
Received: "ops_http_requests_total{method="GET",route="/api/tickets/D41-private-a?ticket=fake-sensitive-value",status_class="4xx"} 1"
```

恢复原字节和SHA-256后同测试通过。截短ID只是减少字符串长度，不能证明标签基数有界。

</details>

## 5. 项目题：就绪正常，但通知一直迟到，查什么？

<details><summary>完整答案</summary>

沿业务链逐段看：Outbox pending数量/最早时间是否增长；maintenance共用全局并发是否被SLA扫描占住；notifications队列是否waiting/failed；Worker是否写出通知行；Pub/Sub或轮询是否唤醒；SSE是否仍有连接以及客户端游标是否补读。健康探针只说明必要依赖能回应，不能证明积压已处理或端到端通知及时。

本章Outbox读WHERE published_at IS NULL；去掉筛选会把已投递历史误算成积压，第二个反证真实失败。最早创建时间是共享资源时间戳，空值0须结合pending>0使用。多实例抓取同一队列/库，不应把共享积压乘上实例数。

采集失败要显示未知或失败，本章返回503，不能catch后返回0。采集等待期限不取消底层查询，合并inFlight只限制应用层重复发起，不解决长期悬挂或数据库池耗尽。

```json
{"case":"outbox-metrics","baseline":108,"pending":109,"oldestTimestampSeconds":978307200}
```

```json
{"case":"metrics-failed","statusCode":503,"code":"METRICS_UNAVAILABLE"}
```

</details>

## 6. 项目题：如何证明requestId确实跨过Nginx和事务？

<details><summary>完整答案</summary>

经过代理发送一个带合法ID的只读通知history请求；检查响应回传ID、Nginx访问日志、http.completed和db.transaction_io都匹配。测试只报告匹配布尔结果，凭据留内存。Nginx记录应用回传头，因此能和应用最终ID一致；上游连接失败没有回传头时该关联不存在。

```json
{"case":"proxy-metrics-trace","statusCode":200,"proxy":true,"http":true,"transaction":true,"traceAbsentFromMetrics":true}
```

这证明本次本机链路，不证明所有SQL、所有代理错误和分布式服务都接入了追踪。它也不是OpenTelemetry trace/span。实际系统应结合时间、接口和状态检索，requestId不能用于权限或业务幂等。

</details>

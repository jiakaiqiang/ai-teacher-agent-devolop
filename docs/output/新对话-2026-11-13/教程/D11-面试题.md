## 一、网络最新题

### 题 1：如何保证接口幂等？有哪些方案，各适合什么场景？

来源：掘金《如何保证接口幂等》，2026-08-02（https://juejin.cn/post/7669028793604718602）。原文列了五种方案：数据库唯一索引、Token 机制、分布式锁、状态机、防重表，并给了对比表和代码。

<details>
<summary>完整答案</summary>

**先说定义和起因**：同一个请求执行一次和执行多次，效果完全一样。重复请求来自网络超时后的重试、用户重复点击、消息队列的重复投递。调用方在超时时分不清对方做没做，只能重试，所以重复是常态。

**按操作类型选方案**：

| 操作 | 方案 | 本项目 |
|---|---|---|
| 插入一条记录 | 唯一约束，加 `INSERT ... ON CONFLICT DO NOTHING` | 告警按 `(source, dedup_key)` 去重 |
| 状态变更 | 带状态条件的更新 `WHERE status = 旧状态`，或版本号 | D8 的流转表、D10 的版本号 |
| 没有业务键的创建（下单、支付） | 客户端生成幂等键，服务端用幂等表记录结果（题 2） | 无 |
| 表单防重复提交 | 服务端发一次性 Token，提交时原子地校验并删除 | 无 |

**唯一约束是所有方案的底线**。其他方案（Token、分布式锁、缓存）都可能因为过期、宕机、并发失效，最后兜底的只有数据库约束。

**原文有三处要注意的地方**：

1. **原文的唯一索引示例是“先查询，再插入，插入时捕获唯一冲突”**。在 MySQL 里可以这么写；在 PostgreSQL 的事务里不行：插入失败后事务进入中止状态，后续任何查询都报 25P02。本项目实测，这种写法下同一条告警并发推送 5 次，结果是 `[201, 500, 500, 500, 500]`。PostgreSQL 里应该用 `ON CONFLICT DO NOTHING`，冲突时不报错。
2. **先查再插本身就有竞态**。原文把“先查询”当作优化，但并发请求会同时查到“没有”。本项目实测：去掉 ON CONFLICT 改成先查再插，同一条告警并发推送 5 次，连续 5 轮都是 `[201, 409, 409, 409, 409]`。数据靠唯一约束保住了，但 4 个重复请求收到了错误。
3. **原文的分布式锁切面只能挡住“同时到达”的重复**。它在 `finally` 里释放锁，第一个请求处理完、锁释放后，同一个请求再来一次（例如超时重试），照样能拿到锁、再执行一遍。锁解决的是互斥，不是幂等。要挡住先后到达的重复，必须把“这个请求已经处理过”持久地记下来：唯一约束、防重表或幂等表。

**重复请求要返回什么**：原文“生产级难点”里提到的“第一次成功但响应超时，重试返回‘重复请求’，前端显示失败”，正是本项目返回 200 而不是 409 的原因。重复请求应该得到和第一次一样的结论。本项目返回 `{ created: false, ticketNo: 第一次建的工单 }`。

**面试时的回答顺序**：先讲为什么会有重复；再按操作类型给方案，说唯一约束是底线；然后讲先查再插的竞态和你的实测；最后讲重复请求的返回值。

</details>

### 题 2：Stripe 的幂等键是怎么设计的？和“加个唯一索引”有什么区别？

来源：掘金《Stripe 幂等表：把「不确定的重试」变成「查表返回」》，2026-10-10（https://juejin.cn/post/7694908808569061417）。原文基于 Stripe 的 API 文档和 Brandur Leach 的参考设计，讲了幂等表的字段、请求流程、并发与崩溃恢复。

<details>
<summary>完整答案</summary>

**要解决的问题**：网络失败有三种，连接前失败（安全重试）、处理到一半失败、处理成功但响应丢失。后两种客户端无法判断对方做没做。支付这类操作，重试可能扣两次款，不重试可能丢一笔订单。

**做法**：

1. 客户端为每个**操作**（不是每次请求）生成一个 UUID，放在 `Idempotency-Key` 请求头。重试时必须用同一个键，换键就等于新操作。
2. 服务端有一张幂等表，`(用户, 键)` 唯一。请求到达时先“认领”这个键：`INSERT ... ON CONFLICT DO NOTHING`，再 `SELECT ... FOR UPDATE` 锁住这一行。
3. 认领后检查：请求参数的指纹和记录里的不一致，返回 409（客户端 bug）；已经有缓存的响应，直接返回它（无论第一次是成功还是失败）；都没有，开始执行业务。
4. 执行完把状态码和响应体存进表里。
5. 同一个键的两个请求同时到达，只有一个执行，另一个返回 409，客户端退避后用同一个键重试，就能拿到缓存的结果。
6. 处理到一半崩溃：把操作拆成几个阶段，每完成一个阶段记一个恢复点，重试时从断点继续。前提是外部调用本身也幂等。
7. 键至少保留 24 小时，后台任务定期清理。

**和唯一索引的区别**（原文的总结）：唯一索引保护的是一张表的一次插入；幂等表保护的是整个请求，能记录“处理中、成功、失败”，能把第一次的响应原样回放。

**和本项目的对比**：

| | Stripe 幂等表 | 本项目告警上报 |
|---|---|---|
| 幂等键 | 客户端生成的 UUID | 监控系统给的 `source` + `dedupKey`，业务自带 |
| 记录在哪 | 单独的幂等表 | 告警表本身，唯一约束就是幂等约束 |
| 重复请求返回 | 缓存的完整响应 | 现查的工单编号 |
| 同键不同参数 | 409 | 保留第一次的内容，返回 200 |

本项目不需要单独的幂等表：告警本身就是要保存的数据，去重键是它的一部分，而且整个处理只写数据库，一个事务就能保证原子性。需要幂等表的情况是：没有天然的业务键，或者处理过程中要调外部接口（扣款、发短信），没法放进一个事务。

**和后面课程的关系**：W17 的 Agent 工具调用里，“写操作的幂等键”就是这个设计。模型可能因为超时重复发起同一个工具调用，创建工单、执行变更这类工具必须带幂等键。

</details>

## 二、题库原题

### 题 3：如何实现一个支持“多轮对话中断”和“重新生成”的状态机？

出处：《2026MiNiMax前端AI开发》第 6-7 页（二面第 5 题）。

**原题**：5. 如何实现一个支持“多轮对话中断”和“重新生成”的状态机？（难度：★★★，考点：逻辑设计、状态机）

<details>
<summary>原文答案</summary>

> 答案要点：
> 通过定义明确的状态（Idle, Generating, Paused, Error）和 Action 来管理复杂的对话流。
>
> - 中止逻辑：利用 AbortController 关联 Fetch 请求，在用户点击“停止”时触发 abort()。
> - 覆盖更新：重新生成时，需定位到当前消息 ID，清空后续内容并重新触发流式请求。
> - 历史回溯：支持修改历史提问，此时需要截断后续对话树，发起新的分支请求。
> - 幂等性：确保多次点击重新生成不会导致状态错乱。
>
> 常见坑：
>
> - 请求已 abort 但前端状态未重置，导致 UI 卡死。
> - 重新生成时未处理好 Token 消耗的统计。

</details>

<details>
<summary>本教程补充：把“幂等性”那一条讲具体</summary>

原文只用一句话带过幂等性，面试时最容易被追问“具体怎么做”。结合 W1、W2 学的内容，可以分前后端两层回答：

**前端：多次点击“重新生成”**

- 状态机本身就是第一道防线。和 D8 的工单流转表一样，“重新生成”只在 `Idle` 和 `Error` 状态下允许；正在 `Generating` 时再点，要么忽略，要么先中止当前请求再开始新的（产品决定）。不允许的动作直接拒绝，状态就不会错乱。
- 中止旧请求后，旧请求已经在路上的数据块仍可能到达。每次生成带一个递增的序号或请求 ID，收到的数据块不属于当前这次生成就丢掉。这是 D6 讲的请求竞态的同一种解法。

**后端：同一次重新生成的请求到达两次**

- 前端超时重试，或者用户网络抖动，同一个“重新生成”请求可能到达服务端两次。如果每次都调用模型，就会生成两条回答、扣两次 Token，这正是原文“常见坑”里提到的 Token 统计问题。
- 做法和今天的告警上报一样：给每次重新生成一个幂等键（例如“消息 ID + 第几次生成”），服务端用唯一约束记下“这个键已经在生成了”，重复的请求不再调用模型，而是返回同一次生成的结果或进度。

一句话总结：前端用状态机挡住**不该发出**的请求，后端用幂等键挡住**重复到达**的请求，两层都要有，因为前端挡不住网络重试。

</details>

## 三、补充题

### 题 4：（补充题）PostgreSQL 里“插入，撞上唯一冲突就查已有记录”为什么不行？怎么改？

本题没有对应的网络原文，来自讲义 1.2 和反证实验 B 的实测。

<details>
<summary>完整答案</summary>

**原因**：PostgreSQL 的事务里，任何一条语句出错，整个事务进入中止状态，之后的语句全部报 `25P02 current transaction is aborted, commands ignored until end of transaction block`，只能回滚。插入撞上唯一约束是一个错误，所以接住它以后的查询注定失败。

本项目实测：告警上报改成这种写法后，第一次上报 201，之后的每一次重复上报都是 500，日志里是 25P02。依次重复推送也失败，不需要并发。

**MySQL 不一样**（来自题 1 引用的文章的写法，本教程没有在 MySQL 上实测）：MySQL 的唯一冲突默认只回滚出错的那一条语句，事务可以继续，所以“插入、捕获冲突、再查”在 MySQL 里是常见写法。从 MySQL 转到 PostgreSQL 时这里容易出错。

**三种改法**：

1. **`INSERT ... ON CONFLICT DO NOTHING RETURNING`**（本项目）：冲突不报错，返回空，事务继续。Prisma 里是 `createManyAndReturn` 加 `skipDuplicates: true`。
2. **保存点**：插入前 `SAVEPOINT s`，失败时 `ROLLBACK TO SAVEPOINT s`，只撤销这一条，事务可以继续。
3. **把插入放在事务外**：插入单独执行，失败了再开事务做后续的事。缺点是插入和后续步骤不再是原子的，插入成功、后续失败时会留下半成品（讲义 1.3）。

</details>

### 题 5：（补充题）工单编号、订单号这种“日期加序号”的编号怎么生成？

本题没有对应的网络原文，来自讲义 1.4 和反证实验 C 的实测。

<details>
<summary>完整答案</summary>

**不能“数一数再加一”**。几个事务同时统计，得到同一个数，生成同一个编号。本项目实测 5 条告警同时建单，`[201, 409, 409, 409, 409]`，唯一约束拦住了重复，但 4 张工单没建成。`max + 1` 一样。这是“先读再写”的竞态，和 D9 的写偏斜同一个结构。

**三种可行的做法**：

| 做法 | 并发 | 编号连续吗 | 代价 |
|---|---|---|---|
| 数据库序列 `nextval` | 安全，不需要等待 | 不连续：回滚时取出的值不退回（实测取到 1 后回滚，下一次是 2） | 不能按天归零，编号是“日期 + 全局序号” |
| 计数表 `INSERT ... ON CONFLICT (day) DO UPDATE SET n = n + 1 RETURNING n` | 安全，同一天的建单排队等这一行的行锁 | 连续，回滚时一起回滚 | 所有建单在这一行上串行，直到各自的事务提交 |
| 应用生成（雪花算法、UUID v7） | 安全，不访问数据库 | 不连续，也不是小数字 | 编号很长，不适合给人看和电话里报 |

本项目用序列：工单编号只要求唯一、大致有序、方便人读，不要求连续。

**两个细节**：

- 补零放在应用里做。SQL 的 `lpad('12345', 4, '0')` 实测返回 `1234`，会截断；JavaScript 的 `padStart` 不会。
- Prisma 的 schema 表达不了独立的序列，要在迁移 SQL 里手写 `CREATE SEQUENCE`。实测应用后再生成迁移仍是空的，Prisma 不会删掉它。

**追问：编号有空洞，财务要求发票号连续怎么办？** 那就不能用序列，要用计数表，并接受建单串行的代价；而且回滚以外，作废的发票也要保留记录，不能删除，否则还是会出现空洞。

</details>

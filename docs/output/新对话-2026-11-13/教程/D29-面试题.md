## 一、题库原题

### 题 1：Redis 在你的项目里主要起什么作用？（这次答“队列”和“持久化”）

出处：《2026美团前端全栈开发》第 9-10 页（二面第 8 题）。

**原题**：8. Redis 在你的项目里主要起什么作用？（难度：★★，考点：缓存、中间件）

<details>
<summary>原文答案</summary>

> 答案要点：
> Redis 主要作为高性能内存数据库，用于缓解持久层压力和处理分布式场景。
>
> - 场景：缓存热点数据、存储 Session/Token、实现分布式锁、简单的消息队列。
> - 数据类型：String（基础缓存）、Hash（对象存储）、List（队列）、Set/ZSet（去重/排行榜）。
> - 持久化：RDB 快照和 AOF 日志保证数据安全。
>
> 常见坑：
>
> - 缓存穿透、缓存击穿、缓存雪崩的风险及应对。
>
> 追问：
>
> - 如何保证 Redis 和 MySQL 的数据一致性？

</details>

<details>
<summary>本教程补充：同一个项目里两个 Redis</summary>

D22 回答了“缓存”那一半。W5 加了队列以后，最有说服力的回答是：**本项目有两个 Redis，配置完全相反**。

| | 缓存、限流、锁（W4） | 队列（W5） |
|---|---|---|
| 持久化 | 不开：丢了可以从数据库重建 | 开 AOF，每秒刷盘：任务是唯一的一份 |
| 内存满了 | `allkeys-lru`：淘汰最久没用的键 | `noeviction`：拒绝写入，不能悄悄删任务 |
| 挂了怎么办 | 回退到数据库，接口照常 | 告警接口返回 503，监控系统重试 |

**为什么不能共用一个**：淘汰策略是整个 Redis 实例的配置。BullMQ 连到 `allkeys-lru` 的 Redis 时会打出警告 `IMPORTANT! Eviction policy is allkeys-lru. It should be "noeviction"`，但照样能用（实测），所以很容易被忽略。

**RDB 和 AOF**：RDB 是定时把整个内存拍一张快照，恢复快、文件小，但两次快照之间的数据会丢；AOF 是把每条写命令追加到文件里，`everysec` 最多丢 1 秒。队列选 AOF。实测：在两个 Redis 里各放一个 1 小时后才执行的任务，重启容器后，缓存那个 Redis 里任务没了，队列那个还在。

**原文说“List（队列）”**：用 `LPUSH`/`BRPOP` 确实能做最简单的队列，但重试、延迟、失败保留、处理中崩溃后的恢复都要自己写。BullMQ 内部用了 List、Sorted Set、Hash 和 Stream 的组合，加上 Lua 脚本保证状态转换是原子的。面试时说“简单场景用 List，生产用 BullMQ 这类库”，再说出自己项目里为什么选它。

</details>

## 二、网络最新题

### 题 2：Node.js 本来就是异步的，为什么还要消息队列？

来源：掘金《Node.js 天生就是异步的，为什么还要消息队列？》，2026-09-16（https://juejin.cn/post/7685816258889547814）。原文用“上传 100 份 PDF 做向量化”的场景，对比了在接口里直接起异步任务和用消息队列的区别。

<details>
<summary>完整答案</summary>

**一句话**（原文的总结，很好记）：语言级的异步解决的是“等”（一个进程里不在 I/O 上浪费时间），消息队列解决的是“崩”（跨进程的持久化、削峰、重试、扩容）。

**在接口里直接起一个不 `await` 的异步任务，会遇到的问题**（原文的四点）：

1. **CPU 密集的任务会卡住事件循环**：解析 PDF、大量计算会让整个进程不响应其他请求。队列可以把 Worker 放到单独的进程里。
2. **一波请求同时进来**：50 个任务同时在内存里跑，内存可能被吃光。队列的 Worker 按固定并发消化（本项目 `concurrency: 5`）。
3. **进程重启、崩溃，任务就没了**：任务只在内存里。队列把任务存在外面。
4. **失败重试要自己写**，写了也扛不住进程重启。队列自带退避重试和失败保留（本项目实测：间隔 1 秒、2 秒，第三次成功）。

**原文有两处要补充**：

- **“消息发到 Broker 是落盘持久化的”不是自动的**。BullMQ 存在 Redis 里，Redis 默认的配置、以及很多人用来做缓存的配置都不保证持久化。本项目实测：不开持久化的 Redis 重启后，还没处理的任务直接没了；开了 AOF 才还在。
- **原文的“双重软降级”**：MQ 投递失败时自动改成同步执行。这是一个可选的设计，不是唯一正确的做法。本项目选择返回 503，理由是：队列的作用之一是保护数据库，故障时全部改成同步处理，正好在最需要保护的时候失去了保护；而监控系统本来就会重试。调用方不会重试、任务又很轻的场景，同步降级更合适。面试时说出你选哪个、为什么。

**原文提到的“上下文穿透”**：Web 层的租户信息在 ThreadLocal 里，Worker 的线程拿不到，要从消息里恢复。本项目是同一个问题的 Node.js 版本：请求 ID 存在 `AsyncLocalStorage` 里，Worker 里没有 HTTP 请求，所以入队时把请求 ID 放进任务数据，Worker 里用 `runWithRequestId` 恢复。反证实验实测：不恢复的话，审计里的请求 ID 是 `null`。

**什么时候不用队列**（原文最后一段）：任务极短、纯 I/O、失败了无所谓、丢了也不影响数据一致性，例如写一条非关键的调试日志。

</details>

### 题 3：用 BullMQ 时，任务会丢吗？会重复执行吗？怎么优雅关闭？

来源：掘金《BullMQ 技术深度解析：从架构设计到生产环境实战》，2026-04-09（https://juejin.cn/post/7626582287637119002）。原文讲了 BullMQ 的架构、任务生命周期、适合和不适合的场景，以及任务丢失、重复执行、队列阻塞、优雅关闭等生产问题。

<details>
<summary>完整答案</summary>

**任务会丢吗**：会丢的几种情况和对策，原文说得基本对：

- Redis 没开持久化：开 AOF，`appendfsync everysec`（本项目的队列 Redis）。
- 失败的任务被自动删掉：`removeOnFail: false`，失败的任务保留下来等人看（本项目实测重试用完后能在 `getFailed()` 里找到）。
- 成功的任务要定期清理（`removeOnComplete` 按时间和数量），否则 Redis 内存一直涨。

**会重复执行吗**：会，而且一定要假设会。原文列了几种原因，本项目实测了另一种更常见的：**生产者这边的重复**。队列 Redis 停掉时，告警接口 2 秒后返回 503，但那条入队命令还在客户端的离线队列里，Redis 恢复后照样入队了；监控系统收到 503 会重试，同一条告警就入队了两次。所以消费者必须幂等，本项目靠 D11 的唯一约束。D30 会实测“Worker 处理到一半崩溃”这种重复。

**原文有三处要纠正**：

1. **原文说“Worker 处理任务时崩溃，如果任务已经从队列中移除但尚未标记为完成，恢复后该任务无法重新处理”**。BullMQ 有“停滞任务”检测：Worker 处理任务时持有一把有过期时间的锁并定期续期，Worker 崩溃后锁过期，任务会被移回等待队列，由别的 Worker 重新处理（默认最多一次，超过就标记失败）。所以 Worker 崩溃通常不会丢任务，而是会**重复**处理，这正是要求消费者幂等的原因。D30 实测。
2. **原文的优雅关闭代码先调用 `queue.pause()`**。BullMQ 的类型注释写得很清楚：`pause()` 是“Pauses the processing of this queue globally”，暂停的是整个队列，所有实例的 Worker 都会停下来。一个实例在滚动发布时调用它，其他正常运行的实例也停了，而且没人负责恢复。单个实例关闭时只需要 `worker.close()`：它会停止领取新任务，等正在处理的任务做完再返回（`@nestjs/bullmq` 在应用关闭时自动调用）。
3. **原文说“事件系统基于 Redis 的 Pub/Sub，消息不会被持久化”**。BullMQ 的队列事件用的是 Redis Stream（`QueueOptions` 里有 `streams.events.maxLen`，默认保留约 1 万条事件），断开一会儿再连上可以接着读。不过事件只用来观察，业务逻辑不应该依赖“一定能收到某个事件”。

**原文值得借鉴的**：什么场景不适合 BullMQ（需要严格顺序、超大吞吐、强持久化），以及要监控的指标：各状态的任务数量（等待的越来越多说明处理不过来）、失败率、Worker 是否在线、Redis 内存。

</details>

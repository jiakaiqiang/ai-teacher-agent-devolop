## 一、题库原题

### 题 1：Redis 在你的项目里主要起什么作用？

出处：《2026美团前端全栈开发》第 9-10 页（二面第 8 题）。

**原题**：8. Redis 在你的项目里主要起什么作用？（难度：★★，考点：缓存、中间件）

<details>
<summary>原文答案</summary>

> 答案要点：
> Redis 主要作为高性能内存数据库，用于缓解持久层压力和处理分布式场景。
>
> - 场景：缓存热点数据、存储 Session/Token、实现分布式锁、简单的消息队列。
> - 数据类型：String（基础缓存）、Hash（对象存储）、List（队列）、Set/ZSet（去重/排行榜）。
> - 持久化：RDB 快照和 AOF 日志保证数据安全。
>
> 常见坑：
>
> - 缓存穿透、缓存击穿、缓存雪崩的风险及应对。
>
> 追问：
>
> - 如何保证 Redis 和 MySQL 的数据一致性？

</details>

<details>
<summary>本教程补充：用本项目回答，而不是背清单</summary>

原文是一个清单，面试官更想听的是“你的项目里具体用它做了什么、为什么这样配置”。按本项目回答：

| 用途 | 数据结构 | 本项目 |
|---|---|---|
| 缓存读多写少的数据 | String 存 JSON，带过期时间 | 设备信息（D22）、权限（D23）、统计（D24） |
| 分布式锁 | String + `SET NX PX` | SLA 扫描任务多实例只跑一份（D25） |
| 限流 | String + `INCR`；Sorted Set | 登录失败次数、评论频率（D26） |
| 任务队列 | BullMQ | W5 |

**原文说“存储 Session/Token”**：本项目的令牌是 JWT，服务端不存会话。Redis 在这里的作用是 D15 推导题提到的**令牌黑名单**（退出登录后让令牌立即失效），而不是存会话本身。

**持久化**：原文说“RDB 和 AOF 保证数据安全”。本项目的 Redis 只做缓存和限流，**没有开持久化**，并且限制了最大内存、内存满了淘汰最久没用的键。理由：缓存丢了可以从数据库重建，开持久化只会多占磁盘和 IO。W5 用 BullMQ 时任务不能丢，那时再开 AOF。说出“为什么不开”，比背出两种持久化方式更能体现理解。

**一个关键原则**：缓存挂了，业务不能挂。本项目所有缓存操作出错都回退到数据库，实测停掉 Redis 后接口照样返回 200。

**追问“Redis 和数据库的一致性”**：D23 的主题。先改数据库再删缓存，加上过期时间兜底。

</details>

## 二、网络最新题

### 题 2：旁路缓存（Cache-Aside）的读写流程是什么？Redis 挂了怎么办？

来源：掘金《Go 项目中 Redis 缓存的实用设计与实现（Cache-Aside 模式）》，2026-04-16（https://juejin.cn/post/7628981003035099171）。原文用 Go 实现了一个消息投递系统的缓存：键名用函数生成，读路径先查缓存再查库，写路径在事务提交后再操作缓存，所有缓存错误都忽略。

<details>
<summary>完整答案</summary>

**读路径**：查缓存，命中直接返回；没命中查数据库，结果写进缓存（带过期时间）再返回。

**写路径**：先改数据库，事务提交成功后再处理缓存（删除，D23 讲为什么删除比更新好）。

**原文值得借鉴的三点**，本项目都这样做了：

1. **键名用函数生成**，不在各处手写字符串。本项目是 `deviceCacheKey(code)`，读和删用同一个函数。
2. **过期时间按数据特点设**：原文对短期热点设几秒，对用户信息设 30 分钟。本项目的设备信息设 5 分钟。
3. **缓存失败不影响主流程**：原文读写缓存的错误都直接忽略。

**原文没提到、但实测很关键的一点**：“缓存错误不影响主流程”不只是加 `try/catch`。本项目第一版也有 `try/catch`，但实测停掉 Redis 后，每个请求慢了约 600ms：ioredis 默认把断开期间的命令放进离线队列，等到超时才报错。关掉离线队列（`enableOfflineQueue: false`）后，Redis 停掉时请求耗时约 20ms，和正常时差不多。降级的设计一定要停掉依赖实际测一次。

**原文写路径里的一个选择要讨论**：原文在事务提交后**更新**了收件人缓存（`SET` 新值），同时**删除**了待投递列表缓存。“更新缓存”在并发写时可能出现后写的旧值覆盖先写的新值，D23 会实测比较。

**面试时的回答顺序**：先讲读写流程；再讲键名、过期时间这些工程细节；然后讲降级，带上你测出来的数字；最后说一致性问题留给写路径（引出下一个话题）。

</details>

### 题 3：缓存和权限怎么配合？缓存的数据会不会被不该看的人看到？

来源：掘金《11.Redis与Cache-Aside旁路缓存策略》，2026-08-31（https://juejin.cn/post/7680014875347583014）讲了旁路缓存的基本流程和 FastAPI 下的三层封装；本题“缓存和权限”是本项目在这个基础上的实测。

<details>
<summary>完整答案</summary>

**原文的基本流程**和题 2 一样。原文有两处说法要纠正：

- 原文把“缓存里没有，去查数据库”称为**缓存穿透**。这不准确：普通的没命中叫**缓存未命中**（miss）；**缓存穿透**特指查询的数据**根本不存在**，缓存里永远没有，每次都打到数据库（D24）。面试时这两个词混用会被追问。
- 原文说缓存让“抗并发能力实现千倍飞跃”。实际收益取决于被缓存的部分在整个请求里占多少。本项目实测，设备信息接口未命中 14.0ms、命中 11.5ms，只省了约 2.5ms，因为同一个请求里权限守卫还查了一次数据库。

**缓存和权限的核心原则**：缓存里放所有人都一样的原始数据，**读出来以后再按当前用户判断**能不能看。

本项目的反例实测：在缓存的 loader 里按当前用户的班组过滤（`findFirst({ where: { code, ...scope } })`），结果放进共用的键 `device:srv-001`。一组的 bob 先查，缓存里有了；二组的 erin 再查，命中缓存，看到了不该看的设备，返回 200 而不是 404。这个漏洞只在“别人先读过”时出现，单独测 erin 时发现不了。

**三种做法**：

| 做法 | 会不会串数据 | 命中率 |
|---|---|---|
| 缓存原始数据，读出来按用户判断（本项目） | 不会 | 高：所有人共用一份 |
| 键名带上用户 id，按用户缓存 | 不会 | 低：每人一份 |
| 按用户过滤后放进共用的键 | **会** | — |

**读出来判断要用同一份规则**：本项目 D17 的 `groupScope()` 给出 Prisma 的条件，今天新增的 `isInScope()` 对已经读出来的数据做同样的判断，两个函数放在同一个文件里，有一个单元测试保证它们对三种情况的结论一致。

</details>

# D109面试题：每一步的Trace与审计

## 一、题库原题与原文答案

关联题：本地《2026已发交个朋友全栈AI工程师.pdf》第7—8页，三面第1题“如果让你从零设计一个企业级 AI Agent 平台的前端架构，你会考虑哪些核心模块？”。选它是因为答案要点里的「调试模块：单步执行、中间状态查看（Trace）、Token 消耗统计」正是本章的内容；题库没有服务端 Trace 与脱敏的原题。

<details><summary>原文（只调整排版）</summary>

1. 如果让你从零设计一个企业级 AI Agent 平台的前端架构，你会考虑哪些核心模
块？​
难度：★★★

考点：系统设计、架构思维、可扩展性
答案要点：
一个成熟的 Agent 平台需要兼顾易用性、调试性和可观测性。​
•
核心模块：可视化工作流编辑器（基于 React Flow）、Prompt 管理中心、插件/工具集市。​
•
调试模块：支持单步执行、中间状态查看（Trace）、Token 消耗统计。
•
存储模块：多端同步的对话历史、用户偏好设置。
•
接入层：多模型适配层（统一不同厂商的 API 格式）。​
•
监控层：错误上报、模型响应质量评估（Eval）。​
常见坑：
•
架构过于耦合，导致更换底层模型或增加新工具时需要大规模重构。
•
忽视了私有化部署的需求，导致静态资源和 API 路径硬编码。​

</details>

<details><summary>补充讲解与纠偏</summary>

原文列的模块（工作流编辑器、Prompt 管理、工具集市、调试、存储、接入层、监控）是平台视角的清单，方向没错，但它把 Trace 当成「前端调试面板的一个功能」。本章的立场不同：

1. **Trace 是服务端的持久化证据，不是前端的调试视图**。前端只能看到自己发起的那次运行，刷新就没了；排查线上问题需要的是「三天前那次运行第 3 步发给模型什么」，这只能存在服务端。本章把它放进 `agent_traces`，并和 Step 一一对应。
2. **Token 统计要分项、可汇总**。原文只说「Token 消耗统计」。本章按步记 `inputTokens`/`outputTokens`，汇总后进审计——因为输入和输出的单价不同（对照 D87 的用量核对），只记总数无法算成本。
3. **「中间状态查看」要先解决能不能看的问题**。原文没提权限与脱敏。本章的 Trace 只给运行发起人，写入前脱敏，正文不进事件与审计。企业级平台里，这一条比可视化更重要：Trace 里有工单正文、设备信息，甚至模型复述的联系人电话。

原文「常见坑」里的「架构过于耦合，换模型或加工具要大改」对本章也适用：`StepOutcome.trace` 是可选字段，循环不关心 Trace 的内容，执行器才落库——所以以后换模型、加工具不需要改循环。

</details>



## 项目面试与自检

### 1. 如何让负责人理解错误，又避免在系统日志复制客户原文？

关联运行号、工具、状态与受权材料引用，原文在原工单权限下查看。

### 2. 三个预算同时触及时，复盘要保存什么？

保存配置、实际消耗、停止原因和已完成的工具步骤。

### 3. 运行成功能否把已给建议的工单标为已完成？

运行记录说明 Agent 是否结束。工单依据用户反馈或人工动作推进。

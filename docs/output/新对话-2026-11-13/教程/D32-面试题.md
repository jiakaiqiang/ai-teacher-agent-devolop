## 一、网络最新题

### 题 1：多个实例各用 Cron 往队列入队，队列能自动保证每个周期只执行一次吗？

来源：[掘金《Node.js 战略级定时任务：自动清理过期 Token》](https://juejin.cn/post/7637099002202882102)，2026-05-08。原文用本地 Cron 定时向 Bull 入队，并讨论多实例。这里把场景改为 D32 的 SLA 扫描；不执行原文的数据清理操作。

<details>
<summary>完整答案</summary>

不能直接保证。要先分清“同一个任务由谁执行”和“这个周期创建了几个任务”。

如果两台应用各有一个 Cron，到点后各调用一次普通入队，两个不同任务 ID 就是两份任务。多个 Worker 的竞争消费只负责领取队列里的任务，不会因为任务名和数据相同就把它们合并。这个结论是对生产者结构的分析；本轮没有运行多实例 Cron 对照实验。

D32 把周期配置放进队列 Redis：所有实例在同一 Redis、prefix、队列范围内，用固定的 `sla-scan-v1` 调用 `upsertJobScheduler`。已有 ID 就更新该调度，不存在才创建。调度器负责产生各次任务，任务 ID 由 BullMQ 生成；不能把调度 ID 和一次任务的 ID 混为一谈。这一用法见 [BullMQ Job Schedulers](https://docs.bullmq.io/guide/job-schedulers/)。

本项目实测重复注册，原样输出：

```json
{"case":"scheduler-upsert","registrations":2,"schedulers":1}
```

**反证 A** 只把 SLA 调度 ID 加上随机数，全局并发仍为 1，重复注册测试就失败。原样失败信息：

```text
 FAIL  test/maintenance-scheduler.e2e-spec.ts > BullMQ 定时调度（D32 e2e） > 固定 ID 重复注册：同一个调度器仍只有一份
AssertionError: expected [ { …(7) }, { …(7) } ] to have a length of 1 but got 2
```

两份调度可以先后执行，即使业务层挡住了重复事件，调度层仍然有重复工作。文件已按实验前备份逐字恢复，字节与 SHA-256 比较记录见讲义 3.2；恢复后的同一测试原样摘要：

```text
 Test Files  1 passed (1)
      Tests  1 passed | 5 skipped (6)
```

**进程重开也要分层理解**：关闭自己的 Worker 和连接，不应删除所有实例共用的调度。本项目用两个真正的 Worker 子进程演示：注册三次只有一份调度；关闭重开后不再 upsert，任务仍能继续。原样输出：

```json
{"case":"process-scheduler-demo","registrations":3,"schedulers":1,"workerProcessesReady":2,"completedBeforeRestart":4,"schedulersAfterReopen":1,"upsertsAfterReopen":0,"completedTotal":8,"uniqueJobIds":8,"duplicateExecutions":0}
```

这个实验中 Redis 持续运行，进程正常关闭，验证的是应用资源重建后的调度保留。它没有证明 Redis 掉电或任务锁失效时永不重做。

**原文需要补充的地方**：原文使用的是 `bull`，本项目使用 `bullmq@6.7.6`，两者的 API 不能直接互换。把本地 Cron 和队列组合起来，也没有自动得到“多实例共用一个周期配置”的保证。若采用这种结构，仍需另行定义触发协调和业务幂等。

最后还要限定执行频率：官方说明下一次任务的生成与上一次任务开始处理有关，队列忙或 Worker 不足时，实际频率可能低于配置的 `every`。固定 ID 解决共享调度，不能承诺准点；重试和任务锁失效后的重做仍由数据库业务约束兜底。

</details>

### 题 2：waitForCompletion、Worker concurrency: 1、全局并发 1 分别限制什么？

来源：[掘金《第十四课：异步处理 — 缓存、队列与定时任务》](https://juejin.cn/post/7637803221285699594)，2026-05-09。题目从原文的 Cron 选项与 BullMQ 消费者部分提炼，以下答案补充作用范围并纠正旧 API 示例。

<details>
<summary>完整答案</summary>

它们限制的范围不同：

| 机制 | 限制什么 | 仍需处理什么 |
|---|---|---|
| Cron 的 `waitForCompletion: true` | 当前 Cron 实例的回调重叠；回调未完成时的新触发直接跳过 | 多进程各有各的 Cron；跳过的触发不会排队补跑 |
| Worker 的 `concurrency: 1` | 一个 Worker 同时处理的任务数 | 两个 Worker 仍各有本地名额 |
| `queue.setGlobalConcurrency(1)` | 同一队列的全局 active 任务数量 | 不限制其他队列，也不能代替业务幂等 |
| 数据库条件 UPDATE | 某张工单当前是否还有资格改变业务标记 | 标记必须与对应事件同事务，通知消费也要幂等 |

**纠正一：waitForCompletion 不会逐次补跑。** 原文对这个选项的解释容易让人以为忙时触发会等到上次结束。按照 [Nest 定时任务官方文档](https://docs.nestjs.com/application/task-scheduling#declarative-cron-jobs)，当前回调运行期间的新触发会被跳过。本轮没有安装并运行 Cron 例子，这一比较依据官方正文。

**纠正二：旧 repeat 示例不能直接用在 6.7.6。** 原文的 `queue.add` 示例带 `repeat`，本项目已安装包的公开 `JobsOptions` 不再接受这个选项；内部的调度任务类型仍带 repeat 信息，不代表调用方可以把它传给普通入队。应使用 `Queue.upsertJobScheduler`。依据是 `dist/esm/types/job-options.d.ts` 的类型和注释，以及 [Nest 队列官方文档的 Job 选项说明](https://docs.nestjs.com/application/queues#job-options)。

**本项目如何组合**：维护 Worker 的本地并发为 1，整个 `maintenance` 队列也设置全局并发 1。`sla-scan` 和 `outbox-relay` 共用这一个全局名额；告警、通知是其他队列，不受它限制。队列全局并发的作用范围见 [BullMQ Queue API](https://docs.bullmq.io/api/classes/v6.Queue.html#setglobalconcurrency)。

实测两个 Worker 的原样输出：

```json
{"case":"two-workers","workersReady":2,"completed":5,"uniqueJobIds":5,"maxActive":1,"duplicateExecutions":0}
```

为了单独检查全局限制，另一个用例把两个 Worker 的本地并发都调成 3，调度间隔 25ms，每个任务耗时 120ms。原样输出：

```json
{"case":"slow-schedule","everyMs":25,"workMs":120,"workersReady":2,"localConcurrency":3,"completed":4,"maxActive":1}
```

增加 Worker 实例在当前配置下主要提高可用性，不会增加维护队列的并行名额。慢 SLA 扫描会延迟 Outbox 投递；是否拆队列或提高并发，应先测耗时和积压，再调整。

**追问：任务失败怎么处理？** Worker 调 `relayOnce()`，让错误抛给 BullMQ。本章最多尝试 3 次，包含首次尝试，使用指数退避；D31 的 `runScheduled()` 会吞掉错误并返回 0，不能用于这个 Worker 分支，否则失败会变成成功结果。一次模拟投递错误后的队列重试，原样输出：

```json
{"case":"maintenance-retry","calls":2,"completed":1,"failed":0,"result":{"published":2}}
```

不认识的维护任务名用 `UnrecoverableError`，重试无法修正任务名与代码版本不匹配。原样输出：

```json
{"case":"unknown-maintenance-job","calls":1,"failed":1,"failedReason":"不认识的维护任务：unknown-task"}
```

全局并发属于运行安排；数据库条件更新属于业务判定。直接调用业务方法、任务重试或锁失效后的重做，都要求保留后者。

</details>

## 二、本项目补充题

### 题 3：超时 31 分钟才恢复扫描，如何在不重复通知的前提下立即升级？

来源：本项目 D32，讲义 1.3、升级测试和维护 Worker。

<details>
<summary>完整答案</summary>

从 `slaDueAt` 起算，而不是从首次扫描发现超时的时间起算。升级资格是：

- `status === 'pending'`，包括已指派但还没接单。
- `slaDueAt <= now - 30 分钟`。
- 已有首次超时标记，且 `slaEscalatedAt` 为空。

processing 不升级，规则已由用户确认。假设截止时间是 10:00：

| 业务时间 | 如何处理 |
|---|---|
| 10:29:59.999 | 还不满 30 分钟，不升级 |
| 10:30:00 | 满 30 分钟，满足其余条件即可升级 |
| 10:31 才恢复扫描 | 本轮先记录首次超时，再检查升级；不另等 30 分钟 |

维护 Worker 在同一轮捕获一个 `now`，先调用 `scanOnce(now)`，再调用 `escalateOnce(now)`。每个阶段分别把“对应标记与对应 Outbox 事件”放在同一事务里；首次超时和升级不是一个覆盖整轮扫描的大事务。

固定业务时间验证的原样输出：

```json
{"case":"escalation-boundary","beforeBy1ms":0,"at30Minutes":1,"processing":0,"notBreached":0}
```

```json
{"case":"late-first-scan","overdueMinutes":31,"breachEvents":1,"escalationEvents":1,"version":0}
```

UPDATE 必须重查完整资格。只有更新 count 为 1 的事务才读取当前班组并写 `ticket.sla_escalated { ticketNo, groupId }`。扫描并发或重试时，后来者看到标记已有值就不再写事件。写事件失败，标记也一起回滚，下一次还可以升级。原样输出：

```json
{"case":"escalation-rollback","markerAfterFailure":null,"eventsAfterFailure":0,"retryMarked":1}
```

Outbox 继续按 D31 的方式投递；通知 Worker 用 `(event_id, user_id)` 唯一约束处理同一事件的重复消费。业务层保证只有一个升级事件，消费层保证这个事件给每个人只有一条通知，两层都需要。

同一轮记录首次超时和升级，是两个不同的业务事件，不是重复升级。通知 Worker 可以并发消费，记录先后不能当作严格送达顺序。“立即”在这里指恢复后的这一轮可以升级，实际通知仍有排队与投递延迟。

扫描标记不增加 `version`，避免仅因后台提醒让用户的旧页面提交冲突；`updatedAt` 仍按 Prisma 更新规则变化。本章不会在重开工单时清零这些标记，当前是每张工单一次升级。多个 SLA 周期需要另行设计周期标识和重置规则。

</details>

### 题 4：两个扫描都先查到“尚未升级”，为什么仍要在 UPDATE 里检查？接单与扫描交错又怎么办？

来源：本项目 D32 并发测试、接单竞态测试、反证 B。

<details>
<summary>完整答案</summary>

SELECT 只读到某个时刻的状态，不能保留之后的写入资格。两个扫描可以都查到同一张未升级工单，然后先后更新。

正确做法是 UPDATE 同时检查工单 ID、pending、截止时间、已首次超时和未升级。第一个事务将标记从空改成有值；另一个事务真正更新时重新检查条件，count 为 0 就不写事件。标记和事件同事务，写失败不会留下阻止以后重试的标记。

实测先预热连接池，再用屏障让两个真实 SELECT 都完成后才开始 UPDATE；没有伪造更新结果。原样输出：

```json
{"case":"escalation-concurrency","readers":2,"marked":1,"events":1}
```

**反证 B** 保留 SELECT 的“尚未升级”，只移除 UPDATE 中同一条件，结果两个扫描各写一个新事件。原样失败：

```text
 FAIL  test/sla-escalation.e2e-spec.ts > SLA 超时升级（D32 e2e） > 两个扫描都先读到同一张工单：条件更新仍只写一个升级事件
AssertionError: expected [ { …(5) }, { …(5) } ] to have a length of 1 but got 2
```

两个事件的 ID 不同，`outbox-<事件 ID>` 任务去重和 `(event_id, user_id)` 通知唯一约束都不能合并它们。这证明业务资格不能只检查在 SELECT 里。

文件已逐字恢复，字节和 SHA-256 比较记录见讲义 3.2；恢复后的同一测试原样摘要：

```text
 Test Files  1 passed (1)
      Tests  1 passed | 6 skipped (7)
```

**接单竞态是另一个条件**：扫描 SELECT 之后，bob 通过 HTTP 接单，工单已变为 processing。UPDATE 再检查 pending，就会放弃升级；如果 UPDATE 只检查标记为空，便会发出过期提醒。指定交错顺序的原样输出：

```json
{"case":"accept-between-select-and-update","status":"processing","escalationEvents":0}
```

这个用例证明接单在 UPDATE 前已完成时不升级。若升级先提交、接单随后发生，记录的是升级当时的事实，本章没有撤回或在消费时取消已产生的事件。没有把一个指定交错顺序的测试当成所有竞态的证明。

</details>

### 题 5：已指派但没接单的工单升级通知谁？本组没人有派单权限时怎么办？

来源：D31 的消费时收件人约定、用户确认的 D32 规则、通知专项测试。

<details>
<summary>完整答案</summary>

升级始终查工单所属班组中有 `ticket:assign` 权限的人，不按“组长”角色名查，也不因为已指派给 bob 就只通知 bob。首次超时与升级的收件人规则要分别说明：

| 事件 | 收件人 |
|---|---|
| `ticket.sla_breached` | 有处理人就通知处理人；没有则通知本组派单人员 |
| `ticket.sla_escalated` | 本组派单人员；仅 pending 符合升级资格 |

种子里一组的派单人员是 carol。实测 pending 工单已指派给 bob，经真实 Outbox 投递和通知 Worker 消费后，升级只给 carol；同一事件再处理不新增通知。原样输出：

```json
{"case":"escalation-recipients","assignedPending":true,"recipients":["carol"],"events":1,"duplicateNotifications":0}
```

**零收件人的当前行为**：二组没有派单权限用户，仍记录升级事件；直接调用通知 Worker 处理该模拟事件时返回 `notified: 0`，没有跨组给一组发通知。原样输出：

```json
{"case":"no-leader-in-group","group":"ops-b","notified":0,"crossGroupNotifications":0}
```

0 条通知在当前实现中是成功返回，不会触发队列错误重试。按实现推导，后续给本组补上派单人员，也不会自动把已完成的事件重投；SLA 标记又已经存在，扫描也不会再产生第二次升级。这里保留了“事件已发生，收件人为空”的业务边界，尚无告警和补投机制。

后续可考虑零收件人指标、人工处理记录或明确的值班兜底规则，再决定是否补投原事件。跨组兜底会改变通知范围，应先确认业务规则。本轮只记录问题，没有实现这些方案。

**收件人何时确定也要说清楚**：沿用 D31，在消费时查询权限与人员。事件里保存 groupId，没有保存一份人员名单。重复消费时，每个 `(eventId, userId)` 至多一条通知；这不意味着同一事件的收件人名单永远不变。如果要求按事件发生时的值班名单通知，需要在写事件时保存收件人快照，并定义权限变更后的处理方式。

</details>

先用 90 秒回答题 1—3，再用题 4、5 追问。不要只说“用了 BullMQ 和幂等”，要说明每条保证的作用范围：

| 追问 | 回答中应出现的内容 |
|---|---|
| 两份调度为何可能没有重复通知？ | 调度层已经重复，业务条件更新可能把事件挡住 |

| 事件已投递是否等于一定有人收到？ | 零收件人可以成功返回；需要独立观察业务结果 |

不会的题按原因记进[错题本](../学习记录/错题本.md)，结合讲义的提示、源码和反证重新解释，再安排复测。

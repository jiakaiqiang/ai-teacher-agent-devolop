## 1. 题库原题：手写Fetch处理ReadableStream

<details><summary>原题与原文答案（含原代码）</summary>

3. 请手写一个 Fetch 处理 ReadableStream 的基本逻辑，模拟获取 AI 流式输出。
难度：★★★


考点：原生 API、流处理
答案要点：
通过 Fetch 获取 Response 对象后，利用 body.getReader() 循环读取数据块，并使用 TextDecoder 进
行解码。
•
获取 Reader：调用 response.body.getReader() 获取可读流读取器。
•
循环读取：使用 while(true) 配合 await reader.read() 持续获取 value 和 done 状态。
•
文本解码：使用 TextDecoder 实例将 Uint8Array 转换为字符串。
•
状态处理：正确处理流关闭、网络异常及业务层面的错误码。
常见坑：
•
忘记处理 TextDecoder 跨 chunk 截断中文字符的问题（需保持 decoder 实例）。
•
没有处理用户主动关闭页面时的流释放。
```javascript
async function getStream(url) {
  const response = await fetch(url);
  const reader = response.body.getReader();
  const decoder = new TextDecoder();
  while (true) {
    const { done, value } = await reader.read();
    if (done) break;
    const text = decoder.decode(value, { stream: true });
    console.log("收到片段:", text);
  }
}
```

</details>
<details><summary>补充与完整答案</summary>

原代码是字节读取的入门骨架，还缺status/content-type检查、空body、EOF解码、事件缓冲、大小限制、取消与finally释放。保持同一个decoder之外，还必须stream:true，EOF再decode收尾；最后一个字节序列不完整时，本项目严格抛错。

随后把文本交给行状态机；空行才分派，多个data行用换行连接，CRLF跨块不重复算行，注释和未知字段忽略。本章不在读取函数里console.log材料。SSE事件的data也不必是JSON，只有业务约定JSON时才解析。

**追问**：网络一次read对应一个token吗？不对应，传输合并、分割与模型生成粒度无固定关系。一个字符、一个JSON、一个事件都可能跨块。

</details>

## 2. 网络提炼：SSE一定要用EventSource吗？

<details><summary>完整答案</summary>

SSE是text/event-stream的文本格式，EventSource是浏览器提供的消费API。原生EventSource构造参数没有POST body或任意Authorization头选项；本项目后续用fetch POST携带问题和现有JWT，再读取Response.body。自动重连、Last-Event-ID等能力不会随fetch自动出现，必须按业务另做。

通知适合持续订阅和补读；一次模型生成不能断了就盲目重发问题，否则可能重复生成与计费。网络文章把SSE的自动重连与所有消费方式混说，需要明确这是EventSource客户端能力。它还说WebSocket必须独立端口，这也不是要求：代理可在同一公开端口处理不同路径和升级请求。

依据：[EventSource接口与SSE格式](https://html.spec.whatwg.org/multipage/server-sent-events.html)。本章只测试解析，不运行浏览器EventSource或WebSocket。

**追问**：如何保证fetch断流后不重复生成？本周不自动重试，显示部分结果与中断；未来若要恢复需服务端生成ID、事件持久化和恢复协议。

</details>

## 3. 项目题：怎样防止中文乱码和半帧误发？

<details><summary>完整答案</summary>

固定decoder跨read保留字节状态，固定parser跨文本保留行和帧状态。CR与LF状态独立处理；EOF只flush字符解码，不能凭空追加事件分隔符。非法UTF-8使用固定错误码，完整data由业务层进一步校验。

所有双块切分位置测试的原样记录：

```json
{"case":"all-byte-splits","splitPositions":76,"frames":[{"event":"delta","data":"中文🙂\n第二行"},{"event":"message","data":"tail"}]}
```

EOF半帧记录：

```json
{"case":"partial-eof","dispatched":["kept"],"discarded":"lost"}
```

**追问**：为什么不在catch里忽略JSON.parse错误继续？那可能掩盖已经丢失或损坏的事件，使后面的done看起来正常。应区分可忽略的协议注释与业务契约错误。

</details>

## 4. 网络与项目题：流式是否保证低内存？

<details><summary>完整答案</summary>

不保证。文章说管道化全程无内存堆积、流式内存恒定极低，缺少条件：消费者必须及时消费，缓冲必须有限，不能一直把全文或DOM节点保留。这里帧预算64Ki代码单元、总量2MiB字节，但push一次会暂存同块内所有事件，不宣称无任何临时积压。

reader.cancel通知底层停止，releaseLock只解除独占读取。异步生成器finally保证break也清理；真正HTTP断连到上游取消还要D46连接signal。原文把所有Fetch流式等同HTTP chunked编码也不准确，应用读取API不应依赖HTTP/1.1专有的传输编码，HTTP/2有不同帧机制。

```json
{"case":"reader-cleanup","cancelled":true,"locked":false}
```

**追问**：单行长度限制能阻止巨大事件吗？不能，多条短data一直没有空行也会增长，需要帧总量和全流预算。

</details>

## 5. 项目题：两个反证分别证明了什么？

<details><summary>完整答案</summary>

A关闭增量解码，中文逐字节输入失败；B删多行data的换行，精确内容断言失败。反证前后均构建shared，否则可能测试旧dist。两个文件恢复的字节和SHA-256相同，复测同用例通过，原样hash见讲义。

这些证据证明测试能抓住两类协议错误；双块切分枚举不是任意分块组合的穷举，更不证明真实代理、网络延迟、模型结束语义正确。

**追问**：只检查最终拼接字符串够吗？不够，可能把多个事件错误合并却碰巧字符串一样；还要检查事件数量、名称、边界和终止状态。

</details>


## 新版项目追问

删掉最后一个空行后关闭连接，应当能否交付最后一个完整事件？

解码器保存未完成字节，SSE 解析器保存未完成的行。事件分隔与网络分包分别处理。

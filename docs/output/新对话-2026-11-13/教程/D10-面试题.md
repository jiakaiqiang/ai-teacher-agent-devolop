## 一、网络最新题

### 题 1：乐观锁和悲观锁有什么区别？怎么选？

来源：掘金《面试官让我解释乐观锁和悲观锁，我用这个方法轻松拿下 Offer！》，2025-03-11（https://juejin.cn/post/7480089438899486770）。原文从 Java 并发讲起，数据库部分讲了 `for update` 和版本号两种实现，最后列了三个追问。

<details>
<summary>完整答案</summary>

**核心区别是什么时候处理冲突**：

- **悲观锁**：假设一定会有人来抢，读的时候就锁住，别人想改或想锁同一行只能等。数据库里是 `SELECT ... FOR UPDATE`。
- **乐观锁**：假设一般没人来抢，读的时候不加锁，写的时候检查数据有没有被改过，改过就放弃。数据库里是版本号加条件更新。

本项目实测：悲观锁下，B 想锁 A 已经锁住的工单，等了 1015ms，A 提交后才拿到，读到的是 A 改完的值；乐观锁下，A、B 都按 `version = 0` 更新，B 等 A 提交后重新检查条件，影响行数是 0，B 的修改被拒绝。

**怎么选**，看三点：

1. **冲突多不多**。冲突少，乐观锁几乎没有开销；冲突多，乐观锁会让大量请求失败重来，不如排队。原文的“读多写少用乐观锁”说的就是这个。
2. **失败重来的代价**。重来便宜（再执行一次事务）可以用乐观锁；代价大（例如要重新调外部接口）用悲观锁排队更合适。
3. **是否跨请求**。用户打开页面、想一会儿、再提交，这段时间不可能一直持有数据库锁，只能用乐观锁：版本号在前端存多久都行。

本项目的工单流转用乐观锁：两个人改同一张工单很少发生，而且一旦发生，必须让后来的人刷新看一眼，不能排队等前一个人改完再自动执行。

**原文的三个追问**：

- **CAS 有哪些缺点？** 原文答 ABA 问题和自旋消耗 CPU。放到数据库里，ABA 就是“值变了又变回来”：如果用状态当条件（`WHERE status = 'resolved'`），工单从已解决被退回、再解决，状态条件照样满足，中间的变化被漏掉。本项目有一个接口测试专门测这个场景。版本号只增不减，没有 ABA 问题。
- **如何优化悲观锁？** 锁的范围要小（`WHERE` 走索引，只锁需要的行）；事务要短，锁住之后不要做慢操作；多行加锁按固定顺序，避免死锁（D12）；不想无限等时用 `NOWAIT` 或 `lock_timeout`。
- **分布式环境下怎么实现乐观锁？** 原文答 Redis 分布式锁、Zookeeper 临时节点。这里要注意：这两种其实是**悲观锁**（先拿到锁才能操作）。如果数据都在同一个数据库里，多台服务器同时更新，数据库的版本号条件更新照样有效，不需要额外的组件。分布式锁要解决的是“要保护的东西不在同一个数据库里”的情况。面试时把这一点指出来，比照着背答案更加分。

</details>

### 题 2：版本号乐观锁怎么实现？更新失败了怎么处理？

来源：掘金《SQL 版本锁（乐观锁 / 版本号锁）以及C#中版本号用法》，2026-04-06（https://juejin.cn/post/7624746314376757288）。原文给了 SQL 写法、EF Core 的 `[ConcurrencyCheck]` 配置，以及捕获并发异常后最多重试 3 次的模板。

<details>
<summary>完整答案</summary>

**实现三步**：

1. 表上加 `version INT NOT NULL DEFAULT 0`。
2. 查询时带出 `version`，交给前端。
3. 更新时把版本号放进条件，同时加一：`UPDATE ... SET ..., version = version + 1 WHERE id = ? AND version = ?`。影响行数 1 是成功，0 是冲突。

检查和修改必须在**同一条** UPDATE 里。先 `SELECT` 比较版本、再 `UPDATE`，两条语句之间别人可能插进来。实测同一条 UPDATE 在读已提交下也是原子的：两个事务同时按 `version = 0` 更新，后到的等前一个提交后重新检查条件，影响行数是 0。

**本项目的 Prisma 写法**：

```ts
const { count } = await tx.ticket.updateMany({
  where: { id: ticket.id, version: dto.version },
  data: { ...plan.update, version: { increment: 1 } },
});
if (count === 0) throw versionConflict(); // 409 VERSION_CONFLICT
```

用 `updateMany` 而不用 `update`：`update` 在条件不满足时抛 P2025“记录不存在”，实测会被映射成 404，用户以为工单被删了。

**失败了怎么处理，要分两种情况**：

- **修改基于某人看到的内容**（关闭工单、编辑表单）：不能自动重试，返回 409，让用户刷新后重新决定。自动用新版本号重发，等于没加乐观锁。
- **修改由服务端重新计算即可**（扣库存、计数）：可以在服务端重试，每次重新读、重新判断。原文的重试模板属于这一种，它每次重试都重新读库存、重新判断够不够扣。

**版本号为什么比其他字段好**：状态字段有 ABA 问题（见题 1）；`updatedAt` 时间戳有精度问题，JavaScript 的 `Date` 只到毫秒，PostgreSQL 到微秒，前端带回来的值可能和数据库里的对不上。整数版本号最简单。

**两个容易漏的细节**：

1. 失败的请求不能让版本号变。本项目的非法流转用例断言了“版本号仍是 0”。
2. 接口的请求体增加必填的 `version` 以后，所有调用方都要改。本项目的测试里，每一个流转请求都跟着改了。

</details>

### 题 3：`SELECT ... FOR UPDATE` 的实现原理是什么？

来源：掘金《谈谈Select For Update的实现原理？》，2025-03-18（https://juejin.cn/post/7482690481043275839）。原文以 MySQL InnoDB 为例，讲了排他锁、索引与锁范围、间隙锁和执行流程。

<details>
<summary>完整答案</summary>

**作用**：在事务里查出几行并给它们加排他的行锁。其他事务想修改这些行、或者也想 `FOR UPDATE` 锁它们，都要等到当前事务提交或回滚。普通的 `SELECT` 不受影响，照样能读（MVCC 读的是快照，不需要锁）。

**必须在事务里用**。不在事务里，语句一结束锁就释放了，没有意义。Prisma 里要放在 `$transaction` 的回调中，用 `tx.$queryRaw` 执行。

**本项目实测（PostgreSQL）**：

| 写法 | 结果 |
|---|---|
| A 锁住工单，B 也 `FOR UPDATE` | B 等了 1015ms，A 提交后拿到锁，读到 A 改完的值 |
| B 用 `FOR UPDATE NOWAIT` | 1ms 就报 `55P03 could not obtain lock on row in relation "tickets"` |
| B 先 `SET LOCAL lock_timeout = '500ms'` | 等了 501ms 报 `55P03 canceling statement due to lock timeout` |
| B 用 `FOR UPDATE SKIP LOCKED` 取第一张待处理工单 | 跳过 A 锁住的 LOCK-1，取到 LOCK-3 |

注意 B 读到的是**最新**的值，不是快照里的旧值：读已提交下，等到锁以后 PostgreSQL 会重新取这一行的最新版本。

**PostgreSQL 和 MySQL 的差异**（MySQL 部分来自原文，本教程没有在 MySQL 上实测）：

| | PostgreSQL | MySQL InnoDB |
|---|---|---|
| 锁记在哪 | 行锁记在行本身的头部，锁一百万行也不占额外内存，不会升级成表锁 | 锁加在索引记录上 |
| 没走索引时 | 只锁真正返回的行 | 原文说退化为表锁；更准确的说法是扫描到的每一行都被锁住，效果接近锁表 |
| 范围查询 | 不锁“间隙”，别人仍能插入新行 | 可重复读下加间隙锁，阻止在范围内插入 |
| 防止幻读靠 | 可串行化（D9 的 SSI） | 间隙锁 |

**面试时的回答顺序**：先说作用和必须在事务里；再说等待、`NOWAIT`、`SKIP LOCKED` 三种行为和各自的用途；最后说你用的数据库的特点，以及要注意的坑：锁的范围要走索引、事务要短、多行加锁按固定顺序（否则死锁，D12）。

</details>

### 题 4：HTTP 层怎么表达乐观锁？`If-Match` 和 412 是什么？

来源：掘金《3.1. If-Match》，2026-06-24（https://juejin.cn/post/7654639896385536063）。原文逐条解读 RFC 7232 的 `If-Match`，用“A、B 都看到 v1，各自要改成 v2、v3”的例子说明它怎样防止覆盖。

<details>
<summary>完整答案</summary>

**HTTP 标准里的乐观锁**：

1. 服务端在响应头返回 `ETag: "v2"`，代表资源当前的版本。
2. 客户端修改时带上 `If-Match: "v2"`，意思是“只有资源还是 v2 时才执行”。
3. 服务端发现当前版本已经不是 v2，返回 **412 Precondition Failed**，不执行修改。原文的例子里，412 的响应还带上了最新的 `ETag`，方便客户端恢复。

和本项目的“版本号放在请求体、冲突返回 409”是同一个思路，区别在于放在哪一层：

| | 请求头 `If-Match` + 412 | 请求体 `version` + 409（本项目） |
|---|---|---|
| 标准化 | HTTP 标准，网关、HTTP 客户端库都认识 | 自己约定，要写进接口文档 |
| 前端使用 | 要从响应头读 ETag，跨域时还要配置 `Access-Control-Expose-Headers` | 版本号就在 JSON 里，和其他字段一起存 |
| 错误格式 | 412 的响应体没有统一格式 | 和其他业务错误一样是 `{ code, message }` |
| 强制客户端带上 | 可以用 428 Precondition Required 拒绝没带 `If-Match` 的请求 | DTO 校验必填，缺少返回 400 |

本项目选请求体：前端要显示和保存版本号，放在 JSON 里最直接；冲突错误和其他业务错误走同一个过滤器、同一种格式。对外开放、给第三方调用的接口更适合用 `If-Match`，因为调用方用的是标准的 HTTP 语义。

**409 还是 412**：412 专指“请求头里的前提条件不满足”，用在 `If-Match` 这类条件请求上；版本号在请求体里时，冲突是业务层面的，用 409 Conflict 更合适。

</details>

## 二、题库原题

### 题 5：协同编辑中的 OT 算法或 CRDT 算法了解吗？

出处：《2026腾讯文档 前端开发2026》第 9 页。

**原题**：6. 协同编辑中的 OT 算法或 CRDT 算法了解吗？（难度：★★★，考点：协同办公、复杂场景处理）

<details>
<summary>原文答案</summary>

> 答案要点：
> 协同编辑的核心是解决多个用户同时修改同一份文档时的冲突问题。
>
> - OT (Operational Transformation)：通过操作转换，将本地操作根据远程操作进行偏移修正。
> - CRDT (Conflict-free Replicated Data Types)：通过数据结构设计，保证不同副本最终一致，无需中心服务器。
> - OT 流程：客户端发送 Op -> 服务器排序并广播 -> 客户端收到后 Transform。
> - 适用场景：OT 适合中心化系统（如腾讯文档），CRDT 适合去中心化或 P2P 场景。
>
> 常见坑：
>
> - 简单地认为“最后一次修改覆盖”就能解决冲突。
> - 不清楚 OT 算法中服务端版本号的作用。
>
> 追问：
>
> - 如果网络延迟很高，OT 算法如何保证用户体验？

《钉钉高级前端工程师 · 面试全流程》有一道同类题（多人实时协同编辑，答案在第 11-12 页），答案更详细，其中 OT 的基本流程写道：客户端把操作“和文档的当前版本号发送给服务器”，“如果 OpA 的版本号和服务器的当前版本号匹配，服务器就将 OpA 应用于自己的文档”；如果服务器已经先处理了别人的操作，“它必须先对 OpA 进行‘变换’，以适应 OpB 带来的影响”。

</details>

<details>
<summary>本教程补充：它和今天的乐观锁是什么关系</summary>

原文“常见坑”里的两条，正好对应今天的内容：

- **“最后一次修改覆盖”**就是今天说的丢失更新。不加版本号时，alice 按过期页面关闭工单成功了，就是“最后一次修改覆盖”。
- **“服务端版本号的作用”**：OT 里客户端发送操作时带上自己所在的版本号，服务端据此判断这个操作是不是基于旧版本做的，和今天工单流转请求带 `version` 是同一个作用。

两者的区别在于**发现冲突以后怎么办**：

| | 乐观锁（本项目） | OT |
|---|---|---|
| 发现基于旧版本的修改 | 拒绝，返回 409，让人刷新后重新决定 | 把操作变换到新版本上，自动合并 |
| 适合 | 修改是一个整体的决定（关闭工单、审批），没法自动合并 | 修改可以拆成很多小操作（插入一个字、删除一个字），大多能自动合并 |

面试被问到协同编辑时，可以从这里切入：先说“基于旧版本的修改”这个共同的问题，再说乐观锁选择拒绝、OT 选择变换、CRDT 用数据结构让合并不会冲突。用工单的例子讲清楚为什么工单流转不能自动合并：alice 关闭工单这个决定本身依赖于她看到的内容，内容变了，决定就要重做。

追问“网络延迟很高时 OT 怎么保证体验”：本地操作立即应用到自己的页面上，不等服务器确认，服务器的确认和别人的操作到达后再做变换。这和前端常说的乐观更新（先改界面，请求失败再回滚）是同一个思路，只是 OT 多了一步变换。

</details>

## 三、补充题

### 题 6：（补充题）有了可串行化，还需要版本号吗？反过来呢？

本题没有对应的网络原文，来自讲义 1.3 和三个反证实验的实测。

<details>
<summary>完整答案</summary>

**两者都需要，各管一件事**：

- **可串行化**发现**时间上重叠**的事务之间的冲突，包括跨多行规则的写偏斜。
- **版本号**发现用户**基于过期内容**做出的修改。读发生在早已结束的另一个请求里，数据库不知道用户看到的是哪个版本，只有客户端带回版本号才能发现。

**实测去掉任何一个都有问题**：

- 只去掉版本号（保留可串行化）：过期页面的“关闭”请求返回 200，alice 在没看到第二次修复的情况下关闭了工单。可串行化没报错，因为 10:08 的事务读到的是最新数据，它本身完全正确。
- 只去掉可串行化（保留版本号，退回读已提交）：同一张工单的并发接单仍然只有一个成功，因为条件更新在读已提交下也是原子的；但接单上限被突破，3 个接单请求有 2 个成功。三个请求改的是三张不同的工单，每张的版本号都没冲突，版本号管不到跨多行的规则。

**顺带的变化**：加了版本号以后，两个人同时接同一张工单，失败的那个收到的是 `VERSION_CONFLICT` 而不是 D9 的 `INVALID_TRANSITION`。因为它重试时读到的版本已经变了，而版本检查排在流转合法性检查之前。这个顺序是故意的：页面已经过期，用户的判断依据不可信，先让他刷新。

</details>

## 一、题库原题与原文答案

关联题：本地《2026已发交个朋友全栈AI工程师.pdf》第5—6页，第4题“什么是 RAG”，原文追问是“向量数据库你了解哪些”。题库没有pymilvus原题，向量数据库相关题已在D71、D72、D74、D80用过；D74讲过这道题的投影同步，本章换成“向量库里该存什么、过滤放在哪一层”。

<details><summary>原文（只调整排版）</summary>

4. 什么是 RAG（检索增强生成）？请描述一个前端参与的 RAG 完整流程。​
难度：★★★
考点：RAG 架构、向量检索、前端交互​
答案要点：
RAG 通过检索外部知识库来弥补大模型训练数据的时效性和幻觉问题。​
•
流程：用户提问 -> 文本向量化（Embedding）-> 向量数据库检索相关片段 -> 拼接 Prompt -> 
LLM 生成回答。​
•
前端职责：处理文档上传、切片预览、展示检索来源（Citations/References）。​
•
交互设计：在回答中高亮显示引用的原始文档片段。
•
性能：前端可以做初步的语义搜索缓存。
常见坑：

•
检索回来的片段过多，导致 Prompt 超过 LLM 的 Context Window。​
•
忽略了检索片段与生成内容的相关性校验。
追问：
•
向量数据库你了解哪些？前端如何调用 Embedding 接口？​

</details>

<details><summary>补充讲解与纠偏</summary>

原文的RAG流程正确，补三点与本章相关的工程细节：

1. 向量库里存什么。本项目只存坐标、版本、班组和向量，不存正文；引用原文由NestJS按坐标从权威库取。这样撤权、关单或改版后，旧向量即使还在，也不会把过期或无权的内容展示出去。
2. 检索前过滤和检索后复核都要有。检索前按班组过滤减少无关候选；检索后在权威库复核权限、状态、版本，处理派生索引的延迟。
3. 原文的“常见坑”提到片段过多超出上下文窗口：本章检索上限24个候选，NestJS最终最多取3条引用（D76），由调用方控制进入提示词的数量。

</details>

## 二、项目与网络关联题

### 1. pymilvus客户端设置了timeout，为什么还要自己加`asyncio.timeout`？

<details><summary>完整答案与追问</summary>

因为实测它没有约束连接不上的情况。
在pymilvus 2.5.18上，指向不可达端口的`AsyncMilvusClient(timeout=2)`，`load_collection`超过8秒外层超时仍未返回，单独运行超过6分钟未结束。外层截止时间保证接口在10秒内给出`MILVUS_TIMEOUT`（504）。追问：取消后服务端可能已执行写入，所以写入用确定性主键upsert，重试幂等。

</details>

### 2. Milvus的过滤表达式怎么防注入？

<details><summary>完整答案与追问</summary>

与SQL参数化同理：不拼接原始输入。
先把班组解析成`uuid.UUID`，非法值在HTTP契约层就422；再用`json.dumps`生成带引号的字面量。本章测试用`" or groupId != "`这样的输入断言被拒。同时`group_id`必填可空，漏传不会变成查全部。已安装的pymilvus 2.5.18在search中接受模板化过滤参数`filter_params`，本章为与Node端保持同一写法没有使用，也未实测，属于可选改进。

</details>

### 3. 把向量读写从NestJS迁到Python，怎么证明检索结果没变？

<details><summary>完整答案与追问</summary>

对照同一份数据、同一组查询的输出。
本章在Node写入的主集合（9个切片、4个班组）上只读执行12次检索：4个查询不过滤，2个查询各按4个班组过滤；Python与Node的候选排序12/12一致，分数最大差1.79e-08（浮点表示差异）。这证明的是“同一集合上读路径一致”；迁移后写入路径是否一致、评测指标是否不变，留到D102接入和D104评测。

</details>

### 4. 网络题：Milvus和pgvector怎么选？

<details><summary>完整答案与追问</summary>

来源：掘金《我相信很多人都答不好 Milvus 和 pgvector的区别》，2026-04-10，https://juejin.cn/post/7626581199797026851 。
原文要点：Milvus是专门的向量数据库，面向大规模、高并发和可扩展；pgvector是PostgreSQL扩展，优势是复用SQL、事务、普通索引，适合把向量检索融入现有业务表。这个框架正确。需要纠正的是原文把“结合业务条件过滤”说成pgvector独有的顺手之处：Milvus同样支持标量字段过滤，本章就用`groupId`过滤，并在真实往返里验证了只返回本班组。两者真正的差别在一致性：pgvector可以和工单在同一个事务里更新，Milvus是派生索引，写入与权威库之间有时间差，必须读侧复核（本项目W11起的做法）。选型看数据量、团队运维能力和是否需要与业务数据同事务，而不是“哪个更专业”。

</details>

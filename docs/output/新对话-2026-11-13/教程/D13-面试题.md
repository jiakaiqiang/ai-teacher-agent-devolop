## 一、网络最新题

### 题 1：前端的乐观更新怎么做？失败怎么回滚？连点时旧结果覆盖新状态怎么办？

来源：掘金《前端也需要事务：Vue Router 乐观更新、回滚与“过期事务”》，2026-10-29（https://juejin.cn/post/7701613493971615795）。原文把“先改界面、再等异步结果”抽象成前端的事务：应用（apply）、执行、成功确认（commit）或失败回滚（rollback），并讨论了连点导致的“过期事务”。

<details>
<summary>完整答案</summary>

**乐观更新是什么**：用户操作后立即改界面，不等后端确认；后端失败了再改回去。点赞、收藏、勾选待办，用户感觉不到网络延迟。

**四步**（原文的结构）：

1. **应用并保存快照**：先记下改之前的状态，再改界面。顺序不能反，先改再取快照，快照就是改后的状态，回滚等于什么也没做。原文特别强调让 `apply` 函数自己返回快照，“改了什么”和“怎么退回去”放在一起，不会不同步。
2. **执行异步操作**：发请求。
3. **成功**：确认，做收尾（例如让缓存失效）。
4. **失败**：用快照回滚，并告诉用户。

**失败有两种形态，都要处理**：抛出异常（网络错误），和正常返回但结果是失败（原文的例子是 Vue Router 的 `router.push` 被守卫拒绝时不抛异常，而是返回一个 `NavigationFailure`）。只写 `catch` 会漏掉后一种。本项目的 `fetch` 也是这样：HTTP 409 不会让 `fetch` 抛异常，要检查 `response.ok`，D6 的 `parseResponse` 就是在做这件事。

**连点导致的“过期事务”**：用户连点两次，两个操作并发，第一个的结果后到，覆盖了第二个的状态。解法是给每次操作一个递增的序号（版本号），结果回来时如果序号不是最新的，就丢掉。这和 D6 取消旧请求、D10 后端的版本号是同一个思路：**谁的结果基于过期的状态，谁就不能生效**。

**本项目的详情页为什么不用乐观更新**：

- 状态流转是一个需要后端确认的决定。乐观地把按钮切成“已接单”，后端却返回“已被别人接走”或“已达上限”，界面要回滚，用户会困惑“刚才明明接上了”。
- 冲突时要让用户重新判断（D10），而不是悄悄回滚。
- 流转请求很快（实测几十毫秒），等待的代价小。

所以本项目用“提交中禁用按钮、等后端返回再更新”。适合乐观更新的是冲突少、失败了回滚也无所谓的操作。W8 的 AI 会话界面里，用户发送的消息先显示在列表里，就是乐观更新。

</details>

### 题 2：防重复提交，前端禁用按钮够不够？防抖和防重有什么区别？

来源：掘金《接口防抖实战：防重复提交的 5 种高级方案》，2025-12-29（https://juejin.cn/post/7588745319400734720）。原文从后端角度讲了 Redis 加 Lua、注解切面等方案，开头先区分了“防抖”和“防重”。

<details>
<summary>完整答案</summary>

**两个概念**（原文的区分，准确）：

- **防抖**：限制触发频率，比如 1 秒内点 5 次只算 1 次。
- **防重**（幂等）：同一个请求执行多次，结果和一次一样。

前者减少重复请求，后者保证重复请求不出错。前者是体验，后者是正确性。

**前端禁用按钮不够**。原文列的场景：爬虫和接口工具直接调用、网络延迟后的重发。加上本项目遇到的：多个标签页、两个人同时操作。这些都绕过了页面上的按钮。

**本项目的三层**：

| 层 | 做法 | 挡住了什么 | 实测 |
|---|---|---|---|
| 前端 | 提交中禁用按钮，函数入口检查 `submitting` | 同一个页面上的连点 | 单元测试：提交中再点，fetch 只被调用 2 次（一次加载、一次提交）；去掉检查后变成 3 次 |
| 后端 | 版本号（D10）、可串行化（D9）、按去重键 `ON CONFLICT`（D11） | 多标签页、多人、重发 | 同一工单并发接单连续 5 轮，每轮只有一个成功 |
| 数据库 | 唯一约束、CHECK 约束 | 代码写错时的最后一道防线 | D11 先查再插时，唯一约束挡住了重复的告警 |

**原文方案的一个局限**：原文的 Redis 方案是“同一个请求标识在 N 秒内只能执行一次”，N 秒后锁自动释放。如果第一次请求处理超过 N 秒，或者 N 秒后客户端重试，同一个操作还会再执行一次。它是“限时防抖”，不是真正的幂等。要真正幂等，需要把“这个操作已经做过”持久地记下来（D11 面试题题 2 的幂等表），或者让操作本身带上能检测重复的条件（版本号、状态条件、唯一约束）。

</details>

## 二、题库原题

### 题 3：手写题：带“立即执行”选项的防抖函数

出处：《2026京东前端面试-AI Coding方向》第 2-3 页（一面第 6 题）。

**原题**：6. 手写题：带“立即执行”选项的防抖函数

<details>
<summary>原文答案</summary>

```js
function debounce(fn, wait, immediate = false) {
  let timer = null;
  return function(...args) {
    if (timer) clearTimeout(timer);
    if (immediate && !timer) {
      fn.apply(this, args);
    }
    timer = setTimeout(() => {
      if (!immediate) fn.apply(this, args);
      timer = null; // 重置
    }, wait);
  };
}
```

</details>

<details>
<summary>本教程补充：逐行讲解、两个改进、什么时候不该用</summary>

**原文答案是对的**，逐行看：

- `clearTimeout(timer)` 取消上一次的定时器，但**不会**把 `timer` 变量清空，所以紧接着的 `!timer` 判断仍然能区分“这是一串点击里的第一次”还是“后续的点击”。这一点很多人会看错。
- `immediate` 为真时，一串点击的**第一次**立即执行；之后每次点击都把定时器往后推，直到停下 `wait` 毫秒，`timer` 被重置为 `null`，下一串点击的第一次才会再执行。
- `immediate` 为假时，只在停下 `wait` 毫秒后执行**最后一次**的参数。
- `fn.apply(this, args)` 保留调用时的 `this` 和参数。返回的必须是普通函数而不是箭头函数，否则 `this` 拿不到。

**面试时可以加的两个改进**：

1. **加 `cancel` 方法**：组件卸载时取消还没执行的调用，避免卸载后还去改状态。
2. **`immediate` 模式下保留返回值**：第一次调用是同步执行的，可以把 `fn` 的返回值返回出去。

```js
function debounce(fn, wait, immediate = false) {
  let timer = null;
  function debounced(...args) {
    const callNow = immediate && !timer;
    clearTimeout(timer);
    timer = setTimeout(() => {
      timer = null;
      if (!immediate) fn.apply(this, args);
    }, wait);
    if (callNow) return fn.apply(this, args);
  }
  debounced.cancel = () => {
    clearTimeout(timer);
    timer = null;
  };
  return debounced;
}
```

改进版用 Node 实测过：连续调用 3 次非立即模式，只执行了最后一次（参数 3）；立即模式下连续调用 3 次，只有第一次执行并返回了值，`this` 正确；停顿后再调用，又立即执行一次；调用后马上 `cancel()`，没有执行。

**什么时候不该用防抖**：本项目的“接单”“关闭”按钮就不该用。防抖按**时间**判断，不知道请求什么时候结束：`wait` 设 300 毫秒，请求要 2 秒，第 500 毫秒的点击照样会发出第二个请求。提交按钮需要的是按**请求的生命周期**加锁，D13 的 `submitting` 就是这样做的。

**该用防抖的场景**：搜索框输入联想（等用户停下来再请求，原文所在面经的其他几道题也问到“AI 搜索建议场景下的作用”）、窗口尺寸变化后重新计算布局、自动保存草稿。共同点是只关心“最后一次”的结果，中间的触发可以丢掉。

**防抖和节流的区别**（常见追问）：防抖是“停下来以后才执行”，连续触发时可能一直不执行；节流是“每隔一段时间最多执行一次”，连续触发时按固定频率执行。滚动加载更多用节流（或者像 D6 一样用 `IntersectionObserver`，根本不需要监听滚动）。

</details>

## 三、补充题

### 题 4：（补充题）两个人同时编辑同一条数据，前端应该怎么提示？

本题没有对应的网络原文，来自讲义 1.2 和步骤 7 的设计。

<details>
<summary>完整答案</summary>

**前提**：后端要能发现冲突（D10 的版本号），并返回能区分原因的错误码。前端按错误码分流，不按错误信息的文字判断。

**按“页面是否过期”分两类处理**：

| 情况 | 例子 | 前端怎么做 |
|---|---|---|
| 页面过期 | `VERSION_CONFLICT`、`INVALID_TRANSITION` | 重新加载最新内容，提示“已被其他人修改，请确认后再操作”；保留用户填的说明，方便他确认后再用 |
| 页面没过期，只是现在做不了 | 接单上限、重试用尽、等锁超时 | 显示后端的说明，不刷新 |

**三条原则**：

1. **不自动重发**。用户的操作是基于旧页面做的决定，页面变了，决定要重做。本项目的单元测试断言：版本冲突后只有 GET、POST、GET 三次请求。
2. **不丢用户的输入**。表单类的编辑尤其重要：用户写了一大段，冲突后全没了，体验很差。更完整的做法是把“你的修改”和“最新内容”并排显示，让用户合并，这就走向了 D10 面试题里的协同编辑。
3. **减少冲突发生的机会**。打开详情页时就通过 SSE 订阅这张工单的变化（W5），别人一改就提示刷新，用户就不会在旧页面上做决定。推送减少冲突，版本号兜底，两者互补。

**怎么测**：把冲突处理放进组合式函数，用模拟的 fetch 构造“GET 成功、POST 返回 409、GET 返回新版本”的序列，断言请求次数、最终的数据和提示文字（本项目 5 个单元测试）。再用两个浏览器窗口手动验证一次真实的交互。

</details>

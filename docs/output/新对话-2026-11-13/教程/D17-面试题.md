## 一、网络最新题

### 题 1：什么是水平越权（IDOR）？怎么防？

来源：掘金《使用 Burp Suite 发现价值 1000 美元的 IDOR 漏洞：实战指南》，2026-06-11（https://juejin.cn/post/7649974149242388526）。原文从漏洞挖掘者的角度讲了 IDOR 的原理和测试方法，作者在一个电商平台上把订单 ID 加一，就看到了别人的订单和地址。文末给了开发者的防御建议。

<details>
<summary>完整答案</summary>

**是什么**：接口用客户端传来的 ID 直接定位数据，却没有检查“当前用户能不能访问这条数据”。改一下 URL 或参数里的 ID，就能看到、甚至改到别人的数据。它是“水平”的：攻击者和受害者的角色、权限点完全一样，所以角色和权限点的检查（D16）发现不了它。

**本项目的场景**：一组的 bob 和二组的 erin 都是运维人员。没有数据权限时，bob 把详情页 URL 里的工单编号改成二组的，就能看到、能接单。

**怎么防**（原文的建议加上本项目的做法）：

1. **在查询里带上归属条件**，原文的例子是 `WHERE id = :requested_id AND user_id = :current_user_id`。本项目是 `findFirst({ where: { ticketNo, ...groupScope(user) } })`。
2. **规则只写一处**：原文提到“在中间件或服务层运行对象级授权检查，确保每个访问路径都被覆盖”。本项目的 `groupScope()` 给出一份 Prisma 条件，原生 SQL 用 `groupCondition()` 翻译同一份规则。实测漏掉任何一处都会出问题：详情漏了，改 URL 就能看到（反证实验 A）；批量指派的原生 SQL 漏了，错误信息就泄露了工单的存在（反证实验 B）。
3. **所有能指向数据的参数都要覆盖**：URL 里的编号、批量接口的编号列表、游标、被指派的人。本项目的接口测试逐个试了别人的值。
4. **越权返回 404**，和不存在一样，不透露数据是否存在（讲义 1.3）。
5. **测试从攻击者的角度写**：用 A 的身份请求 B 的数据，断言 404 且数据没有变化。

**原文有一点要说清楚**：原文第一条建议是“使用不可预测的 ID（UUID）代替连续的 ID”，紧接着在“给漏洞猎人的建议”里又说“不要假设 GUID 是安全的”。两句话都对：UUID 让攻击者猜不到别人的 ID，但 ID 会出现在分享链接、日志、截图里，一旦拿到照样能用。**UUID 只是增加难度，授权检查才是防御**。本项目的工单编号是 `T日期-序号`，完全可预测，所以授权检查是唯一的防线，也是必需的防线。

</details>

### 题 2：多租户（或多班组）的数据隔离，应用层过滤和 PostgreSQL RLS 怎么选？

来源：掘金《多租户隔离：一条 RLS 策略怎么防数据串》，2026-06-08（https://juejin.cn/post/7648861444755341362）。原文是“企业级 AI Agent 实现拆解”系列的一篇，作者用 PostgreSQL 的行级安全（RLS）给 12 张表批量加了租户隔离策略，连 pgvector 的向量检索也一起保护了。

<details>
<summary>完整答案</summary>

**应用层过滤的风险**（原文的出发点）：每个查询手动加 `WHERE tenant_id = ?`，几十张表、几十个查询里只要漏一个，数据就串了。

**RLS 的做法**：

```sql
ALTER TABLE tickets ENABLE ROW LEVEL SECURITY;
CREATE POLICY group_isolation ON tickets
  USING (group_id::text = current_setting('app.group_id', true))
  WITH CHECK (group_id::text = current_setting('app.group_id', true));
```

每个请求在事务里先执行 `SELECT set_config('app.group_id', '当前用户的班组', true)`，之后这个事务里对 tickets 的所有查询都自动带上过滤条件。`USING` 过滤读、改、删的已有行，`WITH CHECK` 拦住写入不属于自己的行。原文还用一个单独的数据库角色（`BYPASSRLS`）给运营后台跨租户查看。

**两种做法的比较**：

| | 应用层（本项目的 `groupScope`） | RLS |
|---|---|---|
| 漏写一个查询 | 数据泄露，要靠测试发现 | 数据库兜底 |
| 每个请求的准备 | 无 | 必须在事务里先 `set_config`，Prisma 里意味着所有查询都要放进交互式事务 |
| 跨班组的人（dave） | 返回 `{}` 就行 | 要换数据库角色，或者在策略里加条件 |
| 排查问题 | 条件写在代码里，看得见 | 查询“莫名其妙”少了行，要想到 RLS |
| 原生 SQL | 要自己加条件（本项目的 `groupCondition`） | 自动生效 |

**容易踩的坑**：

- **表的所有者和超级用户默认不受 RLS 约束**。开发环境常用一个账号既建表又跑应用，这时 RLS 等于没开。要么应用用单独的、不是表所有者的数据库账号，要么执行 `ALTER TABLE ... FORCE ROW LEVEL SECURITY`。
- **`set_config` 的第三个参数要是 `true`**（只在当前事务内有效）。用会话级的设置，连接回到连接池后还带着上一个用户的班组，下一个请求会看到别人的数据。

**纠正原文的一个说法**：原文说 `current_setting('app.tenant_id', true)` 传入空字符串时“某些配置下可能绕过 RLS”。按上面这种写法，设置缺失时 `current_setting` 返回 NULL 或空串，`group_id = ''` 永远不成立，结果是**一行都查不到**，不是全部可见。真正导致“全部可见”的，是上一条说的“用表所有者或超级用户连接”。原文在领域层再校验一次租户 ID 不为空，作为第二道防线是对的，但理由应该是“尽早报错、给出清楚的错误”，而不是防止绕过。

**本项目为什么选应用层**：班组隔离只涉及工单和设备两张表；dave 这种跨班组的人用一个权限点就能表达；所有查询保持现在的写法，不需要全部改成交互式事务。代价是“忘了加”只能靠测试发现，所以今天的 6 个接口测试和反证实验就是这道防线。表多了、规则统一（例如 SaaS 的租户隔离）时，RLS 更合适。

**和后面课程的关系**：W11 的 Milvus 没有 RLS，向量检索的隔离只能在应用层加过滤条件（分区或标量过滤），今天的思路会原样用到。

</details>

## 二、补充题

### 题 3：（补充题）给已经有数据的表加一个必填列，迁移怎么写？

本题没有对应的网络原文，来自讲义 1.4 的实测。

<details>
<summary>完整答案</summary>

**直接加会失败**。`ALTER TABLE tickets ADD COLUMN group_id UUID NOT NULL` 在表里已有数据时报错，因为已有的行没有值。Prisma 生成迁移时就会警告（本项目实测）：“Added the required column `group_id` to the `tickets` table without a default value. There are 5 rows in this table, it is not possible to execute this step.”

**三步**：

1. 加可空的列：`ALTER TABLE tickets ADD COLUMN group_id UUID;`
2. 补数据：`UPDATE tickets SET group_id = ...;`（本项目是迁移里插入的默认班组）
3. 加约束：`ALTER TABLE tickets ALTER COLUMN group_id SET NOT NULL;`，再加外键。

Prisma 里用 `migrate dev --create-only` 生成后手工改，应用后再生成一次迁移，确认是空的（本项目实测为空）。

**为什么不给一个默认值**：`ADD COLUMN ... NOT NULL DEFAULT '某个 UUID'` 能一步完成，但默认值会一直留在表定义里，以后忘了指定班组的插入会悄悄归到默认班组，掩盖了代码错误。本项目希望“忘了指定班组”时直接报错。

**大表要更小心**（面试加分）：

- 一条 `UPDATE` 改几百万行，会长时间持有行锁、产生大量 WAL，主从延迟变大。要分批更新，每批几千行。
- `SET NOT NULL` 要扫描全表确认没有空值，期间持有表锁。PostgreSQL 12 起可以先加一个 `CHECK (group_id IS NOT NULL) NOT VALID` 约束（不扫描），再 `VALIDATE CONSTRAINT`（扫描但不阻塞读写），最后 `SET NOT NULL` 时数据库会利用这个已验证的约束跳过扫描。
- 新代码要先能写入这一列，再执行迁移；或者迁移后再部署依赖它的代码。顺序错了，迁移和部署之间的窗口里会写入空值或者报错。

</details>

### 题 4：（补充题）功能权限不够返回 403，数据权限不够返回 404，为什么要这样分？

本题没有对应的网络原文，来自讲义 1.3 和 D16 的设计。

<details>
<summary>完整答案</summary>

**功能权限**（D16）问的是“你能不能用这个功能”，和具体哪条数据无关。返回 403 告诉 bob“你没有批量指派的权限”，不泄露任何数据，还能帮他去申请权限。

**数据权限**（D17）问的是“你能不能访问这条数据”。如果返回 403，就等于确认了“这条数据存在”。攻击者遍历编号，403 和 404 的区别就能告诉他别的班组有多少工单、编号分布在哪里。所以返回 404，让它看起来就是不存在。本项目实测，bob 打开二组的工单和打开不存在的工单，响应的错误码和措辞格式完全相同。

**做到“完全一样”要注意的细节**：

- 错误信息不能有差别，比如“工单不存在”和“无权访问该工单”。
- 响应时间也可能有差别（D15 讲过时间侧信道）。本项目两种情况都是一次相同的查询，查不到就返回，没有差别。
- 批量接口里混进别人的数据，也按“不存在”报告。本项目的批量指派返回“工单不存在：<那张的编号>”，和真的不存在一样。

**例外**：被指派的人不在班组时返回 409 `ASSIGNEE_NOT_IN_GROUP`，因为“erin 是谁”对组长来说不是秘密，这里拒绝的原因是业务规则，不是数据可见性。

</details>

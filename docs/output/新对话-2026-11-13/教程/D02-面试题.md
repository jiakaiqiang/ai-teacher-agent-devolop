## 一、题库原题

### 题 1：谈谈全栈开发中，CI/CD 流程是如何设计的？

来源：《2026美团前端全栈开发》，题目在第 1 页（三面第 2 题），答案在第 12 页。难度 ★★★，考点：工程化、交付效率。

<details>
<summary>原文答案（第 12 页）</summary>

> CI/CD 旨在通过自动化手段提高软件交付的频率和质量。
>
> - 持续集成（CI）：代码提交后自动触发 Lint 检查、单元测试、集成测试，确保代码合规。
> - 持续交付/部署（CD）：构建 Docker 镜像，推送到私有仓库，通过 K8s 或 Jenkins 自动更新测试/生产环境。
> - 灰度发布：通过 Nginx 权重配置或蓝绿部署，先让小部分用户试用新版本，确认无误后再全量。
>
> 常见坑：缺乏回滚机制，导致发布失败后无法快速恢复业务。
>
> 追问：你们是如何处理前端静态资源的多版本共存问题的？

</details>

<details>
<summary>补充讲解：原答案漏了数据库</summary>

原答案讲的是代码怎样发布，全栈岗位的面试官更想听你怎样处理**数据库结构的变更**，因为代码可以秒级回滚，表结构和数据不行。

**数据库迁移在流水线里的位置**：

1. **CI 阶段**：起一个空的 PostgreSQL 容器，执行 `prisma migrate deploy` 把所有迁移跑一遍，再跑集成测试。这一步能发现迁移 SQL 写错、迁移和 schema 不一致的问题。还可以加一步 `prisma migrate diff`，检查 schema.prisma 有没有忘了生成迁移。
2. **CD 阶段**：先执行 `prisma migrate deploy`，再发布新版本的代码。`deploy` 只执行还没执行的迁移，不会生成新迁移，也不会提出重置数据库。
3. **迁移必须向后兼容**：灰度期间新旧两个版本的代码同时在跑，都在读写同一个库。所以迁移不能让旧代码出错。例如要把列 `name` 改名为 `title`，不能一次改名，要分三次发布：先加 `title` 并让新代码同时写两列；再把旧数据迁到 `title`；最后等旧代码全部下线后删掉 `name`。这叫“扩展-收缩”。

**“常见坑：缺乏回滚机制”放到数据库上怎么说**：代码回滚到上一个版本时，数据库不会跟着回滚。只要迁移是向后兼容的，旧代码在新表结构上依然能跑，代码就可以放心回滚。表结构本身出了问题，用一份新迁移前滚修复，而不是去改已经执行过的迁移。讲义 1.4 实测过：改动已执行的迁移，Prisma 会要求重置数据库。

</details>

## 二、网络最新题

### 题 2：生产环境的 MySQL、PostgreSQL 能用 Docker 部署吗？

来源：掘金《面试官问：MySQL 为什么不能用 Docker 部署吗？答错直接挂！》，2025-06-25（https://juejin.cn/post/7519723338892361737）。原文以 MySQL 为例，结论对 PostgreSQL 同样适用。

<details>
<summary>完整答案</summary>

**先分场景**：开发、测试、CI 用 Docker 跑数据库没有争议，版本统一、随建随删，本项目就是这样做的。争议只在生产环境。

**生产环境的顾虑，核心是数据库是有状态的**：

1. **数据必须活得比容器久**。容器随时可能被删除重建，数据、配置、日志（包括用于恢复的 WAL 或 binlog）都要挂载到卷或外部存储上。不挂载的话，删容器就丢数据。这一点在讲义 1.1 里实测过：数据存在命名卷里，`down` 再 `up` 数据还在，`down -v` 才会删除。
2. **扩容和高可用比无状态服务复杂得多**。Web 服务多起几个容器就能分担流量；数据库要处理主从复制、故障切换、数据一致性，这些不是 Docker 本身能解决的。
3. **性能和资源隔离要专门调**。数据库对磁盘 IO、内存很敏感，和其他容器挤在同一台机器上时会互相影响；容器的存储驱动、网络转发也会带来额外开销。

**现在常见的做法**：

- 用云厂商的托管数据库（例如 RDS），备份、主从、监控都由平台负责。
- 或者把数据库部署在独立的虚拟机或物理机上，只有应用服务容器化。
- 已经全面使用 Kubernetes 的团队，会用 StatefulSet 加上专门的数据库 Operator 来管理，这需要有经验的运维团队。

**回答时把结论说准**：“不能用 Docker 部署”说得太绝对了。准确的说法是“可以，但要解决持久化、高可用和性能隔离三个问题，多数团队选择托管服务，把精力留给业务”。

</details>

### 题 3：Prisma 7 为什么把客户端从 Rust 改成 TypeScript？升级到 Prisma 7 要注意什么？

来源：掘金《Prisma 7 重磅发布：告别 Rust，拥抱 TypeScript，性能提升 3 倍》，2025-11-20（https://juejin.cn/post/7574343024324149289）。

<details>
<summary>完整答案</summary>

**为什么离开 Rust**：Prisma 6 之前，查询由一个 Rust 写的引擎执行，JavaScript 和引擎之间要跨语言通信。原文提到两个原因：一是这层通信本身比纯 JavaScript 实现慢；二是 Rust 抬高了社区参与贡献的门槛，也让 Deno、边缘运行时等环境的支持变得麻烦。Prisma 7 改成 TypeScript 实现的查询编译器，原文称查询速度提升约 3 倍、CPU 和内存占用下降，这是 Prisma 官方的基准数据，本教程没有复测。本机 `prisma --version` 显示 `Query Compiler: enabled`。

**升级要注意的变化**（以下都是本项目用 7.10.1 实测的）：

1. **新的配置文件**。`prisma init` 生成 `prisma7.config.ts`，统一写 schema 位置、迁移目录、种子命令、连接串。旧名字 `prisma.config.ts` 仍能识别。
2. **不再自动读取 `.env`**，要在配置文件里 `import 'dotenv/config'`。用 `env('DATABASE_URL')` 时，变量缺失连 `prisma generate` 都会失败，CI 里要设置这个变量。
3. **客户端生成到项目源码里**。generator 改用 `prisma-client`，必须写 `output`，不再放在 `node_modules`。好处是生成的代码看得见、能被打包工具正常处理；要记得把它加进 `.gitignore`。
4. **必须使用驱动适配器**。PostgreSQL 用 `@prisma/adapter-pg` 和 `pg`。
5. **`migrate dev` 不再自动执行 `generate` 和 `seed`**。

**回答的思路**：先讲原因，再讲变化，最后讲你实际升级或使用时踩到的问题。例如“npm 上 `prisma` 的 `latest` 标签指向 8.0 的预发布版，安装时必须锁版本”，这种具体经历比复述发布公告更有说服力。

</details>

### 题 4：Prisma Migrate 的 `migrate dev`、`migrate deploy`、`migrate reset` 有什么区别？Prisma 怎么知道哪些迁移执行过？迁移怎么回滚？

来源：掘金《Prisma Migrate 操作指南》，2025-11-01（https://juejin.cn/post/7567310605972930606）。

<details>
<summary>完整答案</summary>

**三个命令**：

| 命令 | 用在哪里 | 做什么 |
|---|---|---|
| `migrate dev` | 本机开发 | 对比 schema 和迁移历史，有变化就生成新迁移并应用到开发库；检测到漂移或迁移被改动时要求重置 |
| `migrate deploy` | CI、测试、生产 | 只执行迁移目录里还没执行的迁移；不生成新迁移，不重置 |
| `migrate reset` | 本机开发 | 删除数据库里的所有数据和表，重新执行全部迁移 |

`migrate reset` 会清空数据。按 Prisma 随包附带的命令说明，从 7.9.0 起，它还会检测命令是不是由 AI 编程工具执行的，是的话先拦下来，要求用户明确同意（本教程没有触发过这个拦截）。这也说明它是一个需要谨慎对待的命令。

**怎么知道执行过哪些**：数据库里的 `_prisma_migrations` 表，每执行一份迁移记一行，包括名字、校验和、开始和结束时间。实测这张表里有 `migration_name`、`checksum`、`finished_at`、`rolled_back_at` 等列。

**两条推论**（讲义 1.4 都实测过）：

1. 已经执行过的迁移文件被改动，校验和对不上，`migrate dev` 报 `was modified after it was applied`。
2. 迁移的执行看的是“有没有执行过”，不严格看时间戳顺序：时间戳较早、但后来才加入的迁移，`migrate deploy` 照样会补执行。所以多人协作时，不同环境实际执行迁移的顺序可能不同。

**回滚**：Prisma 没有自动的 down 迁移。

- 常规做法是前滚修复：把 schema 改回去，生成一份新迁移。实测加了 `category` 列之后，删掉这个字段再运行 `migrate dev`，Prisma 生成了 `ALTER TABLE "tickets" DROP COLUMN "category"`，并在文件开头警告这一列的数据会丢失。
- 紧急情况：用 `migrate diff --from-schema 新schema --to-config-datasource --script` 生成反向 SQL，用 `prisma db execute` 执行。之后 schema 和迁移历史要补上对应的改动，否则下次 `migrate dev` 会报漂移。
- `migrate resolve --rolled-back` 不是回滚命令，它只用来标记执行失败的迁移，对成功的迁移实测报 P3012。

</details>

### 题 5：千万级的订单表要加一个字段，怎样做才不影响线上？

来源：掘金《面试官：千万级订单表新增字段怎么弄？》，2025-06-09（https://juejin.cn/post/7513560069276876834），以及《字节一面：怎么在千万级订单表加字段？》，2025-08-06。两篇都以 MySQL 为背景；2026-11-13 抓取时被掘金反爬拦截，**只拿到标题，没有读到正文**。下表耗时来自本教程在 PostgreSQL 16 临时容器中的 100 万行实验。常量默认值如何处理、何时重写已有行，以及修改表所需的锁，均可从已核对的官方文档查证。[PostgreSQL 16 添加列](https://www.postgresql.org/docs/16/ddl-alter.html#DDL-ALTER-ADDING-A-COLUMN) · [ALTER TABLE 锁与约束](https://www.postgresql.org/docs/16/sql-altertable.html)

<details>
<summary>完整答案</summary>

**先说风险在哪里**：`ALTER TABLE` 大多要拿表上最强的 ACCESS EXCLUSIVE 锁，持有期间这张表的所有读写都要等。如果这个操作要重写整张表，千万行可能要几分钟，线上就会大面积超时。所以关键是区分哪些操作只改元数据、哪些要重写或扫描整张表。

**PostgreSQL 16 实测（100 万行）**：

| 操作 | 耗时 | 原因 |
|---|---:|---|
| 加可空字段 `ADD COLUMN remark text` | 3.6 ms | 只改元数据 |
| 加带常量默认值的非空字段 `ADD COLUMN channel varchar(16) NOT NULL DEFAULT 'web'` | 1.2 ms | PostgreSQL 11 起，常量默认值记在元数据里，不改写已有的行 |
| 加带易变默认值的字段 `DEFAULT gen_random_uuid()` | 1517 ms | 每行的值都不同，必须重写整张表，期间锁表 |
| 普通建索引 | 227 ms | 期间阻塞写入 |
| `CREATE INDEX CONCURRENTLY` | 205 ms | 不阻塞读写，代价是总耗时更长、不能放在事务里 |
| 加 CHECK 约束 | 38 ms | 要扫描全表验证已有数据 |
| 先 `NOT VALID` 加约束，再 `VALIDATE` | 1 ms + 39 ms | 加约束只改元数据；验证阶段用的锁更弱，不阻塞正常读写 |

时间随数据量线性增长：100 万行重写表要 1.5 秒，1000 万行就是十几秒以上。

**回答的结构**：

1. **能只改元数据的就只改元数据**：新字段加成可空，或者用常量默认值。
2. **需要回填数据时分批做**：先加可空字段；再用后台任务按主键分批更新，每批几千行，批次之间暂停，避免长事务和主从延迟；最后确认全部回填完，再加 `NOT NULL` 约束（同样可以先 `NOT VALID` 再验证）。
3. **索引和约束用不阻塞的方式**：`CREATE INDEX CONCURRENTLY`，约束用 `NOT VALID` 加 `VALIDATE CONSTRAINT`。
4. **给 DDL 设锁等待上限**：执行前 `SET lock_timeout = '3s'`。如果表上有长事务，DDL 拿不到锁会排队，而排在它后面的所有普通查询也会跟着被挡住；设了超时，拿不到锁就失败重试，不会拖垮业务。
5. **改类型、改名这类变更走扩展-收缩**：新加一列，双写，回填，切换读取，最后删除旧列，分多次发布完成。
6. **MySQL 的对应方案**：MySQL 有 Online DDL（`ALGORITHM=INSTANT/INPLACE`），以及 gh-ost、pt-online-schema-change 这类工具，原理是建一张新结构的影子表、同步数据、最后切换表名。面试官问 MySQL 时可以提这些，但要说明本项目用的是 PostgreSQL。

**和 Prisma 的关系**：Prisma 生成的迁移是普通的 `ALTER TABLE`，`CREATE INDEX CONCURRENTLY` 这类写法需要像讲义里加 CHECK 约束那样，用 `--create-only` 生成后手工修改。注意 `CONCURRENTLY` 不能在事务里执行，写进迁移前要先确认 Prisma 执行这份迁移时是否包在事务里。这一点本教程还没有实测，W6 讲部署时再验证。

</details>

## 一、题库原题

### 题 1：企业级应用对权限控制要求很高，可能会精确到页面上的某个按钮。你在项目中是如何设计和实现前端权限方案的？

出处：《钉钉高级前端工程师 · 面试全流程》，题目在第 2 页（二面第 3 题），答案在第 19-20 页。

**原题**：3. 企业级应用对权限控制要求很高，可能会精确到页面上的某个按钮。你在项目中是如何设计和实现前端权限方案的？

<details>
<summary>原文答案</summary>

> 4. 前端权限方案设计与实现
> 企业级应用的权限控制必须是后端为主，前端为辅。前端的控制主要是为了提升用户体验（不展示无权操作的入口），而不是为了安全。
> 我们的方案分为三层：
>
> 1. 数据层：权限的获取与存储
>    - 用户登录成功后，后端返回用户的角色信息，以及一个扁平化的权限标识（Permission Key）列表，例如 `['page:purchase:view', 'btn:purchase:create', 'field:supplier:edit']`。
>    - 这个权限列表被存储在上面提到的 Zustand 全局状态中，供整个应用随时访问。
> 2. 路由层：页面级权限控制
>    - 我们创建了一个 `<ProtectedRoute />` 组件，用于包裹所有需要权限的路由。
>    - 它会接收一个 requiredPermission 的 prop，例如 `<ProtectedRoute requiredPermission="page:purchase:view">`。
>    - 组件内部会从 Zustand 中获取当前用户的权限列表，检查是否包含所需的权限。如果包含，则渲染子组件（页面）；如果不包含，则重定向到统一的 403 Forbidden 页面。
> 3. 视图层：按钮/字段级权限控制
>    - 为了在页面上方便地控制UI元素的显隐，我们提供了两种方式：
>    - 自定义 Hook `usePermission()`：
>      ```js
>      const { hasPermission } = usePermission();
>      // ... in component
>      {hasPermission('btn:purchase:create') && <Button>创建采购单</Button>}
>      ```
>    - 这种方式灵活，但可能让 JSX 看起来有点乱。
>    - 权限组件 `<Authorized />` (更推荐)：
>      ```js
>      <Authorized permission="btn:purchase:create">
>        <Button>创建采购单</Button>
>      </Authorized>
>      ```
>    - `<Authorized />` 组件内部的逻辑和 `<ProtectedRoute />` 类似，判断有权限时才渲染 children。这种方式让代码更具声明性，更整洁。
>
> 核心思想：通过后端下发的权限码列表，前端实现从宏观（页面）到微观（按钮）的统一权限判断逻辑，同时保证所有敏感操作在后端API层面有最终的权限校验。

</details>

<details>
<summary>本教程补充：用 Vue 和本项目的实现回答，并补上原文没讲的两点</summary>

**原文的三层，本项目都有对应**（原文是 React，换成 Vue 的说法）：

| 层 | 原文 | 本项目 |
|---|---|---|
| 数据层 | 登录后后端下发权限码列表，存在全局状态 | 登录后调 `/api/auth/me`，`permissions` 存在 `session`（一个 `ref`，持久化到 sessionStorage） |
| 路由层 | `<ProtectedRoute requiredPermission>` | D15 的路由守卫判断是否登录；页面级权限可以在 `meta` 里声明，`beforeEach` 里用 `can()` 判断（拓展知识点） |
| 视图层 | `usePermission()` 或 `<Authorized>` | `can(permission)`；组合式函数里决定 `actions`，模板里用 `v-if` 包住“操作审计” |

**一开头就要讲的那句话**：后端为主，前端为辅。本项目的每个前端判断都能指出后端是哪一行在真正拦着：按钮对应 D16 的 `@RequirePermission`，审计时间线对应 `audit:read`，看不到的工单对应 D17 的 `groupScope`。

**原文没讲、面试时值得补充的两点**：

1. **权限码列表会过时**。原文说“登录成功后后端返回权限列表，存在全局状态”，但管理员中途调整了角色，前端存的就是旧的。本项目在三个时机刷新：登录后、刷新页面时、操作返回 403 时。实测（单元测试）：bob 点“接单”收到 403，前端调 `/me` 发现权限只剩 `ticket:read`，按钮立即消失。
2. **权限码的来源要和后端是同一份**。原文的 `'btn:purchase:create'` 这种字符串，前后端各写一份就会拼错。本项目的权限点定义在 shared 的 `PERMISSIONS` 里，前后端都从这里导入，`can()` 的参数类型就是这个联合类型，写错编译就报错。

**原文用了 `btn:`、`page:` 前缀区分按钮和页面权限**。本项目的权限点按“资源:动作”命名（`ticket:assign`），一个权限点同时决定后端接口能不能调、前端按钮显不显示，没有专门的“按钮权限”。这样更简单：前端显示的按钮，一定对应后端允许的操作。代价是不能做“某个按钮只是隐藏、接口其实能调”这类特殊需求，本项目也不需要。

</details>

## 二、网络最新题

### 题 2：Vue 3 的动态权限路由怎么做？它解决了什么问题？

来源：掘金《vue3+router动态权限路由》，2026-06-09（https://juejin.cn/post/7648986930510118922）。原文介绍了一个基于后端权限数据动态生成路由的方案：用 `import.meta.glob` 预加载所有页面组件，按权限数据生成路由配置，在路由守卫里用 `router.addRoute` 加进去。

<details>
<summary>完整答案</summary>

**做法**（原文的实现）：

1. 后端返回的权限数据里带着页面路径、组件路径、菜单名称。
2. `import.meta.glob('@/views/**/*.vue')` 拿到所有页面组件的懒加载函数。
3. 守卫里第一次导航时，按权限数据生成路由配置，`router.addRoute()` 加进路由表，再 `next({ ...to, replace: true })` 重新导航一次（新加的路由要重新匹配）。
4. 菜单也按同一份权限数据生成。

**它解决的问题**：没有权限的页面，菜单里没有入口，直接输入地址也匹配不到路由（显示 404）。用户只看到自己能用的功能。

**要纠正原文的一个说法**：原文开头说这种方案“提高了系统的安全性”。它提高的是**体验**，不是安全性：

- 页面组件的代码仍然打包在前端里（`import.meta.glob` 会把所有页面都打包成独立的文件），有心人可以找到；
- 页面上调用的接口，直接用工具调用照样能访问；
- 权限数据存在浏览器里（原文从本地存储初始化），可以被修改。

真正的安全在后端：每个接口检查权限（D16）、每个查询限定数据范围（D17）。前端隐藏页面，和 D13 隐藏按钮是同一性质的事。面试时说出这一点，比讲清楚 `addRoute` 的用法更重要。

**还有两个实际问题**：

- **退出登录或换账号时，要把动态加进来的路由删掉**（`addRoute` 返回一个删除函数，或者按名字 `removeRoute`），否则下一个登录的人能匹配到上一个人的路由。
- **权限变化后路由不会自动更新**，和题 3 是同一个问题。

**本项目为什么没用**：本项目只有列表、详情两个页面，所有登录用户都能进，区别只在页面里的按钮和区块，用 `can()` 就够了。页面多、不同角色的菜单差异大时（例如加了“用户管理”“角色配置”），再引入路由级的权限。

</details>

## 三、补充题

### 题 3：（补充题）前端拿到的权限过时了怎么办？

本题没有对应的网络原文，来自讲义 1.2 和反证实验 B 的实测。

<details>
<summary>完整答案</summary>

**为什么会过时**：前端在登录时拿到权限并保存下来，之后管理员调整了角色。后端是每次请求查数据库（D16），立即生效；前端的副本不会自己变。

**本项目的三个刷新时机**：

| 时机 | 做法 |
|---|---|
| 登录后 | 调 `/api/auth/me` 拿到权限 |
| 刷新页面时 | `main.ts` 里如果已经登录，调一次 `/me` |
| 操作返回 403 `FORBIDDEN` 时 | 调 `/me`，按钮跟着更新，提示用户“权限可能刚被调整” |

第三条最重要。实测去掉它（反证实验 B），提示说页面已更新，按钮却还在，用户会一直点、一直 403。

**过时会有多大问题**：

- 前端多了权限（被收回了还显示按钮）：点了收到 403，触发刷新，最坏一次错误提示。**不会有安全问题**，因为后端拦着。
- 前端少了权限（新加的权限还没显示）：用户暂时看不到新功能，刷新页面就有了。

所以前端的权限不需要“实时准确”，只需要“出错时能自己纠正”。

**为什么不定时轮询 `/me`**：每个打开的页面每隔几十秒发一次请求，大部分时候权限没变，是浪费。真需要实时，用推送：权限变化时服务端通过 SSE 通知这个用户的页面（W5）。

**D15 的“退出登录”问题在这里也出现了**：前端丢掉令牌只是前端不用了；后端令牌要到过期才失效。权限的问题本项目解决了（每次查库），令牌的问题需要黑名单或令牌版本号（D15 推导题 1.3）。

</details>

### 题 4：（补充题）后端已经脱敏、已经按班组过滤了，前端要不要再做一遍？

本题没有对应的网络原文，来自讲义 1.4 的设计和实测。

<details>
<summary>完整答案</summary>

**不要**。

- **脱敏**：如果后端返回的是完整号码，前端再遮一下，打开浏览器的开发者工具就能看到原值，前端的遮挡没有任何保护作用；如果后端返回的已经是掩码，前端再遮一次就是重复劳动。本项目实测，carol 和 bob 看同一张工单，后端返回的分别是 `13800000002` 和 `138****0002`，前端代码完全一样，原样显示。
- **按班组过滤**：后端的列表只返回当前用户能看的工单（D17），前端再过滤一遍，只是多了一份可能和后端不一致的规则。比如后端给 dave 加了跨班组权限，前端的过滤规则没跟着改，dave 就看不到本来能看的工单了。

**前端应该做的**：

- 根据权限点决定显示哪些入口（按钮、区块、菜单），这是体验。
- 不该发的请求不发：没有 `audit:read` 就不请求审计（本项目单元测试断言了这一点）。
- 正确处理后端的拒绝：401 跳登录、403 刷新权限、404 显示“不存在”。

**一句话**：数据能不能看、能看多少，只能由后端决定；前端决定的是“怎么展示后端给的数据”和“出错时怎么引导用户”。

</details>

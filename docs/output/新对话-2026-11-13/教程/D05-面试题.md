## 一、题库原题

### 题 1：如果要你设计一个支持无限滚动加载的信息流页面，你会怎么设计？需要考虑哪些问题？

来源：《百度贴吧 前端研发工程师面经》，题目在第 2 页（二面），参考答案在第 42-43 页。下面摘录原答案的前端设计部分。

<details>
<summary>原文答案（节选，第 42-43 页）</summary>

> 设计一个无限滚动加载的信息流（如微博、Twitter feed），我会从以下几个方面进行设计和考量：
>
> - 数据请求与状态管理：
>   - 分页逻辑：前端需要维护一个页码（page）或偏移量（offset）的状态。每次滚动到底部时，page++ 并向后端请求下一页数据。
>   - 加载状态：需要维护一个加载状态（isLoading），防止在一次请求未完成时重复发送请求。同时，这个状态可以用来显示加载中的 UI（如菊花图）。
>   - 数据拼接：每次请求回来的新数据列表，需要拼接到现有的数据列表之后。
> - 滚动事件监听与性能：
>   - 触底判断：监听 window 或特定滚动容器的 scroll 事件。通过 `element.scrollHeight - element.scrollTop === element.clientHeight` 来判断是否滚动到底部（需要考虑一定的误差阈值）。
>   - 节流（Throttling）：scroll 事件会非常频繁地触发，必须使用节流函数来包裹事件处理程序，以降低触发频率，避免性能问题。例如，每 200ms 才检查一次是否触底。
> - DOM 性能优化（核心）：
>   - 虚拟列表（Virtual List / Virtual Scrolling）：这是无限滚动最关键的性能优化点。……
> - 用户体验（UX）：
>   - 加载指示器：在请求数据时，在列表底部显示一个加载中的动画。
>   - “没有更多了”状态：当后端返回的数据为空时，显示一个“没有更多数据了”的提示。
>   - 错误处理：如果请求失败，需要给用户一个明确的提示，并提供一个“点击重试”的按钮。
>   - 滚动位置恢复：如果用户离开页面再返回，应该能恢复到上次浏览的位置。这可以通过 sessionStorage 或路由元信息来记录滚动位置。

</details>

<details>
<summary>补充讲解：原答案的分页方式恰好是信息流最不该用的</summary>

原答案的渲染优化和体验部分都对。问题在第一条：“前端维护一个页码或偏移量，每次滚动到底部时 page++”。这正好是信息流最不该用的分页方式。另外两处可以改进：触底判断用 IntersectionObserver 比监听 scroll 加节流更省事、开销更小；“后端返回的数据为空”才判断没有更多，会多发一次空请求，用接口返回的 `nextCursor === null` 判断更准确。

**为什么信息流要用游标而不是页码**：信息流的头部一直有新内容进来。用页码，翻页间隙有新内容就会把旧内容挤到下一页，用户看到重复的条目；删了内容，又会有条目被跳过。讲义 1.1 实测过这个重复：第 1 页的最后一张工单出现在第 2 页的第一行。游标记录的是“上一页最后一条在哪”，新内容排在它前面，不影响下一页。

**完整的设计**，前后端各管什么：

| 环节 | 做法 |
|---|---|
| 接口 | `GET /items?limit=20&cursor=...`，返回 `{ items, nextCursor }`，`nextCursor` 为 `null` 表示没有更多 |
| 触底 | IntersectionObserver 观察列表底部的一个哨兵元素，比监听 scroll 事件开销小 |
| 防重复请求 | 加载中时不再触发；用 AbortController 取消过期的请求，例如切换了筛选条件 |
| 切换筛选条件 | 清空列表和游标，从第一页重新加载（讲义推导题 1.4） |
| 没有更多 | `nextCursor === null` 时停止观察，显示“没有更多了” |
| 新内容 | 不插进当前列表，在顶部提示“有 N 条新工单”，用户点击后从头刷新 |
| 长列表 | 虚拟列表只渲染可视区域；已经加载的数据太多时，可以丢弃很早之前的页 |
| 失败 | 显示重试按钮，重试时用同一个游标 |

最后一点值得强调：**失败重试用同一个游标**，结果和第一次请求时一样，不会因为重试而跳过或重复。页码方案下，重试那一刻如果数据变了，结果就不一样了。

</details>

## 二、网络最新题

### 题 2：数据表上千万行，`LIMIT 1000000, 10` 为什么慢？怎么优化？

来源：掘金《面试官微笑发问：第 100 万页怎么查？我差点当场沉默…》，2025-09-10（https://juejin.cn/post/7548011330273869824）。原文以 MySQL 为背景。

<details>
<summary>完整答案</summary>

**为什么慢**：`OFFSET N` 要先找出前 N 行再扔掉，数据库没有办法直接跳到第 N+1 行。N 越大，读的行越多；如果排序没有用上索引，还要先把所有符合条件的行排序。实测 PostgreSQL 16、7.5 万张已关闭工单，取第 3000 页（`OFFSET 59980 LIMIT 20`）：顺序扫描 7.5 万行，排序 6 万行并且用到了磁盘（`external merge Disk: 3680kB`），约 31-37 ms；第 1 页只要 0.14 ms。

**优化方案，按推荐程度排列**：

1. **游标分页（最推荐）**：记住上一页最后一行的排序值，下一页用 `WHERE (created_at, id) < (游标)` 继续取。不管翻到第几页，都是索引定位后读 20 行，实测第 3000 页 0.07 ms。代价是不能跳页。原文也说这是“很多大厂 API 的默认分页方式”。
2. **延迟关联**：先只查主键并分页，再用主键回表取整行。子查询只需要读索引，不用读整行：

   ```sql
   SELECT t.* FROM tickets t
   JOIN (SELECT id FROM tickets WHERE status = 'closed'
         ORDER BY created_at DESC, id DESC OFFSET 59980 LIMIT 20) page USING (id)
   ORDER BY t.created_at DESC, t.id DESC;
   ```

   实测 PostgreSQL 上子查询变成了 `Index Only Scan`（仍然要读过 6 万个索引项），再按主键回表 20 次，总耗时 5.7 ms，比直接 OFFSET 的 31.9 ms 快，但远不如游标。它适合“必须支持跳页”的场景。注意 PostgreSQL 的 Index Only Scan 依赖 VACUUM 维护的可见性映射（D4 面试题 2）。
3. **业务限制**：限制最多翻到第 N 页；引导用户加筛选条件（时间范围、状态）缩小数据集。真实用户几乎不会翻到第 3000 页，翻到那里的往往是爬虫。

**怎么答**：先讲原理（OFFSET 要先读后扔），再讲方案（游标、延迟关联），最后讲业务取舍（能不跳页就不跳页）。原文作者的总结也是这个思路：“把原理、方案、业务结合一说”。

</details>

### 题 3：分库分表以后，怎么翻页？

来源：掘金《京东二面：分库分表后翻页 100 万条，怎么设计？》，2025-06-18（https://juejin.cn/post/7517116929376043059）。

<details>
<summary>完整答案</summary>

**为什么更难**：数据分散在多个库里，每个库只知道自己那部分的顺序。要取全局第 100 万条之后的 10 条，最朴素的做法是每个库都取前 1000010 条，汇总到应用层再排序，数据量和分库数成正比地放大。

**原文给出的三种方案**：

1. **禁止跳页，只能下一页**：本质就是游标分页。每个库都执行 `WHERE create_time < 上一页最后的时间 ORDER BY create_time DESC LIMIT 10`，各取 10 条，在应用层合并排序后取前 10 条，再记下新的游标。每页的开销只和分库数、每页条数有关，和翻到第几页无关。
2. **二次查询法**：先按 `总偏移 / 分库数` 在每个库查一次，找出全局的最小时间戳，再拿这个时间戳回各库查第二次，算出精确位置。能支持跳页，但要两轮查询，实现复杂。
3. **搜索引擎**：分页和搜索交给 Elasticsearch 这类引擎，数据库只按主键取详情。适合需要复杂筛选、全文搜索的场景，代价是多了一套系统和数据同步。

**和本项目的关系**：工单系统目前是单库，用不到分库分表。但讲义里游标的设计已经为方案 1 做好了准备：游标里同时有 `created_at` 和 `id`，即使两个库里有时间相同的数据，合并时也能按 `id` 排出唯一确定的顺序。

**答题时的分寸**：面试官问分库分表，不代表你要假装做过。可以说“我们的项目是单库，我用游标分页解决了深分页和翻页重复的问题；如果分库，游标方案可以直接扩展成各库各取一页、应用层归并”，再讲二次查询和搜索引擎的取舍。这比背诵一个没做过的方案更可信。

</details>

### 题 4：游标分页的游标应该怎么设计？前端能不能直接传时间戳？

来源：本教程补充题，没有对应的网络原文。游标的设计细节在讲义 1.4 有完整的实测，面试时常作为题 2 的追问出现。

<details>
<summary>完整答案</summary>

**游标里放什么**：排序用到的所有字段，最后一个必须唯一。本项目排序是 `created_at DESC, id DESC`，游标就是 `{ createdAt, id }`。只放时间不行：时间相同的两行被分在两页时，第二页会漏掉其中一行。

**为什么不让前端直接传时间戳和 id**：

1. **前端不需要知道排序规则**。游标对前端是一个不透明的字符串，原样传回就行。以后排序改成“优先级加时间”，游标的内容跟着改，前端代码不用动。
2. **防止被误用**。前端如果自己拼时间戳，很容易拼错格式、时区，或者拿列表里某一行而不是最后一行的时间去拼。

**编码**：JSON 再做 base64url，只含字母、数字、`-`、`_`，放进 URL 不需要转义。base64 只是编码不是加密，用户能解码看到内容，游标里不能放敏感信息。需要防篡改时，可以给游标加 HMAC 签名。

**校验**：游标来自客户端，是不可信输入。解码失败、时间无效、id 格式不对，一律返回 400。本项目实测 `?cursor=abc` 返回 `{"error":{"code":"BAD_REQUEST","message":"cursor 无效"}}`。

**筛选条件变了怎么办**：游标只记位置，不记筛选条件。前端切换筛选时必须清空游标；后端也可以把筛选条件的摘要编进游标，不一致时拒绝。

**怎么判断还有没有下一页**：多取一行，不用另外 `count`。`count` 在大表上本身就很慢，而且无限滚动不需要知道总数。

</details>

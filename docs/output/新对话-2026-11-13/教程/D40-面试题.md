## 1. 题库原题：全栈CI/CD流程如何设计？

<details><summary>原题与原文答案，第12页</summary>

2. 谈谈全栈开发中，CI/CD 流程是如何设计的？
难度：★★★
考点：工程化、交付效率
答案要点：
CI/CD 旨在通过自动化手段提高软件交付的频率和质量。
•
持续集成（CI）：代码提交后自动触发 Lint 检查、单元测试、集成测试，确保代码合规。
•
持续交付/部署（CD）：构建 Docker 镜像，推送到私有仓库，通过 K8s 或 Jenkins 自动更新测试/
生产环境。
•
灰度发布：通过 Nginx 权重配置或蓝绿部署，先让小部分用户试用新版本，确认无误后再全量。
常见坑：
•
缺乏回滚机制，导致发布失败后无法快速恢复业务。

</details>
<details><summary>补充与项目完整答案</summary>

持续集成通过频繁合入和自动检查发现不兼容；持续交付保证可发布状态，生产可以保留人工步骤；持续部署才是自动到生产。原答案把两种CD合写，需要补充这个区别。CI通过不保证所有生产风险已覆盖，也不自动授予发布权限。

本项目当前只准备CI：冻结安装、生成Prisma、build、unit、lint零警告、接口三轮，再构建两个本机镜像。没有push、镜像上传、生产迁移或部署。远端还需实际执行和配置required checks，才形成合并约束。

**追问**：构建是否应放在测试后？要看依赖，本项目测试导入shared的dist，先生成/构建可确保测当前产物；不应照搬与项目依赖无关的固定顺序。

</details>

## 2. 网络提炼：启动失败为什么后面才超时，而启动步骤显示绿色？

<details><summary>完整答案</summary>

后台命令启动返回不代表服务就绪；shell若吞掉错误或最后一条命令返回0，CI只看到成功退出。来源文章中的sudo重置PATH导致找不到pnpm，而脚本又吞掉失败，最终才在端口等待超时。这是其项目案例，本项目没有复刻sudo环境。

我们用真实子进程分别测退出0、退出7、命令不存在和错误cwd。runStages对启动错误/信号/null返回1，对非零码原样返回，并停止后续阶段。两个反证证实错误码不能改写为0，也不能忽略启动错误。

**追问**：加了set -e就万无一失吗？不，shell条件、管道、后台任务等有具体语义；本项目用参数数组和显式退出检查，避免只依赖某个shell选项。远端run仍须遵守工作流shell规则。

</details>

## 3. 网络提炼：Action升级与应用Node升级是同一件事吗？

<details><summary>完整答案</summary>

不是。JavaScript Action有自己的runs.using，setup-node配置的是后续项目命令使用的Node。来源排障文章提示应读action.yml，而不靠主版本数字猜运行时。本章查询checkout v6.1.0和setup-node v6.5.0的完整SHA，并核对二者node24；项目配置Node22.23.3，本机验证使用Node20.19.6。

固定SHA能减少标签移动，但需要后续维护更新，也不能证明Action没有漏洞。contents:read和persist-credentials:false减少运行权限，不能让不可信测试代码因此变可信；工作流不提供生产秘密或部署凭据。

**追问**：本机Node20通过能证明Ubuntu Node22通过吗？不能。D39镜像已测Node22运行，本章远端完整runner仍未运行，必须单独说明。

</details>

## 4. 项目题：CI如何复用隔离测试而不读取开发秘密？

<details><summary>完整答案</summary>

runner启动三个临时服务容器，宿主映射到D36白名单端口；test:e2e先同时预检三个URL，再重建精确测试库与两个Redis1。工作流显式提供测试资源地址，临时脚本生成随机测试凭据写GITHUB_ENV并注册mask，完全不上传本机.env。

本章仅核对该脚本和工作流结构，未在真实Actions执行临时凭据步骤。配置检查原样结果：

```json
{"case": "workflow-local", "yamlParsed": true, "pinnedActions": 2, "isolatedPorts": [5433, 6380, 6381], "permissions": "contents:read", "remoteExecuted": false}
```

job在宿主执行所以使用127.0.0.1；若改container job就要重新核对网络、地址以及现有白名单，不可随手放宽保护。D39应用宿主与e2e也不能并行共享会重置的资源。

**追问**：使用测试密码是否可直接把真实开发密码写workflow？不可，临时资源配置与用户真实秘密是不同范围；本项目严格扫描两个真实密钥值。

</details>

## 5. 项目题：怎样证明门禁确实执行了三轮接口测试？

<details><summary>完整答案</summary>

先检查阶段列表，再运行完整入口，保存每个start/passed和每轮测试统计。不是把同一轮日志复制三次，也不是失败后只重跑某个用例凑次数。本章从同一次成功门禁日志中按阶段原样提取摘要。

```text
[gate] start generate
[gate] passed generate
[gate] start build
[gate] passed build
[gate] start unit
[gate] passed unit
[gate] start lint
[gate] passed lint
[gate] start e2e-1
[gate] passed e2e-1
[gate] start e2e-2
[gate] passed e2e-2
[gate] start e2e-3
[gate] passed e2e-3
```

两个反证通过后原字节与SHA-256一致，再运行完整门禁。它证明本机脚本的行为，不能代称GitHub检查项已出现或required checks已开启。来源入门文章“CI通过即可发布”的表述应限定为既定检查已通过，生产容量、迁移、回滚仍需独立证据。

**追问**：出现一轮失败怎么办？先修复并保留失败日志，再重新开始三轮连续完整回归；不能覆盖失败历史或拼接不同代码版本的成功轮次。

</details>

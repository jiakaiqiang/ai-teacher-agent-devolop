# D107面试题：Step与事件溯源

## 一、题库原题与原文答案

关联题：本地《2026MiNiMax前端AI开发.pdf》第6—7页，第5题“如何实现一个支持‘多轮对话中断’和‘重新生成’的状态机？”。题库没有事件溯源或序号分配的原题；这道题的「中断、重新生成、幂等、历史回溯」正好对应本章的轨迹设计，原文站在前端状态层，本章放到服务端持久化层。

<details><summary>原文（只调整排版）</summary>

5. 如何实现一个支持“多轮对话中断”和“重新生成”的状态机？​
难度：★★★
考点：逻辑设计、状态机
答案要点：

通过定义明确的状态（Idle, Generating, Paused, Error）和 Action 来管理复杂的对话流。​
•
中止逻辑：利用 AbortController 关联 Fetch 请求，在用户点击“停止”时触发 abort()。​
•
覆盖更新：重新生成时，需定位到当前消息 ID，清空后续内容并重新触发流式请求。​
•
历史回溯：支持修改历史提问，此时需要截断后续对话树，发起新的分支请求。
•
幂等性：确保多次点击重新生成不会导致状态错乱。
常见坑：
•
请求已 abort 但前端状态未重置，导致 UI 卡死。​
•
重新生成时未处理好 Token 消耗的统计。​

</details>

<details><summary>补充讲解与纠偏</summary>

原文的四个要点在前端是对的，但它们都假设「状态只活在当前页面」。本章把同样的问题放到服务端，有三处要改：

1. **中断要落库，不只是 abort**。`AbortController` 只让当前请求停止等待；服务端还要把取消写进 Run（D106 的带版本条件更新），否则工作者会继续开下一步。已经发生的步骤和事件**不删**——它们是事实，取消只是在后面追加一条结束事件。
2. **「重新生成」不要覆盖历史**。原文的做法是「定位消息 ID，清空后续内容再重新请求」。在服务端这会丢掉审计证据：谁在什么时候重试过、上一次为什么失败都查不到了。可审计的做法是新开一个 Run（带新的请求键），用「来源 Run」把两次关联起来；事件表只追加，不回头修改。
3. **幂等靠键，不靠「按钮禁用」**。原文把「多次点击重新生成不会状态错乱」归在前端逻辑；实际防线应该在服务端：同一个请求键只建一个 Run（D106），同一步只能收一次（本章的条件更新）。前端禁用按钮只是体验优化，刷新页面或重放请求照样会打到接口。

原文「常见坑」里的两条在服务端也有对应：abort 后状态未重置 → 服务端必须保证终态和结束时间一起写（CHECK 约束兜底）；token 统计没处理 → 本章事件载荷故意不放大段内容，用量在 D109 的 Trace 里单独记。

</details>



## 项目面试与自检

### 1. 序号有缺口时能否宣布运行已正常完成？

按序号发现缺口，回补后再重建。工单事件和运行事件分别存储。

### 2. 运行成功能否把已给建议的工单标为已完成？

运行记录说明 Agent 是否结束。工单依据用户反馈或人工动作推进。

### 3. 只有一题不同，应从哪里找原因？

先核对输入文本、空间和授权过滤，再查编码与排序；说明并列分数的处理。

## 一、题库原题

### 题 1：什么是 GraphQL？它如何与 RESTful APIs 比较？

来源：《【精】2024字节前端面试题（45题）》，题目在第 1 页（第 34 题），答案在第 25 页。今天的 select 白名单解决的，正是原答案里说的“过度获取”问题。

<details>
<summary>原文答案（第 25 页）</summary>

> GraphQL 是一个数据查询和操作语言，它提供了一种更有效和强大的替代 RESTful API 的方法来处理数据和交互。
>
> - 核心特点：
>   - 单一终点：不像 REST API 有多个 URL，GraphQL 通常只有一个端点。
>   - 查询精确数据：客户端可以精确指定它们需要什么数据，减少数据传输。
>   - 获取多资源：一次查询可以获取多个资源，减少请求次数。
> - 与 RESTful APIs 比较：
>   - 效率：GraphQL 允许客户端请求它们需要的确切数据，避免了 RESTful APIs 常见的过度获取和资源获取不足的问题。
>   - 灵活性：GraphQL 查询是自描述的，可以适应多种数据需求和变更，而 RESTful API 可能需要为不同需求建立多个端点。
>
> GraphQL 提供了一种强大的数据获取方式，尤其适合复杂系统和多变的需求场景。

</details>

<details>
<summary>补充讲解：原答案只讲了好处</summary>

原答案的描述没错，但读起来像 GraphQL 全面优于 REST。面试时只讲好处，面试官一定会追问代价。

**REST 也能避免过度获取**：服务端为每个页面设计合适的返回结构。今天的工单详情接口就是这样：用 Prisma 的 select 只返回详情页需要的字段，设备和用户都只取两三列。代价是页面需求变化时，后端也要跟着改。

**GraphQL 的代价**：

1. **N+1 查询**：每个字段由一个 resolver 解析，查 20 张工单、每张再解析处理人，很容易变成 1 + 20 次查询，要专门用 DataLoader 批量加载。D4 会实测 N+1。
2. **缓存难**：所有请求都发到同一个端点、通常是 POST，没法直接用 HTTP 缓存和 CDN。
3. **权限要细到字段**：客户端可以任意组合字段，每个字段都要考虑当前用户能不能看。REST 接口的返回结构是固定的，权限审查的范围小得多。
4. **要防恶意查询**：客户端可以写很深的嵌套查询，服务端要限制查询深度和复杂度。

**怎么选**：前端页面多、变化快、有多个客户端（Web、App、第三方）各取所需的场景，GraphQL 的灵活性值得这些代价；内部业务系统、页面和接口一一对应的场景，REST 加上按页面设计的返回结构更简单。工单系统属于后者。

</details>

### 题 2：常见的 HTTP 状态码有哪些？分别代表什么含义？

来源：《2026转转科技前端面试》，题目在第 1 页（一面第 10 题），答案在第 6-7 页。难度 ★，考点：网络基础。

<details>
<summary>原文答案（第 6-7 页）</summary>

> HTTP 状态码由三位数字组成，首位数字定义了响应的类别。
>
> - 2xx（成功）：200 OK，204 No Content。
> - 3xx（重定向）：301 永久重定向，302 临时重定向，304 未修改。
> - 4xx（客户端错误）：400 参数错误，401 未授权，403 禁止访问，404 未找到。
> - 5xx（服务器错误）：500 服务器内部错误，502 网关错误，503 服务不可用。
>
> 常见坑：混淆 301 和 302 对 SEO 的影响；误用 401 和 403。

</details>

<details>
<summary>补充讲解：后端怎样选状态码</summary>

前端面试问状态码，多半停在“认识”；全栈面试会问“你的接口在什么情况下返回哪个”。用本项目回答：

| 状态码 | 含义 | 本项目里什么时候返回 |
|---|---|---|
| 200 / 201 | 成功 / 已创建 | 查询成功；以后创建工单返回 201 |
| 400 | 请求格式不对 | ValidationPipe 校验失败，例如多传字段、类型不对（D1） |
| 401 | 没有登录或登录失效 | 鉴权守卫（你已经会） |
| 403 | 登录了但没有权限 | W3 的数据权限：查看别的组的工单 |
| 404 | 资源不存在 | 工单编号不存在；要删除的设备不存在（Prisma P2025） |
| 409 | 和资源的当前状态冲突 | 删除仍被引用的设备（P2003）；唯一字段重复（P2002）；W2 的并发抢单 |
| 422 | 格式没问题，但不满足业务规则 | 违反 CHECK 约束（23514） |
| 500 | 服务器自己出错 | 没有映射的未知异常，只返回“服务器内部错误”，细节写日志 |
| 502 / 503 | 网关拿不到后端的响应 / 服务暂时不可用 | 写教程时实测过：后端没启动时，前端访问 `/api` 会收到 Vite 开发代理返回的 502 |

**401 和 403 的区别**：401 是“我不知道你是谁”，重新登录可能解决；403 是“我知道你是谁，但你不能做这件事”，重新登录也没用。前端据此决定是跳转登录页，还是提示没有权限。

**状态码和响应体里的错误码分工**：状态码让网关、监控、前端的通用处理知道大类；响应体里的 `error.code`（例如 `RESOURCE_IN_USE`）告诉前端具体是哪种情况、该显示什么提示。同一个 409，可能是设备被引用，也可能是工单被别人抢先接走，只看状态码分不清。

</details>

## 二、网络最新题

### 题 3：Prisma 里 include 和 select 有什么区别？怎样避免接口把敏感字段返回给前端？

来源：掘金《我的项目实战（七）- Prisma 深入后端开发：从查询优化到数据塑形》，2026-01-26（https://juejin.cn/post/7599528186587938826）。

<details>
<summary>完整答案</summary>

**区别**：`include` 在返回模型自身全部字段的基础上，再带出关联的模型，关联的模型也是全部字段；`select` 是白名单，只返回列出的字段，关联模型也可以再嵌套 `select`。

**include 的两个风险**：

1. **多取数据**：详情页只要处理人的名字，却取回了用户表的整行。表越宽、关联越多，浪费越大。
2. **默认不安全**：用户表以后加一列 `passwordHash` 或 `phone`，所有 `include: { user: true }` 的接口都会自动开始返回它，没有任何代码变化提醒你。本项目实测：把工单详情换成 `include`，返回的工单对象从白名单里的十几个字段变成 19 个，内部主键 `id`、外键 `reporterId`、乐观锁的 `version` 全都出现了，接口测试 `not.toHaveProperty('id')` 立刻失败。

**怎样系统地避免**：

1. **每个接口一个 select 常量**，放在 Service 文件顶部，名字说明用途，例如 `ticketDetailSelect`。它就是“这个接口返回什么”的契约。
2. **用类型把 select 和返回值绑在一起**：`satisfies Prisma.TicketSelect` 检查写法，`Prisma.TicketGetPayload<{ select: typeof ticketDetailSelect }>` 推导返回类型。
3. **用测试锁住**：接口测试里断言敏感字段不存在。本项目的测试就是这样发现 `include` 泄露的。
4. **只要数量时用 `_count`**，不要取出明细再数。原文也把“在循环里逐个查询数量”列为常见陷阱：查 20 篇文章、每篇再查一次点赞数，就是 21 次查询；用 `_count` 一次完成。

**补充一点原文没讲的**：前端拿到的数据也要“塑形”。数据库里是 `assignee: null`，前端可能希望显示“未指派”。这类展示逻辑放前端还是后端，看它是否和业务规则有关：纯展示放前端，涉及权限或业务含义的（例如“是否可以接单”）由后端算好返回。

</details>

### 题 4：PrismaClient 为什么要做成单例？连接池满了会怎样？

来源：同上一篇文章的第二节“Prisma 连接管理”，掘金，2026-01-26。

<details>
<summary>完整答案</summary>

**为什么是单例**：建立数据库连接要经过 TCP 握手、认证、分配后端进程，代价很高。每个 `PrismaClient` 实例都维护自己的连接池，重复使用已经建好的连接。如果每个请求或每个 Service 都 `new` 一个，就会有很多个连接池，每个池都占着若干连接。

**连接用完会怎样**：PostgreSQL 默认最多 100 个连接（`max_connections`）。超过以后，新的连接请求直接被数据库拒绝，报“too many clients”之类的错误。更隐蔽的情况是连接池自己满了：所有连接都被占用时，新的查询要排队等待，等待超时后报错，表现为接口突然变慢、然后批量超时。

**在 NestJS 里怎么做**：

1. `PrismaService` 继承 `PrismaClient`，注册为 provider，依赖注入保证只创建一次；模块标记 `@Global()`，到处可以注入。
2. 在 `onModuleDestroy` 里 `$disconnect()`，配合 `enableShutdownHooks()`，进程退出时归还连接。
3. 开发模式下用 `--watch` 热重启时，旧进程要退出干净，否则旧连接会一直占着。

**实际排查时看什么**：在 PostgreSQL 里查 `pg_stat_activity`，看当前有多少连接、分别来自哪个应用、处于什么状态。如果大量连接处于 `idle in transaction`，说明有事务开启后没有结束，这比连接数本身更危险，W2 讲事务时会遇到。

**扩展**：应用部署多个实例时，连接总数是“实例数 × 每个实例的池大小”。实例扩到 20 个、每个池 10 个连接，就是 200 个，超过默认上限。这时要么调小池、要么在应用和数据库之间加一层连接池代理（例如 PgBouncer）。

</details>

### 题 5：在 NestJS 里，资源不存在时 `throw new Error()` 和 `throw new NotFoundException()` 有什么区别？数据库约束报错又该怎么处理？

来源：掘金《背完 NestJS 文档还是答不上大厂面试？hello 项目 7 个文件讲清 MVC 实战》，2026-08-17（https://juejin.cn/post/7674920095604555826），“错误处理：NotFoundException 为什么是 404 不是 500”一节。

<details>
<summary>完整答案</summary>

**区别**：`NotFoundException` 是 Nest 的 `HttpException` 子类，带着 404 状态码，异常过滤器会把它转成 404 响应。普通的 `Error` 没有状态码，Nest 只能当作未知异常，返回 500。

这不只是状态码好不好看的问题：

- 前端无法区分“工单不存在”和“服务器坏了”。前者应该提示“工单编号有误”，后者应该提示稍后重试。
- 监控会把大量“工单不存在”统计成服务器错误，触发错误的告警。
- 500 的响应如果带了原始错误信息，可能泄露内部细节。本项目的过滤器对未知异常只返回“服务器内部错误”，堆栈只写日志。

**原文没讲的部分：数据库报的错**。很多错误不是业务代码自己抛的，而是数据库约束拒绝时由 Prisma 抛出的。它们也不是 `HttpException`，不处理就同样会变成 500。本项目在全局过滤器里统一映射，实测 Prisma 7 的错误码：

| 场景 | Prisma 错误码 | 映射 |
|---|---|---|
| 唯一约束冲突 | P2002 | 409 |
| 外键约束（删除被引用的行） | P2003 | 409 |
| 要更新或删除的记录不存在 | P2025 | 404 |
| CHECK 约束 | P2039，要看 PostgreSQL 原始错误码 23514 | 422 |

**为什么统一放在过滤器里**：如果在每个 Service 里 `try/catch` 各自翻译，很容易漏掉某个地方，翻译的写法也会不一致。集中在一处，新接口自动获得同样的处理。需要特殊提示的地方（例如“这个用户名已被占用”），再在 Service 里单独捕获、抛出更具体的业务异常。

</details>

### 题 6：Prisma 和 Drizzle 怎么选？

来源：掘金《从零搭建 SQL 数据库到 ORM 选型：Prisma 与 Drizzle 深度对比》，2026-09-23（https://juejin.cn/post/7688305723760361512）。

<details>
<summary>完整答案</summary>

**根本差异是类型从哪里来**：Prisma 用自己的 schema 语言描述模型，运行 `prisma generate` 预先生成客户端和类型；Drizzle 用 TypeScript 代码定义表结构，类型由 TypeScript 编译器在你写查询时实时推断，不需要生成步骤。原文引用的基准测试称，Prisma 生成的类型需要的类型实例化次数远少于 Drizzle，编辑器的类型检查更稳定；Drizzle 的类型开销会随查询复杂度增长。这组数据来自原文，本教程没有复测。

**查询风格不同**：Prisma 的 API 贴近业务概念（`include`、`select`、嵌套创建），SQL 被抽象掉了，上手快；Drizzle 的 API 贴近 SQL（`select().from().where()`），熟悉 SQL 的人更自然，生成的 SQL 也更容易预期。

**结合本项目的取舍**：

| 方面 | Prisma（本项目选择） | Drizzle |
|---|---|---|
| 上手 | 快，schema 读起来像数据模型文档 | 需要熟悉 SQL |
| 迁移 | 内置完整的迁移工作流（D2 用的 `migrate dev`、`deploy`） | 有 drizzle-kit，风格更接近手写 SQL |
| 数据库特性 | CHECK 约束、部分索引等要手写进迁移 SQL（D2 实测） | 表结构在 TS 里定义，原生特性表达得更直接 |
| 生成步骤 | 改 schema 后必须 `prisma generate`，CI 里要记得执行 | 没有生成步骤 |
| 复杂 SQL | 用 `$queryRaw`，类型要自己声明 | 更接近 SQL，复杂查询写起来更顺 |

**怎么回答**：不要说哪个更好，要说“我们的约束是什么”。本项目选 Prisma：团队以前端为主，需要快速建立规范的数据模型和迁移流程；代价是 CHECK 这类数据库特性要手写进迁移，复杂的统计查询要写原生 SQL。如果团队 SQL 能力强、要大量使用 PostgreSQL 的特性，或者要在边缘运行时里用，Drizzle 会更合适。

</details>

## 一、网络最新题

### 题 1：MySQL 和 PostgreSQL 的事务隔离级别有什么不同？读已提交和可重复读的本质区别是什么？

来源：掘金《重新理解 MySQL 和 PostgreSQL 的事务隔离级别》，2026-10-21（https://juejin.cn/post/7698976332215173170）。

<details>
<summary>完整答案</summary>

**本质区别是快照什么时候拍**。两者都基于 MVCC：每一行可能有多个版本，事务按自己的快照决定看哪个版本。

- **读已提交**：每条语句开始执行时拍一张新快照。同一个事务里，后一条查询能看到前一条之后别人提交的修改。
- **可重复读**：事务的第一条语句执行时拍一张，整个事务都用它。

本项目实测：A 读一张工单，B 把它改成已取消并提交，A 再读一次。读已提交下 A 两次读到 `pending`、`cancelled`；可重复读下两次都是 `pending`。

原文还强调了一个容易混淆的点：读已提交仍然是快照读，只是每条语句刷新一次快照。一条查询跑 10 秒，第 5 秒别人提交的数据它照样看不到。

**MySQL 和 PostgreSQL 在可重复读下走了两条不同的路**（原文的总结，本教程只在 PostgreSQL 上实测）：

| | 普通 SELECT | UPDATE、DELETE、FOR UPDATE | 要改的行已被别人改过 |
|---|---|---|---|
| PostgreSQL 可重复读 | 事务开始时的快照 | 同样基于快照 | 直接报错 40001，要求重试 |
| MySQL 可重复读 | 事务开始时的快照 | 读最新版本（当前读） | 基于最新值继续改，不报错；靠间隙锁防止幻读 |

本项目实测了 PostgreSQL 这一行：可重复读下，A 想修改已经被 B 改过并提交的那一行，报 `40001 could not serialize access due to concurrent update`。

**默认级别**：PostgreSQL 默认读已提交；MySQL InnoDB 默认可重复读。从 MySQL 转到 PostgreSQL 的团队，最容易在这里踩坑：同样的代码，换了数据库以后并发行为不一样了。

**面试时的回答顺序**：先讲四个级别分别防住哪些异常；再讲快照拍摄时机的本质区别；最后讲 MySQL 和 PostgreSQL 的差异，说明你的项目用的是哪个、默认级别是什么。

</details>

### 题 2：什么是写偏斜？可重复读能防住吗？怎么解决？

来源：掘金《PostgreSQL 事务与并发系列 · 第四期》，2026-04-24（https://juejin.cn/post/7632034549904244774）。原文用的是经典的“医生值班”例子：规则是至少一名医生值班，两名医生同时请假，各自看到还有另一个人在值班，结果没人值班了。

<details>
<summary>完整答案</summary>

**是什么**：两个事务读同一组数据，基于读到的结果去修改**互不相交**的行，每个事务单独看都没问题，合起来却违反了业务规则。

**本项目的例子**：规则是“每人最多 5 张处理中工单”。carol 已经有 4 张，三个接单请求同时到达，各自统计都是 4、都认为可以接单，各自改的是不同的工单。实测读已提交下，有一轮 3 个请求都成功，carol 变成 7 张。

**为什么可重复读防不住**：可重复读的检查是“我要改的这一行，在我拍快照之后被别人改过没有”。写偏斜里，两个事务改的是不同的行，没有任何一行被同时修改，这个检查发现不了。行锁也不会冲突。原文的说法是：坏掉的不是某一行，而是一条横跨多行的业务规则，行级别的机制管不到它。本项目的演示脚本实测：可重复读下，规则“最多 2 张”被突破成 3 张。

**解决办法**：

1. **可串行化**：PostgreSQL 的可串行化快照隔离（SSI）会跟踪事务之间的读写依赖，发现可能违反串行执行结果时，让其中一个失败。实测可串行化下第二个提交报 `40001 could not serialize access due to read/write dependencies among transactions`，最终 2 张。代价是要写重试。
2. **锁住一个代表行**：先 `SELECT ... FROM users WHERE id = 处理人 FOR UPDATE`，同一个处理人的接单请求就在这把锁上排队。实测读已提交下，B 等 A 提交后才拿到锁，再统计时已经是 2 张，不再接单。原文在可重复读下用的是类似的思路：锁住所有值班医生的行。
3. **把规则变成单行约束**：例如在 users 表上维护一个“处理中数量”的计数列，加 CHECK 约束“不超过 5”，接单时对这一行加一。这样冲突就变成了对同一行的并发更新，数据库能直接处理。代价是计数列要和工单表保持一致。

本项目选可串行化加重试：流转事务很短，冲突不多，而且不用逐条规则去想锁哪一行。

</details>

## 二、补充题

### 题 3：（补充题）可串行化事务失败了，应用应该怎么重试？有哪些坑？

本题没有对应的网络原文，来自讲义 1.4 的实测。

<details>
<summary>完整答案</summary>

**识别哪些错误可以重试**：PostgreSQL 的错误码 `40001`（序列化失败）和 `40P01`（死锁）。唯一冲突 `23505` 这类错误重试也不会成功，不应该重试。

**在 Prisma 7 里要检查两个位置**（实测）：

- 冲突发生在事务里某条查询上：抛 `PrismaClientKnownRequestError`，`code = 'P2034'`，原始错误码在 `meta.driverAdapterError.cause.originalCode`。
- 冲突发生在提交时：直接抛 `DriverAdapterError`（信息是 `TransactionWriteConflict`），不是 Prisma 的已知错误，原始错误码在 `cause.originalCode`。

只认 P2034 的话，提交时的冲突会被当成未知错误，变成 500。实测只设隔离级别、不重试时，6 个并发事务里 1 个失败在提交、3 个失败在查询，两种形态都出现了。

**重试的写法**：重新执行整个事务回调，而不是只重试失败的那条 SQL。回调会重新读数据、重新判断，这时能看到对方已经提交的结果。

**坑**：

1. **回调里有副作用**：发邮件、调外部接口、写日志到别的系统，每重试一次就多做一次。回调里只放数据库操作。
2. **回调外的状态**：回调修改了外面的变量（例如往一个数组里 push），重试时会叠加。
3. **无限重试**：冲突持续发生时会一直重试，要有次数上限，用完返回明确的错误。本项目用完 3 次返回 409 `TRANSACTION_CONFLICT`。
4. **同时重试**：几个冲突的事务立刻同时重试，很可能再次冲突。加一个随机的短暂等待。
5. **重试用尽和业务失败要区分**：实测不重试时，失败的请求收到的是“冲突了”，而不是“工单已被接走”“已达上限”这种确定的答案。测试要断言具体的错误码，只断言 409 会把问题放过去。

</details>

### 题 4：（补充题）PostgreSQL 有脏读吗？设置成读未提交会怎样？

<details>
<summary>完整答案</summary>

没有。PostgreSQL 接受 `READ UNCOMMITTED` 这个设置，但实际行为和读已提交完全一样，读不到别人没提交的数据。本项目实测：A 改了标题但没有提交，B 用读未提交读到的仍然是原来的标题。

原因是 PostgreSQL 的 MVCC 实现里，每个事务只能看到已经提交的行版本，没有办法“看到别人正在改的版本”。SQL 标准只规定每个级别“至少”要防住哪些异常，数据库可以做得更严格，PostgreSQL 的可重复读同样比标准要求的更严格，也防住了幻读。

这道题的考点是：不要死背标准里那张表，要知道你用的数据库实际怎么做。

</details>

## 1. 网络提炼：Node.js 单线程，为什么不能用全局变量保存 requestId？

<details><summary>完整答案</summary>

单线程并不等于请求串行。A 在 await 处暂停，B 改写全局 ID，A 恢复后就会读到 B 的值。AsyncLocalStorage 把 store 关联到异步执行链；run(store, callback) 内创建的异步工作可继承上下文，外层恢复原上下文。不能只在同步函数进入时赋值、退出时清空全局变量。

本项目入口校验 x-request-id，合法值沿用，非法或缺失生成 UUID，响应头带回。事件构造读取 currentRequestId；并发单元和真实 HTTP 测试分别验证 await 后仍独立、响应头与日志一致。

原文用 Map&lt;asyncId, store&gt; 帮助解释传播，但不应把示意图当各 Node 版本固定内部实现；原文“性能小于 5%”也没有在本项目测量，不引用为保证。process.nextTick 本身不是必然丢上下文的原因，特殊回调或自定义 thenable 应按官方排查，并在需要时用 AsyncResource 连接边界。

**追问**：是否要每个请求都 new 一个 AsyncLocalStorage？不需要，共用实例并用不同 store 执行。store 应保持轻量，避免放完整请求或大对象。

</details>

## 2. 网络提炼：requestId、jobId、Trace ID、幂等键有什么区别？

<details><summary>完整答案</summary>

requestId 用于把入口和后续记录关联；jobId 定位队列任务，同任务用 attempt 区分重试；Trace/span 用于表达跨服务调用关系和时序；幂等键是业务重复执行的判断依据，配合数据库约束保护结果。

本项目允许调用者传合法 requestId，所以它不是身份凭证，也不保证全局唯一，不能靠它授权或直接返回旧业务结果。D30 的告警去重依靠来源+dedupKey 和业务唯一约束，日志 ID 不替代这些。

BullMQ 的 Worker 不会自动继承 HTTP 的 AsyncLocalStorage。生产者显式放入 requestId，消费者用 runWithRequestId 恢复，并把 started/completed/failed 都放进上下文。若只在成功路径恢复，错误日志仍会断链。

真实链路原样证据：

```json
{"case":"trace-chain","requestId":"log37-ac93ff86-9e19-4296-9f1e-e38128ac45f5-trace","events":["http.completed","queue.started","db.transaction_io","queue.completed"],"auditMatches":true}
```

证据只覆盖告警入口、Worker、适配器事务和审计。本章没有声称维护队列、通知 Worker、Nginx 或所有数据库查询已全部关联。

**追问**：同一 job 重试要新 requestId 吗？沿用上游关联，用 attempt 区分；完全没有上游的后台任务可生成自己的 ID。

</details>

## 3. 网络提炼：用了 JSON logger 和 redact，是否就不会泄密？

<details><summary>完整答案</summary>

JSON 解决机器解析，redact 解决已声明结构化字段的遮蔽，都不能理解任意字符串里的秘密。Nest 安装类型明确区分属性脱敏与普通字符串、错误 message/stack；把整个 Error 或请求体传进去再期待自动清理是不可靠的。

本项目先用字段白名单构造事件，HTTP 只写 method、路由模板、status、duration、aborted；队列写 queue/jobId/attempt；事务只写操作类别、耗时或错误码。URL 查询串可能含一次性 SSE 票据，因此用 req.route.path，兜底 404 统一 unmatched。未知错误不输出原始 stack/message，只留通用代码。

原样测试证据：

```json
{"case":"private-log","markerPresent":false,"saw401":true,"saw404":true}
```

```json
{"case":"error-log","statusCode":500,"markerPresent":false,"requestId":"log37-ac93ff86-9e19-4296-9f1e-e38128ac45f5-error"}
```

用例中的秘密是模拟标记。它证明这些请求路径没有输出该标记，不证明全仓库第三方库和历史日志已经全部审计。白名单允许的字段也要保证调用点安全，不能把原始 URL 塞进 route。

**追问**：不保留堆栈怎么排错？先按关联 ID、事件和已知错误码定位；确需更详细错误分类时，增加受控字段与专用权限/保留策略，而非恢复任意参数输出。本章详细堆栈采集尚未实现。

</details>

## 4. 项目补充：为什么 HTTP 日志监听 finish 和 close？SSE 耗时怎么算？

<details><summary>完整答案</summary>

中间件能覆盖守卫拒绝、参数错误和 404；普通业务拦截器未必覆盖全部。响应 finish 与 close 可能都发生，因此共用 written 标志只写一条。close 时若 writableFinished=false，记录 aborted=true。

performance.now 差值记录从中间件进入到响应完成或断连的时间。对 SSE，这是连接持续时间，不是首字节延迟，也不是一条通知的处理时延；后续指标应把它与普通请求分开。requestId 在回调注册时捕获，完成回调显式恢复上下文。

本章真实接口覆盖成功、401、404、500；第一次 404 用例暴露 Nest 的兜底通配路由仍有 route.path，已统一为 unmatched。真实 SSE 中途断连以及代理缓冲尚未在 D37 测量，留给 D38-D39。

**追问**：HTTP 200 和 aborted=true 矛盾吗？不矛盾，可能头已写出、流后来断开，状态码不能代表整条流被客户端完整消费。

</details>

## 5. 项目补充：事务回滚后，日志与审计分别应该怎样？

<details><summary>完整答案</summary>

日志描述发生过的尝试与错误，事务回滚后仍应保留；审计记录成功业务变化，本项目与业务同事务，回滚时一起撤销。重试过程中可以有多次失败日志，但不能多出未成功操作的审计事实。

D37 的事务适配器在实际 I/O 执行周围计时，不包含前面的本地排队等待；只记录 query/execute/commit/rollback 类别，不记录 SQL 和绑定参数。这里的 query 完成并不等于事务已提交；commit 完成也不等于通知已经送到用户页面。

两个反证分别检验不同风险：去掉字段白名单让模拟敏感字段进入对象；让 Worker 用新 UUID 则破坏原请求关联。都先跑成功基线，再单点改坏、保存失败、按原字节和 SHA-256 恢复、同测试复测。详细原样失败在配套讲义第三节。

**追问**：这里有了日志能不能称为分布式追踪？尚不能。没有 span 父子关系、采样与外部采集，也未覆盖所有下游。当前是可关联的本地结构化日志。

</details>

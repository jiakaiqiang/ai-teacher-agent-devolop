### 题 1：AsyncLocalStorage 是什么？解决什么问题？

来源：掘金《详解 AsyncLocalStorage》，2026-03-16（https://juejin.cn/post/7617454306796175401）。原文从“异步上下文丢失”讲起，对比了参数传递、全局变量两种旧方案，再讲 AsyncLocalStorage 的原理和用法。

<details>
<summary>完整答案</summary>

**要解决的问题**：一个请求里的很多地方都需要同一份上下文（请求 ID、当前用户、租户），比如日志每一行都要带上请求 ID。Node 是异步的，`await` 之后调用栈已经换了，怎么在深处的函数里拿到“当前是哪个请求”？

**两种旧办法为什么不行**（原文的分析）：

- **参数传递**：每个函数都多一个 `requestId` 参数，很多函数自己根本不用它，只是为了往下传。原文称为“参数污染”。
- **全局变量**：Node 是单线程，但请求是并发处理的。请求 A 设置了全局变量、`await` 一下，请求 B 进来又改了它，A 回来读到的是 B 的值。

**AsyncLocalStorage 的做法**：把上下文绑定到**异步调用链**上，而不是调用栈。`storage.run(store, callback)` 之后，`callback` 以及它创建的所有异步任务（Promise、定时器、数据库回调）里，`storage.getStore()` 都返回这个 `store`；另一个请求的 `run` 有自己的 `store`，互不干扰。这相当于 Java 的 `ThreadLocal`、Go 的 `context.Context`。

**本项目的用法**：

```ts
export function requestContextMiddleware(req, res, next) {
  const requestId = /* 校验过的 x-request-id，或者新生成的 */;
  res.setHeader('x-request-id', requestId);
  storage.run({ requestId }, next);
}
// AuditService 里：
await tx.auditLog.create({ data: { ...entry, requestId: currentRequestId() } });
```

实测审计里的 `requestId` 和响应头的 `x-request-id` 一致，经过了守卫、Service、Prisma 交互式事务的回调。

**注意事项**：

1. **用 `run()` 包住后续的处理**。在 `next()` 调用之后才设置，后面的处理已经开始了，拿不到；`enterWith()` 虽然也能生效，但它改变的是“当前这段同步代码剩下的部分”的上下文，作用范围不清晰，一般推荐 `run()`。
2. **中间件要最先注册**，后面的守卫、拦截器才在上下文里。
3. **只放小的、只读的东西**。把数据库连接、整个用户对象都放进去，代码会变成“哪里都能读，谁也不知道是谁放的”，测试也变难。本项目只放请求 ID，当前用户仍然通过参数显式传递。
4. **外部传来的值要校验**：本项目只接受字母、数字、连字符，实测 `x; drop table audit_logs` 被替换成新的 UUID。

**原文的原理部分要补充一点**：原文说 AsyncLocalStorage 内部维护一个 `Map<asyncId, store>`，子任务继承父任务的 store。这是理解它的一个好模型，但实际实现不是一张全局的 Map：早期版本把 store 挂在每个异步资源对象上，Node 24 起默认改用 `AsyncContextFrame`，性能更好。面试时讲“子任务继承父任务的上下文”这个模型就够了，不必背具体的数据结构。

</details>

### 题 2：只追加（append-only）的日志，遇到修改和删除的需求怎么办？

来源：掘金《深度解构：当 Append-only 的 SLS 遇上 Update/Delete，是如何实现设计权衡的？》，2026-06-24（https://juejin.cn/post/7654816253882482707）。原文是阿里云日志服务团队的文章，讲他们为什么在十几年只追加的 LogStore 上加了修改和删除能力，以及怎样不破坏原有的追加写路径。

<details>
<summary>完整答案</summary>

**只追加的好处**（原文的出发点）：写入不需要锁、不需要版本对齐，按时间组织，下游消费只要记住读到哪里；对审计来说更重要的是**可信**：写下去就是历史。

**为什么还会有修改需求**（原文列的场景）：计费明细月底要订正、AI 模型升级后要重算标签、用户反馈延迟到达要回填、测试流量误入生产要清理。这些数据有日志的形态，但承载了需要订正的业务语义。

**原文的取舍**，值得在面试里复述：

- 修改能力要**显式开启**，开启后不能关闭；**访问日志、审计日志、Trace 明细继续保持只追加**。
- 开启后，普通写入仍然是追加，不会按主键覆盖；修改和删除走单独的请求。
- 实时消费和投递仍然基于原始写入流，不感知后来的修改。

**放到本项目**：

- 审计日志保持只追加，而且在数据库层用触发器强制（实测 `UPDATE`、`DELETE`、`TRUNCATE` 都被拒绝）。
- **订正用追加表达**：如果某条审计记错了（比如写错了原因），不是去改它，而是追加一条“订正”记录，引用原记录。会计的记账方式也是这样：错账不涂改，用红字冲销。
- **需要修改的数据和审计分开存**。工单的当前状态在 tickets 表，可以改；它的变化历史在审计里，不能改。

**最难的情况：“被遗忘权”**。个人信息保护的法规要求用户可以要求删除他的个人数据，而审计要求不能删。常见的做法：

1. 审计里尽量不存个人信息本身，只存 id（本项目的快照只有状态、用户名、版本号）。
2. 必须删除时，删除的是“id 到个人信息”的映射（users 表里的手机号、姓名），审计里只剩一个无法再关联到具体人的 id。
3. 审计有明确的保留期，到期后整批归档或删除（按时间分区，删掉整个分区），而不是逐条修改。

本项目的 `actor_username` 是一个用户名快照，如果用户名本身被视为个人信息，第 2 条就要求改成只存 id。D19 讲脱敏时会再讨论。

</details>

## 二、补充题

### 题 3：（补充题）审计为什么要和业务写在同一个事务里？能不能异步写？

本题没有对应的网络原文，来自讲义 1.3 和反证实验 A 的实测。

<details>
<summary>完整答案</summary>

**同一个事务带来三个保证**（本项目实测）：

1. 业务失败，审计不留：非法流转、越权、版本冲突之后，审计 0 条。
2. 冲突重试作废的尝试，审计也作废：两人同时接同一张工单，连续 5 轮，每张工单只有 1 条审计。可串行化冲突重试会把整个事务重做，事务外写的审计会多出来。
3. 业务成功，审计一定有：它们一起提交。

**反例**：先在事务外记审计、再删除设备。删除被外键拒绝了，审计却已经写进去，实测多出一条“删除了 srv-001”的审计，设备还在。

**能不能异步写**（比如发到消息队列，由别的服务写入）？

| | 同步、同一个事务 | 异步（消息队列） |
|---|---|---|
| 一致性 | 强：和业务一起提交或回滚 | 弱：业务回滚了，消息可能已经发出去；消息丢了，审计就缺一条 |
| 业务耗时 | 多一次插入 | 几乎不增加 |
| 审计库故障时 | 业务也失败 | 业务不受影响 |

要异步又不丢、不错，标准做法是 **Outbox 模式**：业务和“待发送的审计事件”写在同一个事务里的 outbox 表，再由后台进程投递。它保证了“业务成功则一定会投递、业务回滚则一定不投递”，代价是多了一张表和一个投递进程（W5 讲）。

**审计失败时业务要不要失败**：本项目选择要。宁可操作失败，也不能有不留痕迹的操作。对于“审计不可用时也必须能处理紧急故障”的系统，可以降级为写本地文件，事后补录，但这要作为明确的设计，而不是默认行为。

</details>

### 题 4：（补充题）审计日志应该记什么、不记什么？

本题没有对应的网络原文，来自讲义 1.1 的设计。

<details>
<summary>完整答案</summary>

**要回答的问题**：谁、什么时候、对什么、做了什么、改前是什么、改后是什么、为什么、是哪次请求。

| 问题 | 本项目的字段 |
|---|---|
| 谁 | `actor_id`（外键，不可删除）+ `actor_username`（当时的用户名快照） |
| 什么时候 | `occurred_at`，数据库生成 |
| 对什么 | `entity_type` + `entity_key`（工单编号、设备编码，不用外键） |
| 做了什么 | `action`，例如 `ticket.accept`、`ticket.batch_assign`、`device.delete` |
| 改前改后 | `before`、`after`，JSONB，只记被改变的几个字段 |
| 为什么 | 改派的 `reason` 记在 `after` 里 |
| 哪次请求 | `request_id`，和响应头、应用日志一致 |

**不记什么**：

- **不记整行**：整行会把描述、以后新增的敏感字段都复制进审计。
- **不记密码、令牌、密钥**，哪怕是哈希。
- **个人信息尽量只记 id**（题 2 的“被遗忘权”）。
- **失败的操作不记在业务审计里**：业务审计记的是“发生了什么变化”。登录失败、403、越权尝试属于**安全日志**，单独记录、单独告警，保留期和读者也不同。

**审计是给谁用的**：组长查“这张单是谁关的”；安全团队查“这个账号最近做了什么”；开发排查问题时用请求 ID 把审计和应用日志串起来。设计索引时按这些查询来：本项目的 `(entity_type, entity_key, occurred_at)` 服务于“按工单查时间线”，“按人查”以后需要时再加 `(actor_id, occurred_at)`。

</details>

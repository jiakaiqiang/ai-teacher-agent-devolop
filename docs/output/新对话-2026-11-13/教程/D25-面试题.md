## 一、网络最新题

### 题 1：用 Redis 实现分布式锁，要注意哪些问题？

来源：掘金《Redis分布式锁：8个常见面试题》，2026-01-27（https://juejin.cn/post/7599580550296404003）。原文从最简单的错误写法开始，一步步讲到唯一值、Lua 释放、看门狗续期、主从切换丢锁，最后推荐用 Redisson。

<details>
<summary>完整答案</summary>

**按“一个坑引出下一个坑”的顺序讲**（原文的结构，本项目演示脚本都复现了）：

1. **加锁要带过期时间，并且是一条命令**：`SET key value NX PX 30000`。只用 `SETNX`，持有者崩了锁永远不释放；`SETNX` 之后再 `EXPIRE`，两条命令之间崩了也一样。
2. **值要用唯一值（UUID）**：锁过期后被别人拿到，原持有者干完活 `DEL`，删掉的是别人的锁。演示脚本实测：A 的锁过期、B 拿到锁、A 执行 `DEL`、C 又拿到锁，B 和 C 同时持有。
3. **检查和删除放进一个 Lua 脚本**：先 `GET` 再 `DEL` 之间锁可能刚好过期易主。实测用 Lua 释放时，A 的释放返回 0，B 的锁还在。
4. **续期（看门狗）**：活着的持有者每过三分之一的过期时间把锁延长。实测锁 200ms、每 70ms 续一次，A 干活 600ms，B 尝试 6 次全部失败。
5. **主从切换会丢锁**：锁写进主节点、还没复制到从节点时主节点宕机，新的主节点上没有这把锁。

**原文有几处要纠正或补充**：

- **原文的看门狗代码是 `jedis.expire("lock", 10)`，没有检查值**，注释写着“如果是自己的锁就延长”，代码却没有做到。锁已经被别人拿到时，这样会把**别人的锁**续上。续期和释放一样，要用 Lua 先比较值再 `PEXPIRE`。本项目的 `extend` 就是这样，接口测试实测锁易主后 `extend` 返回 `false`。
- **原文用“双 11 秒杀，10000 人抢 100 个商品”说明为什么需要分布式锁**。扣库存一般不用一把全局锁：所有请求排队拿锁，吞吐量就是一把锁的吞吐量。常见做法是原子的条件扣减，例如数据库 `UPDATE ... SET stock = stock - 1 WHERE id = ? AND stock > 0`，或者 Redis 的 `DECR`/Lua 脚本。这和 W2 学的条件更新是同一个思路。
- **原文的对比表说 RedLock“相对可靠”、ZooKeeper“最可靠”**。两者都只是让“两个人同时持有锁”更难发生，都挡不住持有者自己卡住（例如长时间的垃圾回收）之后继续写的情况，题 2 详细讲。ZooKeeper 的优势是能提供递增的版本号，可以拿来当 fencing token。
- **原文说主从切换丢锁的应对之一是“接受风险：业务上做幂等处理”**。这其实是最重要的一条，不是退而求其次：本项目的 SLA 通知就靠条件更新保证每张工单只通知一次，锁失效也不会重复。

**原文 Q3 可重入锁**：值里记录持有者和次数，同一个持有者再加锁时计数加一，释放时减一，到 0 才删除。Node.js 里很少需要：同一个请求的代码一般不会嵌套加同一把锁。

</details>

### 题 2：锁过期了，原来的持有者还在写，怎么办？Redlock 能解决吗？

来源：掘金《一行 SET NX PX 的分布式锁，四个坑一个比一个贵》，2026-09-26（https://juejin.cn/post/7689424360591835172）。原文讲了四个坑：值不带身份、释放不原子、业务比过期时间长、锁过期后的“僵尸写者”，并介绍了 Redlock 以及 antirez 和 Kleppmann 关于它的争论。

<details>
<summary>完整答案</summary>

**问题本身**：A 拿到锁，然后卡住了（长时间垃圾回收、很慢的查询）；锁过期，B 拿到锁、写了数据；A 恢复后不知道这一切，继续写。原文把 A 叫作“僵尸写者”。续期帮不上忙：A 卡住时续期的定时器也卡住了（Node.js 里，同步代码卡住事件循环时 `setInterval` 不会执行，讲义推导题 1.3）。

**解决办法在被写入的那一边：fencing token**。每次加锁拿一个递增的号码，写入时带上号码，存储只接受比见过的更大的号码。本项目演示脚本实测：A 拿到号码 1 后卡住，B 拿到号码 2 并写入；A 恢复后带着号码 1 写入，被拒绝。

**本项目没有用号码，用的是条件更新**：SLA 扫描对每张工单执行 `UPDATE ... SET sla_breached_at = now() WHERE id = ? AND sla_breached_at IS NULL`，只有更新成功的那一次才发通知。实测两个扫描真的同时在跑时（预热连接池后），每张工单仍只通知一次；去掉条件，每张工单通知两次。原文结尾的结论和这一样：**把操作做成幂等，比任何锁都可靠**。

**Redlock**：向 5 个互相独立的 Redis 主节点加锁，多数成功才算拿到。它解决的是“单个 Redis 宕机或主从切换时丢锁”。Kleppmann 的质疑主要两点：持有者卡住的问题它完全挡不住（和单实例一样）；它的安全性依赖各节点的时钟大致准确。antirez 的回应是时钟大幅跳变本身就是运维事故，并且很多下游（第三方支付接口等）根本不支持 fencing token。

**原文给的工程结论值得直接背下来**：先问锁是为了效率还是正确性。

| 锁的用途 | 双跑的后果 | 做法 |
|---|---|---|
| 效率 | 多干一遍活 | Redis 单实例锁加 Lua 释放加续期，足够 |
| 正确性 | 重复扣款、重复发货 | 不要指望 Redis 锁；用带递增版本号的系统（etcd、ZooKeeper）加 fencing，或者把操作做成幂等 |

本项目两种都有：SLA 扫描的锁是效率锁（避免两个实例都扫）；“每张工单只通知一次”是正确性要求，交给数据库。

**原文一处说法的说明**：原文提到 Redis 主从异步复制，切换后 `INCR` 出来的号码也可能回退，并标注了“从业者判断”。这个推理是成立的（没复制到从节点的 `INCR` 会随主节点一起丢失），所以用 Redis 的 `INCR` 做 fencing token 只在单实例、或者能接受这种风险时可用。本项目的演示脚本只是为了说明原理。

</details>

## 二、补充题

### 题 3：定时任务部署了多个实例，怎么保证只执行一次？

来源：本项目 D25 实测。

<details>
<summary>完整答案</summary>

**先拆开“只执行一次”**：一是“同一时间只有一个实例在跑这个任务”（避免重复查询、重复处理），二是“每条数据只被处理一次”（例如每张超时工单只通知一次）。前者是效率，后者是正确性，分别处理。

**本项目的做法**：

1. 每个实例每分钟都执行 `runScheduledScan`，先用 `RedisLockService.runExclusive('sla-scan', 30 秒)` 抢锁，抢不到就跳过这一轮。锁执行期间每 10 秒续期一次，进程崩溃后最多 30 秒别的实例能接手。实测两个同时执行时，一个返回结果，另一个返回 `null`。
2. 扫描里对每张工单做条件更新，只有更新成功才发通知。锁失效也不会重复通知（实测）。
3. Redis 不可用时这一轮不跑，记一条错误日志，下一轮再试。

**通知和标记的顺序**：本项目先标记再通知，进程崩在中间会丢一次通知（最多一次）；反过来先通知再标记，会重复通知（至少一次）。要做到不丢不重，就把“待发送的通知”和标记写在同一个事务里，由后台任务发送、接收方去重。这是 W5 任务队列要做的事。

**一个测试上的教训**：用 `Promise.all` 同时调用两次扫描来模拟两个实例，一开始去掉条件更新也测不出问题。时间记录显示第二个查询要新建数据库连接，慢了十几毫秒，等它查到时第一个扫描已经全部标记完了。先预热连接池，并发才真正发生，反证实验才会失败。写并发测试，要先证明并发真的发生了。

**其他做法**：数据库的 advisory lock（连接断开自动释放，不用担心过期）；任务调度框架（BullMQ 等）自己保证一个定时任务只被一个工作进程拿到。

</details>

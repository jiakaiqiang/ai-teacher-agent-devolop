## 一、题库原题

### 题 1：手写题：实现一个简单的状态机，模拟 AI Agent 的状态切换（Idle、Thinking、Calling_Tool、Responding、Error）

来源：《2026高德 AI agent 前端开发》，题目在第 1 页（第 8 题），答案在第 8 页。难度 ★★，考点：设计模式与状态管理。

<details>
<summary>原文答案（第 8 页，节选）</summary>

> 状态机可以清晰地管理 Agent 复杂的交互逻辑，避免状态混乱。
>
> - 定义状态：明确所有可能的合法状态。
> - 定义动作：触发状态转移的事件。
> - 转移逻辑：编写 transition 函数，判断当前状态是否允许执行目标动作。
>
> ```js
> class AgentStateMachine {
>   constructor() {
>     this.state = 'Idle';
>     this.transitions = {
>       Idle: { START: 'Thinking' },
>       Thinking: { CALL_TOOL: 'Calling_Tool', RESPONSE: 'Responding', ERROR: 'Error' },
>       Calling_Tool: { TOOL_DATA: 'Thinking', ERROR: 'Error' },
>       Responding: { FINISH: 'Idle', ERROR: 'Error' },
>       Error: { RESET: 'Idle' }
>     };
>   }
>   send(action) {
>     const nextState = this.transitions[this.state]?.[action];
>     if (nextState) {
>       this.state = nextState;
>       console.log(`State changed to: ${this.state}`);
>     } else {
>       console.warn(`Invalid action ${action} for state ${this.state}`);
>     ……
> ```

</details>

<details>
<summary>补充讲解：前端的状态机和后端的状态机差在哪里</summary>

原答案是一个标准的表驱动状态机，结构和本项目的工单流转表一样：`状态 → 动作 → 下一个状态`。手写题这样答就够了，可以再补两点让答案更扎实：

1. **非法动作不要只打警告**。原答案 `console.warn` 之后什么都不做，调用方不知道动作被拒绝了。更好的做法是返回结果或抛错，让调用方决定怎么处理。本项目的 `planTransition` 抛 `InvalidTransitionError`，接口再转成 409。
2. **用 TypeScript 让非法状态写不出来**：状态和动作用联合类型，流转表用 `Record<Action, ...>`，漏写一个动作编译就报错。

面试官如果追问“这个状态机放在后端有什么不同”，可以用今天的项目回答。前端状态机只存在于一个页面的内存里，后端的状态机要处理三件前端不用操心的事：

| 问题 | 前端 | 后端（本项目） |
|---|---|---|
| 状态存在哪 | 内存里的一个变量 | 数据库，CHECK 约束保证只能是合法的值 |
| 历史 | 一般不记 | 每次流转追加一条处理记录，可审计 |
| 原子性 | 赋值一步完成 | 改状态和写记录是两步，要放进一个事务（实测没有事务时，出错后状态变了、记录没了） |
| 并发 | 单线程，不会同时改 | 两个人同时接单会同时成功（实测 10/10），要靠隔离级别、条件更新或锁（D9、D10） |

</details>

## 二、网络最新题

### 题 2：为什么要用状态机，而不是在业务代码里写 if-else 改状态？

来源：掘金《状态机设计：比 if-else 优雅 100 倍的设计》，2025-06-09（https://juejin.cn/post/7513752860162129960）。原文以订单系统为例，用 Go 实现。

<details>
<summary>完整答案</summary>

**if-else 的问题**：状态流转的规则散落在各个接口里。原文的例子是订单的“取消”“支付”“发货”各自检查当前状态。新增一个状态，就要找出所有相关的 if 逐个修改，漏一处就出现非法流转。规则也没办法一眼看全，评审时很难确认有没有遗漏。

**状态机的三要素**：状态、事件（动作）、转移（从哪个状态经过哪个事件到哪个状态）。把转移写成一张表，规则就集中在一处。

**表驱动的好处**，结合本项目：

1. **集中**：工单的 5 个动作、5 个状态写在一张表里，一屏看完，能直接画成状态图。
2. **共用**：表放在 `packages/shared`，后端判断合法性、前端决定显示哪些按钮，用的是同一份规则。
3. **好测**：单元测试遍历 25 种“状态 × 动作”组合，断言表里允许的都能执行、不允许的都抛错，不会有漏网的分支。
4. **好扩展**：新增一个“挂起”状态，只需在表里加几行，不用到处找 if。

**原文没讲的部分：状态机之外还有副作用**。每次流转除了改状态，还要改别的字段（接单设处理人、解决写解决时间），还要写处理记录。本项目把这些放在纯函数 `planTransition` 里，状态表只描述“能不能转、转到哪”，副作用由函数按动作补上。两者分开，表保持简单，副作用也能单独测试。

**什么时候不需要状态机**：状态只有两三个、流转没有限制（例如“启用/禁用”），直接改字段就行，引入状态机反而增加理解成本。

</details>

### 题 3：一个状态机模型在系统里怎么落地？哪些场景适合，哪些不适合？

来源：掘金《系统设计——状态机模型设计经验》，2025-06-11（https://juejin.cn/post/7514537797953617935）。原文以信贷审批流程为例。

<details>
<summary>完整答案</summary>

**适合的场景**：原文的说法是“多状态 + 严格控制流转”，状态之间只能在特定事件、满足条件时跳转。典型的有订单、审批、工单、Agent 的执行任务。不适合的是流程非常简单、没有明确事件的场景。

**落地时要回答的四个问题**（本项目的做法）：

| 问题 | 本项目 |
|---|---|
| 状态和规则定义在哪 | 流转表在 `packages/shared`，代码里的常量；规则变化少，不需要放进数据库配置 |
| 当前状态存在哪，怎么保证合法 | `tickets.status`，CHECK 约束只允许五个值（D2） |
| 历史怎么记 | 每次流转在同一个事务里追加一条 `ticket_events`，记录前后状态、操作人、说明（D1 的设计） |
| 并发时怎么办 | 两个请求同时基于同一个旧状态流转时，只能有一个成功（D9 用可串行化隔离级别加重试实现） |

原文提到的“动作”（Action），指状态变化时要执行的操作，例如发通知、写日志。要区分两类：

- **必须和状态变化一起成功的**（写处理记录、改处理人）：放进同一个事务。
- **可以稍后执行的**（发邮件、推送通知、同步到别的系统）：不要放进事务，否则外部调用慢或失败会拖住整个事务。W5 会讲用 Outbox 模式在事务提交后可靠地触发它们。

**工作流状态机和任务状态机的区别**（原文的对比）：任务状态机描述一个对象的生命周期，例如一张工单；工作流状态机描述多个步骤之间的顺序和依赖。S5 做 Agent 时会用到后者：一次诊断要依次调用多个工具，每一步都有自己的状态。

</details>

## 三、补充题

### 题 4：（补充题）在 Prisma 或其他 ORM 的事务里，最容易犯的错误是什么？

本题没有对应的网络原文，来自讲义 1.3 的实测和常见的代码评审问题。

<details>
<summary>完整答案</summary>

**最隐蔽的错误：事务回调里用了外层的客户端**。

```ts
await this.prisma.$transaction(async (tx) => {
  await tx.ticket.update({ ... });
  await this.prisma.ticketEvent.create({ ... }); // 错：这一条不在事务里
});
```

Prisma 的交互式事务绑定在一个数据库连接上，只有通过 `tx` 发出的查询才属于这个事务。`this.prisma` 会从连接池里另拿一个连接，这条 SQL 立即提交。后果是：事务里后面的步骤出错回滚时，处理记录已经写进去了；或者反过来，在事务里读不到刚刚通过 `this.prisma` 写入的数据。代码能跑、测试能过，只有出错时才会暴露。讲义 3.2 的反证实验，就是用这种方式模拟“没有事务”。

**其他常见错误**：

1. **事务太长**：在事务里调用外部接口、发邮件、调用大模型。事务开着就持有锁，别的请求要改同一行只能等，外部接口一慢，数据库的连接和锁都被占住。D12 会实测。
2. **以为事务能解决并发**：事务保证原子性，不保证两个请求之间不互相干扰。实测两个人同时接同一张工单，10 轮里每一轮两个请求都成功。这是隔离性的问题，要靠隔离级别、条件更新或锁来解决（D9、D10）。
3. **在事务回调里吞掉错误**：实测分三种情况，结果完全不同。
   - 吞掉的是**应用自己抛的错**（数据库没报错）：事务照常提交，前面的写入全部生效。如果这个错误本来意味着“不该继续”，数据就错了。
   - 吞掉的是**数据库报的错**（例如唯一冲突），后面还有别的查询：PostgreSQL 已经把整个事务标记为失败，后面的任何语句都报 `25P02: current transaction is aborted, commands ignored until end of transaction block`，事务最终回滚。
   - 吞掉的数据库错误是**最后一步**，回调正常返回：`$transaction` 没有报任何错，正常返回了结果，但所有写入都被回滚了。实测前面改的设备名没有生效。调用方以为成功了，数据其实没写进去，这是最难发现的一种。

   结论：事务回调里要么不捕获数据库错误，要么捕获后重新抛出。确实需要“冲突了就换一种处理”时，用数据库提供的写法（例如 D11 会用的 `ON CONFLICT DO NOTHING`），而不是先报错再吞掉。
4. **在事务里做不必要的读**：读一些和本次写入无关的数据，只会让事务变长。

**怎么在评审里发现第一种错误**：看事务回调里有没有出现回调参数以外的客户端变量；或者给团队约定，事务里的数据库操作都抽成接收 `tx` 参数的函数。

</details>

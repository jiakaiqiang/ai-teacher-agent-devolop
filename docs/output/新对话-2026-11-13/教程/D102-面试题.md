## 一、题库原题与原文答案

关联题：本地《2026已发交个朋友全栈AI工程师.pdf》第6页，第6题“Node.js 作为 AI 中间层时，如何处理高并发的流式请求？”。D26用过这道题讲限流；本章换成“中间层在跨服务调用里负责什么”。题库没有NestJS调用Python的原题。

<details><summary>原文（只调整排版）</summary>

6. Node.js 作为 AI 中间层时，如何处理高并发的流式请求？​
难度：★★★
考点：Node.js Stream、背压（Backpressure）、内存管理​
答案要点：
Node.js 适合处理 I/O 密集型任务，通过 Stream 模块可以高效转发 AI 厂家的流式响应。​
•
使用 pipeline 或 stream.pipe() 建立从 AI API 到客户端的管道。​
•
处理背压：当客户端消费速度慢于 AI 产出速度时，暂停读取上游流。​
•
使用中间层进行 Token 计数、日志记录和权限校验。​
•
部署：利用 PM2 或 Docker 容器化，结合 Nginx 进行负载均衡。​
常见坑：
•
在中间层将流转为字符串处理，导致大并发下内存直接爆满。
•
忘记设置合理的超时时间，导致僵尸连接占用资源。
追问：
•
如何在 Node.js 中实现对不同用户的流式请求限流？

</details>

<details><summary>补充讲解与纠偏</summary>

原文讲的是Node.js转发厂商流式响应。本章的中间层场景不同：NestJS调用Python桥接是一次请求一次响应，没有流；但原文列出的中间层职责仍然适用，而且更重要的是顺序：

1. **先鉴权再转发**。原文把“权限校验”和日志、计数并列；在本项目里它必须发生在调用之前（决定传哪个班组或直接不调用）和之后（复核每个候选），不能交给下游服务。
2. **超时要分层**。原文的坑“忘记设置合理的超时”在多一跳之后变成两个问题：每一跳都要有超时，并且外层比内层长（本章35秒对20+10秒）。
3. **原文提到的背压**对本章不适用：候选最多24条、写入每批最多16条，请求体和响应体都有上限，不需要流式处理。

</details>

## 二、项目与网络关联题

### 1. NestJS调用Python服务时，权限应该放在哪一层？

<details><summary>完整答案与追问</summary>

用户权限只在NestJS判断，Python只认服务令牌。
NestJS掌握用户身份和权威库：调用前按用户范围决定传哪个班组或不调用，调用后按权限、状态、版本和坐标复核每个候选。Python只做编码和向量存取，班组过滤是缩小候选的第一道限制，不是最终授权。追问：Python被绕过直接调用怎么办？它只绑定回环地址并要求服务令牌；即使拿到候选，也只有坐标和版本，没有正文。

</details>

### 2. 跨服务调用的超时怎么设？

<details><summary>完整答案与追问</summary>

外层比内层长，而且各层都有上限。
本章：Python编码20秒、Milvus 10秒，Nest调用Python 35秒，推荐接口失败统一503。外层太短会让上游继续做无人等待的工作，用户重试还会叠加负载。追问：35秒对用户太长怎么办？应该缩短内层（例如限制编码条数或换更快的模型），再相应缩短外层，而不是只缩外层。

</details>

### 3. 把功能从一个服务迁到另一个服务，怎么做才能随时回退？

<details><summary>完整答案与追问</summary>

加一个明确的开关，两条路径并存，用对照证明等价。
本章`RETRIEVAL_BACKEND`默认node，python需显式设置，拼错报错。在同一个集合上对照：12次检索Node直连与经Python桥接排序12/12一致，分数最大差1.79e-8；写路径经桥接写入后读回，主键、版本、字段都符合Node端布局。回退只需改回node，不需要改数据。

</details>

### 4. 网络题：AI应用平台为什么要把业务后端和Python AI服务拆开？

<details><summary>完整答案与追问</summary>

来源：掘金《AI 应用平台为什么要拆分 Java 后端和 Python AI 服务》，2026-08-18，https://juejin.cn/post/7675299245081542696 。
原文主张业务后端负责用户、权限、会话等稳定能力，Python负责模型调用、Prompt、Agent编排，理由是职责边界和Python的AI生态。这和本项目的分工一致：NestJS保留权限复核，Python做编码与向量存取。需要补上的是拆分的代价，原文较少提：多一次网络调用和一组新故障（超时、连不上、契约不一致）；两份部署和两套依赖；契约需要两边同时校验（本章Python用Pydantic、Node用zod）。所以拆分要有收益才做，并且要用对照实测证明迁移前后行为一致，而不是只因为“Python生态好”。

</details>

### 5. 网络题：LangChain的TS版和Python版怎么选？

<details><summary>完整答案与追问</summary>

来源：掘金《面试官：LangChain中 TS 和 Python 版本有什么差别，什么时候选TS》，2026-04-23，https://juejin.cn/post/7631422819831889956 。
原文结论：核心能力已接近，差别在生态厚度（原文称Python集成1000+、JS/TS 100多，本文未核对这个数量）；TS的优势是前后端共用一套类型（表单、DTO、工具参数schema），Python适合重ETL、重索引和离线处理。这个判断可以直接用在本项目：业务链路和类型契约留在TS（NestJS+zod+shared），向量与模型相关的部分放进Python。补充一点：混合架构下两种语言之间的契约无法共享类型，只能靠两边各自校验加对照测试，这是选择混合方案时必须付出的维护成本。

</details>

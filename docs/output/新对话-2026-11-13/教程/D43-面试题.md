## 1. 题库原题：如何优化Prompt构建？

来源：《2026快手前端AI面试》第6页。

<details><summary>原题与原文答案</summary>

4. 如何优化 Prompt 的构建过程？前端如何封装 Prompt 模板？
难度：★★
考点：Prompt Engineering、工程化思维
答案要点：
Prompt 工程化是将业务逻辑与模型指令分离的过程，前端通常负责动态参数的注入。
•
模板化：使用类似 Mustache 的语法定义 Prompt 模板，分离变量与指令
•
角色管理：封装 System Prompt、User Prompt 的构造函数
•
长度控制：在前端预估 Token 长度，必要时进行截断或压缩
•
版本控制：将 Prompt 视为代码资产，支持多版本灰度测试
常见坑：
•
直接在业务代码里硬编码长字符串 Prompt
•
忽略了用户输入中的特殊字符可能导致的 Prompt 注入攻击

</details>
<details><summary>补充与完整答案</summary>

本项目把可信system固定在后端，前端只传问题；服务端查询允许的工单材料并构造user消息。JSON编码保持结构，模板变量不应影响角色、模型地址或认证信息。对于复杂提示词可独立版本管理、保存变更及评测结果；短小固定教学提示词先集中在一个函数，避免散落。

原文提到特殊字符导致注入，需补充：提示注入是模型把不可信语义当指令，普通自然语言也可能注入；转义和角色分离不能保证消除。真正的执行边界由权限、工具参数、人工审批等控制。本章没有工具执行，仅返回建议。

前端预估token用于体验，后端还需独立限制材料和预算；本章仅有响应字节上限与输出token参数，没有真实token计数器。

**追问**：能把system做成前端可编辑字段吗？用户可编辑的内容应被当作user材料，不能直接覆盖服务器的可信约束。任何未来的管理员提示词管理也要单独鉴权与审计。

</details>

## 2. 网络提炼：OpenAI兼容是否只要换base_url？

来源：[OpenAI API协议完全指南](https://juejin.cn/post/7624184992536952867)，2026-04-03。原文宣称主流模型几乎完全兼容，实际不能由接口路径推导全部兼容。

<details><summary>完整答案</summary>

至少核对API根路径、模型名、认证、消息角色、支持参数、错误体、流式事件和结束标记。Chat Completions与Responses不同；某些模型不支持相同采样参数或输出预算字段。本文只验证教学请求的固定子集，不能说换三个变量就适用任意提供商。

本章API根保留/v1再拼/chat/completions，阻止URL凭据/query/hash与重定向。服务端环境全空可选择标明的模拟，部分配置必须报错；不能把错误配置偷偷变成演示结果。当前先使用原生fetch学习协议，已查Nest官方AI方案但它要求更高Node运行时。

本机传输原样证据：

```json
{"case":"local-chat","transport":"real-loopback-http","model":"mock-model","stream":false,"roles":["system","user"],"finishReason":"stop"}
```

依据：[Chat Completions官方请求参数](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create)。

**追问**：为什么不直接在Vue里带API Key？浏览器包、网络面板和页面脚本都能接触它。应由后端保管并做权限与预算控制；VITE_变量不适合放秘密。

</details>

## 3. 网络提炼：token怎样影响长度和费用？

来源：[Token计费机制](https://juejin.cn/post/7621078697472032803)，2026-03-26；只取概念问题，不采用文中的模型价格或推荐。

<details><summary>完整答案</summary>

token来自模型tokenizer。JS length是UTF-16代码单元计数，UTF-8字节数是传输量，二者不能代替token。system、用户材料、历史和工具定义会增加输入；输出、推理及缓存等计费分类以供应商实际usage和合同为准。本文不测价格，不安装tokenizer。

原文先说不同语言有换算差异，后面又把500字system直接当500token计算，口径不一致；固定汉字系数与通用编码也不能适用于所有模型。前端估算只是提示，准确预算应按对应模型核验。

max_completion_tokens限制生成预算，不是可见字符上限；预算耗尽可返回length。本项目单独保留finishReason，不能把HTTP200或有正文当完整成功。某些推理模型的预算包含推理token，512也可能使可见答案很短。

**追问**：temperature=0能保证每次完全相同吗？不能当跨环境绝对承诺；采样配置、模型更新及服务端执行都有影响，且参数可用性因模型而异。本章未运行真实采样实验。

</details>

## 4. 项目题：怎样处理不可信上游响应？

<details><summary>完整答案</summary>

先判断HTTP状态，再判断媒体类型，流式读入时限制原始字节，再验证JSON语义。非2xx映射固定MODEL_UNAVAILABLE，非法JSON/choice映射MODEL_PROTOCOL_ERROR，超过256KiB为MODEL_OUTPUT_LIMIT。不能把上游body或网络异常原文回显，可能包含内部地址、凭据或用户材料。

本章只接受单个index0的文本choice，拒绝refusal、工具调用等不支持的结果；保留stop/length。finally取消并释放reader。没有自动重试，避免不透明地重复付费；调用者必须提供取消/时间预算，D46统一生命周期。

```json
{"case":"upstream-error","upstreamStatus":429,"publicCode":"MODEL_UNAVAILABLE","attempts":1}
```

**追问**：为什么429不直接重试？需要知道Retry-After、预算、幂等与已输出情况；本周先证明一次调用一次请求，W9再设计有限重试。

</details>

## 5. 项目题：怎样证明自己的测试抓住了关键错误？

<details><summary>完整答案</summary>

用node:http真实回环服务检查path、headers、body，不只断言fetch mock被调用。配置反证把部分配置throw改null，结束原因反证把length改stop；同用例基线先过，改坏后失败，再恢复相同字节/hash，复测成功。

```text
 FAIL  src/assistant/chat.client.spec.ts > 模型配置与本机HTTP契约（D43） > 全部缺省返回null，部分配置不能悄悄回退
AssertionError: expected [Function] to throw an error

- Expected:
null

+ Received:
undefined
```

```text
 FAIL  src/assistant/chat.client.spec.ts > 模型配置与本机HTTP契约（D43） > 长度终止保留length，不伪装完整回答
AssertionError: expected 'stop' to be 'length' // Object.is equality

Expected: "length"
Received: "stop"
```

两项恢复记录与SHA-256见讲义第三节。这能说明用例约束了关键行为，仍不能证明外部中转站兼容、回答正确或没有全部提示注入。

**追问**：网络chunk能直接JSON.parse吗？不能。D44将区分UTF-8字节、文本行、完整SSE事件，只有完整data事件才交给JSON解析。

</details>

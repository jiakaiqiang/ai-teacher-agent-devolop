## 一、题库原题

### 题 1：全栈开发中，如何设计数据库表结构以应对高频读写？

来源：《2026美团前端全栈开发》，题目在第 1 页（二面第 7 题），答案在第 9 页。难度 ★★★，考点：数据库设计、后端能力。

<details>
<summary>原文答案（第 9 页）</summary>

> 良好的表结构设计需要平衡规范化与查询效率。
>
> - 索引优化：对高频查询字段建立索引，注意最左匹配原则，避免索引失效。
> - 读写分离：通过主从架构，主库负责写，从库负责读。
> - 反规范化：在某些场景下冗余部分字段，减少多表 Join 关联查询。
> - 缓存策略：配合 Redis 存储热点数据，减轻数据库压力。
>
> 常见坑：索引建立过多导致写操作性能大幅下降。
>
> 追问：什么是数据库事务的 ACID 特性？

</details>

<details>
<summary>补充讲解与追问答案</summary>

**原答案的问题**：四条都是性能手段，跳过了表结构设计本身。面试官问“表结构怎么设计”，先要讲清楚数据怎么拆、怎么保证正确，再讲怎样变快。一个只会说读写分离、却说不清表为什么这样拆的候选人，很难让人相信他做过真实的后端。

**建议的回答顺序**：

1. **先保证正确**：按业务实体和关系拆表；当前状态和历史分开存；用 NOT NULL、唯一、外键、CHECK 约束兜底。可以用工单系统举例：工单表存当前状态，处理记录表只追加不修改。
2. **再针对读优化**：索引只建在真正高频的查询条件上，并用 `EXPLAIN ANALYZE` 证明它被用上了；复合索引注意最左前缀；列表分页用游标而不是越翻越慢的 offset（D4、D5 会实测）。
3. **读远多于写时加缓存**：例如按客户公司或运维部门范围统计的工作台计数。要同时讲清缓存和数据库怎样保持一致（W4）。
4. **反规范化要说清代价**：冗余一个字段，就要回答“它由谁、在什么时候更新，不一致了怎么办”。例如在工单上冗余处理人姓名，用户改名后所有工单都要同步。
5. **最后才是架构层面**：读写分离会带来主从延迟，刚写入的数据从从库可能读不到；分库分表会让外键、跨表事务、全局唯一 ID 都变难。数据量没到那个级别，就不必引入。

**追问：ACID 是什么？**

- **原子性（Atomicity）**：一个事务里的操作要么全部生效，要么全部不生效。例如改工单状态和写处理记录，不能只成功一半。
- **一致性（Consistency）**：事务前后，数据都满足所有约束。数据库的约束就是用来保证这一点的。
- **隔离性（Isolation）**：并发执行的事务互不干扰，干扰到什么程度由隔离级别决定。这是 W2 的重点。
- **持久性（Durability）**：事务一旦提交，即使数据库马上崩溃，结果也不会丢。PostgreSQL 靠预写日志（WAL）实现。

</details>

### 题 2：谈谈你对前端工程化中 Monorepo 架构的理解，以及在 AI 项目中的适用场景。

来源：《2026腾讯音乐 前端开发（AI产品）》，题目在第 1 页（二面第 4 题），答案在第 6 页。难度 ★★，考点：工程化架构选型。今天的项目初始化用的就是 pnpm workspace 的 Monorepo。

<details>
<summary>原文答案（第 6 页）</summary>

> Monorepo 是指在一个代码仓库中管理多个项目或模块的策略，常配合 pnpm workspaces 或 Turborepo 使用。
>
> - 优势：代码复用方便、依赖版本统一、跨项目重构简单。
> - AI 场景适用性：AI 产品通常包含 Web 端、插件端、管理后台、公共 UI 组件库和 AI SDK，非常适合 Monorepo。
> - 挑战：CI/CD 耗时增加、权限管理困难、工具链配置复杂。
> - 常用工具：pnpm（速度快、磁盘占用低）、Nx（功能全）、Turborepo（配置简单）。
>
> 常见坑：依赖幽灵（Ghost Dependencies）问题；仓库体积过大导致 Git 操作缓慢。
>
> 追问：如何在 Monorepo 中实现只对修改过的包进行增量构建？

</details>

<details>
<summary>补充讲解与追问答案</summary>

**原答案缺了什么**：只列了优缺点，没有结合自己的项目。用一个具体收益开头更有说服力，例如“工单类型放在共享包里，后端加字段时前端编译直接报错”。“依赖版本统一”也要说准：Monorepo 本身不保证版本统一，今天的项目里前后端的 `vite` 版本范围就不一样，要靠 pnpm 的 catalog 这类机制统一。

**追问：只对修改过的包增量构建**。分两层：

1. **选出改动的包**：`pnpm --filter "[origin/main]" build` 只构建相对 main 分支有改动的包；写成 `"...[origin/main]"` 还会带上依赖它们的下游包。本机实测：只改 `apps/web` 下的一个文件时，`pnpm --filter "[HEAD]"` 只选中了 `apps/web`。
2. **跳过没变的任务**：Turborepo、Nx 给每个任务的输入（源码、依赖、环境变量）算哈希，哈希不变就复用上次的产物；配置远程缓存后，CI 和同事之间也能共享。

**幽灵依赖**：npm 把依赖平铺到顶层，代码能 import 自己没声明的间接依赖。pnpm 让每个包只能看到自己声明过的依赖。本机实测：后端能 import `@nestjs/core`，import `express` 报 `ERR_MODULE_NOT_FOUND`，尽管 express 已经作为 `@nestjs/platform-express` 的依赖装进来了。

</details>

### 题 3：为什么要用外键？加了外键，删除和修改数据时会怎样？高并发系统为什么有人不用外键？

来源：掘金《外键是个啥？为什么我要加它？——从面试复盘聊聊数据库设计》，2025-03-28（https://juejin.cn/post/7486736248020140051）。作者在面试中被问到这道题，没有答好，事后复盘。

<details>
<summary>完整答案</summary>

**外键保证什么**：引用方的值必须在被引用的表里存在。例如工单的 `assignee_id` 必须是一个真实存在的用户。没有外键，删掉一个用户后，他名下的工单就指向一个不存在的人，这种“孤儿数据”在列表页不会报错，但关联查询会查不到，统计会对不上。

**删除被引用的行时有三种策略**：

| 策略 | 行为 | 适合 |
|---|---|---|
| RESTRICT / NO ACTION | 报错，不让删 | 有审计价值的业务数据，例如工单、订单 |
| CASCADE | 引用方一起删除 | 完全从属、没有独立价值的数据，例如购物车条目 |
| SET NULL | 引用方的外键改成空 | 关联可有可无、引用方要保留的数据 |

修改被引用的主键时同样有这三种策略（ON UPDATE）。主键本来就不该改，这也是主键不夹带业务含义的原因之一：主键里没有业务信息，就永远没有理由去改它。

**选择要看业务，不能凭“省事”**。工单系统的处理记录如果用 CASCADE，删一张工单就会无声地删掉它的全部审计记录。新版 D01 草稿给处理记录的工单外键设置 RESTRICT，试图删除仍有记录引用的工单会触发外键检查。

**不用外键的理由**：

1. 每次插入、更新、删除都要多一次检查，写入量极大时有开销。
2. 分库分表后，两张表可能不在同一个数据库，外键无法跨库。
3. 级联操作是隐式的，大表上一次级联删除可能锁住大量行。

**不用外键的代价**：一致性全靠代码。每一条写入路径（接口、定时任务、修复脚本）都要自己检查引用是否存在，一个遗漏就会留下孤儿数据，而且发现得很晚。不用外键的团队通常还会做定期的数据巡检。

**回答时给出自己的选择和理由**：单库、数据量可控、审计要求高的系统（例如本项目）应该用外键，删除策略默认 RESTRICT；真正到了分库分表的规模，再在应用层补偿，并接受它的代价。原文作者的总结是“高并发时可以用代码替代，但得做好兜底”，这一句话说对了方向，面试时要能接着说出兜底具体是什么：唯一约束、写入路径的统一封装、定期巡检。

</details>

### 题 4：一个系统的表应该怎么拆？联合主键 `(user_id, post_id)` 上，还要不要给 `user_id` 单独建索引？

来源：掘金《一个博客系统，为什么要拆成 6 张表？》，2026-08-26（https://juejin.cn/post/7678157950376378383）。

<details>
<summary>完整答案</summary>

**拆表的依据是业务实体和实体间的关系，不是“哪种写法快”**。把文章、用户、评论、点赞全塞进一张宽表，开始时看起来省事，但每一行都很宽，同一个用户的信息会重复存很多份，改名要改很多行，数据量一大，查询和扩展都很难。

**拆的方法**：

1. **实体各一张表**：用户、文章、标签这类独立存在的东西。本项目里是客户公司、运维部门、问题分类、用户、工单、材料和处理事件。
2. **一对多：外键放在多的一侧**：一篇文章有多条评论，`comments.post_id`。本项目里一张工单可附多份日志，外键放在材料表的 `ticket_id`。
3. **多对多：建关系表**：用户点赞文章，`user_like_post(user_id, post_id)`，两列组合成主键，天然保证同一个人不能对同一篇文章点赞两次。
4. **当前状态和历史要不要分开**：本项目的工单表和处理记录表就是这样拆的。

**索引问题：`user_id` 不需要单独建，`post_id` 需要**。B-tree 复合索引按列的顺序排序，先按 `user_id` 排，`user_id` 相同时再按 `post_id` 排。所以只按第一列 `user_id` 查询时，可以直接用这个联合主键的索引（最左前缀）；只按第二列 `post_id` 查询时用不上，因为 `post_id` 相同的行分散在索引的各处。

在 PostgreSQL 16 里实测（2000 个用户 × 50 篇文章，共 10 万行）：

```text
-- 只按第一列 user_id 查：用上了联合主键的索引
Bitmap Index Scan on user_like_post_pkey   Index Cond: (user_id = 42)

-- 只按第二列 post_id 查，且没有单独索引：全表扫描
Seq Scan on user_like_post   Filter: (post_id = 7)

-- 给 post_id 建索引后再查
Index Scan using user_like_post_post_id_idx   Index Cond: (post_id = 7)
```

多建一个 `user_id` 的单列索引不仅没用，还会让每次点赞和取消点赞多维护一棵索引树，浪费空间和写入性能。D4 会在工单表上做同样的实验：复合索引 `(status, priority)` 能支撑哪些查询、不能支撑哪些。

</details>

### 题 5：软删除和硬删除怎么选？软删除有哪些坑？

来源：掘金《数据库数据删除策略：硬删除 vs 软删除的最佳实践指南》，2025-01-13（https://juejin.cn/post/7459279998395744267）。

<details>
<summary>完整答案</summary>

**两者的区别**：硬删除用 `DELETE` 把行从表里移除，无法从数据库恢复；软删除只做标记，例如加一个 `deleted_at` 字段，查询时过滤掉已删除的行。

**怎么选**：

- 需要恢复、需要审计、被其他数据引用的业务数据，用软删除或者干脆不删。
- 临时数据、日志明细、有隐私合规要求必须真正删除的数据，用硬删除。例如用户要求注销账号并删除个人信息时，只做标记是不合规的，要么真删，要么把个人字段抹掉。

**软删除的坑**，原文提到了前两个，后三个是面试时能拉开差距的地方：

1. **每个查询都要记得加过滤条件**。漏一处，已删除的数据就出现在列表里。ORM 的全局过滤或者数据库视图可以减少遗漏，但联表查询时仍然容易漏。
2. **表会越来越大**。需要定期把很久以前删除的数据归档到历史表。
3. **唯一约束会冲突**。用户名唯一，用户 A 被软删除后，新用户想用同一个用户名，会被唯一约束拦住，因为旧行还在。PostgreSQL 的解决办法是部分唯一索引：`CREATE UNIQUE INDEX users_username_active ON users (username) WHERE deleted_at IS NULL`，只在未删除的行之间保证唯一。PostgreSQL 16 实测：软删除 alice 后，可以再插入一个 alice，表里同时有两行；再插第三个未删除的 alice，报 `duplicate key value violates unique constraint "users_username_active"`。
4. **外键约束失去意义**。被停用的问题分类仍然存在，外键依然允许工单引用它。删除时要在应用层检查，或者限制只能关联未删除的数据。
5. **用状态和事件描述业务结果**。用户在已复核后点击“未解决”，应记录反馈并退回原处理人。删除旧单再新建会割裂日志和历史。用户验收时间与记录归档时间也各有含义。

</details>

### 题 6：主键用自增 ID、UUID 还是雪花 ID？雪花 ID 有哪些风险？

来源：掘金《雪花算法 ID 重复了？惨痛教训：请勿轻易造轮子！》，2025-05-22（https://juejin.cn/post/7507203999102648360）。这是一次订单号重复的线上事故复盘。

<details>
<summary>完整答案</summary>

**三种方案的对比**：

| 方案 | 优点 | 缺点 | 适合 |
|---|---|---|---|
| 自增整数 | 小、快，按插入顺序递增，索引写入效率最高 | 暴露业务量；接口里可以按顺序遍历；多个库合并数据时冲突；分库后要额外协调 | 单库、内部系统、不对外暴露 ID 的场景 |
| UUID v4 | 全局唯一，应用里随手生成，不暴露信息 | 16 字节；完全随机，大量插入时 B-tree 索引页频繁分裂，写入变慢、索引变大 | 写入量不大，或者对 ID 的随机性有要求 |
| UUID v7 | 前 48 位是毫秒时间戳，大致按时间递增，索引写入接近自增；仍然全局唯一 | 能从 ID 看出大致的创建时间 | 大多数新系统的默认选择 |
| 雪花 ID | 64 位整数，比 UUID 小；按时间有序；分布式环境下各节点独立生成 | 要正确分配机器号、处理时钟回拨；自研极易出错 | 需要整数 ID 的高并发分布式系统 |

**雪花 ID 的结构和风险**：标准结构是 1 位符号 + 41 位毫秒时间戳 + 10 位机器号 + 12 位序列号。风险集中在两处：

1. **时钟回拨**：服务器时间被 NTP 校正回退，时间戳变小，可能生成和之前重复的 ID。成熟实现会检测回拨，短时间内等待，时间长了就报错拒绝生成。
2. **机器号重复**：多个实例用了同一个机器号，同一毫秒内就会撞号。

原文的事故三个问题同时发生：自研实现把时间戳只留了 31 位，大约 24.85 天就会循环一轮；机器号取 IP 地址的最后一段，不同网段的机器很容易相同；WorkId 和 DataCenterId 都没配置，全是 0。结果是 ID 大面积重复。

**原文的两条建议值得记住**：不要自研这类通用组件，用成熟的实现；不要把业务标志拼进 ID 里，业务信息单独存字段，ID 只负责唯一标识和排序。

**本项目的选择**：主键用 UUID v7，单库场景下没有必要引入雪花 ID 的复杂度；另设 `ticket_no` 给人看，格式是 `T日期-序号`。两者分开，编号格式以后怎么改都不会影响外键。

</details>

### 题 7：请求进入 NestJS 后会依次经过哪些环节？全局配置写在哪里，为什么测试里要再写一遍？

来源：掘金《〈NestJS 从入门到资深〉书稿（Markdown）》，2026-04-17，第 2 章练习题“画出请求从进入到返回的链路，标注 Guard/Pipe/Interceptor/Filter 在哪里生效”（https://juejin.cn/post/7629246556790439974）。这些你已经会用，这道题练的是讲清楚。

<details>
<summary>完整答案</summary>

**顺序**：

```text
请求
 → Middleware          和路由无关的通用处理，例如生成 requestId
 → Guard               鉴权、权限；不通过就到此为止（通常 401 或 403）
 → Interceptor（前）    计时、超时、缓存
 → Pipe                参数校验和类型转换；失败返回 400
 → Controller 方法 → Service
 → Interceptor（后）    包装响应，例如今天的 { data }
 → 响应
任何一步抛出异常 → Exception Filter → 统一的错误响应，例如今天的 { error: { code, message } }
```

注册在不同层级时，从外到内执行：全局 → 控制器 → 路由；Interceptor 的“后”半段顺序反过来。

**常被追问的两点**：

1. **Guard 和 Middleware 都能做鉴权，为什么选 Guard？** Middleware 执行时还不知道请求会落到哪个方法，读不到方法上的 `@Roles('admin')` 这类元数据；Guard 能拿到执行上下文，知道将要调用哪个类的哪个方法。
2. **全局配置写在哪里？** 两种方式。一种是在 `main.ts` 里调用 `app.useGlobalPipes()` 等方法，这种配置不属于任何模块，测试模块不会执行 `main.ts`，所以测试里拿不到。今天的做法是把它们收进 `configureApp(app)`，`main.ts` 和接口测试都调用它。另一种是在模块的 providers 里用 `APP_PIPE`、`APP_FILTER` 这类令牌注册，它属于模块，测试导入 `AppModule` 时会一起生效，而且这些全局组件可以依赖注入其他服务。需要注入依赖的全局组件（例如要读配置的过滤器），用第二种。

</details>

## 三、用新项目做口述变式

1. 甲、乙公司的单都归网络部，为什么要存两个归属？从公司管理员和部门负责人各自的查询条件讲起，再解释为什么材料下载也要复用工单的可见范围。
2. 一条合法的“已复核”记录可以通过数据库约束，为什么接口还可能要拒绝？分别说明外键验证什么、行约束验证什么，以及前态和操作者由谁检查。
3. 已完成工单是否一定有处理人？用 Agent 给出建议、提单人确认的路径反驳，再举出必须有处理人的状态。补充用户验收和成功方案发布分别由谁决定。

# D106面试题：Agent运行时与Run状态模型

## 一、题库原题与原文答案

关联题：本地《2026海外岗前端AI架构师面试.pdf》第6页，第4题“如何设计一个 AI Agent 的状态机？如何处理多步任务中的中断与恢复？”。这是本周最直接对应的题库原题；原文站在前端视角（IndexedDB、AbortController、UI 同步），本章把同一问题放到服务端持久化状态上。

<details><summary>原文（只调整排版）</summary>

4. 如何设计一个 AI Agent 的状态机？如何处理多步任务中的中断与恢复？​
难度：★★★
考点：复杂状态管理
答案要点：
AI Agent 涉及思考、行动、观察的循环（ReAct 模式），需要一个强类型的状态机来管理。​
•
状态建模：定义 Idle、Thinking、Acting、Awaiting_User、Success/Fail 等明确状态。​
•
序列化存储：将 Agent 的执行轨迹（Trace）实时持久化到 IndexedDB，支持刷新页面后恢复进
度。
•
中断机制：利用 AbortController 实现任务撤回，并记录中断时的断点数据。​
•
循环检测：前端需监控 Agent 是否陷入死循环（如反复执行同一个失败操作），并及时介入。​
常见坑：
•
状态更新与 UI 渲染不同步，导致 Agent 已经结束但界面仍显示加载中。​
•
忽略了多窗口同步问题，用户在 A 窗口的操作影响了 B 窗口的 Agent 状态。​
追问：
•
你会选择哪个状态管理库（如 XState, Zustand）来实现 Agent 逻辑？为什么？​

</details>

<details><summary>补充讲解与纠偏</summary>

原文的状态建模、轨迹持久化、中断机制、循环检测四点都成立，但它默认 Agent 跑在浏览器里。放到服务端，有四处要改：

1. **状态的权威副本在服务端**。原文把轨迹存 IndexedDB 以支持刷新恢复；本章存在 `agent_runs` 表里，刷新、换设备、换客户端看到的都是同一份事实，前端只是读。原文提到的“多窗口同步”问题也因此消失——所有窗口读同一行。
2. **状态集合要收敛**。原文列的 `Idle/Thinking/Acting/Awaiting_User/Success/Fail` 把单步阶段和整体生命周期混在一起。本章 Run 只留五个状态，`Thinking`/`Acting` 属于 Step 的阶段（D107），`Awaiting_User`（人工审批）是 W19 的主题。
3. **中断不只是 AbortController**。`AbortController` 只让本进程停止等待；服务端还要把“已取消”写进库（带版本条件），否则工作者可能继续推进。已经发出的外部副作用不会回滚，这要靠工具层的幂等（W17）。
4. **循环检测应该在服务端有硬上限**。原文让前端“监控并及时介入”，但前端可以关掉。本章的 `stopReason` 已经预留 `step_limit`/`time_limit`/`token_limit`，D108 会在服务端强制执行。

原文的追问“选哪个状态管理库”在服务端不适用：状态机本身是一张常量表加三个纯函数，真正的难点是并发控制（条件更新）和持久化一致性（CHECK 约束），不是库的选择。

</details>



## 项目面试与自检

### 1. 运行成功能否把已给建议的工单标为已完成？

运行记录说明 Agent 是否结束。工单依据用户反馈或人工动作推进。

### 2. 两端都返回 HTTP 200 能说明迁移成功吗？

需要逐题核对来源与拒答，用同一题集保存迁移前后的差异。

### 3. 超时回退能否自动放宽检索范围？

回退仍带原范围，授权失败和下游不可用分别记录。

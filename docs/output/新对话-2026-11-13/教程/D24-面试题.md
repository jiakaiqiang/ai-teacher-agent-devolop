### 题 1：缓存穿透、缓存击穿、缓存雪崩的风险及应对

出处：《2026美团前端全栈开发》第 10 页，二面第 8 题“Redis 在你的项目里主要起什么作用？”的“常见坑”（D22 面试题 1 是主问题，D23 面试题 1 是它的追问）。

**原题**：常见坑：缓存穿透、缓存击穿、缓存雪崩的风险及应对。

<details>
<summary>本教程答案</summary>

**先把三个词分清楚**，面试官最常追问的就是区别：

| 问题 | 数据存在吗 | 失效的键 | 风险 |
|---|---|---|---|
| 穿透 | **不存在** | 缓存里永远没有 | 持续地打数据库，常见于恶意请求 |
| 击穿 | 存在 | **一个**热点键过期或被删 | 一瞬间大量请求同时查同一份数据 |
| 雪崩 | 存在 | **一大批**键同时过期，或 Redis 整个不可用 | 一瞬间大面积请求打到数据库 |

**应对，用本项目的实现回答**：

- **穿透 → 空值缓存**。设备信息查不到时，缓存字符串 `'null'` 30 秒。实测同一个不存在的编号请求两次，数据库只查一次；去掉空值缓存后查两次。空值的过期时间要短，否则之后新建的数据要很久才能查到。攻击者每次换新编号时空值缓存没用，要靠参数校验、布隆过滤器、限流。
- **击穿 → 重建锁**。工单统计未命中时，用 `SET lock:<key> 1 PX 5000 NX` 抢锁，抢到的去查数据库，其余每 20ms 看一次缓存，最多等 1 秒，等不到就自己查。实测 20 万张工单、50 个并发冷启动：没锁时查库 50 次，中位耗时约 300ms（单次查询只要 28.6ms，慢在连接池排队）；有锁时查库 1 次，所有请求约 55ms 拿到结果。
- **雪崩 → 过期时间加随机数**。统计缓存 60 秒加 0-10 秒随机，各班组的统计不会在同一秒过期。Redis 整个不可用的情况，本项目所有缓存操作都回退到数据库，接口不报错但数据库要承担全部请求；规模大的系统靠 Redis 高可用和熔断降级。

**最后说取舍**：三个开关不是都要打开。本项目的权限缓存一个都没开：用户 id 来自验证过的令牌，不会被随便编造（不怕穿透）；每个用户一个键，不是热点（不怕击穿）。按数据的特点选，比“全加上”更能体现理解。

</details>

## 二、网络最新题

### 题 2：缓存穿透、击穿、雪崩，线上怎么排查、怎么处理？

来源：掘金《Redis缓存三大经典问题的排查与处理》，2026-08-17（https://juejin.cn/post/7674783303250411571）。原文按“现象、排查、解决”分别讲了三个问题，并给了 Java 示例代码。

<details>
<summary>完整答案</summary>

**排查**（原文的思路，值得记住）：

- **穿透**：数据库 CPU 升高但慢查询里没有明显的慢 SQL（查的都是不存在的数据，很快返回空）；某个接口缓存命中率接近零而请求量很大；Redis 的 `INFO stats` 里 `keyspace_misses` 远高于 `keyspace_hits`。
- **击穿**：数据库压力出现**周期性的尖峰**，间隔和某个键的过期时间吻合；慢查询集中在同一个条件上。
- **雪崩**：数据库 CPU 和连接数突然飙升，**整体**命中率断崖式下跌；或者 Redis 连接直接报错。

本项目对应的观察点是 `CacheService.stats`（命中、未命中、错误次数），D27 会把命中率展示出来。

**处理**：穿透用空值缓存加布隆过滤器，击穿用互斥锁或逻辑过期，雪崩用随机过期时间加 Redis 高可用、熔断降级、缓存预热。和题 1 一致，不再重复。

**原文有几处要纠正或补充**：

1. **互斥锁代码没抢到锁时“睡 50ms 再递归调用自己”，没有次数上限**。抢到锁的请求如果查得很慢或者失败了，其他请求会一直递归下去。本项目的做法是最多等 1 秒，等不到就自己查。
2. **互斥锁代码在 `finally` 里直接 `del` 锁**。查询超过锁的过期时间（原文是 10 秒）后，锁可能已经被别的请求重新抢到，这时删掉的是别人的锁。防击穿时后果只是多查一次数据库；用锁保护“只能做一次”的事情时，要用唯一值加 Lua 脚本释放（D25）。
3. **逻辑过期代码的刷新锁 `setnx(refreshLock, "1")` 没有过期时间**。刷新任务所在的进程如果崩溃，`finally` 不会执行，刷新锁永远不会释放，这个键以后再也不会被刷新，用户一直拿到越来越旧的数据。加锁一定要带过期时间：`SET key value NX EX 10`。
4. **原文说“Redis 4.0 以后通过 RedisBloom 模块原生支持布隆过滤器”**。4.0 引入的是模块机制，布隆过滤器要另外加载 RedisBloom 模块（或者使用带模块的发行版），不是 Redis 自带的命令。本项目用的 `redis:7-alpine` 镜像实测执行 `BF.RESERVE` 返回 `ERR unknown command 'BF.RESERVE'`。面试时说“用 RedisBloom 模块”更准确。
5. **原文说命中率“95% 以上算健康”**。这是经验值，取决于数据特点：工单统计 60 秒过期，每个班组每分钟至少一次未命中，访问量小的班组命中率不可能很高，但这不是问题。看命中率要结合访问量和过期时间。

</details>

### 题 3：防击穿用互斥锁，并发很高时还能用吗？锁的超时应该设多大？

来源：掘金《高并发下如何防缓存击穿？90% 的人死在面试第一个追问上》，2026-06-05（https://juejin.cn/post/7647708270295384074）。原文以电商大促的热点商品（单键峰值 3000 请求/秒、PHP-FPM 多进程）为例，比较了 Singleflight、互斥锁、逻辑过期三种方案，并列出 5 个追问。原文的完整答案放在作者的公众号里，正文没有给出，下面的答案由本教程编写。

<details>
<summary>完整答案</summary>

**原文的结论**：PHP-FPM 每个请求在独立进程里，进程内的 Singleflight 合并不了；单键并发不高时用互斥锁；并发很高、能接受短暂的旧数据时用逻辑过期。

**互斥锁在高并发下的代价是等待**。没抢到锁的请求要等缓存写好才能返回，延迟约等于“一次查询的时间加上一次轮询间隔”。本项目实测：单次统计查询 28.6ms，轮询间隔 20ms，50 个并发请求全部在 53-58ms 内返回。并发再高，等待时间不会变长（大家等的是同一次查询），但等待期间轮询会给 Redis 带来更多 `GET`。原文说 3000 并发时“P99 劣化 100-200ms”，这取决于查询本身多慢和轮询间隔，不是互斥锁固有的。

**原文追问的回答**：

1. **锁的超时设多大**：要明显长于一次正常的查询（本项目查询约 30ms，锁 5 秒）。太短：查询还没结束锁就过期了，又有请求抢到锁去查，防护失效。太长：抢到锁的进程崩溃后，在锁过期之前，这个键的每次未命中都要让请求等满等待上限。所以还要有**等待上限**（本项目 1 秒），和锁的超时分开设置。
2. **逻辑过期怎么防止多个请求同时触发重建**：同样要抢一把刷新锁，抢到的才去后台刷新，其余直接返回旧值；刷新锁也必须有过期时间（题 2 第 3 点）。
3. **重建失败（数据库超时）怎么办**：互斥锁方案里，失败的请求释放锁后报错，下一个请求重新抢锁再试；要防止持续打数据库，可以在失败后短时间内缓存一个“失败”标记，或者对重建做限流。逻辑过期方案里，刷新失败就继续返回旧值，等下次再刷新。
4. **进程内合并（Singleflight）和 Redis 锁的区别**：进程内合并靠同一个进程里共享的 `Map`，只在本进程有效；Node.js 是单进程事件循环，一个实例里用 `Map<key, Promise>` 就能实现，但部署多个实例时每个实例还是各查一次。Redis 锁所有实例共享。两者可以叠加：进程内先合并，每个实例只派一个请求去抢 Redis 锁。
5. **大促前怎么预热**：提前把热点键写进缓存，并且过期时间加随机数，避免预热的键同时过期（又变成雪崩）。对极热点的键可以不设过期时间，由后台任务定时刷新。

**面试时的回答顺序**：先说互斥锁怎么实现（`SET NX PX`、等待上限、Redis 不可用时降级）；再说代价是等待，给出实测数字；然后说并发更高、能接受旧值时用逻辑过期；最后说多实例下进程内合并和 Redis 锁的配合。

</details>

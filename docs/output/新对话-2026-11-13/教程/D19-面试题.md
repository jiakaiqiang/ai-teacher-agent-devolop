## 一、网络最新题

### 题 1：敏感字段怎么处理？掩码和加密有什么区别？

来源：掘金《数据脱敏 - 03 字段脱敏：字段级掩码与加密实战，敏感字段到底该怎么处理》，2026-09-26（https://juejin.cn/post/7689258467467919403）。原文是一个系列的第 3 篇，讲字段掩码、字段加密、接入方式（白名单还是手动）和“脱敏反而搞坏数据”的场景。

<details>
<summary>完整答案</summary>

**两种能力，用途不同**（原文的核心结论）：

| | 掩码 | 加密 |
|---|---|---|
| 例子 | `13800000001` → `138****0001` | `13800000001` → `ENC_9f3ae2…` |
| 能否还原 | 不能 | 能，用密钥解 |
| 保护什么 | 展示、缓存里不出现明文 | 传输链路、存储里不出现明文 |

原文的一句话分工：掩码管“端内”（展示），加密管“链路”（传输）；只做一层都有缺口。

**常见字段的掩码规则**（原文的表格）：手机号前 3 后 4；身份证前 3 后 4；姓名保留首字；银行卡前 4 后 4；邮箱保留首字符和域名。本项目的手机号规则就是前 3 后 4。

**最隐蔽的坑：掩码值被当成有效值回传**。页面上显示的是 `138****0001`，用户编辑资料时没改手机号，前端把这个值原样提交，后端就把号码改坏了。原文的做法是给回传的掩码值加 `MASK_` 前缀，后端识别后跳过更新。本项目更简单：修改手机号的接口用 `@Matches(/^1\d{10}$/)` 校验，掩码值里有 `*`，直接 400，前端必须提交用户真正输入的值。

**接入方式：在哪里做脱敏**。原文比较了“按接口登记白名单”（拦截器按 URL 找到要处理的字段）和“在每个调用点手动处理”，结论是按接口粒度混合使用。本项目的出参脱敏用的是第三种：**按字段名在所有出口统一处理**。

| 做法 | 新接口忘了处理时 | 代价 |
|---|---|---|
| 每个接口手动处理 | 泄露（本项目反证实验 A 实测：流转接口漏了） | 靠人记得 |
| 按接口登记白名单 | 泄露（没登记的接口不处理） | 维护一张表 |
| 所有出口按字段名统一处理（本项目） | 默认遮住 | 敏感字段的命名必须统一；需要显示明文的接口要显式豁免 |

原文的白名单是针对**入参加密**的，那里“默认不处理”是为了不影响存量接口，是合理的取舍；**出参展示**更适合“默认遮住”，因为漏遮的代价是泄露，多遮的代价只是不方便。

**原文另一个值得记住的细节**：加密失败的降级上报“只带原因码，绝不带字段值”，否则上报通道本身就成了泄露渠道。这和本项目的日志脱敏是同一个思路。

</details>

## 二、题库原题

### 题 2：在电信业务场景下，AI 前端如何处理数据安全和隐私保护？

出处：《2026电信前端AI工程师面试》第 8 页（第 2 题）。

**原题**：2. 在电信业务场景下，AI 前端如何处理数据安全和隐私保护？（难度：★★★，考点：数据安全、合规性）

<details>
<summary>原文答案</summary>

> 答案要点：
> 电信数据敏感度高，前端需配合后端建立多重防护体系。
>
> - 脱敏处理：在发送 Prompt 前，通过正则或本地模型识别并拦截手机号、身份证等敏感信息。
> - 传输加密：全量使用 HTTPS，对敏感 Payload 进行二次加密。
> - 权限控制：严格校验会话 Token，防止越权访问历史对话。
> - 审计日志：记录用户的所有输入输出行为，用于事后溯源，但前端不存储敏感明文。
>
> 常见坑：
>
> - 将敏感信息缓存在 localStorage 中被恶意脚本读取。
> - 在报错日志中泄露了用户的输入内容。
>
> 追问：
>
> - 如果需要在前端实现本地脱敏，你会选择什么技术方案？

</details>

<details>
<summary>本教程补充：用 W3 的实现逐条对应，并回答追问</summary>

原文的每一条，本项目都有对应的实现，面试时可以逐条举例：

| 原文要点 | 本项目 |
|---|---|
| 发送前脱敏 | W7 接入模型时要做；今天的 `redactForLog` 是雏形（手机号、令牌、密码哈希） |
| 传输加密 | HTTPS 在 W6 部署时配置；本地开发走 Vite 代理 |
| 权限控制，防止越权访问 | D15 令牌、D16 权限点、D17 班组范围（越权返回 404） |
| 审计日志 | D18，只追加；D19 起审计里只存脱敏后的值 |
| 坑：localStorage 被恶意脚本读取 | D15 的取舍：令牌放 sessionStorage，XSS 仍能读到，讨论过 HttpOnly Cookie |
| 坑：报错日志泄露用户输入 | 实测 Prisma 的校验错误信息会带出同一次调用的参数值（`phone: "13800000001"`），全局过滤器写日志前经过 `redactForLog` |

**原文“审计日志记录用户的所有输入输出”要补充一点**：记录输入输出用于溯源是对的，但审计本身也是敏感数据的集中地。本项目的审计只记快照的几个字段，个人信息只记脱敏后的值（反证实验 B 实测，存完整号码时测试失败）。对 AI 应用来说，对话内容可能包含大量个人信息，更要分级：审计记“谁在什么时候问了什么类型的问题”，原文存到有访问控制、有保留期的单独位置。

**追问：前端本地脱敏用什么方案？**

1. **规则优先**：手机号、身份证、银行卡、邮箱、IP 这类有固定格式的，用正则识别，快、可预测、可测试。
2. **替换成占位符，而不是直接删除**：`13800000001` 换成 `[手机号1]`，发给模型；模型的回答里出现 `[手机号1]` 时，前端再换回原值显示给用户。这样模型能理解“这里有一个手机号”，回答也不会断。映射表只存在当前页面的内存里。
3. **规则识别不了的（人名、地址）**：可以用浏览器端运行的小模型做命名实体识别，代价是体积和速度；或者在后端统一做。
4. **前端脱敏只是第一道**：用户可以绕过前端直接调接口，后端发给模型之前必须再做一次。这和 D13 的“前端隐藏按钮只是体验”是同一个道理。

</details>

## 三、补充题

### 题 3：（补充题）脱敏应该放在哪一层？

本题没有对应的网络原文，来自讲义 1.2 和反证实验 A 的实测。

<details>
<summary>完整答案</summary>

| 层 | 做法 | 问题 |
|---|---|---|
| 数据库 | 视图或者存储时就只存掩码 | 存掩码就再也拿不到原值了（组长要看完整号码）；视图难以按“当前用户的权限”变化 |
| Service | 每个方法返回前处理 | 出口很多，总有一个漏掉。实测只在详情接口脱敏，流转接口返回的详情里是完整号码 |
| 出口拦截器（本项目） | 所有接口的返回值都经过它 | 要靠字段名识别，命名必须统一；需要明文的接口显式豁免 |
| 前端 | 页面上显示时遮住 | 完全无效：接口返回的已经是明文，打开浏览器开发者工具就能看到 |

**本项目的选择和配套规则**：

1. 拦截器按 `SENSITIVE_KEYS` 处理，`phone` 是唯一的敏感字段名，新的敏感字段要在这里登记。
2. 有 `contact:read` 权限的人看完整的；`@Unmasked()` 只用在“返回的一定是当前用户自己的数据”的接口上。
3. 审计、日志是另外两个出口，分别在写入时用 `maskPhone`、`redactForLog` 处理。
4. 导出 Excel、发消息通知、发给大模型都是出口，以后加的时候都要走同样的规则。

**一句话**：找出数据离开系统的所有出口，在出口处统一处理，并且让“没处理”的默认结果是安全的。

</details>

### 题 4：（补充题）日志里怎么避免出现敏感信息？

本题没有对应的网络原文，来自讲义 1.4 的实测。

<details>
<summary>完整答案</summary>

**泄露的来源比想象的多**：

- 打印整个请求体、整个用户对象。
- 异常信息带出了参数。本项目实测：给 Prisma 的 `update` 传一个类型错误的参数，错误信息里原样列出了同一次调用的其他参数，包括 `phone: "13800000001"`。
- 打印请求头，里面有 `Authorization: Bearer ...`。
- 第三方库的调试日志。

**三层做法**：

1. **不记**：不打印请求体和整个对象；用用户 id 做关联，不用手机号；令牌、密码永远不打印。这是最根本的。
2. **结构化日志加字段过滤**：日志库支持按字段名脱敏（例如 pino 的 `redact` 选项配置 `req.headers.authorization`），比在文本上用正则可靠。W6 做可观测性时会换成结构化日志。
3. **文本兜底**：本项目的 `redactForLog` 用正则擦掉手机号、JWT、scrypt 哈希，处理“异常信息里意外带出的内容”。实测上面那条 Prisma 错误信息处理后变成 `phone: "138****0001"`。

**正则兜底的局限**：只能识别有固定格式的内容；误伤（11 位的订单号也会被当成手机号遮住）；漏网（换个格式就认不出来）。所以它只是兜底，不能代替第 1 条。

</details>

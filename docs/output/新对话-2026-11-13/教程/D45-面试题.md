## 1. 题库原题：Node中间层处理LLM长连接要注意什么？

<details><summary>原题与原文答案</summary>

6. Node.js 作为全栈中间层，在处理 LLM 长连接请求时有哪些需要注意的地方？
难度：★★
考点：Node.js 后端开发、流处理
答案要点：
Node.js 需处理好流的转发、超时管理以及内存压力，确保高并发下的稳定性。
•
流转发：使用 stream.pipe() 或 pipeline() 将模型响应直接导向客户端，避免全量内存缓冲。
•
超时控制：设置合理的 Socket 超时，防止模型响应过慢导致连接堆积。
•
异常捕获：监听 stream 的 error 事件，防止因模型侧断开导致 Node 进程崩溃。
•
安全校验：在中间层进行 Token 鉴权和敏感词过滤（Moderation）。
常见坑：
•
忘记设置 res.setHeader('Content-Type', 'text/event-stream')。
•
未处理客户端主动断开连接的情况，导致后端继续消耗 Token。

</details>
<details><summary>补充与完整答案</summary>

从鉴权与行范围开始，避免把不可见工单送上游；只取必要字段，服务器保管密钥。然后按流增量解码、验证协议、转换应用事件，区分发头前JSON错误和发头后SSE错误。要限制输入、单帧、总字节及输出，清理reader，并把下游取消、总/空闲超时和应用关闭传给上游。

原文直接pipe适合保持相同协议的透明转发，但本项目要检查结束语义、改事件契约和隐藏供应商细节，因此用转换器。socket超时也不能替代完整请求预算；Moderation不是简单关键词过滤，本文没有实现模型内容审核。今天临时15秒signal，D46才统一生命周期。

**追问**：Node非阻塞就不会被高并发压垮吗？不会阻塞线程不等于连接、缓冲或供应商预算无限，仍需配额、背压和观测；本章未验证压力上限。

</details>

## 2. 网络提炼：为什么SSE适合增量文本，为什么不能直接重连生成？

<details><summary>完整答案</summary>

一次POST提交问题，服务端持续返回文本增量，符合请求后单向输出。fetch可带JWT头和JSON body；原生EventSource不提供这些自定义选项。SSE格式本身没有“自动恢复同一次生成”的语义；自动重发POST可能重复生成和计费，需要生成ID与可恢复事件日志才能谈续接。

文章中的id/retry只提供客户端重连线索，服务端仍需保存并按游标重放，不能凭一个id保证不丢数据。SSE也不局限于HTTP/1.1；应用帧与传输版本分开。[SSE规范](https://html.spec.whatwg.org/multipage/server-sent-events.html)。

**追问**：W5通知与本周助手的重连策略为何不同？通知有持久通知行与序号补读；助手目前没有持久生成记录，所以不做自动续接或重试。

</details>

## 3. 项目题：怎样防止模型读取越权工单？

<details><summary>完整答案</summary>

沿用JWT 和 ticket:report，再把visibleTickets合入ticketNo查询。查不到统一404，模型源尚未打开。白名单仅ticketNo、category、description 和 logs，不传联系人详情或完整事件；问题限制长度并拒绝额外role/model/baseURL参数。标题仍可能含敏感文本，所以白名单不等于内容安全，练习只能使用模拟工单。

```json
{"case":"scope-before-model","status":404,"upstreamCalls":0}
```

反证删scope后实际从404变200，说明前端隐藏不能代替后端范围控制。

**追问**：原始业务权限会不会在15秒生成中被撤销？当前只在请求开始检查，缓存还有既有边界；没有持续重新鉴权的证明，生产要求需另行定义。

</details>

## 4. 项目题：怎样确定回答真的结束了？

<details><summary>完整答案</summary>

上游文本增量来自delta.content，空choices可用于usage尾块。本客户端只支持单choice文本；stop或length后再见DONE才发应用done。length仍是预算截断，不能改为stop。非法JSON、未知结束原因、工具调用、拒绝或EOF缺终止均error，保留已经发出的delta。

```json
{"case":"loopback-stream","contextFields":["priority","status","ticketNo","title"],"upstreamCalls":1,"eventTypes":["meta","delta","delta","done"]}
```

```json
{"case":"interrupted-stream","eventTypes":["meta","delta","error"],"last":{"type":"error","code":"MODEL_PROTOCOL_ERROR"}}
```

这是本文严格兼容子集，真实供应商若省略DONE会被拒绝，需要有依据的适配，不凭EOF猜成功。meta的model模式在测试中仍指回环模拟上游，不是质量证据。

**追问**：done后为什么取消reader？业务已得到终止，不应无限等多余传输数据；生成器return触发D44 finally清理。

</details>

## 5. 项目题：怎样验证错误通道和范围控制？

<details><summary>完整答案</summary>

用真实Nest和隔离数据库跑401/403/404/400，断言源未调用；用回环HTTP检查实际请求最小字段和stream:true。完整响应为meta→delta→done，截断流为meta→delta→error；发头前异常返回JSON503且不泄漏异常文本。

反证A删除scope：

```text
 FAIL  test/assistant.e2e-spec.ts > 工单AI助手出口（D45） > 跨客户不可见工单404且不调用模型
Error: expected 404 "Not Found", got 200 "OK"
```

反证B在EOF补done：

```text
 FAIL  test/assistant.e2e-spec.ts > 工单AI助手出口（D45） > 上游EOF中断后只发error，不能伪造done
AssertionError: expected { type: 'done', finishReason: 'stop' } to deeply equal { type: 'error', …(1) }

- Expected
+ Received

  {
-   "code": "MODEL_PROTOCOL_ERROR",
-   "type": "error",
+   "finishReason": "stop",
+   "type": "done",
  }
```

同测试先过、原字节与SHA-256恢复及复测记录在讲义第三节。完整回归固定空模型环境，不会因为本机将来填密钥就自动调用外部服务。

**追问**：流式200错误是否进入普通5xx指标？不会直接等同HTTP5xx，需要独立流事件指标；本章没有新增助手事件指标，不能用现有HTTP成功率衡量回答成功率。

</details>

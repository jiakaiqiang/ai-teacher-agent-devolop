## 1. 题库原题：多轮中断与重新生成状态机

<details><summary>原题与原文答案</summary>

5. 如何实现一个支持“多轮对话中断”和“重新生成”的状态机？
难度：★★★
考点：逻辑设计、状态机
答案要点：


通过定义明确的状态（Idle, Generating, Paused, Error）和 Action 来管理复杂的对话流。
•
中止逻辑：利用 AbortController 关联 Fetch 请求，在用户点击“停止”时触发 abort()。
•
覆盖更新：重新生成时，需定位到当前消息 ID，清空后续内容并重新触发流式请求。
•
历史回溯：支持修改历史提问，此时需要截断后续对话树，发起新的分支请求。
•
幂等性：确保多次点击重新生成不会导致状态错乱。
常见坑：
•
请求已 abort 但前端状态未重置，导致 UI 卡死。
•
重新生成时未处理好 Token 消耗的统计。

</details>
<details><summary>补充与完整答案</summary>

先定义单次请求的connecting/streaming及completed/truncated/stopped/interrupted/error终态，再定义会话层的消息ID、分支和历史。停止是终止当前请求，除非有恢复协议不能叫可续接Paused。重新生成是新请求，会消耗新的预算；需要保留或替换哪些历史必须由产品规则决定。

本周只做单次工单建议，不提前实现多轮树。stop保留部分，reset清空，dispose清监听与资源；busy拒重复点击，但这只是前端互斥，不能称服务端业务幂等。每次回调与finally检查请求序号和身份。

**追问**：没有多轮会话还能谈状态机吗？可以，状态机描述单次生成状态及允许转换，复杂度由需求决定，不必先引入大型库。

</details>

## 2. 网络提炼：序号与AbortController能互相替代吗？

<details><summary>完整答案</summary>

取消用于减少继续做无用工作，序号用于决定结果是否仍属于当前请求。旧Promise可能已完成、回调已排队，或第三方transport不支持取消，因此二者配合。比较token还不足以隔离同一用户两次请求，序号才区分A/B。finally也要保护，避免旧请求清掉新controller。

原文只取消旧请求的方案没有对最终render再检查归属；流示例每块新建decoder会损坏跨块字符，且声明服务端自动停止生成过强，取决于取消传播。文中fetchWithTimeout在fetch完成头部时清计时器，也没有覆盖后续body消费；D46预算贯穿模型流。

原样隔离证据：

```json
{"case":"old-request-isolation","text":"新内容","status":"completed","oldAborted":true}
```

**追问**：abort后catch应该一律静默吗？只有已被用户停止或替代的旧请求应静默；当前请求的超时/网络中断需要明确状态，不能隐藏全部异常。

</details>

## 3. 项目题：前端怎样知道模型完成？

<details><summary>完整答案</summary>

检查200和SSE媒体类型，按D44读取完整事件，校验schema、event/type及meta首帧。delta只追加；done.stop完整完成、done.length截断；error根据是否有正文分error/interrupted。EOF没终止报STREAM_INTERRUPTED，不在finally设置completed，也不自动重发POST。

```json
{"case":"frontend-contract","eventTypes":["meta","delta","done"],"finishReason":"length"}
```

反证去掉EOF抛错，Promise错误resolve：

```text
 FAIL  src/api/assistant.spec.ts > 助手POST流读取（D47） > EOF无终止时拒绝，不把部分输出当成功
AssertionError: promise resolved "undefined" instead of rejecting

- Expected:
Error {
  "message": "rejected promise",
}

+ Received:
undefined
```

**追问**：error之后又来了done怎么办？消费方在第一个合法终止事件return并取消reader，不再接受后续帧。

</details>

## 4. 项目题：切用户、切工单和停止如何处理？

<details><summary>完整答案</summary>

用户停止保留部分正文并invalidate序号；新请求reset清空再开始。身份token变化同步reset、abort并让旧回调失效。旧401只有请求token仍为当前token才清会话，避免alice过期请求注销bob。工单路由变化由D48组件watch调用reset，卸载dispose；今天模块本身不知道路由。

反证只去掉序号检查：

```text
 FAIL  src/composables/useAssistant.spec.ts > 助手界面状态（D47） > 主动停止保留部分，晚到旧帧不能污染新请求
AssertionError: expected '新内容迟到污染' to be '新内容' // Object.is equality

Expected: "新内容"
Received: "新内容迟到污染"
```

**追问**：浏览器刷新能恢复建议吗？本章不存对话，刷新丢失；不是漏做持久化，后续会话设计另有范围。不能把sessionStorage里登录令牌和AI回答历史混为一谈。

</details>

## 5. 项目题：测试如何避免被mock藏住竞态？

<details><summary>完整答案</summary>

请求层用真实Response/ReadableStream夹具检查协议，状态层注入可控制emit/resolve/reject的transport。故意让它无视abort，A停止后B开始仍让A迟到，验证旧delta、旧finally都不会污染B；再测切用户、当前/旧401、重复提交、无终止返回和dispose。

这能验证状态规则，不能证明浏览器渲染、焦点或网络取消。两个反证先过基线、单点改坏、原字节与hash恢复，记录见讲义。D48要用真实浏览器把组件接线再验证一遍。

**追问**：只用快照测试文本够吗？不能覆盖时间交错，必须明确控制完成顺序，并检查文字、busy和取消句柄归属。

</details>

## 一、题库原题与原文答案

关联题：本地《2026已发交个朋友全栈AI工程师.pdf》第6页，第5题“如何实现一个 AI Agent 的工具调用（Function Calling）流程？”。本周题目都在服务边界上，题库没有对应原题；选这道题是因为下周（W16）进入Agent运行时，它正好承接本周的“参数校验与权限边界”。

<details><summary>原文（只调整排版）</summary>

5. 如何实现一个 AI Agent 的工具调用（Function Calling）流程？​
难度：★★★
考点：Agent 逻辑、JSON Schema、状态机​
答案要点：
Function Calling 允许模型根据需求调用外部 API，实现从“思考”到“行动”的跨越。​
•
步骤：定义工具函数描述（JSON Schema） -> 发送给 LLM -> LLM 返回 call_info -> 前端/后端执
行本地函数 -> 将结果回传给 LLM。​
•
前端需要维护一个“执行中”的状态，展示工具调用的进度（如“正在搜索天气...”）。​
•
异常处理：如果工具执行失败，需要将错误信息反馈给模型让其重试。
•
安全性：严格校验模型返回的参数类型，防止执行恶意代码。
常见坑：
•
递归调用陷阱：模型不断调用工具进入死循环。
•
忽略了多工具并行调用的场景。
追问：
•
怎么在 UI 上优雅地展示 Agent 的思考过程（Thought Process）？​

</details>

<details><summary>补充讲解与纠偏</summary>

原文的步骤（定义JSON Schema → 交给模型 → 模型返回调用意图 → 执行 → 回传结果）和两个坑（递归调用死循环、忽略并行调用）都成立，W10做过有界工具循环。

把它和本周的服务边界对照，有三点可以直接复用：

1. **模型返回的参数是不可信输入**。原文说“严格校验参数类型”，本周的做法更具体：严格模型拒绝未知字段与隐式类型转换，涉及权限范围的参数必填可空（漏传422而不是放大范围）。
2. **执行工具的权限不来自模型**。本周Python只认服务令牌、不认用户；W16的工具调用同样不能让模型决定“以谁的身份执行”。
3. **每一跳都要有上限和超时**。原文的递归死循环对应本周的超时分层与请求体上限：轮数、并发、字节数、时限都要有明确的上限，并且外层比内层长。

</details>

## 二、项目与网络关联题

### 1. 用两分钟讲清本周做了什么。

<details><summary>完整答案与追问</summary>

把检索链路的编码与向量存取迁到Python，并用对照证明效果不变。
顺序是：先定FastAPI契约与服务令牌（严格入参、固定错误码、不回显输入），再接本机Ollama编码（规则与Node逐条对齐，向量逐元素相同），再用pymilvus读写同一个集合（主键含内容版本、班组过滤只来自解析后的UUID、每次调用外套截止时间），然后NestJS加后端开关调用它（切片与复核不动），接着补故障面（请求体上限、统一错误体、gRPC错误映射，十步故障注入），最后用W12的固定评测跑迁移前后对照，指标与逐题排名完全一致。默认后端仍是node。

</details>

### 2. 这次迁移最容易出但不会报错的问题是什么？

<details><summary>完整答案与追问</summary>

两边输入处理不一致。
查询要加任务指令、文档不加、禁用截断、按码点计长度——少任何一条，向量仍是1024维、照样能写进同一个集合、接口照样200，只是检索质量下降。所以必须有逐元素向量对照（D100）和固定评测对照（D104），不能靠“接口通了”判断迁移成功。D105的变式二同理：读侧少一行版本比对，结果看起来正常，引用的却是过期内容。

</details>

### 3. 跨服务调用的失败面你怎么覆盖？

<details><summary>完整答案与追问</summary>

按“谁的错”分层，每种失败都有固定码和实测。
4xx是调用方：422入参、401令牌、413请求体超限（512KiB，依据最大合法请求实测约393KB）。5xx是服务端或上游：502上游不可用或契约不符、504上游超时、500兜底。NestJS侧另有`BRIDGE_UNAVAILABLE`（连不上）和`BRIDGE_TIMEOUT`。实测十步：桥接未启动、错令牌、两种超大请求、停Ollama、停Milvus，各记录码与耗时；依赖恢复后同一进程自动可用。所有错误都不带上游正文、地址和令牌。

</details>

### 4. 为什么说“客户端配了timeout”不等于有超时保护？

<details><summary>完整答案与追问</summary>

因为它可能不覆盖所有失败路径，必须实测。
pymilvus 2.5.18的`AsyncMilvusClient(timeout=2)`指向不可达端口时，`load_collection`在8秒外层超时内都没返回，单独运行超过6分钟。所以每次调用外面再套`asyncio.timeout(10)`。同理httpx2要显式`trust_env=False`，否则开发机的代理变量会把回环请求转走。结论：接入新客户端时，先用一个不可达地址和一个停掉的依赖各试一次。

</details>

### 5. 一个功能从A服务迁到B服务，怎么做到可回退？

<details><summary>完整答案与追问</summary>

开关、并存、对照、不改默认。
`RETRIEVAL_BACKEND`默认node，python需显式设置，拼错直接抛错而不是静默回退；两条路径共用同一个集合和同一套复核逻辑，所以回退不需要改数据；对照在独立集合上跑，避免互相覆盖造成假一致。切默认前还要补真实数据重建对照和并发观察。

</details>

### 6. Python服务不认用户权限，安全吗？

<details><summary>完整答案与追问</summary>

这是边界设计：它只认服务令牌，不做授权判断。
它绑定回环地址、要求至少32字符的服务令牌（两端都校验）、只返回坐标与版本不返回正文；用户权限由NestJS在调用前（决定传哪个班组或不调用）和调用后（按权限、状态、版本、坐标复核）两次把关。班组过滤只是缩小候选的第一道限制，不是授权。未做的是令牌轮换与审计，已写进验证范围。

</details>

### 7. 本周的性能数字能怎么用？

<details><summary>完整答案与追问</summary>

只能说明量级没变，不能当性能结论。
固定评测里单题耗时Node p50 399.6ms、Python p50 399.5ms（p95分别431.2、465.3），样本14题、单次运行、无并发、未丢弃预热。可以说“多一跳HTTP没有改变单次检索的量级”；要给延迟结论需要固定并发、多轮重复、完整分布和交替运行。简历里引用必须附条件。

</details>

### 8. 网络复盘：本周纠正过哪些资料里的说法？

<details><summary>完整答案与追问</summary>

三处。
一是2026-10-10[HTTPX用法文章](https://juejin.cn/post/7694632392433401882)在请求函数里`async with httpx.AsyncClient()`，每次新建连接池，等于放弃了它自己推荐的复用；服务里应在lifespan创建一次。二是2026-03-05[Semaphore文章](https://juejin.cn/post/7613282719574261810)把并发上限当成避免第三方QPS限制的手段；Semaphore限制同时在途数，短任务一秒内可完成多轮，限QPS需要按时间计数的限流。三是2026-04-10[Milvus与pgvector文章](https://juejin.cn/post/7626581199797026851)把“结合业务条件过滤”说成pgvector独有的顺手之处；Milvus同样支持标量过滤（本周就用`groupId`过滤并实测只返回本班组），两者真正的差别在于能否与业务数据同事务。另外多篇文章把`Depends`称作装饰器，实测它是函数、返回标记对象；“校验失败返回422”只对请求成立，响应模型校验失败实测是500。

</details>

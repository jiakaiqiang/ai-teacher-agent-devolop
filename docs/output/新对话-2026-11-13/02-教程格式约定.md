# 教程格式约定

确认日期：2026-11-13。来源：用户本轮确认。

## 每章教程的组成

1. **知识点讲解**：把本章要用到的知识点逐个讲清楚。
2. **代码示例**：每个知识点配可运行的示例代码，用来说明用法和原理。
3. **用户开发**：用户根据讲解和示例，自己动手实现本章功能。AI 不往用户的项目里写代码。
4. **本章完整源码**：给出本章涉及的全部源码，每段代码都标明文件路径和名称，方便开发完成后对照。
5. **关联面试题**：放在教程最后，分两部分。
   - **题库原题**：从大厂面试题目录中按与当天知识点的关联性挑选。每题给出**原题原文**、**原文答案**（摘自 PDF，标来源文件和页码），再给出补充讲解：结合本项目展开，并纠正原答案中过时或不准确的地方。
   - **网络最新题**：后端、Agent 等题库覆盖不足的方向，从网上查找最新的面试题（优先近一年），给出题目和**完整答案**。每题标来源链接和发布日期；答案由教程编写，不照搬原文。
6. **个人建议**：结合用户画像和当天知识点，指出用户容易出错或需要加强的地方，以及怎样把当天内容讲进面试和简历。
7. **拓展知识点**：和当天内容相关、值得往下深挖的知识点，说明为什么要学、学到什么程度。

## 网络题目来源

- 2026-11-13 实测：Claude Code 的 `web_search` 和 `WebFetch` 都返回 API 错误（`requires adaptive thinking`），属于工具配置问题；Bing 返回的结果和查询无关。
- 可用的渠道是掘金：搜索接口 `api.juejin.cn/search_api/v1/search` 能按关键词返回文章列表，文章页面是服务端渲染，可以直接抽取正文。抓取结果存在 `.cache/网络面经/`，已被 git 忽略。
- 掘金有反爬：连续抓取十几篇后会返回校验页面，需要隔一段时间再抓。
- 只采用能抓到正文的文章作为题目来源。只拿到标题、没读到正文的，会明确标注。
- 面经文件名不代表企业官方题库。

## 学习闭环（2026-11-13 起采用，见 [改进建议](04-教程架构改进建议.md)）

- **每天两个文件**：讲义 `DXX-主题.md` 在工作日用；`DXX-面试题.md` 放完整的题库原题、原文答案和网络题，周日用。讲义末尾只保留 3 道核心题的题目和答题要点，并链接到面试题文件。
- **工作日 2 小时**：开头回忆 10 分钟 → 知识点 35 分钟 → 动手 55 分钟 → 自检与提交批改 20 分钟。讲义要标出必做和选做，并给出超时预案：时间不够时先砍哪些。
- **开头回忆**：3 道题，分别来自昨天、3 天前、7 天前的内容，不看资料作答，答案折叠。D1 没有前序内容，改为环境体检。
- **提示阶梯**：需要自己写代码的步骤，下面各给三级折叠提示：方向 → 关键 API 和文档位置 → 伪代码。三级都看过仍写不出来，才看完整源码，并记一次“需要复测”。只执行命令的步骤，改为给“常见问题”。
- **提交批改**：用户说“DX 提交了”，我读 `D:\demo\ops-ticket` 的实际 diff、跑测试、对照验收标准，再逐题追问 3 到 5 个问题，每次一题。我只读不改用户的代码。批改结果和薄弱点记进 [错题本](学习记录/错题本.md)，分别在 1 天、3 天、7 天后复测，连续答对两次才移出。

## 写作要求

- 代码带简洁的中文注释。
- 涉及新建文件时，开头先给出本章的目录结构。
- 完整源码必须和讲解中的示例、目录结构保持一致，并在发布前实际运行验证。

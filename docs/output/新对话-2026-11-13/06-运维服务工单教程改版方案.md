# 运维公司客户服务工单 · 教程改版方案

## 一、业务目标与角色

一家运维公司服务多家客户公司。用户遇到问题，提交工单，先从 Agent 获得基于日志和资料的排查帮助。需要人工介入时，由运维公司内部接手。同一张单保留问题、已尝试的步骤、处理结果和用户反馈。用户确认有效的方案，经部门负责人审核，可以成为下一次排查的资料。

| 角色 | 可以做什么 | 数据范围 |
|---|---|---|
| 运维公司账号管理人员 | 给客户公司开通管理员账号 | 被服务的客户公司和管理员账号 |
| 客户公司管理员 | 审批本公司的用户注册申请，查看本公司全部工单 | 本公司 |
| 普通提单人（含客户和第三方人员） | 注册时选择所属公司，获批后按问题分类、描述及日志报障，查看进度、申请人工、反馈结果 | 本人提交的工单 |
| 运维部门负责人 | 接收按分类转入的工单，指派本部门内部运维人员，复核人工结果，审核共享知识草稿 | 本部门承办的工单，可来自多家客户 |
| 内部运维处理人 | 阅读交接材料、记录处理过程、提交结果，继续处理被退回的工单 | 分派给本人的工单 |
| Agent | 识别意图，结合本单日志和 RAG 证据排查，给出建议或显示人工接入入口 | 当前工单、允许使用的资料和已发布案例 |

## 二、工单如何流转

| 起点 | 触发动作 | 结果和下一位操作人 |
|---|---|---|
| 用户报障 | 已获批的用户提交问题分类、描述和日志等材料 | 创建工单并启动 Agent。问题分类决定人工承办部门 |
| Agent 处理中 | Agent 给出解决步骤 | 等待提单人验证。点“已解决”即已完成，点“未解决”即进入该部门负责人待派单列表 |
| Agent 处理中 | 资料不足、无法给出可用方案，或诊断服务失败 | 显示“人工接入”。提单人点击后，同一工单才进入负责人待派单列表 |
| 待派单 | 负责人指派内部处理人 | 人工处理中。处理人可读原问题、日志、Agent 排查步骤和已有反馈 |
| 人工处理中 | 处理人提交结果 | 已处理，等待负责人复核 |
| 已处理 | 负责人复核通过并发送结果 | 已复核，通知提单人验证 |
| 已复核 | 提单人点“已解决”或“未解决” | 已解决则已完成。未解决直接回原处理人，重新处理后再交负责人复核 |
| 已完成 | 系统提炼有效方案，交对应运维部门负责人审核 | 审核通过的通用步骤进入共享知识库。审核期间，原工单已经完成 |

课程设计建议：负责人复核不通过时，也将理由退回原处理人。Agent 直接帮助用户解决的工单，知识草稿按同一问题分类找到审核部门。这两条用于补齐教程中的退回和送审路径。

## 三、按原教学目标逐周修改

课程面向已有约七年 Vue 经验、会搭建 NestJS 和写接口的学习者。25 周约 500 小时，依次训练全栈、AI 前端、AI 全栈、Python 桥接和企业级 Agent 开发。第 13 周形成可投 AI 全栈岗位的作品，第 25 周用两条作品线答辩并投 Agent 方向。工单规则决定案例写什么，每周原定的工程能力决定学员要亲手实现什么、拿什么证据说明自己会了。[原路线阶段总览](03-路线大纲.md) · [用户确认的起点和目标](01-用户画像与记忆汇总.md)

### 修改范围和课时安排

优先重写 D01、D08、D11、D17、D29、D62、D74–D76、D123–D124、D146 的业务规则、参考实现和验收。随后沿共享类型、数据库状态、队列事件、检索来源和工具权限查找依赖，同步相应的集成日、面试题和周复盘。分页、Python 基础、流式解析、容器、代理等原理课按引用到的字段和样例调整。D104、D160、D167 这类对照实验要基于新版固定数据重新跑，结论以新结果为准。

沿用原定工作日 2 小时（回忆 10 分钟、知识点 35 分钟、动手 55 分钟、自检与提交 20 分钟），周六 5 小时集成，周日 5 小时复盘。注册页面、普通表单、工作台外观给需求和参考实现，工作日的手写时间用于当天的技术难点。讲义与面试题仍按天配对，提供分级提示与章末源码。提交后以学员实际 diff、测试和逐题口述批改，错题按第 1、3、7 天复测。表中的验收证据放入原有练习和周六集成，不另设考核周。[教程格式约定](02-教程格式约定.md) · [已确认的课时安排](04-教程架构改进建议.md)

### 用 D11 检查改版是否教到了原知识点

原练习模拟告警请求已落库但响应丢失。新版让客户发起提单，服务端已经创建成功，浏览器却因网络中断再次提交。学员要亲手设计幂等键和唯一约束，验证并发重试得到同一工单号，并解释为什么同一键换了描述应该报冲突。面试仍追问“请求超时后怎样证明没有重复写入”。只做按钮防连点无法通过这个练习。[D11 原讲义](教程/D11-幂等与告警上报.md)

## 四、改写顺序与验收

1. 先调整路线大纲的业务主线、角色表、状态表和分类到部门的映射。验证工程先实现共享类型、数据库模型和状态流转，再同步 D01、D08 和 D17 的讲义、源码与面试题。旧版“已关闭”没有用户验收证据，若复用旧数据，保留原状态来源，不能据此生成成功案例。
2. 用两家客户、一名负责人和两名内部运维人员贯穿前六周。分别从提单人、客户管理员和运维人员的正常页面操作，检查列表、详情、下载、按钮和通知。两次点击“人工接入”应只出现一项派单待办。
3. 接通 Agent 和 RAG，核验两个不同的入口：Agent 无法处理时等待用户点击“人工接入”；用户反馈建议“未解决”时直接转人工。若稍后才收到旧的 Agent 响应，应保留已进入的人工状态。
4. 将工单复核与知识审核做成两条独立记录。验收时让用户在负责人复核后点“未解决”，检查原处理人收到任务。再次处理、复核、用户确认后才生成知识草稿。分别验证审核拒绝、审核通过，以及另一家客户检索已发布方案的结果。
5. 按周同步验证工程、每日代码、面试题、周复盘和教程进度表。旧版的实测数字属于旧场景；新版用相应的接口、界面和检索用例重新验证后，再写入新的结果。

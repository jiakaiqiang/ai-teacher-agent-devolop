0. 今天在 90 天路线中的位置

承上：

  • Day 1 建立了 AgentEvent 事件流和 reducer 状态机
  • Day 2 为事件类型加上了 zod schema 运行时校验
  • Day 3-4 实现了指标读取与图表渲染
  • Day 5-6 建立了 WebSocket 实时推送 + 心跳重连

启下：

  • Day 8 会把今天的异常事件写入告警中心
  • Day 15 会用今天的确定性测试跑历史数据回归
  • Day 30 会用今天的领域事件模式扩展多种检测算法

今天的核心： 在服务端对 WebSocket 推送前的指标数据做异常检测，通过 NestJS DI → 领域事件 → 确定性测试三个递进层次，保证异常告警的正确性、可测性和可扩展性。

1. 今天要交付的功能模块

1.1 用户能看到什么

在 p1-monitor 运维监控系统的服务器详情页：

  1. 实时告警：CPU/内存超过阈值时，图表上出现红色标注点
  2. 趋势告警：连续 5 个点显著偏离历史均值（Z-Score > 3）时，出现黄色警告
  3. 告警去重：同一异常在 5 分钟内只上报一次，不刷屏
  4. 可回溯：切换到"告警历史"页面，可以看到每条告警的原始数据和检测规则

关键：告警必须"稳定复现"——同一份历史数据回放，产生的告警集合完全一致，不能靠调阈值掩盖 bug。

1.2 这个模块在项目里承担什么

在 p1-monitor 项目中的定位：

  • 架构层：领域层（domain），负责业务规则的核心逻辑
  • 依赖方：Day 8 告警中心、Day 15 历史回放都依赖今天的检测规则
  • 被依赖方：今天依赖 Day 2 的 MetricSnapshot 类型、Day 5 的 WebSocket Gateway

为什么是 Day 7：

  • Day 1-6 建立了"数据传输管道"，但数据本身没有业务判断
  • 今天开始加入"业务规则层"，必须处理 NestJS DI 生命周期 + 领域事件解耦 + 确定性测试问题
  • 这些问题在 Day 8 告警中心会更复杂，所以先在检测算法这个纯逻辑场景练习

1.3 三版演进的目标（v1 / v2 / v3）

版本 核心目标 用户体验 技术关键点
v1 简单阈值检测 CPU > 80 就告警 if 判断
v2 Z-Score 统计检测 显著偏离均值时告警 滑窗均值 + 标准差
v3 领域事件 + DI 隔离 + 确定性测试 检测规则可插拔，测试稳定复现 NestJS Provider + EventEmitter

痛点演进：

  • v1 痛点：阈值写死、单值判断、不同服务器共用阈值不合理
  • v2 痛点：滑窗数据放在 Service 里成为跨请求共享状态，并发时串台
  • v3 终态：REQUEST scope 隔离状态 + 领域事件解耦告警和检测 + 固定样本集测试

3. v1：最小闭环（阈值检测）

3.1 v1 要实现什么

用户视角：

  • CPU > 80% 时上报告警
  • 内存 > 90% 时上报告警

技术视角：

  • 一个函数 if (metric.value > threshold) return true
  • 阈值写死在代码里

3.2 v1 完整代码

backend/src/domain/anomaly/detectors/threshold-detector.ts（v1 版本）

import type { MetricSnapshot } from '@/domain/metrics/metric.types'

/**
 * v1: 简单阈值检测
 * 缺点：阈值写死、不同服务器共用阈值不合理
 */
export function detectByThreshold(metric: MetricSnapshot): boolean {
  const thresholds = {
    cpu: 80,
    memory: 90,
    network: 100,
    disk: 500,
  }
  return metric.metric.value > thresholds[metric.type]
}

backend/src/anomaly/anomaly.service.ts（v1 版本）

import { Injectable } from '@nestjs/common'
import { detectByThreshold } from '@/domain/anomaly/detectors/threshold-detector'
import type { MetricSnapshot } from '@/domain/metrics/metric.types'

@Injectable()
export class AnomalyService {
  check(metric: MetricSnapshot): boolean {
    return detectByThreshold(metric)
  }
}

3.3 v1 用到的知识点

  1. NestJS @Injectable：

    • 解决的问题：让 Service 可以被 DI 容器管理
    • 运行机制：装饰器在启动时注册 provider
    • 项目落点：AnomalyService
    • 生产误区：忘记加装饰器，注入时报错 "Nest can't resolve dependencies"
    • 验证方法：nest start 无 error 且能被注入

  2. 纯函数检测器：

    • 解决的问题：把业务规则从框架里剥离，可以 Node.js 直接测
    • 运行机制：输入 metric，输出 boolean
    • 项目落点：detectByThreshold
    • 生产误区：在纯函数里 import 框架（@nestjs/common）
    • 验证方法：vitest run detectors/*.spec.ts（无 NestJS 依赖）

3.4 v1 暴露的痛点

痛点 1：阈值写死

生产不同服务器负载不同（Web 服务器 CPU 70% 就异常，计算服务器 90% 才异常），阈值应该按服务器配置。

痛点 2：单值判断，误报率高

一个瞬时的 CPU 90% 不代表异常（可能是短暂任务），需要看趋势（连续 5 个点偏离均值才算异常）。

痛点 3：检测和告警耦合

AnomalyService.check 返回 boolean，调用方需要自己判断"要不要发告警"、"要不要写库"，逻辑分散。

4. v2：加统计层（Z-Score 检测）

4.1 v2 要实现什么

用户视角：

  • CPU 值显著偏离最近 20 个点的均值时告警（Z-Score > 3）
  • 减少瞬时抖动的误报

技术视角：

  • 维护每个 serverId 的滑窗历史（最近 20 个点）
  • 计算均值、标准差
  • 判断 abs((x - mean) / stddev) > 3

4.2 v2 完整代码

backend/src/domain/anomaly/detectors/zscore-detector.ts（v2 版本）

import type { MetricSnapshot } from '@/domain/metrics/metric.types'

export interface ZScoreResult {
  isAnomaly: boolean
  zscore: number
  mean: number
  stddev: number
}

/**
 * Z-Score 检测：判断当前值是否显著偏离历史均值
 * 需要至少 5 个历史点才能计算
 * 阈值：|Z-Score| > 3（3σ 原则）
 */
export function detectByZScore(
  history: readonly number[],
  current: number,
  threshold = 3,
): ZScoreResult {
  if (history.length < 5) {
    return { isAnomaly: false, zscore: 0, mean: current, stddev: 0 }
  }
  
  const mean = history.reduce((sum, v) => sum + v, 0) / history.length
  const variance = history.reduce((sum, v) => sum + (v - mean) ** 2, 0) / history.length
  const stddev = Math.sqrt(variance)
  
  if (stddev === 0) {
    return { isAnomaly: false, zscore: 0, mean, stddev: 0 }
  }
  
  const zscore = (current - mean) / stddev
  return {
    isAnomaly: Math.abs(zscore) > threshold,
    zscore,
    mean,
    stddev,
  }
}

  1. Z-Score 算法：

    • 解决的问题：判断单点是否显著偏离历史

    • 验证方法：detector 测试不 import NestJS

4.4 v2 暴露的痛点

痛点 1：DI 单例导致跨请求串台

AnomalyService 默认是 singleton scope，this.history 是全局共享的。并发场景下，请求 A 的滑窗数据被请求 B 的写入污染，检测结果串台。

痛点 2：检测和告警耦合

check 返回 boolean 后，调用方还要自己决定"要不要写 anomaly 表、要不要发通知"，逻辑散在多个地方。

痛点 3：测试不稳定

滑窗依赖调用顺序，同一测试脚本重跑结果可能不同（前一个测试留下的历史污染下一个测试）。

5. v3：生产就绪（领域事件 + DI 隔离 + 确定性测试）

5.1 v3 要实现什么

  • 问题 1：跨请求串台 → REQUEST scope，每请求新实例
  • 问题 2：检测和告警耦合 → 领域事件，AnomalyDetectedEvent 派发给多个订阅者

  • 问题 4：检测规则不可插拔 → Detector 接口 + 多个实现

backend/src/domain/anomaly/detectors/zscore-detector.ts

import type { MetricSnapshot } from '@/domain/metrics/metric.types'
import type { Detector, DetectionContext } from './detector.interface'
import type { Anomaly } from '../anomaly.types'

const Z_THRESHOLD = 3
const MIN_HISTORY = 5

function computeZScore(history: readonly number[], current: number): number {
  const mean = history.reduce((s, v) => s + v, 0) / history.length
  const variance = history.reduce((s, v) => s + (v - mean) ** 2, 0) / history.length
  const stddev = Math.sqrt(variance)
  return stddev === 0 ? 0 : (current - mean) / stddev
}

export const zscoreDetector: Detector = {
  ruleId: 'zscore-v1',
  detect(metric, ctx): Anomaly | null {
    if (ctx.history.length < MIN_HISTORY) return null
    
    const zscore = computeZScore(ctx.history, metric.metric.value)
    if (Math.abs(zscore) <= Z_THRESHOLD) return null
    
    return {
      id: `anomaly-${metric.id}-zscore`,
      metricId: metric.id,
      serverId: metric.serverId,
      metricType: metric.type,
      ruleId: 'zscore-v1',
      severity: Math.abs(zscore) > 5 ? 'critical' : 'warning',
      zscore,
      detectedAt: new Date().toISOString(),
    }
  },
}

backend/src/anomaly/anomaly.service.ts（v3，REQUEST scope）

import { Injectable, Scope } from '@nestjs/common'
import { EventEmitter2 } from '@nestjs/event-emitter'
import { thresholdDetector } from '@/domain/anomaly/detectors/threshold-detector'
import { zscoreDetector } from '@/domain/anomaly/detectors/zscore-detector'
import { AnomalyDetectedEvent } from '@/domain/anomaly/anomaly.events'
import type { MetricSnapshot } from '@/domain/metrics/metric.types'
import type { Anomaly } from '@/domain/anomaly/anomaly.types'

@Injectable({ scope: Scope.REQUEST })
export class AnomalyService {
  // REQUEST scope: 每个请求独立实例，history 不会跨请求污染
  private history = new Map<string, number[]>()
  private detectors = [thresholdDetector, zscoreDetector]
  
  constructor(private readonly events: EventEmitter2) {}
  
  check(metric: MetricSnapshot): Anomaly[] {
    const key = `${metric.serverId}:${metric.type}`
    const hist = this.history.get(key) ?? []
    
    const anomalies: Anomaly[] = []
    for (const detector of this.detectors) {
      const anomaly = detector.detect(metric, { history: hist })
      if (anomaly) {
        anomalies.push(anomaly)
        this.events.emit(AnomalyDetectedEvent.type, new AnomalyDetectedEvent(anomaly))
      }
    }
    
    // 更新滑窗（保留最近 20 个点）
    this.history.set(key, [...hist, metric.metric.value].slice(-20))
    
    return anomalies
  }
}

5.4 v3 用到的知识点

  1. NestJS Scope（REQUEST / DEFAULT / TRANSIENT）：

    • 解决的问题：控制 Provider 实例的生命周期，避免跨请求状态污染
    • 运行机制：DEFAULT 是单例，REQUEST 每请求新实例，TRANSIENT 每次注入新实例
    • 项目落点：AnomalyService 用 Scope.REQUEST
    • 生产误区：REQUEST scope 的 Service 在 EventListener（默认 DEFAULT）里注入会拿到旧实例，必须用 moduleRef.resolve
    • 验证方法：并发跑 50 个请求，检查每个请求的 history 是否独立

  2. 领域事件（Domain Events）：

    • 解决的问题：解耦发生方和处理方，一个事件可以被多个订阅者处理
    • 运行机制：EventEmitter2.emit(type, payload) → 所有 @OnEvent(type) 方法被调用
    • 项目落点：MetricCreatedEvent、AnomalyDetectedEvent
    • 生产误区：把事件类型写成字符串魔术值，改名时漏改；应该用类的 static 属性
    • 验证方法：单元测试用 spyOn(events, 'emit') 验证被调用

  3. 领域层与应用层分离：

    • 解决的问题：核心业务规则不依赖框架，可以脱离 NestJS 独立测试
    • 运行机制：domain/anomaly/* 只用 TypeScript，anomaly/* 用 NestJS
    • 项目落点：detectors 是纯函数，AnomalyService 是 Provider
    • 生产误区：在 detector 里 import { Injectable }
    • 验证方法：grep -r 'from.*@nestjs' src/domain/ 应该无结果

  4. 接口 + 多实现（策略模式）：

    • 解决的问题：检测规则可插拔，加新规则不改 Service
    • 运行机制：Detector 接口 + 多个实现对象 + Service 遍历执行
    • 项目落点：detector.interface.ts + thresholdDetector/zscoreDetector
    • 生产误区：把所有规则的 if-else 写在 Service 里
    • 验证方法：加新规则时只需新增一个 detector 对象，不改 Service

  5. 纯函数检测器与可测性：

    • 解决的问题：算法逻辑可以在 Node.js 直接测，不需要 NestJS TestingModule
    • 运行机制：输入 (metric, ctx)，输出 Anomaly | null，无副作用
    • 项目落点：thresholdDetector.detect / zscoreDetector.detect
    • 生产误区：在 detector 里 console.log 或读环境变量，测试不稳定
    • 验证方法：vitest run src/domain/anomaly/detectors/*.spec.ts 无 NestJS 依赖

  6. 确定性测试（固定样本）：

    • 解决的问题：测试结果不依赖运行时间、执行顺序，随时可复现
    • 运行机制：把测试输入放 JSON 文件，测试代码读 JSON 断言
    • 项目落点：fixtures/*.json + spec.ts
    • 生产误区：用 new Date() 生成时间戳，测试结果每次不同
    • 验证方法：连续跑 10 次测试，结果完全一致

  7. Z-Score 与统计学：

    • 解决的问题：单点判断异常时，避免瞬时抖动误报
    • 运行机制：(x - mean) / stddev，绝对值 > 3 表示统计上极端
    • 项目落点：computeZScore 函数
    • 生产误区：stddev = 0 时不做保护会除零；history < 5 时算 Z-Score 不可靠
    • 验证方法：用 [10,10,10,10,10] 序列 + current 100，应该返回 stddev=0 分支

  8. EventEmitter fire-and-forget vs emitAsync：

    • 解决的问题：区分"派发即可返回"和"等所有监听器处理完"的场景
    • 运行机制：emit 立即返回，emitAsync 等所有异步 handler 完成
    • 项目落点：metrics.service 用 emit（不阻塞主流程）
    • 生产误区：在 handler 里抛异常，emit 会吞掉，需要监听 error
    • 验证方法：故意在 handler 里抛异常，验证主流程不受影响

情境题 1：乱序 + 重复 metric 导致误报刷屏

背景： 异常检测输入包含乱序时间点和重复 Metric，算法把下降趋势判断为上升，10 分钟产生 300 条重复告警。

任务： 请用原始序列、排序前后数据、确定性测试和领域事件日志定位；先暂停自动建异常止损，再修复时间排序和去重不变量，并用上升、下降、少样本、重复样本固定集验证。

回答框架（定位证据 → 临时止损 → 根因修复 → 回归验证）：

  1. 定位证据：

    • 抓取原始 metric 序列：kubectl logs metrics-service | grep "metric.created"
    • 对比排序前后的 timestamp：证明时间戳乱序
    • 领域事件日志：AnomalyDetectedEvent 短时间内 300 次

  2. 临时止损：

    • 关闭 AnomalyListener：注释 @OnEvent
    • 或加限流：5 分钟内同一 ruleId + serverId + metricType 只触发 1 次

  3. 根因修复：

    • 在 AnomalyListener 入口按 timestamp 排序历史
    • 用 metric.id 作为去重键（Set 或 Redis）
    • 见 §5.3 v3 代码

  4. 回归验证：

    • 用 out-of-order.json fixture 验证排序生效
    • 用 duplicate.json fixture 验证去重生效
    • 连续跑 10 次结果完全一致

题目 1：TypeScript 装饰器是什么？在 AI 框架中有什么潜在用途？

来源：《2026京东前端面试-大模型方向》，第 9 页。

初级答法：

  • 装饰器是函数，可以修饰类/方法/属性
  • 语法：@decorator

中级答法：

  • 装饰器在编译期被 tsc 转换为函数调用
  • 分为类装饰器、方法装饰器、属性装饰器、参数装饰器
  • 常见框架用法：NestJS 的 @Injectable、@Controller、@Get

高级答法（今天项目里的应用）：

  • @Injectable({ scope: Scope.REQUEST })：注册 Provider 到 DI 容器，控制生命周期
  • @OnEvent(MetricCreatedEvent.type)：注册事件监听器
  • AI 框架场景：LangGraph 的 @task 装饰器把普通函数变成可编排的 Node，需要装饰器机制来读取元数据

题目 2：项目中怎样处理前端异常监控？

来源：《2026美团前端架构师面试-数据权限方向》，第 10 页。

初级答法：

  • window.onerror、unhandledrejection、Vue errorHandler
  • 采集后上报到 Sentry / 自研平台

中级答法：

  • 分类：JS runtime error、Promise reject、资源加载失败、接口 500
  • 去重：按错误堆栈 hash 去重，避免刷屏
  • 采样：高频错误按比例采样

高级答法（关联今天）：

  • 今天做的是后端异常检测（指标异常），前端异常监控是同类问题
  • 都要处理："定义什么算异常"、"去重"、"回溯原始输入"
  • 前端异常也可以用领域事件模型：error.captured → 采集 → error.deduped → 上报
  • 确定性测试同样适用：固定错误样本 → 期望的采集结果

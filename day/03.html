课程总览 第 1 周

Day 03

异步与竞态（单项读取 → 四项并发 → 切换时取消与防串台）

任务版本：标准版

日期与时长：2026-07-16 周四，3h（90 分钟阅读 + 90 分钟动手）

项目：D:\demo\ai-techer\p1-monitor\frontend，配合相邻的 backend

角色视角：你已经能用 Vue 展示状态，也会用 Day 02 的合同校验一条指标。今天要判断一批合法数据属于哪一次点击。

前置课程：Day 01 事件与状态 · Day 02 领域合同

0. 今天在 90 天路线中的位置

阶段一的第一天，你根据事件决定界面能进入哪个状态。第二天，你在数据进入页面前检查了字段。现在看一个两者都能通过的故障：你点了 B，最后显示的是 A 的 CPU。A 的字段全部合法，问题出在页面把一次已经过时的读取当成了当前结果。

今天沿着一次服务器切换，从点击、发请求、校验、提交状态，一直走到屏幕。明天的四张图直接消费这里取回的时间序列。

1. 今天要交付的功能模块

1.1 用户能看到什么

在现有页面打开指标面板，默认读 srv-001。点 srv-002 后标题和加载提示一起切换。四项请求结束后，面板显示 CPU、内存、温度和磁盘 I/O 的最新读数。数据库还没有样本时显示“暂无采样”。仅温度接口出错时，另外三项照常显示，温度一行给出失败原因。

1.2 输入、输出与项目边界

后端的 src/main.ts 设置了 api 前缀，metrics.controller.ts 暴露 GET /api/metrics/recent/:serverId?type=cpu&limit=20。metrics.service.ts 按采样时间降序返回数组，最新点在下标 0。下面是一条用于读代码的响应样例：

[{"id":"42","serverId":"srv-001","metricType":"cpu","value":52,"unit":"%","timestamp":"2026-07-16T01:00:00.000Z"}]

API Client 把 JSON 交给合同层，输出一项指标的点列。加载逻辑决定这批点能否提交。Vue 面板只读当前状态。Day 04 绘制从左到右的时间轴时，可以复制点列再反转，今天保留接口的原始排序。

1.3 三版演进的目标

版本 这次加什么 怎样看出还缺什么
v1 读一台服务器的 CPU，穿过 Day 02 的合同，显示一个真实值 把写法重复四次，观察后一个请求何时才能发出
v2 同时发起四项读取，显示加载和整批结果 让 A 晚于 B 返回，观察 B 的标题下出现 A 的样本
v3 切换时取消上一批，按请求序号提交，逐项保留成功结果 用可控响应重放旧成功、旧失败、超时及空数组，核对屏幕状态

3. v1：先把数据库的一条 CPU 指标显示出来

3.1 先预测合同会在哪里拒绝

把 §1.2 的样例直接交给第二天的 toMetric。它需要 met-42、name 和领域单位 percent，而网络上传来 "42"、metricType 和 "%"。如果你把拒绝结果换成数值 0，用户会把合同错误读成“CPU 很空闲”。

3.2 v1 完整示例

在 Day 02 的 metric.schema.ts 中，把原有单位枚举扩为 z.enum(['percent', 'bytes', 'count', 'ms', 'celsius', 'MB/s'])。若你的 Domain 单独声明了单位联合，同步增加后两项。保留原有单位以继续接受第二天的合法样本。下面的 client 逐条核对服务端返回的服务器、指标名及单位，再复用 toMetric 校验值和时间戳。

src/features/metrics/metrics-client.ts（三版共用）

import { z } from 'zod'
import { toMetric } from '../../domain/contracts/adapters/dto-to-domain'

export const kinds = ['cpu', 'memory', 'temperature', 'disk_io'] as const
export type Kind = typeof kinds[number]
export type Metric = NonNullable<ReturnType<typeof toMetric>>

const rowSchema = z.object({
  id: z.string().regex(/^\d+$/),
  serverId: z.string(),
  metricType: z.enum(kinds),
  value: z.number(),
  unit: z.string(),
  timestamp: z.string(),
})

const units: Record<Kind, Record<string, string>> = {
  cpu: { '%': 'percent' }, memory: { '%': 'percent' },
  temperature: { C: 'celsius', '°C': 'celsius' }, disk_io: { 'MB/s': 'MB/s' },
}

export class ReadError extends Error {
  constructor(message: string, readonly retryable: boolean) { super(message) }
}

export async function readSeries(serverId: string, kind: Kind, signal?: AbortSignal) {
  const url = `/api/metrics/recent/${encodeURIComponent(serverId)}?type=${kind}&limit=20`
  const response = await fetch(url, { signal })
  if (!response.ok) {
    throw new ReadError(`HTTP ${response.status}`, response.status >= 500 || response.status === 429)
  }
  const json: unknown = await response.json()
  const rows = rowSchema.array().safeParse(json)
  if (!rows.success) throw new ReadError('指标列表格式错误', false)
  return rows.data.map(row => {
    const unit = units[kind][row.unit]
    if (row.serverId !== serverId || row.metricType !== kind || typeof unit !== 'string') {
      throw new ReadError('返回的服务器、指标或单位不匹配', false)
    }
    const metric = toMetric({
      id: `met-${row.id}`, serverId, name: kind, value: row.value, unit, timestamp: row.timestamp,
    })
    if (!metric) throw new ReadError('指标未通过 Day 02 合同', false)
    return metric
  })
}

3.3 知识点拆解

Event Loop。 面板发出请求后，浏览器仍能响应下一次点击。await 挂起当前异步函数，Promise 兑现或拒绝后，后半段通过微任务继续执行。浏览器有机会在任务之间渲染，await 本身不保证出现一帧新画面。先预测下面三行日志的顺序，再贴进浏览器控制台验证。第二行登记的回调会等当前同步代码跑完。

console.log('1 发起 CPU 读取')
Promise.resolve().then(() => console.log('3 继续处理结果'))
console.log('2 点击处理结束')

HTTP 成功与数据可用是两个判断。 fetch 收到 500 时仍可兑现为 Response，因此先检查 ok。200 配 [] 应该走“暂无采样”，200 配 [{"value":"52"}] 应该走合同错误。分别给 client 这两个响应，观察页面文字。到这里，页面已经能区分 0%、空数据和读失败。

3.4 触发 v2 的实验

临时将 v1 中的一次读取改为 for (const kind of kinds) await readSeries('srv-001', kind)，同时导入 kinds。在 Network 打开节流，观察后一个请求的起点。假设每项读 200 ms，串行约需 800 ms；请在自己的瀑布图上标出实测值。内存请求的参数并不依赖 CPU 的结果，它为什么要等？

4. v2：一次选择，同时读四项指标

4.1 这版要实现什么

四个请求使用同一个服务器 ID，分别取四种时间序列。保留 v1 的 client，用下面的组件替换 v1 面板。成功读数带上样本里的 serverId，方便观察“当前选择”和“实际数据来源”是否一致。

4.2 v2 完整面板

<script setup lang="ts">
import { onMounted, ref } from 'vue'
import { kinds, readSeries } from './metrics-client'

const selected = ref('srv-001')
const lines = ref<string[]>([])
async function load(id: string) {
  selected.value = id
  lines.value = ['加载中']
  try {
    const series = await Promise.all(kinds.map(kind => readSeries(id, kind)))
    lines.value = series.map((points, i) => {
      const p = points[0]
      return p ? `${p.serverId} · ${p.name} · ${p.value} ${p.unit}` : `${kinds[i]} · 暂无采样`
    })
  } catch (error) {
    lines.value = [error instanceof Error ? error.message : '读取失败']
  }
}
onMounted(() => load(selected.value))
</script>

<template>
  <button v-for="id in ['srv-001', 'srv-002']" :key="id" @click="load(id)">{{ id }}</button>
  <h2>{{ selected }}</h2>
  <p v-for="line in lines" :key="line">{{ line }}</p>
</template>

4.3 知识点拆解

并发的起点。 map 调用四次 readSeries，每次都能走到第一个 await 并发出请求。Promise.all 汇总已经启动的工作，结果数组按输入顺序排列。给温度请求加延迟，在 Network 看四项开始时间，再检查第三行仍是温度。把四个函数本身交给 Promise.all 不会启动读取。

整批失败。 若 CPU 成功、温度返回 500，聚合 Promise 会拒绝，v2 的 catch 会把面板改成一行错误。其他请求仍可完成。在 Network 暂时阻止一个指标 URL，比较“成功请求数”和“可见读数数”。这两个数字的差距就是 v3 要修的第二个问题。

4.4 触发 v3 的实验

在 v2 的 await Promise.all(...) 之后、写 lines.value 之前临时加入：

if (id === 'srv-001') await new Promise(resolve => setTimeout(resolve, 1500))

让两台服务器都有采样。点 A（001），等它的四项读取结束但还处于延迟中，立即点 B（002）。等 B 出现后再等到 A 醒来。记录标题和样本上的服务器号：

点击 A ── A 的数据到达 ────────────── A 提交 → 标题 B，样本 A
                 点击 B ── B 提交 → 标题 B，样本 B

A、B 都通过了 schema。错误发生在赋值那一行。即使此时取消 A 的网络请求，那个已经拿到结果的异步函数仍然能继续。移除临时延迟，进入 v3。

5. v3：取消上一批，只允许当前批次提交

5.1 先写下这版必须守住的规则

每次点击（包括连续两次点同一台）都有独立序号。切换时立即显示新服务器的 loading。全部成功且点数为零时进入 empty，全部失败进入 error，其他情况进入 ready，逐项展示点列、空采样或失败原因。旧批次成功、失败、超时或被取消，都不能写入当前页面。

5.2 目录与职责

沿用 §1.4 的目录。v1 的 client 已支持 signal，今天实际发请求和读响应体的地方只有 readSeries。现在增加 useMetrics.ts，把一次点击的生命周期从组件中提出来。保留 §3.2 的 client 和 §1.5 的 App 入口，下面两个文件即构成 v3 的新增与替换代码。

5.3 v3 完整加载逻辑与面板

src/features/metrics/useMetrics.ts

import { shallowRef } from 'vue'
import { kinds, readSeries, ReadError, type Kind, type Metric } from './metrics-client'

type Issue = { message: string; retryable: boolean }
type Card =
  | { kind: Kind; ok: true; points: Metric[] }
  | { kind: Kind; ok: false; issue: Issue }
type State =
  | { status: 'loading' | 'empty'; id: string }
  | { status: 'ready' | 'error'; id: string; cards: Card[] }

function explain(reason: unknown): Issue {
  if (reason instanceof ReadError) return { message: reason.message, retryable: reason.retryable }
  if (reason instanceof DOMException && reason.name === 'TimeoutError') {
    return { message: '请求超时', retryable: true }
  }
  if (reason instanceof SyntaxError) return { message: '响应不是合法 JSON', retryable: false }
  if (reason instanceof TypeError) return { message: '连接失败，请检查网络', retryable: true }
  return { message: '读取失败，请检查请求日志', retryable: false }
}

export function useMetrics(read = readSeries, timeoutMs = 5000) {
  const state = shallowRef<State>({ status: 'empty', id: '' })
  let latest = 0
  let active: AbortController | undefined

  function cancel() {
    latest += 1
    active?.abort()
    active = undefined
  }

  async function load(id: string) {
    cancel()
    const requestId = latest
    const controller = new AbortController()
    active = controller
    state.value = { status: 'loading', id }
    const timer = setTimeout(() => {
      controller.abort(new DOMException('超过读取时限', 'TimeoutError'))
    }, timeoutMs)

    try {
      const results = await Promise.allSettled(kinds.map(kind => read(id, kind, controller.signal)))
      if (requestId !== latest) return
      const cards: Card[] = results.map((result, i) => result.status === 'fulfilled'
        ? { ok: true, kind: kinds[i]!, points: result.value }
        : { ok: false, kind: kinds[i]!, issue: explain(result.reason) })
      if (cards.every(card => card.ok && card.points.length === 0)) {
        state.value = { status: 'empty', id }
      } else {
        const status = cards.every(card => !card.ok) ? 'error' : 'ready'
        state.value = { status, id, cards }
      }
    } finally {
      clearTimeout(timer)
      if (requestId === latest) active = undefined
    }
  }

  return { state, load, cancel }
}

5.4 把六个判断落到具体代码

你会遇到的现象 机制与代码落点 怎样验证自己的解释
切到 B 后，A 的四项还占着连接 每批只有一个 controller，四次 fetch 共享 signal。切换和卸载都调用 cancel 放慢响应，在 Network 里找仍在传输的 A 请求，观察取消状态。已完成的请求会保留成功记录
A → B → A，最早的 A 能通过服务器 ID 比较 每一次 load 都取得新序号。比对发生在聚合完成后、写响应式状态之前 让第一批 A 最后返回，对照 §7 的旧批次测试；两次 A 的样本值应设成不同值
A 的收尾赶在 B 读取期间执行 每批清自己的 timer，只有当前批能释放 active。清错引用会使下一次点击无法取消 B 临时无条件清空 active，让 A 收尾后再点 C，检查 B 的 signal
CPU 已成功，温度超时 超时会以 TimeoutError 中断本批未完成的 fetch；allSettled 保留已经成功的点，按输入顺序返回每项结局 只拖慢温度，等到时限；页面可同时出现 CPU 读数和温度超时
切换、500、脏 JSON 都可能结束一次等待 先按序号丢弃过期批次，再由 explain 区分当前批的 HTTP、超时、网络与合同错误。合同错误要修数据或映射 404 与 500 都能看到状态码，仅 500 可触发重试；切换导致的取消不会弹错误
空库容易被画成四个 0，或一直转圈 State 一次替换整份快照。四个成功空数组进入 empty；真实的 0 存在长度为 1 的点列中 用 [] 和 [{…, value: 0}] 分别读取，观察“暂无采样”和数值 0

读时序图。 当 A 的 HTTP 已经结束，取消能省下的网络工作可能是零。此时 §4.4 的延迟仍会到期，序号检查挡在唯一的结果提交点。另一方面，仅有序号能保住画面，旧读取仍可能占用带宽。在 §7 的两个反证里，观察取消是否传到网络，以及旧数据是否还能写入页面。MDN 的 abort 语义 · MDN 的 allSettled 返回顺序

7.6 用可控 Promise 固定返回顺序

src/features/metrics/useMetrics.spec.ts。假读取只替换网络，保留真实的状态提交代码。第一个用例故意让旧读取忽略 signal，模拟响应已经到手、后续异步工作还在继续。

import { expect, it } from 'vitest'
import { useMetrics } from './useMetrics'
import { kinds, ReadError, type Metric } from './metrics-client'

function pending<T>() {
  let release!: (value: T) => void
  const promise = new Promise<T>(resolve => { release = resolve })
  return { promise, release }
}

it('旧批次迟到时保留 B 的错误快照，同时向 A 传播取消', async () => {
  const a = pending<Metric[]>()
  const signals: AbortSignal[] = []
  const { state, load } = useMetrics(async (id, _kind, signal) => {
    if (id === 'srv-002') throw new ReadError('HTTP 500', true)
    signals.push(signal!)
    return a.promise
  })
  const first = load('srv-001')
  await load('srv-002')
  expect(signals).toHaveLength(4)
  expect(signals.every(signal => signal.aborted)).toBe(true)
  a.release([])
  await first
  expect(state.value).toMatchObject({ id: 'srv-002', status: 'error' })
})

it('当前服务器的四项均成功且无采样时显示 empty', async () => {
  const { state, load } = useMetrics(async () => [])
  const task = load('srv-001')
  expect(state.value.status).toBe('loading')
  await task
  expect(state.value.status).toBe('empty')
})

it('温度超时保留其他三项结果，可重试温度错误', async () => {
  const { state, load } = useMetrics(async (_id, kind, signal) => {
    if (kind !== 'temperature') return []
    return new Promise<Metric[]>((_resolve, reject) => {
      signal!.addEventListener('abort', () => reject(signal!.reason), { once: true })
    })
  }, 5)
  await load('srv-001')
  expect(state.value).toMatchObject({
    status: 'ready',
    cards: kinds.map(kind => kind === 'temperature'
      ? { kind, ok: false, issue: { message: '请求超时', retryable: true } }
      : { kind, ok: true, points: [] }),
  })
})

再自行补两条回归。① A → B → A，第一批最后失败，第三批成功，页面保留第三批状态；② 面板卸载后才兑现旧读取，断言已 abort 且状态对象引用不再变化。切换实验同时记录“最后一次选择”和“最后一次提交”，只截最终页面会漏掉中途短暂串台。

7.7 反证一：去掉提交前的序号判断

只注释 if (requestId !== latest) return，运行第一个测试。B 已进入 error，A 返回空数组后却把它改成 A 的 empty。记下期望值与实际值，恢复判断，确认同一用例转绿。用例里的 A 显式忽略了 signal，因此结果可重复。

7.8 反证二：保留序号，去掉网络取消

只注释 cancel() 函数体内的 active?.abort()，保留 latest += 1。第一个用例的 signal 断言失败。单看页面仍可能正常，但旧请求继续占用连接。恢复取消，重新运行三条用例。把两次失败分别对应到“错误提交”和“多做工作”。

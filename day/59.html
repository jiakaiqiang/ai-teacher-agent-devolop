课程总览 第 9 周

Day 59

Day 59 - 求职证据：把项目能力变成可追溯的交付包

日期与时长：2026-09-10 周四，180 分钟（90 分钟阅读 + 90 分钟动手）
项目：p1-monitor（复用 Day58 的事故证据和 Day57 的观测契约）
阶段：阶段二（Day31-60，AI 前端 -> AI 全栈）

《90 天拆分规则说明》校正口径（本 Day 的权威执行口径）

  • 本日交付一个完整、可运行、可核验的求职证据模块：README、架构图、ADR、Eval/安全/性能证据、岗位矩阵和 8 分钟演示脚本必须互相链接。
  • v1 是未经核验的原始材料，v2 是按岗位能力建立的证据矩阵，v3 是带失败演示、数字来源、诚实缺口和可复现命令的最终交付包。
  • 复用 Day58 的真实 replay.log、metrics.json、Runbook 和测试输出；禁止重新编造指标或把模拟数据写成生产数据。
  • 时间盒固定为 90 分钟阅读 + 90 分钟动手。本日不使用周末扩展时长。
  • 完成门槛：任意数字都能追溯到命令、日志或报告；React/Electron 等未覆盖能力必须明确标注“未验证”，不得写成已掌握。

今日交付

创建并提交以下文件：

  • `docs/career/day59-evidence-matrix.md`：岗位要求、项目能力、证据路径、验证命令、证据等级和缺口。
  • `docs/career/README.md`：项目叙事、架构边界、失败与恢复、可复现入口。
  • `docs/career/architecture.md`：C4 上下文/容器图及关键数据流。
  • `docs/career/adr-001-retry-and-rollback.md`：Day58 的 retry budget、幂等和回滚决策。
  • `docs/career/eval-security-performance.md`：Eval 样例、安全边界、性能基线及来源。
  • `scripts/check-day59-evidence.mjs`、`tests/career/day59-evidence.spec.ts`：检查链接、数字来源、失败演示和缺口声明。
  • `evidence/day59/demo-script.md`：8 分钟演示逐分钟脚本，包含一次失败和一次恢复。

版本演进

v1：原始材料包（约 20 分钟）

把 Day58 的 Runbook、测试输出和架构草图复制到证据目录，标注来源和采集时间。README 只能写已验证事实，未验证的数字写为“待测”，不得填充漂亮指标。

pnpm tsx scripts/replay-day58.ts --fault provider429 --requests 20 > evidence/day59/day58-replay.log
pnpm vitest run tests/incident/day58.spec.ts --reporter=verbose > evidence/day59/day58-tests.log

验收：每个结论至少有一个文件路径和命令；没有来源的数字从 README 删除。

v2：岗位证据矩阵（约 25 分钟）

把目标岗位拆成后端、Agent/RAG、可靠性、安全、性能、协作沟通六类能力。每行写证据等级：A=真实命令输出，B=代码+测试，C=设计说明，D=未验证。用矩阵决定 8 分钟演示顺序，不用“熟悉/精通”等不可验证形容词。

pnpm node scripts/check-day59-evidence.mjs --matrix docs/career/day59-evidence-matrix.md
pnpm vitest run tests/career/day59-evidence.spec.ts -t "matrix"

验收：岗位每项要求都有 A/B/C/D 级别和下一步补证动作；React/Electron 缺口必须可见。

v3：诚实可复现的演示包（约 25 分钟）

完成 8 分钟演示：1 分钟问题与边界，2 分钟正常链路，2 分钟注入 429/队列故障，2 分钟恢复与指标，1 分钟风险和未验证项。演示时直接运行脚本并展示失败输出，不用剪辑隐藏错误。

pnpm node scripts/check-day59-evidence.mjs --strict
pnpm vitest run tests/career/day59-evidence.spec.ts

验收：从 README 能跳到架构、ADR、Eval、安全、性能和原始日志；随机删除一个证据文件时检查应失败；演示结束能回答指标来源和局限。

90 分钟阅读

  • 30 分钟：阅读 Day58 的 Runbook、timeline、metrics 和 replay.log，区分演练约束、代码事实和个人判断。
  • 30 分钟：阅读目标岗位描述，提取 10 项能力，给每项定义可观察证据和最低验证命令。
  • 30 分钟：阅读项目的 C4、ADR、Eval、安全和性能材料，检查是否存在过度承诺、断链或没有采集时间的数字。

阅读输出：岗位能力矩阵初稿、证据等级定义和三条必须诚实披露的缺口。

90 分钟动手

  1. 20 分钟：整理 v1 原始材料并为每个数字补来源、命令和采集时间。
  2. 25 分钟：完成 v2 矩阵、C4 架构图和 ADR；每个结论链接到实际文件。
  3. 25 分钟：完成 v3 失败/恢复演示脚本、严格检查脚本和测试。
  4. 20 分钟：完整跑一次 8 分钟演示，记录失败输出、修订 README，并提交证据目录。

测试与验收

测试 必须观察到的结果
来源完整性 README 的每个数字都能定位到日志、命令或报告
链接完整性 架构、ADR、Eval、安全、性能和原始日志链接均可打开
失败演示 注入 429 或队列故障时屏幕出现预期失败和 traceId
恢复演示 回滚/重放后指标和幂等断言恢复，输出保存到 evidence
诚实边界 React/Electron 或未做压测的能力标为 D/未验证
删除证据 随机移除一份原始日志，strict 检查必须失败

必做测试与两个反证（必须实际运行）

  1. 反证 1：删除来源引用：临时删除 metrics.json 的来源链接或采集命令，运行 strict 检查，预期失败并指出具体行；恢复来源后重新通过。
  2. 反证 2：夸大未支持指标：把“演练 P95 约束”改成“生产 P95 降低 60%”，运行证据检查和人工复核，预期被拒绝；恢复为带范围、时间和来源的表述。

课末三道核心问题

  1. 从 README 入口到最终演示，项目叙事、C4、ADR、Eval 和性能证据分别解决什么可信度问题？为什么这个顺序能让面试官复核？
  2. 如果删除最关键的证据文件，最小复现、定位证据、修复动作和防复发测试是什么？如何防止文档继续引用失效路径？
  3. 逐项引用本日真实 diff、测试输出和矩阵，说明已经覆盖哪些岗位要求、哪些仍未验证，以及下一步如何补齐而不夸大能力。

真实项目情境题

以下是教学模拟，指标不代表本项目生产数据。

  1. README 声称“P95 降低 60%、准确率 92%”，但找不到数据集、压测命令和原始报告。请撤下不可证数字，用日志、Trace、Eval 和版本报告重建证据，并现场注入一次失败验证恢复能力。
  2. 10 个目标岗位中 6 个要求 React/Electron，而项目主要是 Vue/NestJS。请用岗位矩阵和投递记录区分“可迁移基础”和“已验证经验”，完成一次最小补齐实验，不得把迁移计划写成掌握证明。

人与 AI 分工

  • 人：选择目标岗位、确认数字是否可公开、决定证据等级、讲述失败和缺口，并对最终简历负责。
  • AI：扫描文档断链、生成矩阵初稿、汇总测试输出和演示计时；任何措辞升级必须由人用原始证据批准。
  • AI 不得创建不存在的指标、项目经历或岗位匹配；所有接受、修改、拒绝理由写入 review 记录。

教师五连问

提交证据包后，教师根据真实 diff 随机追问五题，范围覆盖局部机制、边界一致性、线上事故、工程权责和架构演进。每一问必须现场打开证据路径并运行或解释对应命令。

PDF 面试题映射

  • 《2026 阿里云前端技术专家 AI 领域》：第 10 页，如何量化技术挑战和结果。
  • 《2026 美团前端架构师面试：数据权限方向》：第 12 页，项目叙事与可追溯架构回答。
  • PDF 题只作为迁移练习，不能替代本日证据矩阵和真实演示。
